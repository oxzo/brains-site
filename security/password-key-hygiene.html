Password and Key Hygiene

What it is

Password and key hygiene is the set of habits and controls that keep authentication secrets — passwords, API tokens, SSH keys, GPG keys, signing keys — secret, usable only by their owner, and revocable when they leak. It spans how secrets are generated, where they are stored, how access to them is gated, and how they are rotated or retired over their lifecycle.

Why it matters

Most account compromises do not require breaking cryptography; they exploit weak, reused, or carelessly stored secrets. A single password reused across services turns one breach into many, because attackers replay leaked credential pairs against unrelated sites (credential stuffing). A private key checked into a repository or left in a plaintext config file is a standing liability that no amount of network hardening offsets. Good hygiene shrinks both the chance a secret leaks and the blast radius if one does.

The asymmetry is stark: generating and storing a secret well costs minutes once; cleaning up after a leaked secret can mean rotating dependent systems, auditing access logs, and rebuilding trust. Hygiene is cheap insurance against an expensive incident.

Details

Passwords

  • Length and randomness beat complexity rules. A long passphrase or a randomly generated string resists guessing far better than a short password padded with symbols to satisfy a policy. Entropy comes from unpredictability and length, not from a mandatory punctuation character.
  • Never reuse passwords across services. Reuse is the mechanism that converts an unrelated site’s breach into a compromise of your important accounts. Unique-per-service is the single highest-leverage password habit.
  • Use a password manager. A reputable password manager generates unique high-entropy passwords, stores them encrypted behind one strong master secret, and removes the incentive to reuse or simplify. The master secret and the manager’s own recovery path then become the things you protect most carefully.
  • Layer on a second factor. Multi-factor authentication means a leaked password alone is not enough to log in. Hardware-backed factors (security keys implementing public-key challenge-response) resist phishing in a way that one-time codes typed into a page do not, because the key will only authenticate to the legitimate origin. App-generated time-based codes are a strong middle tier; SMS codes are the weakest common factor because they are interceptable and SIM-swappable.

Cryptographic keys

  • Generate keys with strong, modern algorithms and adequate key sizes; prefer well-reviewed defaults over hand-tuned parameters. The reasoning is the same one that governs all cryptographic choices: avoid rolling your own, and prefer authenticated, well-vetted primitives over clever custom schemes.
  • Protect private keys at rest. Encrypt private keys with a passphrase, restrict file permissions so only the owner can read them, and prefer storing them in a hardware token or OS keystore over a bare file when the threat model warrants it. A private key with world-readable permissions on a shared host is effectively public.
  • Separate keys by purpose and scope. Distinct keys for distinct roles (per-host, per-service, per-environment) mean compromising one does not compromise all, and revoking one is surgical rather than catastrophic. The same logic applies to API tokens: scope each token to the least privilege it needs.
  • Keep signing keys offline where practical. Keys whose job is to vouch for identity or releases — code-signing keys, root certificate keys — gain disproportionate value to an attacker. Keeping them off general-purpose, network-connected machines is proportionate to that value; keep them instead on hardware tokens, or in air-gapped or dedicated signing environments.

Secret storage anti-patterns

  • Plaintext secrets in config files or environment files committed to version control are the classic leak. Once a secret enters git history, deleting the file does not remove it — the secret must be treated as compromised and rotated, and the history scrubbed.
  • Secrets pasted into chat, tickets, or logs spread copies you cannot track or revoke. Treat any secret that lands in an unencrypted shared channel as leaked.
  • Long-lived secrets that are never rotated accumulate exposure: every backup, every former employee, every prior leak window is a chance the secret escaped. Prefer short-lived, automatically issued credentials where the platform supports them.

Rotation and revocation

  • Rotate on a schedule and on suspicion. Periodic rotation bounds how long a silently-leaked secret stays useful; immediate rotation on any suspected exposure stops an active attacker.
  • Make revocation fast and rehearsed. The value of being able to revoke a key is only realized if you can actually do it under pressure — know in advance how to revoke each key type and what depends on it, so revocation is a known procedure, not an improvisation during an incident. This ties directly into incident-response-basics.
  • Maintain an inventory. You cannot rotate or revoke secrets you have forgotten exist. Knowing what secrets exist, where they live, and what they grant is a prerequisite for the rest.

The mental model

Treat every secret as something that will eventually leak, and design so that when it does, the leak is detectable, contained to a small scope, and recoverable by revocation and rotation rather than by hoping no one noticed. Hygiene is less about preventing every leak and more about ensuring no single leak is catastrophic or permanent.
