Linux Hardening Checklist

What it is

A practical, prioritized guide for securing a Fedora workstation (or server). Covers the layers that matter most — from firewall and SELinux through SSH, disk encryption, auditing, and container isolation. Focused on Fedora and the Red Hat ecosystem but most concepts transfer to any systemd-based Linux distribution. A quick-reference checklist for periodic review sits at the end of this note.

Why it matters

A default Fedora install is reasonably secure out of the box — SELinux is enforcing, firewalld is active, and the kernel has modern exploit mitigations. But “reasonably secure” isn’t enough when the machine holds SSH keys, GPG keys, API tokens, and access to production systems. Every layer you harden reduces the blast radius when (not if) something gets compromised.

Use threat-modeling-basics to decide which layers to prioritize. Not every system needs every item here — a personal workstation has different risks than a public-facing server.

Details

Fresh Fedora Install — First Steps

Do these before connecting to untrusted networks:

  1. Full-disk encryption (LUKS) — Enable during installation. You can’t retrofit this without pain.

  2. Set a firmware/BIOS password — Prevents boot-order tampering.

  3. Update everything: sudo dnf upgrade --refresh

  4. Review running services: systemctl list-units --type=service --state=running — disable anything you don’t need.

  5. Create a non-root user and use sudo exclusively. Fedora does this by default but verify.

  6. Verify Secure Boot is enabled: mokutil --sb-state — Ensures only signed kernels and modules load. Fedora supports Secure Boot out of the box.

  7. Set a boot loader password (GRUB): Prevents single-user mode access without credentials.

Disk Encryption (LUKS)

Full-disk encryption protects data at rest — critical for laptops that might be lost or stolen.

  • Enable during Fedora install — The Anaconda installer offers LUKS encryption on the storage configuration screen. Use a strong passphrase (6+ random words).
  • Verify it’s active: lsblk -f will show crypto_LUKS type for encrypted partitions.
  • Backup the LUKS header: sudo cryptsetup luksHeaderBackup /dev/sda3 --header-backup-file luks-header.img — Store this securely offline. If the header is corrupted, all data is lost.
  • Add a recovery key: sudo systemd-cryptenroll /dev/sda3 --recovery-key — Gives you a printable recovery key separate from your passphrase.

Performance: LUKS2 with AES-XTS on modern CPUs with AES-NI has negligible performance impact (< 3% in most workloads). Verify hardware acceleration is available: grep -o aes /proc/cpuinfo | head -1.

LUKS with TPM2 auto-unlock — Decrypt at boot without typing a passphrase, while still protecting against offline disk theft:

Encrypted swap: Ensure swap is also encrypted. If you used full-disk encryption during Fedora install, swap is inside the LUKS volume. Verify: swapon --show should point to a device inside the LUKS container, not a raw partition.

Hardening Quick-Reference Checklist

Summary checklist for periodic review. Not every item applies to every system — use threat-modeling-basics to prioritize.

Boot and Physical:

  • LUKS full-disk encryption enabled
  • Firmware/BIOS password set
  • Secure Boot enabled (mokutil --sb-state)
  • GRUB boot loader password configured
  • USB device restrictions (USBGuard or module blacklist)

OS and Kernel:

  • System fully updated (dnf upgrade --refresh)
  • Automatic security updates enabled (dnf-automatic)
  • Unnecessary services disabled (systemctl list-units)
  • Kernel hardening sysctls applied
  • Kernel boot parameters hardened

Access Control:

  • SELinux enforcing (getenforce)
  • No direct root login (SSH and console)
  • sudo configured with least privilege
  • Home directories 700
  • umask 027 set

Network:

  • Firewall active with minimal open ports
  • Network hardening sysctls applied
  • DNS-over-TLS/HTTPS enabled
  • Unused network services disabled
  • WiFi MAC randomization enabled

SSH:

  • Password authentication disabled
  • Root login disabled
  • Strong algorithms only (Ed25519, ChaCha20)
  • Fail2ban or equivalent active
  • SSH config tested with ssh-audit

Monitoring:

  • auditd running with custom rules
  • Audit log integrity protected
  • Failed login monitoring active
