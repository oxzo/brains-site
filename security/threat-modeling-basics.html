Threat Modeling Basics

What it is

Threat modeling is a structured process for identifying, quantifying, and addressing security threats to a system. Rather than reacting to vulnerabilities after they’re exploited, threat modeling forces you to think like an attacker during the design phase — systematically decomposing a system into components, mapping data flows, and asking “what could go wrong?” at every boundary.

Why it matters

Most security breaches exploit architectural weaknesses, not exotic zero-days. A system that was never threat-modeled tends to accumulate implicit trust assumptions that attackers love to violate — “the database is only reachable internally” or “users won’t modify the request body”. Threat modeling surfaces these assumptions early, when fixing them is cheap. It also gives you a rational basis for prioritizing security work instead of chasing the latest CVE.

The case for it is primarily temporal: before implementation, the architecture is still cheap to change, and cross-boundary authority errors have not yet been buried in code. That is a strong argument, and it is not the same as an evidence-backed one — see Does it work? The cost and coverage evidence below before treating threat modeling as a control rather than a design activity.

Details

The Threat Modeling Process

The core loop, regardless of framework:

  1. Decompose the system — Draw a data flow diagram (DFD) showing processes, data stores, external entities, and trust boundaries.
  2. Identify threats — For each element and data flow, enumerate what could go wrong using a structured framework (STRIDE, PASTA, attack trees, etc.).
  3. Rate severity — Score each threat by likelihood and impact. DREAD (Damage, Reproducibility, Exploitability, Affected users, Discoverability) or CVSS can help here, but even a simple High/Medium/Low matrix works for small teams.
  4. Plan mitigations — For each threat, decide: mitigate (fix it), accept (risk is tolerable), transfer (insurance, SLA), or avoid (remove the feature).
  5. Validate — Verify mitigations actually address the threats. Re-model when the system changes.

Data Flow Diagrams (DFDs)

DFDs are the starting artifact. They use four element types:

  • External entities (rectangles) — Users, third-party APIs, anything outside your control.
  • Processes (circles) — Code that transforms data. Your application logic.
  • Data stores (parallel lines) — Databases, files, caches, queues.
  • Data flows (arrows) — How data moves between elements. Label with protocol and data type.

The critical addition is trust boundaries (dashed lines). Every place where the trust level changes is a trust boundary — between your frontend and backend, between your backend and a third-party API, between user input and your parser. Most threats live at trust boundaries.

Start with a Level 0 DFD (context diagram) showing the whole system as one process, then expand to Level 1 showing major subsystems. You rarely need to go deeper than Level 2 for threat modeling.

Tooling for DFDs:

  • draw.io / diagrams.net — Free, works offline, exports to SVG/PNG. The Threat Modeling shape library has DFD elements built in.
  • Microsoft Threat Modeling Tool — Windows only, generates STRIDE threats automatically from DFDs. Free.
  • OWASP Threat Dragon — Open-source, browser-based, generates threat reports from DFDs.
  • Mermaid diagrams — If you prefer text-as-code: embed DFDs in markdown and render in Obsidian or CI.
  • threagile — Threat model as YAML, auto-generates risk reports and DFDs. Good for infrastructure-heavy models.

STRIDE Framework

Developed at Microsoft as part of the SDL (Security Development Lifecycle). Each letter maps to a category of threat and its corresponding security property:

ThreatViolated PropertyExample
SpoofingAuthenticationAttacker impersonates a legitimate user via stolen credentials or forged tokens
TamperingIntegrityAttacker modifies data in transit (MITM) or at rest (SQL injection altering records)
RepudiationNon-repudiationUser denies performing an action and there are no logs to prove otherwise
Information DisclosureConfidentialityError messages leak stack traces; API returns fields the user shouldn’t see
Denial of ServiceAvailabilityResource exhaustion, algorithmic complexity attacks, or simply flooding endpoints
Elevation of PrivilegeAuthorizationUnprivileged user gains admin access via IDOR, path traversal, or broken access control

STRIDE-per-element: Apply STRIDE to each DFD element. External entities are primarily susceptible to Spoofing. Processes are susceptible to all six. Data stores are susceptible to Tampering, Information Disclosure, and Denial of Service. Data flows are susceptible to Tampering, Information Disclosure, and Denial of Service.

STRIDE-per-interaction: Apply STRIDE to each data flow crossing a trust boundary. This is more focused and scales better for complex systems.

Beyond STRIDE — Other Frameworks

PASTA (Process for Attack Simulation and Threat Analysis) — A seven-stage, risk-centric methodology that starts with business objectives and works down to technical threat enumeration. Better than STRIDE when you need to tie threats directly to business impact and present findings to non-technical stakeholders. Stages: (1) Define objectives, (2) Define technical scope, (3) Application decomposition, (4) Threat analysis, (5) Vulnerability analysis, (6) Attack modeling, (7) Risk/impact analysis.

LINDDUN — Privacy-focused threat modeling framework. Six categories: Linkability, Identifiability, Non-repudiation (in privacy, non-repudiation is a threat — users want plausible deniability), Detectability, Disclosure of information, Unawareness, Non-compliance. Use when GDPR or other privacy regulations apply.

VAST (Visual, Agile, and Simple Threat modeling) — Designed for Agile/DevOps environments. Produces two types of models: application threat models (for developers) and operational threat models (for infrastructure teams). Integrates into sprint workflows rather than being a separate phase.

MITRE ATT&CK — Not a threat modeling methodology per se, but a comprehensive knowledge base of real-world adversary tactics and techniques. Use it to validate your threat model: for each STRIDE threat you identify, check ATT&CK for known techniques an attacker would use. This grounds your model in reality rather than theory. Browse at https://attack.mitre.org/.

Attack Trees

Attack trees model threats as a hierarchical goal structure:

  • Root node: The attacker’s goal (e.g., “Steal user credentials”).
  • Child nodes: Ways to achieve the parent goal, connected by AND/OR gates.
  • Leaf nodes: Concrete attack steps.

Attack trees are powerful because they let you assign costs and probabilities to leaf nodes and propagate them up. If phishing costs 50andhasan8010K exploit toolkit, you know where to focus defenses.

Quantitative risk scoring with attack trees: Assign each leaf node three values — cost to attacker, probability of success, and impact to defender. Propagate up: OR gates take the max probability (attacker picks the easiest path), AND gates multiply probabilities (attacker must succeed at all steps). This gives you a rational basis for security investment — spend on mitigations where the attacker’s cost-to-benefit ratio is most favorable.

Tools for attack trees: ADTool (open-source, graphical), SecuriCAD (commercial, simulation-based), or simply a markdown outline with annotations.

Threat Modeling Real-World Examples

Example 1: Self-hosted web app with API

  1. Draw DFD: Browser → Nginx reverse proxy → Node.js API → PostgreSQL. Trust boundaries: internet/DMZ (at Nginx), DMZ/internal (at API), API/database.
  2. STRIDE at each boundary:
    • Internet/DMZ: Spoofing (forged JWTs), DoS (HTTP flood), Information Disclosure (server version headers).
    • DMZ/Internal: Tampering (SSRF from API to internal services), Elevation of Privilege (API escape to host).
    • API/Database: SQL injection (Tampering), excessive data returns (Information Disclosure).
  3. Mitigations: Rate limiting at Nginx, JWT validation with iss/aud claims, parameterized queries, network segmentation, Server header removal.

Example 2: CI/CD pipeline (a la the xz-utils attack)

  1. DFD: Developer workstation → GitHub → GitHub Actions → Container registry → Kubernetes.
  2. Key trust boundaries: developer identity (SSH/GPG keys), CI runner (shared infrastructure), registry upload credentials.
  3. STRIDE analysis reveals: Spoofing (compromised maintainer account), Tampering (malicious PR modifying build scripts), Information Disclosure (secrets leaked in CI logs).
  4. Mitigations: Branch protection rules, required code review, SLSA provenance, secret scanning, ephemeral CI runners.

Does it work? The cost and coverage evidence

Threat modeling is one of the most confidently recommended practices in security and one of the least measured. The evidence that exists is worth knowing because it is encouraging about validity and discouraging about completeness.

Scandariato, Wuyts & Joosen’s descriptive study of Microsoft’s technique (Requirements Engineering, 2015) is the standard reference. It ran STRIDE with 57 final-year master’s students and measured productivity, precision, and recall against a researcher-constructed baseline. The headline results: precision ≈ 0.81, recall ≈ 0.36.

Read those two numbers together:

  • Most threats identified were real. Four in five findings were valid, so the output of a session is not noise.
  • Roughly two-thirds of the baseline threats were missed. A completed threat model is not a coverage claim.

(Precision and recall corroborated across two independent secondary sources on 2026-08-07; the paywalled paper was not read directly. Per-hour productivity figures circulate for this study but were not verified and are deliberately omitted here. Scope: students, one method, one modeled system, an expert-built baseline — not a production breach study.)

The practical consequence is not “don’t threat model.” It is: treat the output as a set of leads with a known miss rate, never as the reason a design is safe. A model that finds five real threats and misses ten is still worth the afternoon; a model treated as an assurance artifact is average-case evidence against an adversary who selects the tail.

Make it an executable design review

The failure mode this evidence points at is ceremony — a diagram and a taxonomy that create confidence without changing anything. The counter is a completion rule: every accepted threat must produce at least one of —

  • a removed authority,
  • an architectural boundary,
  • an invariant or type that makes the state unrepresentable (designing-out-defect-classes),
  • a negative or metamorphic test (authorization-as-a-protocol),
  • an observable event in the evidence plane (post-breach-investigability),
  • a recovery action,
  • or an explicitly accepted, dated residual risk.

If a session produces none of these, it produced a document. Re-run the model on boundary-changing diffs rather than on a calendar, and stop when new scenarios stop changing the design or the tests.

When to Threat Model

  • During initial design — Before writing code. The DFD doesn’t need to be perfect; even a whiteboard sketch helps.
  • Before major changes — New authentication flow? New external integration? New data store? Re-model the affected area.
  • After incidents — A breach reveals gaps in your model. Update it.
  • Periodically — Systems drift. Annual reviews catch creeping assumptions.

Lightweight Threat Modeling for Solo Developers / Small Teams

You don’t need a formal process or expensive tools. The minimum viable threat model:

  1. Sketch the DFD on paper or in a tool like draw.io. 15 minutes.
  2. Walk each trust boundary and ask the STRIDE questions. Write threats in a markdown file or issue tracker. 30 minutes.
  3. Rank by gut feel — High/Medium/Low. Don’t overthink scoring.
  4. File issues for the High and Medium threats. Accept the Lows explicitly (write it down so future-you knows it was deliberate).
  5. Timebox it — A 1-hour session per quarter is infinitely better than never modeling.

Adam Shostack’s “four question” framing is useful for teams new to threat modeling:

  1. What are we building?
  2. What can go wrong?
  3. What are we going to do about it?
  4. Did we do a good enough job?

Connection to AI Security

LLM-based systems introduce novel threat modeling challenges. Mapping STRIDE to AI agents:

  • Spoofing: Prompt injection can make an agent impersonate system instructions — the model can’t reliably distinguish user input from system instructions.
  • Information Disclosure: Prompt extraction attacks leak system prompts and tool configurations. Indirect injection can exfiltrate context window contents.
  • Elevation of Privilege: An attacker’s injected prompt can escalate from “user message” trust level to “system instruction” trust level, gaining access to tools and data the attacker shouldn’t control.
  • Tampering: Poisoned training data or compromised tool outputs alter agent behavior.
  • Denial of Service: Context window exhaustion, infinite tool-calling loops.

When threat modeling an AI system, treat the model itself as an untrustworthy process — it’s a probabilistic component that can be manipulated. Draw trust boundaries around every tool the model can call, and assume injected content can cross those boundaries. See prompt-injection and ai-agent-security for deeper treatment.

Threat Modeling Checklist

Quick-reference checklist to run through during a threat modeling session:

  • System scope defined — Clear boundary of what’s in/out of scope for this model
  • DFD drawn — All processes, data stores, external entities, and data flows mapped
  • Trust boundaries identified — Every point where privilege, ownership, or network zone changes
  • STRIDE applied — Each trust boundary examined for all six threat categories
  • Severity rated — Each threat scored (at minimum High/Medium/Low)
  • Mitigations assigned — Each High/Medium threat has a planned mitigation or explicit acceptance
  • Third-party dependencies reviewed — Threats from external APIs, libraries, and services considered (see supply-chain-security)
  • Authentication and authorization flows traced — Token lifecycle, session management, privilege boundaries mapped
  • Data classification done — Sensitive data (PII, credentials, keys) identified and their flows traced
  • Findings documented — Threats, mitigations, and accepted risks recorded in a persistent, reviewable format
  • Review date set — Next scheduled review on the calendar
