Clause Loop

A development method for one person and one AI agent — plus the fresh contexts that agent dispatches for reader checks and spot-checks — for any work whose output can be checked: code on a greenfield or a brownfield, a feature on a live system, a throwaway prototype, a specification, a document. You say what should be true next and what would prove it false; the agent builds the smallest thing that could settle it inside a declared envelope; you decide, from a short packet, what deserves to become a clause — a requirement pinned to a check that has been shown to fail for the right reason. The spec is a byproduct of building, not a prerequisite, and it grows one chosen clause at a time.

This note is the normative description of the method: where it and its two parent notes disagree, this note wins, and the parents link here rather than restate. The engine it runs is accretive-spec-development; the reasoning for why the requirement gates some builds and the check gates others, and how the loop and spec-driven development run as one system, is spec-driven-development-operating-model. Read those for the argument; read this to do the work.

The idea

The problem it answers. Working with a coding agent, there are two familiar ways to keep the work honest and both cost something. Spec-first methods (Spec Kit, Kiro, OpenSpec and their kin) derive the code from requirements, design and tasks agreed first, a document per phase. That buys agreement before building, at the price of committing to a reading of the problem before anything has run. Their specs do evolve — OpenSpec’s accumulate change by change — so what separates this method from them is the direction of derivation and the grain, not whether the spec grows. Building with no spec at all is fast, but nothing stops the agent from quietly solving a slightly different problem than the one you asked for — and the tests it writes to check its own work only ever encode its own reading of your intent.

The bet. Sit between the two. State an intent plus a falsifier, build the smallest probe that could falsify it, confront the running result, harvest clauses from what held. Exploration stays fast because you react to a running artifact, not a document; the spec you end with can be trusted because every clause in it is pinned to a check that has failed on demand for a named reason. Once a domain of the spec has been exercised and its clauses all chosen, freeze it — and a frozen domain is a contract other agents and services build against, which is where spec-first practice takes over. The loop is the on-ramp to a contract, not a replacement for one. Its distinctive value is turning explored behaviour into an explicitly chosen, evidence-linked contract — not the number of documents or gates it accumulates.

The pieces that make it hold. Each is a rule below; here is why it exists.

  • A clause is a SHALL sentence, a WHEN/THEN scenario, and a pin. The pin carries a stable id, the check, and the evidence — the mutant the check was watched failing against, with the assertion that caught it named. A check that cannot fail is not a check; a check that fails for an unrelated reason proves nothing; and a requirement with no check drifts from the code the day after it is written. Nothing enters the spec without all three.
  • Independence comes from the human, at decision boundaries. The agent writes the probe, the check and the proposed clause, so left alone every check would encode the agent’s interpretation of the intent. The human owns the falsifier — writes it, or substantively revises the agent’s candidate counterexamples — at every user-visible outcome and every consequential decision; mechanical tasks inherit it. The human decides which harvested clauses are wanted, and chooses and reads the spot-check of the evidence while a trusted runner executes it. Ownership of intent is not the same as typing every line, and the method asks for the first.
  • Observed is not wanted. Harvest records what the artifact does; promotion records what you want. The two are separate acts so that accidental behaviour — especially on brownfield code, where the first harvest captures everything that happens to be true — never becomes contract by default. Turning a clause down is three decisions, not one: whether it is contract, whether the behaviour stays in the artifact, and whether its check stays as characterization coverage.
  • Wanted is not verified. Acceptance is a human decision and changes rarely; verification is what the last run says and changes every run. A wanted clause whose check fails is still wanted — it is wanted and failing, and the failure is a stop, not a change of mind. Keeping the two axes apart is what lets a stale reader check, a flaky dispatch, or a known implementation debt be named without rewriting what was agreed.
  • Permission and impact gate the build, not file layout. Every probe declares an execution envelope. Hard gates — production writes, destructive operations, credentials, externally visible actions, anything on the irreversibility list, edits to a frozen verification surface — stop for permission whatever the path. Planning heuristics — uncertainty, rework, growth, cross-domain coordination, a contract change — send work to a proposal before the expensive probe. Both stay active inside an approved proposal, and what the agent actually changed is compared to what it declared.
  • Freeze is a mechanism, not a label. A domain whose clauses are all wanted and all currently verified gets a manifest naming its verification surface, and a guard fails the build on an unapproved change to that surface or on a required check that did not run. This is the guarantee, stated at its honest size: the guard rejects missing or failing required checks and unapproved changes to the declared verification surface. It does not prove that the checks express the requirement, or your intent. Drift between the spec and your intent is bounded by the human-owned falsifier, the locked checks and the evidence rule with its spot-check; it is not prevented.
  • Consolidate, or the spec becomes a test index. Harvest order is a changelog. Every ten or so archives the domain spec is rewritten by concept, scanned for clauses that contradict each other at intent level while both pass, and its expired re-check dates and exceptions listed.

Why one method for code and prose. A clause is the same object whether the artifact is a service or a quickstart; only the oracle changes — what runs the check and what counts as evidence it can fail. For code that is a test. For a document it is a reader check: a fresh context, given the artifact and nothing else, must complete a task from it, and the mutant is deleting everything that carries the clause’s content and watching the reader fail. The generalisation strains at the grammar — SHALL is borrowed from requirements engineering and sits stiffly on prose. What carries over is the scenario and the pin, so if the SHALL sentence reads as ceremony for a document, keep the scenario and drop the keyword.

Where it comes from. The change-folder skeleton follows the shape of OpenSpec-style tools; the requirement-to-check link follows the shape Kiro-style tools build, run in the opposite direction. The reader and consistency oracles, the mutant-by-deletion rule for documents, the spec rule and the profile table generalise the accretive note’s architecture mapping (spike, fitness function, scenario walk) to non-code work; they are this vault’s own design, precedent check deferred. The 2026-09-05 revision — the envelope and hard gates, the acceptance-versus-verification split, the three-decision rejection, the evidence record, the four-action surface and the contract guard’s approval boundary — came from an external design review of the previous version, applied in one pass and then corrected against three fresh-context reviews of the result.

It has not been run end to end. The first rule of the method is that the human owns the falsifier, so here is this note’s own: the method is wrong if, in the first month of real use, hard gates or heuristics fire on most probes so nothing is ever harvested; if a task you later judge consequential ran on an inherited falsifier because the agent did not flag it; if DECISIONS.log goes unwritten after a few sessions; or if the pilot in What to test next finds, by its independent read, an intent substitution that the loop’s own packet did not surface. The two worked examples below are constructed illustrations — the paths, dates and log lines in them are invented to show the shape, not records of anything that happened.

The four actions

Four things you do, in a loop: Start, Probe, Decide, Close. Everything else — grounding, proposals, freezing, consolidating — is machinery the agent runs when one of the four asks for it, listed under Operations in the reference. The action names are steps you write in a prompt, not installed skills.

  1. Start. You give one sentence of intent. The agent copies changes/_template/ to changes/<name>/, copies its specs/_domain/ once per domain the intent touches, renamed, writes the intent into proposal.md, proposes two or three candidate counterexamples marked as its own, and drafts the envelope. You write the falsifier — from scratch or by substantively revising a candidate — and confirm or tighten the envelope. Probe refuses to run while the falsifier’s origin is missing or reads agent, unrevised.
  2. Probe. The agent checks the envelope against the hard gates and the heuristics. A hard gate stops for your permission on that specific action; a heuristic hands the change to a proposal. Otherwise it builds the smallest thing that could falsify the intent, together with the check, runs it against a prediction of pass and fail drafted from your falsifier, records what it actually wrote and did against what the envelope declared, and ends with the not-exercised list. For each check it earns the evidence: baseline passes, mutant on a scratch copy, the named assertion goes red, restore passes. A crash or compile error is logged as an attempt, not as evidence. It logs the loop with minutes.
  3. Decide. The agent hands you a packet: what you asked for, what ran and what happened, what remains untested, the clauses it proposes with their evidence and any relevant failures, the actual-versus-declared envelope, the log lines written since the last packet, and the decisions it needs. You answer in chat. Per clause: contract — wanted or not; if not, whether the behaviour stays in the artifact and whether the check stays as characterization. On a brownfield first harvest you may answer once for the batch — not contract, behaviour kept, checks kept as characterization — and name only the exceptions; the default is yours because you said it. Plus: loop again on a gap the not-exercised list named, escalate, or permit a gated action. The agent writes the pins and the log lines from your answer, quoting the answer verbatim in the proposal’s Decisions section, and you spot-check one piece of evidence per change by choosing which and reading a trusted runner’s re-application of it. Cap about five loops per intent; the cap is a signal the intent should be split or escalated, not extended.
  4. Close. The agent runs every check, reports verification per clause, lists any clause you never ruled on and refuses to close until you have — silence is not a decision — gates on every scenario or invariant outside RETIRED carrying a wanted pin with evidence, compares the change’s total writes and actions to the envelope, reads the intent against the promoted clauses for anything quietly substituted, merges the delta into specs/<domain>/spec.md, writes the archive line, and moves the folder to changes/archive/<date>-<name>/. If the domain was under contract, the manifest is rewritten and the surface change goes through the approval boundary.

When a heuristic fires at Probe, the requirement gates instead: the agent writes a proposal and design, they are red-teamed, you agree the delta spec before the build, and each task then runs Probe and Decide inside the change folder. Tasks inherit the change’s falsifier unless a task introduces a new assumption, trade-off or externally visible behaviour, in which case it gets its own decision; the agent flags which tasks it thinks qualify, and the flag is its judgement, which you can overrule either way. Hard gates and the envelope stay live inside the proposal; exceeding the envelope pauses for an amendment, not a second proposal. Worked example A shows both paths on the same codebase; example B shows a document.

Getting started

  1. Copy the kit. cp -r templates/clause-loop <repo>/clauses — the kit lives at templates/clause-loop/ in this vault and carries its own README with the target tree. Everything the method’s own bookkeeping writes lives under that one root; the artifact and its checks stay wherever the project keeps them.
  2. Ground the project. Fill GROUND.md: the profile (one of greenfield-code, brownfield-code, feature, prototype, specification, documentation) and, for the last three, the artifact — a folder or a single file; two or three sentences of context; constraints, each with a check id, a manual procedure, or an exception reference, which ground writes into their domain specs once step 3 has created them; preferences; the irreversibility list; the domain table; the Checks section — how to run all checks, how to run one, how the runner reports which check ids executed, the command that dispatches a reader check, how a walk is performed, the id form per oracle, and the evidence rule; the Envelope defaults — which environments a probe may touch without permission; and the Approval boundary — where your decisions on gated actions and surface changes are recorded so the agent cannot write them itself. Keep it to a screen: past that you are sneaking upfront design back in.
  3. Create the domains. Copy specs/_domain/spec.md once per domain Ground names, stripping the placeholder requirement and invariant and setting Status: open — then let ground write each constraint into its domain as a wanted clause with born=ground, which moves that domain to harvesting — and leave manifest where it is — it is the template freeze fills, not a file an open domain owns. A file that belongs to no domain leaves the cross-domain heuristic unreadable, and Probe refuses an envelope it cannot read; if two people would draw the boundary differently, settle it in Ground before the first intent.
  4. Wire the contract guard. The kit ships no guard script; you write one for your CI from the behaviour Ground describes, and until it exists rule 6 is a convention like the others. Both halves run in CI on the protected branch. The surface guard reads each frozen domain’s manifest as it stands on the protected branch, so removing an entry is itself a surface change, and fails when a listed surface file changes in a diff that adds no permit line naming it; the boundary — on GitHub, branch protection with required code-owner review on the surface paths — is what refuses the merge without your review. The execution guard compares the manifest’s check ids to the ids the runner reports as executed and passed, and fails on any that are missing, skipped or failing. Define the guard where the candidate diff cannot reach it — a workflow the forge requires from outside the repository, where that exists — because a job defined in the candidate tree can be skipped, and on GitHub a skipped required job reports success (checked 2026-09-05 against GitHub’s documentation). If it must live in the repository, its workflow file is the one surface file the guard cannot protect from a skip, and your review of any change to it is the only enforcer. A pre-push hook is advisory: the agent can edit or skip it. Describe the behaviour in Ground rather than the hook’s path. Outside a version-controlled repo — a standard drafted in a shared drive, a report — there is no diff, so the guard has no enforcer and the consistency oracle usually has no runner; what survives is the pin, the reader check and the log. Say so in Ground rather than pretending the guard exists.
  5. Pick the first intent by profile. On brownfield code it is harvest what is already true — everything lands observed, so nothing accidental becomes contract. On greenfield it is the skeleton runs end to end. On a prototype it is the riskiest assumption, written as a falsifier. On a documentation or specification project the document, not the code, is what the clauses are about; the first intent is a fresh reader can do X from this alone. The profile table in the reference names the usual oracles for each.
  6. Run changes. Copy changes/_template/ per change and follow the four actions. Once Probe reports no heuristic fired, delete design.md, tasks.md and the proposal’s proposal-path sections — they are requirement-first files, and an empty one archived beside a check-gated change is noise.
  7. Run until a domain qualifies for freeze. On code, the bet is that the first freeze is when the method starts paying: before it, this is bookkeeping; after it, the contract guard holds. On a prototype, which never freezes, or a document, which rarely does, the payoff is the pin itself: a claim about the artifact that a fresh reader has been shown to fail without. Walk and manual clauses get a scheduled re-check instead, an unmanifested reader clause is re-dispatched whenever the section it covers changes, and a mutant shows a check is not vacuous, not that it is adequate.

Turn the operations that earn it into skills after a real run, not before. If the method is too heavy, keep the pin, the evidence rule and the manifest and relax everything else first; the bet is that the likeliest failure is not a bookkeeping error but dropping the method.

Reference

The seven rules

Each rule names what it prevents and where it is checked. Only rule 6 is machine-enforced. The rest are conventions the agent follows because the prompt says so — “Probe refuses” means the agent is instructed to refuse, and nothing detects an agent that does not — which is why the loop log, the packet and the actual-versus-declared comparison are mandatory: they are where a human can see that a step was taken.

  1. The human owns the falsifier at every decision boundary. One line in proposal.md, before the agent builds, with its origin recorded: human, or agent, revised when you substantively changed a candidate the agent proposed. An unrevised candidate does not count, and Probe refuses while the origin is missing or unrevised. The boundaries are the change’s intent — a user-visible outcome — and any task inside a proposal that introduces a new assumption, trade-off or externally visible behaviour; every other task inherits the change’s falsifier and says so. The agent flags which tasks it thinks cross that line; the flag is its judgement, and you may overrule it either way. The agent proposes candidate counterexamples first so you are checking for omissions rather than composing from nothing; a narrow falsifier leaves the same interpretation gap an agent’s would, so the candidates are there to widen yours. Prevents the agent authoring both the intent and the test of it. Checked at Probe.
  2. A clause is a SHALL plus a scenario plus a pin with evidence. The Pin: line carries a stable id=, and its evidence field must be filled: mutant= for every oracle that re-runs without a person walking it (test, property, guard, consistency, reader), last= for a walk, owner= and next= for a manual check. mutant= names something that happened — the four-step record in Evidence below, with the assertion that caught it named in the loop log. Anything less is a note, not a clause. A clause you already mean to reject earns none of this; only a clause you promote needs a pin. The agent earns the evidence and reports it, so you are trusting its report on the one piece of evidence every pin rests on: spot-check one per change by choosing which mutant and reading a trusted runner’s re-application, or mutant= decays into a slug. Checked at Decide.
  3. Acceptance is yours; verification is the run’s. Clauses arrive observed, with mutant=pending until you promote them; only you flip one to wanted, and only you retire one. A wanted clause’s check is locked — the agent may change the artifact but not that check — and the lock is a rule the agent follows until freeze makes it machine-enforced. Turning a harvested clause down deletes its block from the delta — the reject line is its record — and is three decisions, recorded on that line: it is not contract; whether the behaviour stays in the artifact or is removed; whether its check stays as characterization coverage or is deleted. “Not promised” does not mean “not worth testing”: a brownfield characterization test may protect callers who depend on the accident, guard a regression while a migration is planned, or cover behaviour a wanted clause shares. Delete a check only when its purpose is obsolete. A kept characterization check is written in the loop that observed the behaviour, so the reject line can name it, and carries a comment with the clause id and the reject date. A reject whose ref is a change name records a deliberate omission from the artifact, not a clause, and carries no decisions. Close refuses while any clause is still observed, so accidental behaviour never becomes contract by default and never leaves by default either: you rule on it, in the packet. Verification — passing, failing, stale, unknown — is not a pin field; it is read off the latest recorded run, and a wanted clause that is failing is a stop until the artifact is fixed, the clause is revised by a new decision, or — while the domain is harvesting — an exception with owner, scope and expiry is logged. Prevents brownfield habits and agent guesses being promoted silently, and prevents a failing check being read as a change of mind. Checked at Decide and Close; the prototype profile is the one exception on promotion.
  4. The envelope gates the build: hard gates stop, heuristics escalate, and actual is compared to declared. Every probe declares an envelope before building. Hard gates read it against Ground and stop for your permission on that specific action, on either path, recorded as a permit line with an approval reference: a write to production or any shared environment; a destructive operation — delete, drop, migrate, overwrite; a credential or secret; an externally visible action — send, publish, pay, deploy; any item on the irreversibility list; any edit to a frozen domain’s verification surface. Heuristics are judged, not computed, and send the change to a proposal: uncertainty the agent names about the approach; rework — two reject lines naming a clause of this domain across the last three changes that touched it, or a wanted clause currently failing; growth — the envelope’s minute budget exceeds the summed minutes of the project’s last three building loops, read from the loop logs of open and archived changes, where a building loop is one that changed the artifact, and it cannot fire until three exist; cross-domain coordination — the intent spans two or more domains and at least one is under contract; contract change — the intent would modify or retire a wanted clause in a domain under contract, which is where spec-first practice takes over. Inside an approved proposal the heuristics are not re-evaluated, but the hard gates and the envelope stay live: exceeding the envelope pauses for an amend decision, not a second proposal. At every loop and at Close the agent lists what it actually wrote and did against what it declared, because a rule that reads only what the agent says it will do cannot see undeclared work. Prevents an irreversible action riding on a small diff, and an unrelated test added to a frozen file being treated as a design question. Checked at Probe and Close.
  5. One spec file per domain; every change is a delta. specs/<domain>/spec.md is the only spec; a change writes changes/<name>/specs/<domain>/spec.md and the merge at Close carries pins verbatim: ADDED blocks are appended under the domain’s Requirements — or, for an ### Invariant: block, under its Guarded invariants — MODIFIED replaces the block of the same name, RETIRED removes it from the domain spec and keeps the block with its last pin in the archived delta, and the delta’s own headings do not survive. The pin is the canonical record: the manifest, the packet’s clause list and the consolidate report are written from the pins, never maintained as a second copy. Ground constraints, written by ground with born=ground, are the one entry that arrives without a delta. Prevents a second set of books. Checked at Close.
  6. A frozen domain has a manifest and a contract guard. Freeze writes the manifest from the domain’s pins — clause id, check id, the verification surface, the contract-test export, the approval reference — and the guard’s two halves enforce it: the surface guard fails a change to any listed surface file that carries no permit line, reading the manifest from the protected branch; the execution guard fails a run in which any listed check id did not execute and pass. Authorization is the boundary Ground names — a review the agent cannot give itself, bound to the exact commit; the permit line is the record, and its approval= is a pointer for the reader, not a credential the guard verifies. A check changed under a permit re-earns its evidence before Close and its clause appears as MODIFIED in the delta. Reader and walk ids count, so freezing a document is expensive in a way freezing code is not: every edit to a section a reader check covers is a surface change. Freeze a document only once it is genuinely a published contract. Prevents check-tampering after the fact, including the indirect kinds — a fixture, a helper, discovery, a runner-level skip, the manifest, the requirement’s wording. Enforced by the guard you wire in Ground.
  7. Every departure is a line in DECISIONS.log, written by the agent from your reply. Kinds: reject · retire · permit · freeze · unfreeze · exception · amend · archive · consolidate. You decide in chat on a packet; the agent records, quoting your reply verbatim in the proposal’s Decisions section. The log trusts that transcription — nothing else in the repository holds your words — so every packet echoes the lines written since the last one, and a mismatch is yours to catch there. Every ~10 archives, and at every freeze, consolidate rewrites the domain spec by concept rather than birth order, runs a clause-versus-clause conflict scan, re-points any check= the rewrite breaks — never an id= — and lists overdue next= and last= dates and expired exceptions. Without it the spec converges on a check index with prose labels.

Evidence

A pin’s mutant= is the one thing every clause rests on, so what counts is defined narrowly.

The record. For every re-runnable check, four steps on a scratch copy, logged in the loop entry:

  1. Baseline. The unmodified artifact passes the check.
  2. Mutant. A sabotage that introduces the specific behavioural violation the scenario forbids — the guard removed, the store moved before the validation, the sentence and the example line deleted.
  3. Named failure. The check fails at the assertion that carries the scenario’s THEN, and the log names it. A THEN with two parts — “the request fails and nothing is stored” — needs an assertion for each, and a mutant that trips only the first leaves the second unproven; either add a second mutant or record the second part as unproven.
  4. Restore. The scratch copy is discarded and the check passes again.

What does not count. A compile error, a missing dependency, a runner crash, a timeout, or a failure in a different check are logged as attempts with their class, never as evidence. A red result is not a mutant kill unless step 3 names the assertion.

A failing baseline. When the check fails before any mutant, that is the falsifier firing — not evidence and not an attempt. Log it as the loop’s observed outcome and start the record once the artifact passes.

The contrast twin. A scenario that forbids something — rejects, refuses, never — carries a companion scenario under the same requirement showing the accepted case, or “reject everything” satisfies the check. The twin has its own pin and its own mutant; one twin per requirement covers every forbidding scenario under it.

Strength by consequence. One targeted mutant per scenario is the baseline and is cheap. Where a clause sits on the irreversibility list or in a domain under contract, add what the consequence warrants: a mutation score over the check (mutation-testing-ai-generated-code), a property oracle, or a hidden test the agent has not seen. A mutant shows a check is not vacuous, not that it is adequate.

Spot-check. Once per change you choose one clause and a trusted runner — a CI job, a script, a second agent with no stake in the result — re-applies its mutant while you read the outcome. Independent selection and interpretation is what the spot-check buys; operating the terminal yourself is not required.

A reader check is a file naming a question, a task, a closed list of what the reader is given, what is withheld, whether the reader may run anything, a repeat policy, a pass criterion, the mutant, and a Runs table. Running it means dispatching a fresh context — an agent, or a person who has not seen the work — with the check file as the task and exactly the files it names, nothing else; every dispatch goes in the check’s Runs table. Six decisions determine whether the check can fail at all and what a pass means, so the file states them:

  • Which question. locate: can a reader find and interpret the required information from the artifact, with everything that answers the task another way withheld? complete: can a reader finish the real task under realistic conditions, with whatever a real reader would have? Withholding the source makes the locate mutant bite and distorts complete; the two are both legitimate and never share one pass label. A clause about the document pins to locate; a complete run is recorded beside it as a realism check.
  • What is withheld. A locate check on a document about a system has to withhold the system — including what the reader could reach but must not open, such as a source tree it has just cloned. Give the reader the quickstart and the source and the mutant proves nothing: with the line deleted, the reader reads the source and passes anyway.
  • Whether the reader may execute. A text-only reader and a reader with a machine can return opposite verdicts on the same document — the first sees a coherent narrative, the second hits the error. Name which this check is.
  • That the reader states blocking questions instead of guessing. A dispatched agent has nobody to ask, so left alone it invents a plausible value and reports success, and the oracle degrades into whether it bluffed convincingly.
  • Whose context it is. A fresh context from the same model family that drafted the artifact shares training data and fails in correlated ways (oracle-problem-verification); dispatch cross-family where the clause matters, as diversity, not as a guarantee of independence.
  • The repeat policy. The check is stochastic in a way test is not. Fix the count before dispatching — three is the kit’s default — and the rule: unanimous is the result; a majority with one dissent is the result marked mixed; anything less is uncertain, which cannot promote a clause. Every dispatch is recorded, so “re-dispatch a disagreement” cannot become “run until it passes”.

The mutant removes everything that carries the clause’s content, not only the one sentence, and is applied to a scratch copy rather than the artifact. In the Runs table mutant-fail means the reader failed under the mutant — the check proving it can fail. Re-run whenever the section the check covers changes, not on every edit: at the default policy a pin costs nine dispatches — baseline, mutant and restore, three each — and each re-check costs three more. A reader completing a task does not establish that the document’s claims are true; a factual document keeps a separate consistency check against its sources for that.

A walk check is a dated procedure: a stimulus, the response the artifact promises, a measure, and the steps you take through the artifact to see whether it holds. It has no mutant because it cannot be re-run for free; the pin carries the date of the last walk instead, and consolidate lists walks that have gone stale.

States

A clause has two axes. Acceptance is the human’s and lives in the pin: observed (harvested, provisional, dropped at Close unless promoted), wanted (chosen by you, check locked, eligible to freeze), retired (withdrawn by you with a retire line; the block and its last pin stay readable in the archived delta). Verification is the run’s and is not a pin field: passing (the latest recorded run passed and nothing the clause covers has changed since), failing (the latest run failed), stale (what the clause covers changed after the latest run — on free oracles a run clears it, on readers and walks a re-dispatch or re-walk does), unknown (no run recorded in this environment). For free oracles the run record is the runner’s output; for readers and walks it is the check file’s Runs table, written by whoever dispatched or walked — usually the agent — and trusted the way the log is, through the packet’s echo. Close reports verification per clause; under contract, failing fails the build.

An exception is the third thing, logged separately and only while the domain is harvesting: a wanted clause that is failing or cannot currently be verified, excused by you with an owner, a scope and an expiry, so the clause stays wanted and the gap stays visible. A Ground constraint is the one clause that does not arrive through a delta: the ground operation writes it into its domain’s spec as a wanted clause with born=ground — evidence earned then if it has a check, a guarded invariant if it has none — and that domain is harvesting from that moment; one the artifact violates carries an open exception from day one. Consolidate lists expired exceptions, and an expired one counts as failing. Freeze requires none open, and under contract there are none: a failing check fails the build until the artifact is fixed or the clause is changed through a proposal, so the agent has no excuse path it can write for itself.

A domain is open (no clauses), harvesting (clauses exist; checks may well run in CI, but no manifest guards them), or under contract (frozen: every clause wanted and verified, a manifest written from the pins, a contract test exported to consumers). The state is the Status: line at the top of specs/<domain>/spec.md: open when the file is copied from the template; a Ground constraint written into it, or the first Close that touches it whether or not that Close promoted anything, moves it to harvesting; freeze and unfreeze move the last edge. Harvesting is a legitimate resting place — a domain with every clause wanted and no consumers to contract with stays there, and most documentation domains never leave it. A domain keeps its state while a proposal runs against it: a frozen domain stays frozen, its surface edits take permits, and it is re-frozen at Close. The full transition table is in spec-driven-development-operating-model.

Retiring is not the same as failing. A failing clause’s check fails; a retired requirement’s check still passes, so retirement is deliberate — a retire line carrying the decisions on behaviour and check, at Close — or a dead clause survives as a green test.

The contract guard

What “under contract” means mechanically, and what it does not.

The surface. Freeze declares, per domain, the files whose change could weaken its checks: the check files; the fixtures, helpers and assertion utilities they import; runner configuration and test discovery; the CI job that runs the execution guard; specs/<domain>/spec.md; the manifest itself; GROUND.md, whose irreversibility list, envelope defaults and approval boundary the hard gates read; and, for a reader or walk id, the artifact section the check covers. Before the first freeze, an amend to those three Ground sections is a packet decision you make, echoed back like any other. The manifest lists the surface explicitly, so the guard is a path check on a diff, not a heuristic.

The approval boundary. A change to the surface needs an approval the implementing agent cannot produce, bound to the exact candidate commit. Ground names which. On GitHub: a protected-branch review by you on that commit, with code owners on the surface paths and stale reviews dismissed on new pushes, or an environment approval; other forges have equivalents. A chat decision you post that a separate controller records with the commit is the headless shape — a design slot, not built here. Two preconditions make any of these hold, and the guarantee is void without them: the agent commits under its own identity, not yours, since an author cannot approve its own pull request and you could not approve one pushed under your account; and administrators cannot bypass the protection, which on GitHub is off by default and must be switched on (both checked 2026-09-05 against GitHub’s documentation). A permit for a gated action rather than a diff — a migration, a send — binds to the reviewed commit that adds the script or the decision reference the boundary provides. You never edit the log or the manifest. The permit line’s approval= field carries the reference; the line is the record, the boundary is the authorization, and the guard does not verify the string.

The execution guard. The CI job on the protected branch reads each frozen manifest as it stands on the base, not in the candidate, and compares the listed check ids to the ids the runner reports as executed and passed. Missing, skipped, or failing fails the build. It is a required status check, defined where the candidate diff cannot reach it wherever the forge allows, because a skipped required job reports success on GitHub. This is what catches a test skipped through the runner’s configuration, a discovery change, a deleted test, and a manifest entry removed in the same diff.

The export. Freeze also writes a contract test for consumers — the domain’s wanted scenarios and the ids of their checks, in whatever form the project’s consumers can run: a test file they import, a schema, a fixture set — and names it in the manifest as export:, or none where consumers have nothing to run, as on most documentation freezes. It is what makes “other agents build against it” a mechanism rather than a sentence: a downstream service runs it on its side and learns of a contract change from a failure, not a message.

What it covers. Unapproved changes to the declared surface, and required checks that did not run or did not pass.

What it does not cover. Whether the checks express the requirement, whether the requirement expresses your intent, a mutant that was weak, a surface file you forgot to declare, its own workflow file if that lives in the repository, an agent committing under your identity, or anything outside a version-controlled repo. Those are bounded by the human-owned falsifier, the locked checks and the evidence rule with its spot-check, and only bounded.

Files and the pin line

The method’s own files live under one root, so adopting it is one copy; the artifact and its checks stay where the project keeps them.

The folder shape matches the root an OpenSpec-style tool uses; whether such a tool’s CLI tolerates the extra Pin: line, or RETIRED where it writes REMOVED, is unverified, and nothing here depends on one. Ground and the log sit inside the root rather than beside it.

The Pin: line goes directly under each #### Scenario: and each ### Invariant:, one line, no spaces inside values:

id= is assigned at harvest and never changes; consolidate may re-point check= and logs it, and nothing re-points id=. born= names the change that harvested the clause, or ground for a constraint entered at Ground. A THEN with two parts takes two mutants, joined with +. walk swaps mutant= for last=<date>; manual swaps it for owner=<name> next=<date>, and its check= is either a procedure slug or a file under checks/manual/. Two roots are in play and the grammar does not distinguish them: a checks/... or specs/... id or path, and the kit’s own GROUND.md and DECISIONS.log, are relative to the clauses/ root; every other id is relative to the repo root, which is the folder clauses/ sits in. pending is legal for check= and mutant= only inside a delta — an agreed scenario before its task, an observed one before promotion — and Close refuses it. Verification is not a pin field; it is read from the run record. A decisions line is YYYY-MM-DD | kind | domain | ref | text, where ref is a clause id, a check id, a surface file, a change name, a manifest path, a gated action or irreversibility-list item, or -.

The pin is the one record for now. Once tooling exists, the shape to move to is a small structured file per domain from which the readable pins, the manifest and the packet’s clause list are rendered; until then the pin line is that file, one line per clause, and the agent writes the manifest from it at freeze rather than maintaining a second copy.

The proposal path

A heuristic fired inside Probe, so the requirement gates the build.

  1. propose writes proposal.md (why, what changes, the heuristic) and design.md (approach, at least one alternative, files and domains touched, the envelope for the whole change, rollback). red-team runs on both; the strongest objection becomes either a #### Scenario: in the delta or a reject line. A red team whose findings go nowhere is theatre.
  2. You review and agree. The delta spec is written before the build — this is the agreement the check-gated path gives up — with each agreed scenario carrying acceptance=wanted and check=pending mutant=pending until its task earns them; Close refuses a pending. Agreeing also permits the hard-gated items the proposal names, one permit line each with the agreement’s approval reference.
  3. tasks.md decomposes the work (task-decompose shape). Every row names its falsifier as inherited or its own; a row gets its own — human-owned, per rule 1 — when it introduces a new assumption, a trade-off or externally visible behaviour, and the agent flags which rows it thinks do.
  4. Each row runs Probe and Decide inside the change folder until the scenario it names has its check and evidence; it was wanted at agreement. Heuristics are not re-evaluated inside a proposal; the escalation already happened. The hard gates, the envelope and the evidence rule stay live: an action outside the envelope pauses for an amend decision on the proposal, not a new proposal.
  5. Close merges, then re-freezes if the domain was under contract, which kept its state throughout: a permit line per surface change made during the tasks, its ref the check id or file, and one freeze line whose approval covers the rewritten manifest and spec.

For drafting the proposal itself, to-prd produces the requirement shape this path wants.

The spec rule. If what you are writing will later have executable checks, write it as clauses in specs/<domain>/spec.md, pinned to walk or reader now, and re-point the pin to test when the code lands — an oracle upgrade, logged as consolidate. If instead it is read by people — documentation, a standard, a brief, a report — the document is the artifact and the clauses are about it, pinned to reader and consistency.

Cadences and stop rules

  • Per loop: the envelope before the build; a prediction before the run; the evidence record; actual-versus-declared; minutes; the not-exercised list.
  • Per intent: cap about five loops.
  • Per change: Close refuses while any clause is still observed, then gates on every scenario or invariant outside RETIRED carrying a wanted pin with evidence, envelope actual matching declared, and the intent read.
  • Freeze eligibility: every clause in the domain is wanted, every free-oracle check executed and passed in the freeze run, every reader check dispatched and every walk walked since the section it covers last changed, no manual next= overdue, and no open exception. One recent probe of the domain is not enough; freeze needs current evidence for every clause it lists.
  • Consolidate: every ~10 archives and at every freeze.
  • Re-checks: last= on walks and next= on manual pins are dates that expire, and so is every exception; consolidate lists the overdue ones.
  • The numbers are starting values, not measurements. Five loops, three changes, ten archives, three building loops, three reader dispatches — none of these has been calibrated against a real project. Recalibrate them after the first one.

What to test next

Do not expand the method into a framework before it has been compared to something. The hypothesis is:

Clause Loop reduces intent drift and undetected regression enough to justify its additional human effort.

Arms. Baseline: intent, tests, code review and a changelog. Thin Clause Loop: the baseline plus the observed-versus-wanted separation, one targeted mutant per clause with a named failure, and protected clause-to-check links. Nothing else from this note.

Changes. Comparable real ones, one of each: an exploratory feature, a brownfield bug fix, a contract-sensitive change, a documentation task.

Measures. Human active time, not agent runtime; end-to-end delivery time; intent substitutions caught; defects found by independent checks; unnecessary escalations and approval friction; whether the records are usable in a fresh session; whether the workflow was followed without reminders.

Controls. Keep failed and abandoned attempts in the record. Strip clauses/ from the loop arm’s artifacts before evaluation so the evaluator cannot tell the arms apart. Give both arms’ artifacts to a fresh context for an intent-fulfilment read against the original intent, so “substitutions caught” has a ground truth that is not the loop’s own instrument. Seed one frozen domain before the contract-sensitive change, or the thin arm’s protected links never come into play. Alternate which arm goes first across the four changes.

What it can show. With one change per cell and one person in both arms this is a pilot, not an experiment: it yields observations — did gates fire, was the log written, minutes per loop, dispatches per pin, what the independent read found — not estimates of effect. Across four changes the expected number of intent substitutions is near zero, so a clean run is weak evidence for the method and one substitution the packet missed is strong evidence against it. The result feeds the falsifier in The idea and recalibrates every number in Cadences.

When not to use it

Against the obvious baseline — a test suite, a changelog and code review — what this buys is the pin and the contract guard: the link from a chosen requirement to a check demonstrated able to fail for the right reason, and a build that breaks when that link is cut or a required check goes missing. If you would not use those two, the remaining ceremony is overhead. The entry cost is real: six words to run a loop, about twenty more to set a project up, and none of the actions is free.

  • Where the smallest falsifier of an intent is “build it in production”, the work is plan-first and the loop does not apply.
  • Where the artifact has no checkable output at all — team topology, build-versus-buy — there is no probe; what remains is an intent, an adversarial walk, and a decision record with a reversal criterion, which is a decision journal rather than this method.
  • The rest of the boundary — multi-team contracts before anything has frozen, regenerate-from-spec practice, regulated audit trails, parallel agents and session handoff — is in spec-driven-development-operating-model.
