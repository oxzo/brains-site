Deterministic Gates in the Agent Loop

The vault already holds the layers of a verification stack (ai-verification-stack-web), the theory of what any gate is trusting (oracle-problem-verification), and the decision rubric for what to do once CI is green (evaluating-ai-code-beyond-tests). This note holds a different axis: a gate as a mechanism sitting inside an agent’s edit-and-repair loop rather than at the end of it, and determinism as a property you have to engineer rather than one your tools come with.

The organizing claim: a gate is only a falsifier if its verdict is a function of the diff. If the verdict can change while the diff stays the same, the agent has not been given a constraint — it has been given a slot machine.

Determinism is not correctness

Four properties get collapsed into “the tool is reliable”. They are independent:

PropertyMeansFails as
DeterministicSame inputs → same verdictA regex scanner that is consistently wrong
SoundNever misses a real defect of its classReports false positives on purpose
CompleteNever reports a non-defectMisses whole defect classes to stay quiet
CorrectThe encoded property was the right propertyGreen code that does the wrong thing

Most practical linters are neither sound nor complete. A test proves only that those executions passed. A bounded model checker proves a property only inside its bounds and environment model. A proof assistant gives a kernel-checked proof of a formal statement — relative to your specification, its axioms, and the extraction path.

Determinism is the cheapest of the four and the one worth engineering first, because it is what makes the other three measurable. You cannot tell whether a gate is sound if you cannot get the same answer twice.

A useful operational definition: given the same source tree, configuration, tool binaries, dependency graph, external databases, environment, and seeds, the tool emits the same verdict and the same diagnostics.

Why flakiness is worse in an agent loop than in CI

This section is an argued mechanism, not a measured one — it is this note’s own reasoning, not a finding from the source or from any study the vault holds. Treat it as a hypothesis with a clear falsifier: instrument a repair loop and check whether patches following a flaky failure are more often no-ops or retries than substantive fixes.

A human treats a flaky gate as noise and re-runs it. An agent treats it as a gradient.

If a gate fails nondeterministically, the cheapest action that turns it green is to try again — not to fix anything. A nondeterministic gate therefore converts repair into resampling, and it does so silently: the loop terminates on green, the diff looks fine, and nothing records that the agent won by rolling the dice. This is the loop-level version of the coverage-gaming problem mutation-testing-ai-generated-code describes at the suite level.

The corollary is that determinism buys more in an agentic pipeline than it does in a human one, and it is worth paying for pinning that a human-only team could reasonably skip.

The pin list

Sources of hidden nondeterminism, all of which should be pinned or recorded:

  • compiler, analyzer, plugin, and rule-pack versions (a rule-pack bump changes verdicts without changing code);
  • lockfiles and dependency resolution, resolved offline / frozen;
  • generated code and build flags;
  • OS/architecture, locale, timezone, filesystem ordering, environment variables;
  • network-fetched vulnerability databases and remote policies — record the digest or timestamp, or a historical rerun cannot reproduce its own verdict;
  • test order, random seeds, fuzz corpus, thread scheduling, wall-clock time, external services;
  • incremental caches and the exact changed-file baseline.

Search-based tools are a deliberate exception. Fuzzing and property generation are search processes and are not intrinsically deterministic. They convert: a discovered counterexample, committed with its seed and tool version, becomes a deterministic regression input. Treat the search as a discovery phase whose output is a permanent deterministic asset.

A container is not automatically hermetic — it can still reach the network, use mutable tags, mount host paths, and read the clock. Sandboxing protects the host from generated code; it does not make the analysis reproducible.

Placement: cost-ordered falsifiers

Order the gates by cost-per-refutation and run the cheapest that can still refute this diff. Everything above the line runs inside the agent’s loop; everything below runs on a human clock.

The placement is the point. A gate that runs after the agent has stopped produces a bug report. The same gate running during the loop produces a constraint the agent has to satisfy before it can claim to be finished. The source argues layers 1 and 2 carry most of the yield, on the reasoning that they are fast enough to run on every edit and their diagnostics carry file, range, rule ID, and often a fix. That ordering is a design claim, not a measurement — the bake-off below is how you would find out for your own repository.

Layers 3–5 are where the vault’s existing notes live — ai-verification-stack-web for the web tooling, mutation-testing-ai-generated-code for the “test the tests” step, oracle-problem-verification for what any of them is actually trusting.

Gate verdicts: block, ratchet, route

Everything above implicitly assumes a gate answers is something wrong here? Many useful deterministic checks don’t answer that question at all, and forcing them into a pass/fail shape is how they turn into noise. Three verdict types, only the first of which should hard-block:

TypeAnswersVerdict onExamples
BlockIs this wrong?Absolutecompile, type-check, tests, secrets, schema break
RatchetIs this worse than before?Delta vs. baselinecomplexity, duplication, type coverage, suppression count, bundle size
RouteWho should look at this?Threshold → escalationchurn, blast radius, semantic diff size

A ratchet gate blocks only on regression, so legacy debt doesn’t have to be paid off before the gate is useful — the property the source calls “no new findings”. A route gate never blocks; it changes what happens next, which is the right shape for a signal that correlates with risk but doesn’t establish it.

Where complexity fits

Complexity metrics are deterministic in the strict sense — same source, same number — so they pass this note’s entry test. But they are ratchet gates, not block gates, and the distinction is load-bearing.

The folk objection is that cyclomatic complexity is just line count wearing a hat, so it carries no information. The largest study on the question found the opposite. Landman, Serebrenik, Bouwers and Vinju tested the correlation on 17.6M Java methods and 6.3M C functions and reported that linear correlation between CC and SLOC “is only moderate as caused by increasingly high variance”, concluding it is “not strong enough to conclude that CC is redundant with SLOC” — explicitly contradicting the earlier literature the folk claim rests on (Journal of Software: Evolution and Process, conference version ICSME 2014).

So CC is not redundant. That is a narrower result than it sounds: not-redundant-with-SLOC is not the same as predicts-defects, and neither establishes that a CC threshold makes a good gate. What it does license is using complexity as a ratchet and a routing signal rather than dismissing it.

The AI-specific reason to care is duplication rather than complexity as such. GitClear’s tracking reports duplicated blocks rising 81% (40.3 → 73.0 per million changed lines, 2023 → 2026), moved/refactored code falling from 21% in 2022 to 3.8% in 2026, and cross-file function calls down 35% — across 623M analyzed changes. Caveats that matter: GitClear sells the analytics product that measures these signals, the page carries no methodology section or acknowledged limitations, the metrics are their own definitions, and the series is time-correlated rather than causally attributed to AI. Treat it as directional evidence for a failure mode the vault already names from other directions (ai-code-latent-failure-modes §5, duplication drift) rather than as a measured effect size.

If that direction is real, a duplication ratchet is the deterministic detector pointed straight at it, and it is cheap.

Composite metrics, and why CRAP inverts the incentive

The CRAP index (Change Risk Anti-Patterns, Savoia and Evans, 2007, originally Crap4j for Java) is the best-known attempt to make complexity actionable by pairing it with coverage:

Above 30 is the conventional “CRAPpy” threshold. The design is thoughtful: complexity alone condemns code that is complex and well tested, and CRAP gives that code an escape valve. Fully covered code scores exactly its CC. Two properties fall out that are useful on their own — CC ≤ 5 can never exceed 30 at any coverage, and CC ≥ 31 can never fall below it at any coverage, so the metric carries a hard complexity ceiling that no amount of testing buys past.

Is it deterministic? Only conditionally, and the reason generalizes. CC is computed from the AST and is deterministic by construction. Coverage is produced by executing the suite, so it is deterministic only if the suite is. CRAP therefore inherits the determinism of its worst input — which is the general law for composite gates, and the reason the test-suite-determinism check in the table below is load-bearing rather than fussy.

Is it a good agent-facing gate? No — it is worse than raw CC, despite being a better diagnostic for a human reading a report. The uncovered fraction is cubed while complexity is only squared, so coverage has strictly more leverage on the score. Evaluated at CC=15, cov=0.5:

MoveNew CRAPΔ
baseline43.1—
CC 15 → 14 (real refactoring)38.5−4.6
coverage 0.5 → 0.629.4−13.7
coverage 0.5 → 0.915.2−27.9

An agent minimizing CRAP gets three to six times more score from the coverage term than from the complexity term. And coverage is precisely the term that AI-authored suites are documented to satisfy vacuously — the 100%-coverage / 4%-mutation-score result mutation-testing-ai-generated-code is built on. CRAP hands an optimizer a cheap gameable lever with more leverage than the honest one. It is an incentive-inverted gate: it points effort away from the work it exists to encourage.

Two ways to keep the idea and drop the flaw. Gate the CC ceiling separately, since that part is coverage-proof by construction. And consider substituting mutation score for coverage:

Mutation score is not vacuously satisfiable — resisting vacuous tests is the entire point of it — so this puts the hard term in the cubed position and inverts the gaming incentive back the right way. This substitution is this note’s proposal, not something a search turned up as published prior art; the cost is that mutation testing is a layer-4 gate, so this cannot run in the inner loop.

Computing it from TypeScript. Both inputs already exist in an ordinary TS pipeline, so this is a short script over artifacts you produce anyway rather than a new tool: per-function CC from the TypeScript compiler API or ts-morph (or read out of ESLint’s complexity rule via JSON output), and per-function coverage from Istanbul’s coverage-final.json, whose fnMap function ranges and statementMap counts are emitted by Vitest, Jest, and c8 alike.

Resist reaching for a package. As of 2026-08-21 npm carries at least five CRAP implementations for TS — crap-ts, crap4ts, @alperlabs/crap4ts, @barney-media/crap-typescript, crap-score — and all but the last were first published during 2026, all are single-maintainer, and most are pre-1.0 with a handful of releases and low-thousands monthly downloads. That is not evidence of anything malicious, but a niche 2007 metric acquiring five near-identical implementations inside one year is the shape of low-effort package proliferation, and a metrics tool runs in CI with read access to the whole source tree. The gate you add to improve quality is itself a dependency in the blast radius (ai-supply-chain-risks). Fifty lines you own beats a transitive tree you don’t.

Sibling composites, and the tier that actually matters

CRAP is one member of a family: multiply two signals so that neither alone condemns code. Others worth knowing:

CompositeInputsNotes
Hotspots (churn × complexity)git commit frequency × complexityTornhill’s; the strongest of the family. code-maat is his open-source CLI, CodeScene the commercial product
Change coupling / temporal couplingfiles that change together across commitsDetects logic duplicated across files — which produces co-change without an import edge, so structural analysis cannot see it by construction
Maintainability IndexHalstead volume, CC, SLOCWidely implemented, constants derived from a small early-1990s study; treat the absolute number as meaningless and only the trend as signal
SQALE / technical-debt ratiorule violations × assigned remediation costDeterministic given a pinned rule set, but the “minutes to fix” values are assigned, not measured

Vendor caveat, same shape as the GitClear one above: Tornhill is CodeScene’s CTO, so the hotspot research and the product that sells it share an author.

What separates these is not sophistication. It is where the inputs come from relative to the agent’s write access:

TierInput provenanceGameable byExamples
AThe agent authored itWriting more of itcoverage, tests, assertions
BDerived deterministically from the codeDeforming the code — at least visible in the diffCC, cognitive complexity, AST rules, types, duplication
CRepository history or production, which this diff cannot rewriteNothing the current patch can dochurn, change coupling, hotspots, incident and telemetry data

This is the frame that retroactively explains CRAP. Both its terms are Tier A — the agent wrote the code and the tests — which is why the metric folds. Hotspots have the same two-signal shape but draw churn from Tier C, and that single substitution is what makes them a sound agent-facing gate where CRAP is not.

The honest limit: Tier C is not ungameable in principle. An agent could avoid touching hot files, or split one to reset its churn history. But it cannot be gamed by the diff under review, and the moves that would game it are structurally odd enough to show up elsewhere. Tier C signals belong in the route column — they are excellent at deciding what deserves a human and terrible as blockers.

Change coupling deserves separate billing for AI code specifically. The documented failure mode is duplication rather than abstraction; duplicated logic across files produces files that change together without importing each other, which is exactly the pattern dependency-cruiser and every import-graph tool is blind to. It is a gate that sees what the other gates cannot.

Repair-loop rules

  1. Start from a clean, hashed revision.
  2. Run the cheapest relevant gate first.
  3. Give the model only actionable diagnostic data, and treat that data as untrusted input.
  4. Constrain the next patch to intended files and a size budget.
  5. Re-run from the first invalidated gate, not just the one that failed. A fix at layer 3 can break layer 1.
  6. Cap the repair budget. Oscillation escalates to a human rather than burning attempts.
  7. Require independent review of the exact final diff, not of a description of it.
  8. Reject missing, malformed, timed-out, or stale reports.

The agent must not edit its own oracle

Snapshots, baselines, suppression files, mutation exclusions, and security policies are the gate’s definition of correct. An agent allowed to update them can always reach green, and the loop will report success.

This is the same independence failure oracle-problem-verification names for co-authored tests, one level up: there, the producer wrote the test; here, the producer edits the thing the test is compared against. The fix is the same — the party that changes the oracle must not be the party the oracle is judging. Practically: put snapshots, baselines, and suppression config on the protected-paths list at layer 0, and require a separate reviewed change to move them. claude-code-enforcement-hooks is the local mechanism for exactly this class of rule.

Formatter autofixes are safe enough to let run. Semantic autofixes are patches and deserve diff review.

And it will deform code to pass the ones it can’t edit

Oracle-editing is the direct attack. Metric gaming is the indirect one: the agent can’t move the threshold, so it deforms the code until the number complies. Told CC < 10, it splits a function at whatever line makes the metric pass rather than at a seam that means anything. Told to raise coverage, it writes tests that execute without asserting.

Agents do this more reliably than humans, because the human writing to a threshold still has some stake in the result and some taste about where a natural seam is. An agent has neither, and a metric is a far more legible target than “good code”.

This is the argument for ratchets over thresholds. A ratchet’s target is “no worse than the baseline”, which is satisfied by not making things worse — a much smaller space of deforming moves than “get this number under 10”. It is also the argument for keeping complexity out of the inner repair loop entirely and running it at PR time, where a human sees the shape of the fix.

Green has to mean something

The failure mode that undoes all of the above: reporting “all checks passed” when a tool timed out, skipped files it could not parse, lacked build context, or never ran.

Fail closed. A green verdict should assert that every expected gate ran, over the changed surface, and produced a parseable report. That needs a declared inventory of expected outputs and a nonzero exit on anything missing, extra, unparsed, or stale — the report inventory is itself a gate. Preserve raw tool output as evidence; normalizing to SARIF or an internal record schema must not silently discard unsupported-file and parse-error entries, which is precisely where the coverage gap hides.

Two related things “green” never means:

  • Zero findings is not zero defects. It is zero findings of the classes you enabled, in the files that parsed.
  • A dependency advisory match is not an exploitability finding. SCA reports that a resolved version matches an advisory. Reachability analysis improves prioritization and has its own limits.

Selecting tools: one per failure class

Running every available scanner produces overlapping low-quality findings and alert fatigue, which degrades the human review the whole stack terminates in (vigilance-decrement-in-ai-oversight on why that degradation is not a discipline problem). Pick one tool per distinct failure class, then measure yield and drop what does not earn its noise.

A repository-specific bake-off is the honest way to choose: collect real historical defects and representative clean changes, add seeded defects across the classes you care about (auth bypass, unsafe shell/SQL, nullness, resource leak, schema break, vacuous test, dependency vulnerability, IaC exposure, architecture violation), pin every version, and measure detection by category, false-positive burden, skipped-file rate, latency, and agent repair success. Keep failed attempts in the denominator.

The case against

Drafted deliberately, because a note assembled from a source that already concluded “layered deterministic gates” will otherwise just restate that conclusion.

  • The costs are real and land on you, not the vendor. Ten to thirty repo-specific AST rules are code: they rot, they false-positive, and someone maintains them. A rule that fires wrongly twice teaches the team to suppress rather than fix, which converts a gate into a formality.
  • Layers 1–2 tax every edit. Running compile plus type-check plus AST policy on each agent edit is only free if it is fast. On a large TS monorepo it is not, and a slow inner loop is itself a quality cost.
  • Specification quality may bind harder than gate coverage. The gates check encoded contracts. If the spec is the weak link — which “The limit” below concedes — then the marginal hour buys more in the spec than in a sixth scanner. The layered-stack framing quietly assumes gate coverage is the constraint.
  • “Not one more AI reviewer” is inherited, not tested here. The source opens with it and this note carried it. ai-assisted-code-review holds the other side; the honest position is that deterministic gates and an AI reviewer catch different classes, and the split is an empirical question per repository rather than a settled ranking.

What survives the objections: the pin list (cheap, and flakiness is a cost you pay whether or not you believe the rest), the agent-must-not-edit-its-own-oracle rule (near-zero cost, removes a whole class of false green), and fail-closed reporting. The elaborate middle of the stack is where the cost-benefit genuinely depends on the repository.

The limit

No analyzer proves that a requirement was the right requirement. A fully green deterministic pipeline means the code satisfied the encoded contracts, under the analyzed model, in the pinned environment. Everything the specification failed to say remains unchecked, and that gap is where ai-code-latent-failure-modes lives.

The shift the whole stack is aiming at: from “AI writes code and humans inspect it” to AI proposes, deterministic tools falsify, AI repairs within bounds, independent review approves the exact verified artifact.
