Reducing Quality Variance in Agent Output

The goal this note serves: a framework around a codebase that makes an agent produce higher-quality code and makes that quality consistent, accepting generation time and token cost as the price. deterministic-gates-agent-loop covers the gates, constrained-shape-for-verifiability covers narrowing the code’s shape. This note is the level above both — what the objective is, which control addresses which part of it, and what the whole thing costs.

The framing is worth being precise about, because it is a reliability problem rather than a capability one, and reliability-vs-capability-agents establishes those diverge systematically. Peak quality and consistent quality are different targets with different instruments.

Gates truncate; they do not lift

A gate can only reject. It cannot make acceptable code better. So a gate stack does not shift the quality distribution rightward — it cuts the left tail off, and the mean rises as a consequence of that truncation rather than independently.

For an explicit variance-reduction goal this is good news: gates are the correct instrument, and the instinct to build a framework out of them is right. But two consequences follow immediately.

  • The floor sits at your weakest gate’s threshold, not at the strength of your strongest one.
  • Defect classes you do not gate pass through with their full original variance. Truncation is per-class. A stack of eleven gates that all target correctness leaves readability, naming, and architectural fit exactly as variable as they were.

If you want the mean raised rather than the floor, the levers are different ones — better context, better specification, a stronger model — and no amount of gating substitutes.

Five sources of variance, and only one of them is gate-shaped

This is the part most gate-centric frameworks get wrong. Ask where the run-to-run spread actually comes from:

SourceWhat variesThe control that addresses it
SamplingSame input, different roll of the diceGates plus bounded retry — the one gates genuinely fix
ContextWhich files were loaded, in what order, whether compaction firedDeterministic context assembly; pin what gets loaded (context-repo-loading-patterns)
SpecificationAn ambiguous requirement read differently each runSpecification work. Gates cannot see this at all
HorizonLong runs degrade — context pressure, compaction loss, self-conditioningTask sizing and checkpointing (agent-autonomy-horizon)
SubstrateThe agent imitates whatever surrounds the editExemplar quality in the touched area (ai-friendly-repo-structure, constrained-shape-for-verifiability)

A framework made only of gates addresses one row of five. That is the central design point, and the reason “add more gates” stops paying long before the problem is solved.

Of the four that gates miss, specification variance is the one to worry about most, because it is plausibly dominant in real work and it is invisible to every downstream control. Two runs that interpret “handle the error case” differently both pass every gate you own. The framework’s specification layer is not a nicety on top of the gates; it is doing more of the work.

Substrate variance is the one with compounding returns. An agent’s output regresses toward the local mean of what it can see, so cleaning the exemplar surface reduces variance on every future edit in that area, permanently, at no per-run cost. Gates charge rent forever; substrate work is bought once.

What the stack costs

Gate runtime is not the dominant cost. First-try pass rate is. If a stack has n gates and the agent satisfies each on the first attempt with probability q, the combined pass rate is q^n and expected attempts is 1/q^n — so cost rises superlinearly in gate count.

Fifteen gates at a 90% per-gate first-try rate means half of all tasks exhaust a three-attempt budget and escalate. At that density the framework has not reduced variance — it has moved the variance onto the human review queue, which is the resource vigilance-decrement-in-ai-oversight says degrades under exactly that load.

Model caveats, because the shape matters more than the digits: gate failures are not independent (a bad diff trips several at once, and one repair often clears several), and q is wildly non-uniform — a compile gate might sit at 0.98 for a competent agent while a bespoke architecture rule it has never been told about sits near 0.5. Read the tables as the shape of the curve, not as calibrated predictions for a real repository.

The highest-return move: give every gate a context-side twin

Because p = q^n is multiplicative, raising q beats reducing n. And the cheapest way to raise q is to stop letting gates be a surprise.

A gate whose rule the agent was never told is being used for discovery — the agent finds out the rule by violating it, and you pay a full generation cycle for information you could have given away for free in the prompt. State the rule up front and the same gate becomes pure verification.

The arithmetic is worth seeing, at n=10:

first-try rateexpected attempts
q = 0.80 → 0.959.3× → 1.7×5.6× cheaper
q = 0.90 → 0.982.9× → 1.2×2.3× cheaper

So the design rule is: every gate gets a context-side twin. The rule is stated in CLAUDE.md, the skill body, or the task prompt; the gate exists to verify it held, not to teach it. A gate with no twin is a tax you chose to pay.

The corollary is that this bounds gate count in a useful way. If a rule cannot be stated compactly enough to sit in context, it is probably too intricate to be a good gate — the agent will keep tripping it, q stays low, and it drags the whole stack’s economics down.

Retry is rejection sampling, and it selects on the proxy

Bounded retry against a gate is rejection sampling: you draw until a sample passes, then keep it. Which means output becomes conditional on passing the gate, and unmeasured quality dimensions move according to how they correlate with the gate.

  • Positively correlated with the gate (compile, type-check, tests that assert): selection improves them too. Retry is free quality.
  • Uncorrelated: unchanged.
  • Negatively correlated: selection actively degrades them. Where satisfying the gate costs the unmeasured property, more retries make it worse.

The negatively-correlated cases are precisely the metric thresholds from deterministic-gates-agent-loop — a complexity threshold traded against natural seams, a coverage threshold traded against test meaningfulness. Retrying harder against those does not converge on good code; it converges on code shaped to the metric.

Practical reading: retry freely against Tier B structural gates and correctness gates. Do not build a retry loop around a metric threshold.

Measure the variance, or the framework is faith

The objective is a distributional property, so a single run cannot confirm it. The instrument is pass^k from reliability-vs-capability-agents: run the same task k times from the same starting commit and look at the spread, not the best result.

Minimum viable measurement — pick five to ten representative tasks, run each k times with and without the framework, and record escaped defects by class, the spread of a quality proxy, attempts-to-pass, escalation rate, and wall-clock and token cost per accepted change. Keep failed attempts in the denominator.

Without this you cannot distinguish a framework that reduced variance from one that merely made the failures quieter, and measuring-own-ai-leverage is blunt that self-report is a broken instrument for exactly this question.

The case against

  • Truncation cuts the right tail too. Over-tuned gates reject unusual-but-correct solutions along with bad ones. Variance falls, and so does the ceiling. Linters banning valid idioms are the everyday version.
  • The framework is code. It rots, it has bugs, and a false-positive gate is a permanent tax on every future change plus a standing incentive to suppress.
  • Escalation is variance, relocated. Past a certain density the human queue absorbs everything the stack could not resolve, and that queue has its own degradation curve.
  • The strongest objection: if specification variance dominates, almost none of this helps. Every control here operates downstream of the requirement. Two defensible readings of an ambiguous spec both pass everything. Before building the stack, it is worth checking whether the observed variance is actually sampling variance — the kind gates fix — or disagreement about what was being asked, in which case the money belongs in the specification layer instead.
