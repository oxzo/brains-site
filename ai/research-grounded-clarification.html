Research-Grounded Clarification

What it is

A four-phase protocol for handling a vague but load-bearing request: research → grounded questions → clarify → execute. The discipline is that no clarifying question is asked before the research is done, and every option offered to the user traces to something actually found — a file path, a recent error, a git-log signal, a function signature. Nothing is invented from base knowledge to fill an option slot.

Why it matters

Asking a clarifying question feels like rigor. It often isn’t. The failure mode is ungrounded clarification: when the model intercepts a vague request like “fix the bug” and immediately responds “do you mean authentication or session handling?” — with the two options pulled from training-data priors rather than the user’s actual codebase.

Three things go wrong at once:

  1. The options are confabulated. Neither may correspond to a real bug in this repo. The user is now forced to mentally translate “is this close enough?” instead of recognising their own context.
  2. The user-side cost is real. Every choice-presentation costs attention; making a wrong-target choice costs more (course-correction later, or silent acceptance of a bad framing).
  3. Multiplied ambiguity. A vague request followed by ungrounded options produces an interaction that is more ambiguous than the original request alone — the user now isn’t sure whether to answer the question or push back on the framing.

The source repo (see Sources) argues that grounded clarification produces better first-try outcomes; the sharper “ungrounded clarification is actively worse than no clarification” framing above is my synthesis, not a claim the source makes directly.

The fix is structural, not behavioural: do the research first, then ask the question with options the user will recognise as their own context.

The four phases

1. Research

Before formulating any questions, gather enough context that the question itself is informed:

  • Mine conversation history first — recent errors, files mentioned, decisions already made. Often the disambiguation is already in-session.
  • Codebase pass — Glob/Grep for related patterns, git log for recent change areas, look for failing tests, TODO/FIXME, recently-touched files.
  • External pass when warranted — local docs, WebFetch on a referenced URL, WebSearch for current state of a named library.

The output of this phase is a small set of actual candidates the question can offer — not a list of plausible-sounding options invented at question-formulation time.

2. Generate grounded questions

Construct 1-6 multiple-choice questions where:

ConstraintWhy
Every option comes from research findingsOtherwise the options are confabulation in a checkbox
2-4 options per questionMore than 4 → split into separate questions; less than 2 → not a question
Each question addresses one decision pointCompound questions force compound answers; users skip the nuance
Brief trade-off context per optionA bare label without trade-off is unanswerable without the model’s reasoning
Any ungrounded option is explicitly marked speculativeThe user always has “Other (specify)” available via free-text; the discipline is to flag the model’s confidence on each option, not to ban escape hatches

1-6 is a working range borrowed from the source repo, not a hard limit — the principle is one decision point per question, no more questions than there are genuine decision points. The number-of-questions heuristic:

  • 1-2 questions — simple ambiguity (which file? which error?)
  • 3-4 questions — moderate (scope + approach + validation criterion)
  • 5-6 questions — complex feature with multiple genuine decision points

If you want to ask more than 6, the request is too vague to clarify in one round — split into research artefacts the user can react to instead.

3. Clarify

Present via AskUserQuestion (the structured multiple-choice prompt tool). The structural fact that the options came from actual findings is what makes this phase cheap for the user — they’re recognising their own context, not adjudicating between the model’s guesses.

4. Execute

Proceed with the original intent enriched by the clarification answers and the research already done. The research is not wasted if the user picks an option different from what was guessed — the gathered context still grounds execution.

Anti-patterns

  • Asking before researching. The fastest path to the wrong target. The model feels efficient; the user pays for the confabulated options.
  • Ungrounded options to fill a slot. If the research found two candidates, the question has two options. Padding to three with a base-knowledge guess is the failure mode this entire protocol exists to prevent.
  • Asking five questions when one decision determines the rest. Resolve the upstream decision first, then ask the downstream ones only if they remain open.
  • Skipping the protocol on “small” requests. If a small request is vague, doing the small amount of research is cheap; doing it wrong because the question was guessed is not.
  • Treating clarification as a substitute for verification. Even after the user picks, the research findings still need verification against current state — answers don’t make stale context fresh.

Skip conditions

This protocol does not apply when:

  • The request is already clear and specific (named target, named action, named success criterion)
  • A factual answer is the entire deliverable (“what does this function do?“)
  • Conversation history already disambiguates without any research
  • The user has explicitly bypassed clarification (e.g. “just pick one and go”)

The default for a clear request is to proceed, not to invent ambiguity to clarify.

When the pattern itself is the wrong tool

The protocol has real costs and the costs are not always smaller than the failure it prevents. Cases where the pattern is over-engineered for the situation, or where it fails on its own terms:

  • Cost-asymmetric requests. If a slightly-wrong clarifying question would cost one extra turn (“no, I meant X”), the four-phase protocol is more expensive than the failure mode it’s preventing. Skip when the cost of being wrong is one round-trip.
  • Intentional vagueness. “Just try something and we’ll iterate” is a legitimate working style. The user wants the model to commit to a first interpretation and react to its output. The protocol gates exploratory action behind clarification the user did not want.
  • Research-frame confabulation. Phase 1 does not gather neutral evidence; it gathers evidence about the model’s interpretation of the vague request. If the model misreads the request (e.g., “fix the bug” → “the auth bug we discussed earlier”), the grounded options are now grounded in a confabulated frame. The protocol launders the misinterpretation into evidence-shaped options. Grounded options also exert stronger anchoring force than open-ended questions — if research missed the user’s actual answer, the options actively pull away from it.
  • Skip-conditions are self-evaluated. “Skip when the request is already clear” presupposes the model can judge clarity. The same model that confabulates options is judging whether to invoke the protocol. The safety valve runs on the same gauge as the failure mode; treat skip-conditions as soft, not hard.

The discipline is: invoke when the failure cost is large and the protocol’s cost is small relative to the failure. Both halves of that check matter.
