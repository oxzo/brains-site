Temporal Logic for Agent Runtime Verification

Linear Temporal Logic (LTL) is a modal logic over linear sequences of states, introduced by Amir Pnueli in 1977 for reasoning about reactive systems. Its relevance to AI agents is direct: an agent’s execution is a sequence of states and effects, and many of the safety / correctness properties we care about are temporal — “always X”, “if X happens then eventually Y”, “no Z until W”. LTL gives those properties a precise, machine-checkable form.

This note covers what LTL can and cannot do for agent supervision, with concrete examples for a coding agent. It is not an introduction to LTL as a logic; it is a decision aid for when reaching for the formalism is worth the cost.

The operators (just enough)

LTL extends propositional logic with operators over future states in an execution trace — the sequence of states or actions the agent moves through:

OperatorReadingHolds iff
◯ φ”Next”φ holds in the immediate next state
φ U ψ”Until”φ holds in every state until ψ becomes true (and ψ must eventually become true)
□ φ”Globally” / “Always”φ holds in every state of the trace
◇ φ”Eventually”φ holds in some future state
◇≤k φ”Bounded eventually”φ holds within k steps

A constraint is satisfied by a trace iff the trace makes the LTL formula true.

What kinds of agent properties become LTL formulas

The natural fit is trace-level safety and liveness properties — properties that quantify over the sequence of actions or observable states, not over the content of generated text.

Concrete coding-agent examples:

  • Globally safety. “The agent never writes outside the project directory.” □ (¬write_outside_workspace)
  • Globally with implication. “Every install of a third-party dependency is preceded by a vulnerability-database check.” □ (install_dep → vuln_check_was_run_first)
  • Until. “No commit until all tests pass.” ¬commit U all_tests_pass
  • Bounded eventually. “After a tool error, a recovery action occurs within 3 steps.” □ (tool_error → ◇≤3 recovery_action)
  • Mutual exclusion / sequencing. “Read-only mode persists until the human approves write capability.” read_only U human_approves_write

The structural test for “is this an LTL property”: you can describe it as a constraint on the sequence of events without needing to evaluate the content of any natural-language artifact in the sequence.

Runtime verification (RV)

The agent is non-deterministic and unbounded; you cannot verify the entire state space. So LTL’s most useful realisation for AI agents is not offline model-checking but runtime verification: a monitor evaluates the LTL formula step-by-step against the actual execution trace. When the trace is about to violate the formula, the monitor intercepts.

In a typical agent pipeline, the monitor sits between the agent’s plan (what it intends to do next) and the effect handler (what actually touches the world):

  1. Agent proposes effect e (write file, run shell, install dep).
  2. Monitor projects the effect against the LTL formula given the trace so far.
  3. If e would cause violation, monitor intercepts — denies the effect, signals back to the agent, optionally triggers a recovery rule.
  4. Otherwise, effect proceeds and the monitor advances its automaton.

This is where LTL meets functional-agent-architecture: typed effects give the monitor a clean alphabet — a fixed set of observable event types — over which to evaluate the formula. Untyped string-prompt-to-string-output agents don’t give a monitor anything to observe except the surface text.

What LTL cannot do

Recognising the limits is half the value. LTL is the right tool for trace-level safety. It is the wrong tool for:

  • Content-of-generated-output properties. “The generated code contains no SQL injection.” LTL has nothing to say about whether a string of Python is or isn’t injection-vulnerable. You need a different tool (taint analysis, static analyser) at the content layer; LTL can then enforce “static analyser was run and passed before the code is committed” as a trace property.
  • Properties requiring LLM judgment to evaluate. “The agent’s reasoning was sound.” Not expressible without grounding “sound” externally first. Same for “the diff is a refactor, not a rewrite.”
  • Probabilistic compliance. Classical LTL is binary — a trace satisfies the formula or doesn’t. LLM agents are stochastic and may transiently violate soft constraints. Extensions exist (Probabilistic CTL, statistical model checking, runtime-quantitative LTL), but they require committing to a specific extension; the 2026 literature on this for LLM agents is unsettled — recent papers proposing (p,δ,k)-style soft compliance frameworks have not yet stabilised into a citable standard, so treat compound-named variants in current writing with scepticism.
  • Real-time deadlines in wall-clock terms. LTL counts in steps of the trace, not seconds. For wall-clock real-time, MTL (Metric Temporal Logic) or TLTL (timed LTL) is the variant; wall-clock real-time is usually not the constraint that matters for coding agents.

Where the formalism is worth the cost

LTL has a tooling burden — you need a monitor, a trace alphabet, and a way to map agent effects to atomic propositions. The cost is worth paying when:

  • The safety property is load-bearing — getting it wrong is expensive or unrecoverable (production data, secret exposure, force-push).
  • The property is trace-shaped — expressible as “always/eventually/until” over a sequence, not as a content predicate on a single output.
  • The atomic propositions are observable — the monitor can determine if each one holds without LLM judgment.
  • The agent runs long enough that the temporal structure matters; for a single-turn completion, LTL is overkill.

For all other safety properties, lighter tools usually suffice — capability tokens that simply can’t issue the forbidden effect, pre-commit hooks, structured-output schemas. LTL is the right tool when the constraint is genuinely about the sequence, not the single action.

Tooling

  • Spin (Holzmann) — classic LTL model-checker; useful for offline verification of protocol-shaped agent designs, less so for runtime.
  • MOP / JavaMOP (Meredith & Roşu) — runtime monitoring framework supporting LTL and related logics; the closest match to “drop a monitor in front of an arbitrary system.”
  • Runtime Verification libraries — Bauer, Leucker, Schallhart’s runtime-LTL work is the citation backbone; specific libraries (e.g., LamaConv, AspectLTL) exist but vary in maintenance.
  • Domain-specific monitors — for typical coding-agent uses (no write outside workspace; no commit before tests pass), a hand-rolled state machine is often simpler than wiring a general LTL monitor. The LTL formula then lives as documentation and tests for the hand-rolled monitor.

Where this sits in the verification stack

Different from the content-level checks already in the vault:

  • ai-verification-stack-web — content-level verification (types, tests, mutation, visual regression). LTL doesn’t replace any of these.
  • evaluating-ai-code-beyond-tests — heuristics for evaluating the output; LTL evaluates the trace that produced the output.
  • functional-agent-architecture — provides the typed-effect alphabet that an LTL monitor needs; the architectural prerequisite.
  • multi-agent-governance — runtime governance layers; LTL monitors are one mechanism within the broader governance stack.
  • ai-agent-security — permission tiers and capability classification; LTL constraints often formalise the rules these tiers approximate.

What this doesn’t cover

  • Encoding standard policies as LTL. That is a per-policy authoring exercise; this note doesn’t catalogue them.
  • Performance overhead of monitors. Runtime monitoring is cheap relative to LLM inference but not free; for high-throughput pipelines this needs measurement.
  • Composition of monitors. Multiple LTL formulas form a conjunction; their joint monitor is constructable but engineering-non-trivial.
  • Branching-time logics. CTL and CTL* reason over branching futures, useful for would-have analysis; LTL is the linear cousin and the right starting point for runtime monitoring.

Sources

  • Pnueli, A. (1977). “The temporal logic of programs.” Proc. 18th FOCS, 46–57. The foundational paper introducing LTL for program verification; Pnueli later received the Turing Award (1996) in part for this work.
  • Manna, Z. & Pnueli, A. (1992). The Temporal Logic of Reactive and Concurrent Systems: Specification. Springer. The standard reference for LTL applied to reactive systems.
  • Holzmann, G. J. (2003). The SPIN Model Checker: Primer and Reference Manual. Addison-Wesley. SPIN remains the canonical LTL model-checker.
  • Bauer, A., Leucker, M. & Schallhart, C. (2011). “Runtime verification for LTL and TLTL.” ACM TOSEM, 20(4). The reference for runtime (rather than offline) LTL verification.
  • Meredith, P. & Roşu, G. (2010). “An overview of the MOP runtime verification framework.” Software Tools for Technology Transfer, 12(3). The MOP / JavaMOP framework — practical runtime monitoring.

The application of LTL-style runtime monitoring specifically to LLM agents is an emerging 2025-2026 research area; recent compound-named frameworks are not yet citation-settled (probabilistic LTL extensions, drift-bounded compliance, agent behavioural contracts with explicit (p,δ,k) tuples). Use the classical LTL + runtime-verification base; add probabilistic / soft-compliance layers only against a specific verified paper.
