Agent Policy Enforcement Gap

Third of four. agent-sandbox-isolation-tiers asks which boundary; agent-isolation-hardening asks does the boundary hold; this one asks can you make anyone use it, and what does the policy itself guarantee. Verified against Claude Code 2.1.220 docs as of 2026-07-31.

The organizational failure mode is a category error: shipping a configuration policy and believing you have deployed a security boundary.

The central distinction: who holds the authority, and where is it decided

The intuitive split — “configuration is soft, OS enforcement is hard” — is the wrong axis, and it breaks on the first example. The built-in Bash sandbox is enforced by the kernel, but it is switched on by sandbox.enabled, a settings key. A client that ignores that key never calls bwrap, and no kernel mechanism compels it to. The same holds for a developer who simply doesn’t start the container. An isolation tier the subject activates for themselves is not categorically stronger than a setting the subject can edit.

The axis that actually predicts strength is who controls the substrate the decision is made on:

Subject-controlled substrateSeparately-controlled substrate
ExamplesSettings on a developer’s laptop; a sandbox or dev container that same developer opts into; hooks and MCP servers they can editMDM-locked policy file; CI runner image; cloud VM the developer can’t reconfigure; egress enforced by a network the workload doesn’t administer
Decision made bySoftware running as, and configurable by, the party being constrainedA different principal, out of the constrained party’s reach
Survives a non-compliant or modified client?No — regardless of whether the mechanism is a JSON key or a hypervisorYes
Failure modeSilent detachment; nothing looks brokenAvailability — the control can block legitimate work

Anthropic states the limit for server-delivered policy plainly: it “provide[s] centralized policy enforcement, but … operate[s] as a client-side control, not a security boundary. On unmanaged devices, a user doesn’t need admin or sudo access to bypass them.”

That sentence generalizes further than the page it appears on. The same is true of an OS-level sandbox that the constrained party enabled. Isolation strength is a property of the deployment topology, not of the mechanism.

The corollary, which the rest of this note is an argument for: an org’s real enforcement surface is whatever it runs on infrastructure the developer does not administer. Everything else is a strong default that a motivated or merely misconfigured endpoint steps around.

Three delivery channels, and what each is worth

  1. Server-managed settings — from the claude.ai admin console, fetched at startup and polled hourly. Requires Team or Enterprise, Owner/Primary-Owner role, and reachability of api.anthropic.com. Built for orgs without device management.
  2. Endpoint-managed settings — MDM configuration profiles (macOS managed preferences, Windows registry) or files at /Library/Application Support/ClaudeCode/ (macOS) and /etc/claude-code/ (Linux/WSL). Anthropic’s own guidance: these “provide stronger security guarantees because the settings file can be protected from user modification at the OS level.”
  3. policyHelper — an admin-deployed executable that computes policy at startup from device posture or a remote service. Only honored from MDM or a system managed-settings file; when configured, its output replaces every other managed source, server-managed included.

Precedence has a sharp edge: server-managed and endpoint-managed settings do not merge. Claude Code takes the first source delivering a non-empty configuration — server first, then endpoint. If the server payload has any keys, the endpoint file is ignored. An org running both, expecting union semantics, is mostly running one of them.

But not entirely, and the exception matters operationally. A short list of keys is “honored when any admin-controlled managed source sets them, rather than only the winning source” — with the user-writable HKCU registry tier excluded, and the whole carve-out superseded when a policyHelper is configured. Those keys are sandbox.network.allowManagedDomainsOnly and sandbox.filesystem.allowManagedReadPathsOnly with their allowlists, allowAllClaudeAiMcps, the sandbox binary paths sandbox.bwrapPath / sandbox.socatPath, and forceRemoteSettingsRefresh. Do not decommission an MDM-delivered managed file on the strength of the general rule: it may still be the thing enforcing your sandbox locks and your fail-closed startup.

The managed tier is also five levels, not two — policyHelper > server-managed > MDM/OS-level policy > file-based (managed-settings.d/*.json + managed-settings.json) > HKCU registry. The same non-merge surprise therefore recurs inside the endpoint channel, between an MDM profile and a managed settings file. Note also that the HKCU tier is user-writable, i.e. there is a user-writable rung inside the “managed” hierarchy.

For multi-team policy authoring, file-based delivery supports a managed-settings.d/ drop-in directory on the systemd convention: base file merged first, then *.json sorted alphabetically, scalars overriding, arrays concatenated and de-duplicated, objects deep-merged. Numeric prefixes (10-telemetry.json, 20-security.json) control order.

The keys that lock, and the keys that merely win

Most settings merge across scopes, so a developer can widen an array-valued policy locally. Two different mechanisms push back, and conflating them produces a false map of what is actually locked.

Managed-only — “only read from managed settings. Placing them in user or project settings files has no effect.” The on-thesis subset of the documented list:

KeyEffect
allowManagedPermissionRulesOnlyPrevents user and project settings defining allow, ask, or deny rules; only managed rules apply
sandbox.filesystem.allowManagedReadPathsOnlyOnly managed allowRead paths honored; denyRead still merges from all sources
sandbox.network.allowManagedDomainsOnlyOnly managed domains honored; non-allowed domains blocked without prompting
allowManagedHooksOnlyOnly managed, SDK, and force-enabled-plugin hooks load; user and project hooks blocked
allowManagedMcpServersOnlyOnly managed allowedMcpServers respected; deniedMcpServers still merges
strictPluginOnlyCustomizationBlocks skills, agents, hooks, and MCP servers from user and project sources
disableSideloadFlagsRejects --plugin-dir, --plugin-url, --agents, --mcp-config at startup — without it these bypass strictKnownMarketplaces for a single run
requiredMinimumVersionExits at startup below the floor (claude update/install/doctor still work)
forceRemoteSettingsRefreshBlocks startup until policy is freshly fetched; exits if the fetch fails

Managed precedence, not a lock — these work from any scope; managed simply wins:

KeyActual behavior
permissions.disableBypassPermissionsModeDocs: “typically placed in managed settings … but it works from any scope. A user can set it in their own settings to lock themselves out of bypass mode”
permissions.disableAutoModeSettable in any settings file; “most useful in managed settings where they can’t be overridden”
sandbox.enabled, sandbox.failIfUnavailable, sandbox.allowUnsandboxedCommandsOrdinary booleans: “Claude Code uses the managed value and ignores anything a developer sets locally”

The practical difference: a managed-only key cannot be set locally at all, so finding one in a user’s settings file means something is wrong. A precedence key can sit in a user’s file looking authoritative while the managed value is what applies — and it produces identical observable behavior right up until the managed source stops being delivered.

requiredMinimumVersion is the partial answer to the “user runs an older client” bypass below — partial by construction, since “versions that predate this setting ignore it,” and it fails open on an invalid value by design so a bad policy push can’t brick the fleet.

On the deny/allow asymmetry. In the default configuration, deny is the more robust half: rules are “evaluated in order: deny, then ask, then allow. The first match in that order determines the outcome,” and permission rules merge across scopes rather than override — so a deny added in any scope holds. But this inverts under allowManagedPermissionRulesOnly, the first lock in the table above, which blocks user and project settings from contributing deny rules too. Under that lock the org gains total control and simultaneously loses the property that a developer can always tighten their own machine. Choose deliberately; the two goals are in tension.

excludedCommands has no managed-only lock. The docs say so directly: a developer can always append entries that run additional commands outside the sandbox. Keep the managed list narrow, and treat this as a known, unclosable widening path.

The bypass matrix

These are the vendor’s own disclosed limitations, not findings — the full eight-row security-considerations table for server-managed settings, plus two detachment paths from the platform-availability section. They are reproduced here because the set is more instructive than any single row, and because a reader who only skims the delivery docs will not assemble it.

ScenarioOutcome
User edits the cached settings fileTampered file applies at startup; correct settings restore on next fetch
User deletes the cacheFirst-launch behavior — brief unenforced window while settings fetch async
User runs an older clientVersions predating the feature never fetch or apply it (partly answered by requiredMinimumVersion)
User runs a modified binary”A user who can run a modified client can bypass any client-side control”
API unreachableCached settings apply if present; otherwise unenforced until next fetch
User authenticates with a different organizationSettings are not delivered for accounts outside the managed org
Network traffic intercepted or redirected”Disabled TLS validation or intercepted traffic can alter the settings the client receives”
User sets a third-party provider variableServer-managed settings bypassed entirely

Plus two more, from platform availability:

  • apiKeyHelper — “Keys returned by an apiKeyHelper script don’t trigger the settings fetch.” A user-settings key silently kills delivery, exactly parallel to the provider variable below.
  • Cloud sessions — “Endpoint-managed settings don’t reach cloud sessions,” so orgs using Claude Code on the web need server-managed settings as well. This partially undercuts the standard remedy of “just use the endpoint channel.”

The provider-variable row is worth stating precisely. Exporting CLAUDE_CODE_USE_BEDROCK, CLAUDE_CODE_USE_VERTEX, CLAUDE_CODE_USE_FOUNDRY, CLAUDE_CODE_USE_MANTLE, CLAUDE_CODE_USE_ANTHROPIC_AWS, or a non-default ANTHROPIC_BASE_URL makes the client skip the settings fetch. You cannot fix this from server-managed settings, because the block arrives through the fetch the export prevents. An endpoint-managed env block doesn’t restore it either — eligibility is checked before managed env blocks apply. Documented remedies: remove the export, set the variable to "" in user settings, or deliver policy through the endpoint channel. For Bedrock/Vertex/Foundry a self-hosted Claude apps gateway restores equivalent delivery.

The same variable has a CVE against it, from the opposite direction. CVE-2026-21852 (Claude Code < 2.0.65, CVSS 3.1 7.5, CWE-522, GHSA-jh7p-qr78-84p7): a malicious repository’s .claude/settings.json set ANTHROPIC_BASE_URL to an attacker-controlled endpoint, and the client issued authenticated requests before the trust prompt appeared — sending the API key in plaintext to the attacker. Check Point’s write-up: “every request included the authorization header – our full Anthropic API key, completely exposed in plaintext.”

So the endpoint-redirect surface is load-bearing in both threat models at once: a user exports it and silently leaves central policy; an attacker plants it and takes the credential. That convergence is the practical argument for treating API-routing configuration as a locked, managed-only concern rather than an ordinary setting — and it is why the fix deferred all network operations until after explicit consent.

Relatedly, CVE-2025-59536 (< 1.0.111, CVSS 3.1 8.8, CWE-94, GHSA-4fgq-fpq9-mr3g) is why the scope restrictions matter: hooks in a repo’s .claude/settings.json and MCP servers in .mcp.json executed at session start — MCP servers “immediately upon running claude, before the user could even read the trust dialog.” The keys a checked-out project is not permitted to set are a list written in incident response.

Read the matrix structurally rather than as a vulnerability list: two of its paths require no privilege and leave nothing visibly broken. That is the property worth carrying — not that policy can be defeated, but that the common detachment paths are silent. Being defeatable is true of all client-side policy by definition. Who is actually exposed: orgs on server-managed delivery without MDM. The docs steer security-sensitive deployments to endpoint-managed precisely because the file can be OS-protected, so the population most affected is the one that chose the convenience channel — which is also the population the channel was built for.

The startup race. Even in the compliant path, first launch without a cache fetches asynchronously and there is “a brief window before settings load where restrictions are not yet enforced.” forceRemoteSettingsRefresh: true converts this to fail-closed — the CLI blocks until a fresh fetch and exits if it fails. The trade is availability: if api.anthropic.com is unreachable, nobody can start Claude Code. Note claude auth subcommands are exempt so users can re-authenticate.

One hardening worth crediting: since v2.1.198 the cached env block withholds proxy/TLS, API-routing, and credential variables until the server confirms the payload — so a tampered cache can’t redirect the very fetch that would correct it.

Policy robustness details

  • Tolerant parsing. An invalid entry is stripped with a warning and the rest of the policy still applies; a typo cannot disable an organization’s whole ruleset. /doctor lists stripped entries with source file and field.
  • Hooks and claudeMd require user approval. Because they execute shell commands or inject context, delivered hooks show a security dialog; rejecting exits Claude Code. Non-interactive runs can’t show it — the settings apply for that run only, are not cached as approved, and the dialog appears in the next interactive session.
  • Auto-mode trust configuration is policy too. autoMode.environment tells the classifier which repos, buckets, and domains the org trusts, in prose. Without it, a correctly-behaving classifier blocks routine internal work and users hit the fallback threshold.

Detection and audit

Enforcement you can’t observe isn’t enforcement. Three documented layers:

  • ConfigChange hooks — documented purpose: “To detect runtime configuration changes, use ConfigChange hooks to log modifications or block unauthorized changes before they take effect.” Scope limit worth knowing: it fires on config changes during a session, with matchers for user_settings, project_settings, local_settings, policy_settings, and skills. There is no matcher for the server-managed cache, and a pre-startup tamper is not a during-session change — so this does not cover the cache-editing row above, and it is itself a hook delivered through the same client-side channel.
  • OpenTelemetry metrics — the documented path for monitoring fleet usage.
  • Audit log export / compliance API — settings-change events including action type, account, device, and previous/new values. Access via the Anthropic account team.

What this means for the isolation tiers

The recommendation, restated on the authority axis from the top of this note: push enforcement onto substrate the developer does not administer — the CI runner image, the VM template, an MDM-locked policy file, a network that enforces egress independently. Not because OS mechanisms beat config keys, but because a control the constrained party can switch off is not a control regardless of what enforces it.

This is why “commit a dev container to the repo” is a weaker answer than it looks, and the note should not have listed it as a remedy: Anthropic calls dev containers “a convention rather than an enforcement boundary,” and a repo file is squarely subject-controlled substrate. Enforcing one requires device management or software allowlisting — i.e. leaving the product’s control surface entirely, which is precisely the point.

Managed settings remain worth deploying. They are how the sandbox locks, deny rules, and requiredMinimumVersion reach compliant machines, which is most of them. Endpoint-managed delivery on MDM-enrolled devices also genuinely sits on separately-controlled substrate. The error to avoid is treating server-managed delivery to unmanaged laptops as equivalent, or letting either be the only thing standing between a hostile repository and production.

Counterargument

This note treats client-side controls as weak because they’re bypassable by a determined user — but that framing imports a threat model most organizations don’t have. The realistic population is developers who want to ship, not adversaries; for them a managed deny list is fully effective, and the bypass paths above are things nobody stumbles into by accident. Under that model the enforcement gap is close to irrelevant and the effort belongs in making the default path good — sensible allowlists, auto mode configured with real trusted infrastructure so it doesn’t cry wolf.

The gap becomes load-bearing in exactly two cases: when the threat is the code rather than the developer (a hostile dependency, an injected instruction — where the compromised client is the attack, not a policy violation), and when the guarantee is being made to somebody else — a regulator, a customer, an auditor. In the first, client-side controls fail by construction. In the second, “we deployed a setting” and “we enforced a boundary” are different claims, and only one is defensible under scrutiny.
