Generative UI Security — Rendering Untrusted Interface in a Privileged Host

Extracted from generative-ui-landscape, which covers the field, the options, and the research. This note covers one question in the depth it needs: when a model or a third-party server supplies interface markup, what stops it from doing whatever it likes?

Last verified: 2026-08-25. Every normative quote below is from a raw source file fetched and read directly — not a summary. See Corrections for why that is stated rather than assumed.

Which spec, and why it matters

ext-apps ships two files. specification/2026-01-26/apps.mdx is the Final one — what shipped as MCP’s first official extension, and what a host implements against. specification/draft/apps.mdx is the work in progress; it carries 73 normative statements to Final’s 56. Everything below is sourced to Final, with draft-only material labelled as such and never counted as an obligation. An earlier version of this note quoted the draft throughout while its sibling advertised MCP Apps as a finalized standard.

Different layer from the vault’s other isolation notes. agent-sandbox-isolation-tiers and agent-isolation-hardening contain a coding agent at the OS boundary, with containers and VMs. This note is further in: containing rendered markup inside a client the user already trusts.

The browser’s primitives are not the only tools available. The high-privilege hosts in question are Electron apps, which have process-level controls sitting underneath the iframe. Because this premise carries the whole section, here is what actually backs it per product, at three different evidence grades:

HostElectron?How this note knows
VS CodeYes — verified first-handA local install ships the Chromium/Electron runtime: chrome_crashpad_handler, v8_context_snapshot.bin, libffmpeg.so, resources.pak, LICENSES.chromium.html. Upstream package.json carries @vscode/gulp-electron and an electron build script. Checked 2026-08-25.
CursorYes, by inheritance — secondaryConsistently reported as a VS Code fork retaining its extension/runtime ecosystem. No vendor-documentation quote obtained; the fork claim is universal in coverage but not verified at Cursor’s own docs.

And a caveat that matters more than the table. Establishing that a host is Electron says the controls below are available. It says nothing about whether they are switched on — an Electron app can ship nodeIntegration: true and have none of them. “Is it Electron” is the question that makes the next questions worth asking; it is not itself an assurance.

Quoted from Electron’s own security docs, read directly 2026-08-25:

  • Process sandboxing — “Starting from Electron 20, the sandbox is enabled for renderer processes without any further configuration.” The checklist restates it: “This recommendation is the default behavior in Electron since 20.0.0.”
  • Context isolation — “Context Isolation is the default behavior in Electron since 12.0.0.” It runs preload and Electron APIs in a dedicated JS context, so renderer scripts cannot modify globals like Array.prototype.push out from under the preload.

The coupling is the part worth knowing, and it is a single-flag cascade. These defaults are not independent, and one setting silently removes both:

“Enabling Node.js integration for a renderer process by setting nodeIntegration: true disables the sandbox for the process.” “Disabling context isolation (see above) also disables process sandboxing, regardless of the default, sandbox: false or globally enabled sandboxing!”

So nodeIntegration: true → context isolation off → process sandboxing off, even if you enabled it globally. A host can believe it has three layers and have one. Electron’s own verdict on that state: “Loading, reading or processing any untrusted content in an unsandboxed process, including the main process, is not advised.”

VS Code additionally moved its extension host out of the renderer into a separate utility process and replaced the Electron webview tag with a plain iframe — reported in its process-sandboxing write-up, not verified against VS Code source.

Electron’s full security checklist is twenty items, not the handful summarised here; treat this as the subset that interacts with rendering untrusted UI.

So there are three layers, not one: OS/process sandbox → renderer configuration → iframe isolation. This note owns the third and the seams around it. If you are building an Electron host, the first two are yours too and they are stronger controls than any sandbox token — verify them, and verify the cascade above has not quietly collapsed them, before spending effort on flags.

Why this is not the usual iframe problem

Embedding untrusted third-party content in a web page is a solved-ish problem with well-worn answers. What changes here is what the embedding process is holding.

Browser tabIDE, desktop AI client, agent shell
Assumed hostile contentYes, by designNo, historically
Ambient authoritySite-scoped cookies and storageSSH keys, cloud tokens, repo write, shell
Cost of an escapeThat tabEverything the user has

Backslash Security’s analysis of the 2026-07-28 MCP spec (published 2026-05-28) puts it in one line:

“A sandbox escape in a tab costs you that tab. A sandbox escape here is a full IDE compromise.”

Provenance matters: that is a security vendor’s blog, it is architectural analysis, and it describes no disclosed exploit. The framing is useful and the risk is real in principle; treat the urgency as marketing-adjacent until an incident exists. The web-platform mechanics in the rest of this note are independently checkable and carry more weight than the framing does.

This is ambient-authority-and-blast-radius applied to a render path. The blast radius is not a property of how carefully the UI was generated. It is a property of what the host process can reach.

What the attacker controls

Assume the markup is fully attacker-chosen. The Final spec’s threat model, verbatim:

  • Malicious server delivers harmful HTML content
  • Compromised View attempts to escape sandbox
  • View attempts unauthorized tool execution
  • View exfiltrates sensitive host data
  • View performs phishing or social engineering

Note what that list assumes, and what this note inherited from it. Every entry names a third party — a hostile server, or a View compromised by one. It is the right model for MCP Apps, where markup arrives across an organizational boundary.

It is not the model for the case generative-ui-landscape identifies as the largest deployment: a first-party model generating raw HTML/CSS/JS for its own host, with no server in the loop. There the markup is authored by a component you trust, and the failure modes are different — output steered by injected content that reached the model’s context (prompt-injection), or simply wrong markup with no adversary at all. Neither a server allowlist nor predeclared-resource hashing applies, because there is no predeclaration and no server.

What still applies to the first-party case: the origin rule (§2), CSP as destination containment (§3), and the process layer. What does not: everything premised on reviewing a template before it arrives. This note is scoped to the third-party case. The first-party case needs its own treatment and does not have one here.

UI mimicry — the threat no sandbox flag addresses

The spec files this under “Other risks” and its advice is one line: “UI can still display misleading content. Hosts should clearly indicate sandboxed UI boundaries.”

A server ships HTML that renders as a pixel-accurate copy of the host’s own authentication prompt or permission dialog. The sandbox works perfectly. The user types their credentials into it anyway. Defenses are presentational, not technical: visible provenance on every server-supplied surface, host chrome that generated content cannot reproduce, and never rendering third-party UI in a region where native dialogs also appear.

The isolation stack

Five controls. They are not alternatives — each covers what the others miss, and the common failure is shipping one and assuming it is the sandbox.

1. The sandbox attribute, flag by flag

A bare sandbox is the strictest setting: no scripts, no forms, no storage, opaque origin. Every flag you add gives something back.

All fourteen tokens defined for the sandbox attribute, enumerated from MDN’s <iframe> reference source (fetched 2026-08-25) rather than from memory — an earlier version listed eight without saying so, and a partial list reads as a completed check:

FlagGrantsFor untrusted UI
allow-scriptsJS executionRequired for interactive UI. See the origin rule below.
allow-same-originThe frame keeps a real originDepends entirely on whose origin. See below — this is the subtle one.
allow-formsForm submissionConstrain with CSP form-action; do not assume CSP reaches the frame (see §3).
allow-modalsalert/confirm/promptWorkable; mild phishing surface.
allow-popupswindow.openPopups inherit the sandbox unless the next flag is set.
allow-popups-to-escape-sandboxPopups open unsandboxedNever. A documented escape hatch, not a convenience.
allow-top-navigationNavigate the whole host awayNo.
allow-top-navigation-by-user-activationSame, gated on a real gestureOnly if genuinely needed.
allow-top-navigation-to-custom-protocolsInvoke registered protocol handlersNo on a desktop host — custom protocols are a route out of the web sandbox entirely.
allow-downloadsTrigger file downloadsNo reason to grant. (The Final spec says nothing about downloads at all; a host-mediated ui/download-file flow exists only in the draft.)
allow-storage-access-by-user-activationRequest storage accessNo.

2. allow-scripts + allow-same-origin is only unsafe relative to the embedder’s origin

The single most important mechanic here, and the one most often stated wrongly — including by an earlier version of this note. The wrong version is the absolute one: “allow-scripts plus allow-same-origin is not a sandbox; always omit allow-same-origin.” Stated that way it would lead you to reject the MCP Apps spec’s own required design.

Content granted both flags keeps a real origin. If that origin is the embedder’s, the content can reach the parent DOM or locate its own <iframe> element and delete the sandbox attribute — no containment at all. If the frame is served from a different origin than the host, the same flag pair is fine: same-origin policy separates it from the host, and it can hold its own storage without that meaning anything to the embedder.

So the control doing the work is origin separation, not the flag in isolation. Two ways to get it:

  • Opaque origin — omit allow-same-origin. The frame gets a unique origin and cannot touch localStorage, sessionStorage, IndexedDB, or cookies at all. Strongest, and correct for content you never want to persist anything.
  • A different real origin — serve the frame from a separate origin you control. Keeps storage working, which a proxy layer needs. This is what ext-apps mandates (§5).

Ask “which origin, relative to what?” rather than “is allow-same-origin set?“.

3. Content Security Policy

The sandbox governs capabilities. CSP governs destinations — and exfiltration is a destination problem. A frame with scripts and no network policy can encode whatever it can read into a request to a server the attacker controls.

ext-apps makes this a host obligation rather than advice. Verbatim from the spec’s host-behavior section: “Host MUST construct CSP headers based on declared domains”; “Host MAY further restrict but MUST NOT allow undeclared domains”; “Host SHOULD log CSP configurations for security review.”

When ui.csp is omitted the host MUST apply this default, which is worth reading closely because it is a good starting policy for any untrusted-UI frame:

default-src 'none';
script-src 'self' 'unsafe-inline';
style-src 'self' 'unsafe-inline';
img-src 'self' data:;
media-src 'self' data:;
connect-src 'none';

connect-src 'none' is the exfiltration control — no fetch, no XHR, no WebSocket. default-src 'none' denies everything not listed. 'unsafe-inline' is present for scripts and styles, which is unavoidable for srcdoc-injected content and is exactly why the sandbox and origin controls have to carry the weight.

One gap worth catching if you copy this: the Final spec’s restrictive default omits object-src 'none', while the CSP-construction example a few lines later in the same document includes it (and font-src, and base-uri). The draft’s default has object-src and Final’s does not. Add it yourself — a policy with default-src 'none' covers object-src by fallback, but do not rely on reading that subtlety correctly under time pressure.

The spec’s construction example also maps declared permissions (camera, microphone, geolocation) onto the inner iframe’s allow attribute — Permissions Policy, a separate mechanism from both CSP and sandbox tokens. Three policy systems on one frame; know which one you are editing.

Note that CSP also offers a sandbox directive as a header-level equivalent of the attribute, though coverage differs — some sandbox tokens are implemented only for the iframe attribute. Use the attribute as the primary control.

4. postMessage origin validation

The channel out of the sandbox is the channel in. A handler that does not check event.origin accepts messages from anything that can get a handle on the window. Validate the sender origin on every inbound message, and treat the message body as untrusted input rather than as a command — the same discipline prompt-injection demands of model input.

Reusing a structured protocol helps here. ext-apps routes UI-to-host traffic over MCP’s JSON-RPC precisely so every message is typed and loggable, rather than a bespoke postMessage shape that nobody audits.

5. The sandbox-proxy pattern — and who it actually binds

Read the first clause before the rest, because it inverts who this section is for:

“If the Host is a web page, it MUST wrap the View and communicate with it through an intermediate Sandbox proxy.”

  1. “The Host and the Sandbox MUST have different origins.”
  2. “The Sandbox MUST have the following permissions: allow-scripts, allow-same-origin.”

The proxy is sandboxed, with allow-same-origin, and its safety comes from sitting on a different origin than the host — exactly the case §2 describes. The frame holds a real origin; that origin just is not the host’s.

The rest of the proxy’s obligations, from the Final spec:

RequirementLevel
Sandbox announces readiness (sandbox-proxy-ready); Host then sends the raw HTML (sandbox-resource-ready)MUST (both — the draft has these as SHOULD; Final is stricter)
Load the View’s raw HTML with CSP enforcing the domains declared in ui.cspMUST
frame-src 'none' unless frameDomains declared; base-uri 'self' unless baseUriDomains declared; object-src 'none'MUST
Restrictive defaults when no CSP metadata is providedMUST
Forward messages both ways, except methods starting ui/notifications/sandbox-MUST
Host must not send any request or notification to the View before receiving initializedMUST NOT
Proxy originates no requests of its own (it would have to synthesize request ids)SHOULD NOT
Set the inner iframe’s allow attribute from declared permissionsMAY

The scope problem, stated plainly. That conditional — if the Host is a web page — means this entire contract binds for browser-based hosts, which this note’s own trust table calls the low-privilege case. For an Electron desktop host (VS Code, Cursor, Claude Desktop — the high-privilege case this note exists for), the sandbox-proxy MUST does not apply, and the spec prescribes nothing in its place.

That is a genuine gap in the standard, not an omission in this note, and it is worth knowing before you cite the spec as your desktop containment story. What fills it:

  • The process layer documented at the top of this note — renderer sandboxing, context isolation, and not tripping the nodeIntegration cascade. This is the desktop host’s real containment, and it is Electron’s contract, not MCP’s.
  • The origin rule in §2 holds regardless of host type: an opaque origin, or a real origin that is not yours. A desktop host is free to adopt the proxy pattern voluntarily and probably should; it simply is not obligated to.
  • Mitigation 1 does bind universally: “All View content MUST be rendered in sandboxed iframes with restricted permissions.” That MUST has no host-type conditional. It just does not say which tokens.

So the honest summary for a desktop host: one unconditional MUST (sandbox the iframe), no prescribed token set, no prescribed origin model, and the Electron layer doing the actual work.

Confirmation: one direction, and it is a bare MAY

The only relevant flow in the Final spec is the View calling out — the app’s UI triggering a tool. It is governed by sandbox-proxy item 8:

“The Host MAY forward any message from the View (coming via the Sandbox) to the MCP Apps server, for any method that doesn’t start with ui/. While the Host SHOULD ensure the View’s MCP connection is spec-compliant, it MAY decide to block some messages or subject them to further user approval.”

MAY on both blocking and approval, with no recommendation attached. A server cannot assume the host will prompt. That is the whole answer for the shipped standard.

Draft-only, and this note previously presented it as an obligation. The draft adds app-registered tools — an agent invoking a tool the app declared — under a 5. App-Provided Tools Security section carrying SHOULD-level host protections, “Require explicit user approval for tools with readOnlyHint: false”, and a “user confirmation required” safe default for unannotated tools. None of that exists in Final. Grepping Final for readOnlyHint, app tool, or register their own tools returns nothing; its Mitigations run 1–4 plus “Other risks”, with no fifth section. If app tools land as specified, that second direction becomes real. Today it is not something a host is obligated to do or a server can rely on.

The practical rule is the same either way and does not depend on the spec: do not use the host’s confirmation UI as your authorization boundary. That is guardrail 3 in generative-ui-landscape.

Predeclared review — the control most likely to go unused

Worth pulling out because it is the spec’s most distinctive idea and the easiest for a host to skip silently. UI ships as ui:// resources referenced by tool metadata rather than embedded in tool results, specifically so hosts receive templates during connection setup, before tool execution. The spec’s host behaviors: review HTML for obviously malicious patterns, generate a hash or signature per resource, warn users about suspicious content, and allowlist or blocklist by resource hash.

Hashing is the part that turns this from a vague “review the HTML” into something operable — it gives you a stable identity for a template, so an approved template that later changes is detectable. If you are auditing a host, ask whether it does that or merely renders what arrives. The review window exists only if someone uses it.

Review checklist

Split by role, because most of these controls are only actionable by one of the two.

If you are building or auditing a host (the controls actually live here):

  1. How privileged is this process? Per-session, not per-product — the same IDE differs with and without cloud credentials loaded.
  2. If Electron: is the renderer genuinely sandboxed? sandbox: true, contextIsolation: true, nodeIntegration: false — and confirm the cascade above has not silently collapsed all three.
  3. Whose origin does the frame have? Not “is allow-same-origin set” — an opaque origin or a different real origin both work; the embedder’s own origin does not.
  4. Are the dangerous tokens absent? allow-popups-to-escape-sandbox, allow-top-navigation, allow-top-navigation-to-custom-protocols (this one matters more on desktop than on web).
  5. Is there a CSP, and does it block undeclared destinations? connect-src is the exfiltration control.
  6. Does every postMessage handler validate event.origin?
  7. Is the predeclared-review window actually used — templates inspected and hashed at connection setup — or does the host just render what arrives?
  8. Is a View-initiated tool call gated by something the host controls? The spec only says MAY; the decision is yours and nobody makes it for you.
  9. Is server-supplied UI visually distinguishable from host chrome?
  10. Are View-initiated RPC calls logged? Post-incident this is the only record — agent-audit-trails-provenance, post-breach-investigability.

If you are shipping a server that supplies UI (you control almost none of the above):

  1. Assume no host prompts before your tool calls. MAY is the spec’s word.
  2. Do not let the UI be your authorization boundary. Enforce server-side; treat anything arriving from a View as an untrusted request regardless of which UI produced it.
  3. Declare the narrowest CSP domains you can. Hosts may tighten what you declare but must not loosen it, so a tight declaration is a control you actually own.
  4. Assume your template is inspected and hashed — and that changing it may invalidate an allowlist entry.

What this note does not cover

  • No incident data. No CVE against MCP Apps, MCP-UI, or A2UI surfaced in this pass, and no public post-mortem of an attacked generative-UI system. Everything here is architectural.
  • No implementation was checked. This is the sharpest limit and it deserves stating first among them. Every claim here describes what a document requires. Nothing in this note establishes that Claude Desktop, VS Code, Cursor, or any other host actually implements the sandbox-proxy contract, the CSP default, or the predeclared-review window. A reviewer could complete every checklist item against an architecture no shipping product implements. Treat the checklist as questions to ask an implementation, not as a description of one.
  • First-party generation. Covered in the threat-model section: the model-generates-its-own-markup case needs separate treatment this note does not provide.
  • Server-side compromise. Contained markup from a malicious server is still a malicious server; this note bounds the damage the UI can do.
  • Model-level defenses. Stopping a model from being steered into hostile output is prompt-injection; this note assumes that failed.
  • OS-level containment of the agent itself — agent-sandbox-isolation-tiers, agent-isolation-hardening. The host process layer is now covered above; the agent-in-a-container layer is not.
  • Supply chain. A compromised renderer library, or a malicious UI template in a registry, sits upstream of every control listed here and defeats all of them. ai-supply-chain-risks, supply-chain-security.

Corrections

Kept in the note rather than only in git, because this is security guidance: a reader may have acted on an earlier version, and each of these was wrong in a way that would change what someone built. Four errors across two revisions, and the pattern in them is the useful part.

  1. The sandbox-proxy architecture was described backwards. An early version said the outer proxy is same-origin with the host and unsandboxed, with an opaque-origin inner frame. The spec requires the opposite: different origins for Host and Sandbox, and the Sandbox holding allow-scripts and allow-same-origin.

  2. The origin mechanic was stated as an absolute — “allow-scripts + allow-same-origin is never a sandbox.” True only relative to the embedder’s origin. Stated absolutely it would lead a reader to reject the spec’s own mandated design as insecure.

  3. The consent claim was wrong twice, in opposite directions. First flatly (“the spec does not mandate consent”). Then the correction quoted the App-Provided Tools Security recommendations — which govern the agent invoking app tools — to overturn a claim about View-initiated calls, a different flow with a bare MAY. The second version sounded better-sourced and was wrong about which question it answered.

  4. An A2UI inner-frame sandbox flag list was published from a documentation summary. It is not what the specification requires. Removed rather than corrected.

  5. The wrong specification file was quoted throughout. Every normative claim was sourced to specification/draft/, while the sibling note advertised MCP Apps as a finalized standard. The load-bearing requirements — sandbox proxy, CSP — turn out to be identical in Final, so most of the note survived on luck. Two things did not: the app-registered-tools consent model (draft-only; absent from Final entirely) and the ui/download-file flow (same). This also means error 3’s “correction” was arguing about a feature that has not shipped, and the original blunt claim was right for the Final spec all along.

  6. The Electron premise was asserted about three named products without a source, in the very section added to fix an earlier premise error. Caught before it was wrong — all three check out — but it was the last unsourced specific in a note that had made a virtue of sourcing everything, and it was asserted from background knowledge, which is exactly what produced errors 1, 2 and 4. Now carries per-product evidence grades, two of which are secondary.

The pattern, revised. Errors 1, 2 and 4 came from treating an LLM summary of a page as a source read — a diagnosis this note published after round two, which then made error 5 harder to see, because provenance had been so visibly fixed that nobody asked which file. Error 3 came from a confident correction of an earlier error; error 5 was underneath it the whole time and was the actual root cause. Error 6 is the interesting one because it was a near-miss rather than a mistake: the claim was true, and it was still unsourced in a note whose entire credibility rests on sourcing. Being right by luck reads identically to being right by method until someone checks.

Four lessons, in order of how much they cost: name the document version, not just the document; fetch the raw file and grep normative keywords; when correcting, re-verify what question the new citation answers; and an unsourced specific is a defect even when it turns out to be true.

A reader is entitled to ask what this record implies about the claims that remain. The honest answer: every normative statement above is now quoted from the Final spec file and can be checked against it in a minute, which is the only assurance worth offering. The architectural reasoning around those quotes — the three-layer framing, the origin rule, the first-party gap — has not been tested against any implementation, and that limit is stated below rather than buried.
