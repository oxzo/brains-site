The Oracle Problem in AI-Code Verification

Every scan, gate, and monitor in the verification stack presupposes a test oracle — a mechanism that decides whether an output is correct — and then silently trusts it. The vault has treated this as a one-line aphorism (“the oracle problem is irreducible; someone must define correct” — ai-verification-stack-web, bias-aware-verification-protocol). This note holds the oracle layer itself as the object of study: the types of oracle a verification layer can pick, the independence failure each one carries, and the oracle-free escape (metamorphic / differential relations) for the common AI case where no reference output exists.

This is the meta-layer over the property-testing notes, not a re-derivation of them. functional-agent-architecture §5 already argues “test properties, not outputs” and ai-verification-stack-web catalogs the stack’s layers; this note asks the prior question those skip — where does the “is this property satisfied?” judgment get its authority, and is that authority independent of the thing it judges?

What an oracle is, and why it’s the hard part

A test oracle answers one question: given an input and the program’s output, is this right? Weyuker’s “non-testable programs” (1982) named the failure mode: for many programs there is no practical oracle — either the correct answer isn’t known in advance, or computing it is as hard as the program under test (the program is the most authoritative way to compute the answer). Barr et al.’s survey (2015) splits the available oracles into specified (a stated correctness condition), derived (a relation inferred from other artifacts or runs), implicit (universal properties like “doesn’t crash”), and human (a person judges).

The five types below are the cut that matters for AI-generated code — they are not exhaustive. Barr et al.’s implicit oracle (the program crashes, an assertion trips, a type-checker rejects) is a separate universal category folded out of scope here: it’s genuinely independent of authorship but only fires on the crudest failures, so it adds little to the AI-specific independence analysis.

AI-generated code sharpens the oracle problem because the two cheapest oracles both lose independence: the AI can write the test that judges its code, and it can draft the spec the code is checked against. An oracle that shares a source with the implementation can’t catch an error the two share. The whole problem reduces to: find a correctness signal that does not derive from the implementation it judges.

The five oracle types — and each one’s independence failure

A verification layer always picks one of these, usually without saying so. Naming the pick exposes what that oracle can’t catch.

Test (reference output / golden assertion)output matches a hand-written expected valueCo-authorship. When the AI wrote the test beside the code, the assertion encodes the same misunderstanding — the hollow-test pathology (100% coverage, ~4% mutation score; ai-verification-stack-web Layer 3). The oracle is downstream of the implementation, not independent of it.

Even a human spec only tests what it encodes (Quine–Duhem): a passing contract is silent on every property the spec didn’t mention — the bug lives in the gap.
Human (manual review / judgment)a person says it’s rightVigilance decrement. The human oracle decays under repeated exposure — rubber-stamping, automation bias (ai-automation-biases, cognitive-burden-of-ai-use). It also can’t perceive non-surface properties (a missing authorization check looks identical to a present one; vibe-coding-authorization-flaws) and doesn’t scale to the volume AI produces.
Formal / LTL (runtime monitor over traces)execution trace satisfies a temporal-logic propertyExpressiveness ceiling. LTL captures trace-level safety/liveness (ordering, “never X before Y”) but not content-of-output correctness (temporal-logic-for-agent-verification). It is genuinely independent of the implementation — and partial: a trace can be perfectly well-ordered while every value in it is wrong.
Cross-model (llm-as-judge / differential against another implementation)an independent model or version agreesCorrelated errors. The independence the method assumes is the thing AI breaks: same-family models share training data and fail in correlated ways — self-evaluation bias (ai-output-bias-fingerprints §8). Knight & Leveson’s classic N-version result (1986) already showed independently-written versions fail together more than chance predicts; two outputs from one model are far worse. Cross-family judging (e.g. a local Qwen/GLM label scored by Claude) is the mitigation, not a fix.

The pattern across the rows: the two cheap oracles (test, spec) fail on shared source; the human oracle fails on attention; the two independent oracles (LTL, cross-model) are either partial or correlated. There is no single oracle that is cheap, total, and independent — which is why the verification stack is a stack and why the protocol leans on diversity rather than any one gate.

The oracle-free escape: metamorphic relations

When no reference output exists — the normal case for AI-generated business logic — you can still test without an oracle by checking a metamorphic relation (MR): a relation that must hold between the outputs of related inputs, derived from the problem domain rather than from the implementation or any reference answer (Chen, Cheung & Yiu 1998). The canonical illustration: you may not be able to compute sin(x) to certify it, but you know sin(x) == sin(π − x) — feed both, compare, no oracle needed.

This is the derived oracle from Barr et al., and it is the one row above that AI doesn’t poison: the relation comes from the domain, so its authority is independent of the code under test even when the code was AI-written and the test was too.

Inputs can be random-generated (fast-check), so metamorphic testing rides the property-based-testing machinery functional-agent-architecture already describes — MRs are just the relations you assert in that harness.

The honest limit — necessary, not sufficient. A filterProducts that returns [] for everything satisfies MR1, MR2, and MR3 vacuously. Metamorphic relations constrain the shape of the answer, not its truth; a degenerate implementation can satisfy all of them. So pin one anchored point — a single hand-checked (input, known-correct-output) pair — to rule out the trivial-satisfaction collapse, and let the MRs cover the combinatorial space the anchor can’t. This is the metamorphic-plus-anchor discipline, and the trivial-satisfaction collapse is the failure mode to watch for when an MR suite is “all green.”

The practical move

The takeaway is not “use metamorphic testing.” It is: make the oracle pick explicit, then diversify so the failures don’t correlate.

  1. For any verification gate, name which oracle it is using (test / spec / human / LTL / cross-model / metamorphic). Most gates won’t have said.
  2. Read off that row’s independence failure and ask whether this artifact is exposed to it (AI-authored test → co-authorship; AI-drafted spec → circular; high-volume review → vigilance; same-family judge → correlated).
  3. Add a second oracle whose failure is uncorrelated with the first. A co-authored test (shared-source failure) pairs well with a metamorphic relation (domain-sourced, independent); a same-family judge (correlated failure) pairs with a cross-family judge or a human spot-check.

The oracle problem stays irreducible — Weyuker’s point holds, someone ultimately defines “correct.” What’s reducible is silently inheriting a single oracle’s blind spot, which is what the verification stack does today when it doesn’t say which oracle each layer trusts.
