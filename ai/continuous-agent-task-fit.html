Continuous Agents — What the Clock Buys, and What It Doesn’t

A standing agent is a process with a persistent identity that is woken repeatedly across weeks, by a schedule or by an event, rather than given a task in a session and exited. This note is about which work fits that shape. It is not about how long a single run may go (a different question with a different evidence base) or how many agents to run at once.

As of 2026-08-28. The vendor primitives cited here are months old and moving fast.

Confidence legend: ✅ = source re-fetched and the quoted text matched verbatim during this pass · ○ = single-source or secondary, not independently corroborated · (est.) = synthesis judgment, not a measured value.

The claim, stated so it can fail

Continuous operation does not deepen what an agent can think. It changes what it can be present for.

That sentence is easy to agree with and hard to test, so here is the operational form. Classify a task by when its inputs arrive:

  • A depth task has all of its inputs available at the start. A proof, a refactor, a research question with a fixed corpus.
  • A presence task has inputs that arrive after the start — a new commit, a deadline passing, a page changing, a message landing.

One shape fits neither cleanly and is named below rather than smuggled in: a sweep has all its inputs at the start but more of them than any single session can get through. For a sweep the clock buys windows, not thinking — which is consistent with the claim, and worth saying so the definition is not quietly doing the second disjunct’s work.

The hypothesis forbids one thing: a depth task improving under scheduled operation at equal spend and equal context resets. Same model, same total tokens, same number of fresh context windows and the same progress file — one arm runs its N sessions back-to-back in a day, the other spreads the same N sessions across a week. Only calendar spread differs. If the spread arm wins on a static-input task, the “presence” account is wrong and the clock is buying thinking after all. (est.) Nothing found in this pass reports such a result; that is absence of evidence, and the claim stays a hypothesis.

Two pins, and both matter. Equal spend: a standing agent that spends ten times more is not demonstrating a duration effect. Equal resets: splitting a large task across several fresh sessions with a progress file is standard practice for work that cannot fit one window, and an arm that gets more fresh contexts than the other is testing compaction, not the calendar. A comparison that lets those differ would “falsify” this note for a reason that has nothing to do with presence.

The counterargument first

The strongest case against this note is that there is nothing here — that a “standing agent” is a cron job with a language model in the loop, and cron is a solved problem.

The case is well made and partly right. ○ One practitioner account of replacing a working cron script with an agent doing the same job reports it cost more and ran slower, and frames the pattern as “bolting agents onto workflows that a script already handled.” ○ Two separate commentaries make the same reduction: “In their current form, AI agents are essentially cron jobs with a chatbot interface,” and, in software engineering, “a ‘job’, ‘worker’, and even ‘agent’” have always been things that wait “for a stimuli in the form of an application request or user input” and can “operate on a schedule, in the form of a ‘cron job’.” ✅ Anthropic’s own worked examples for scheduled routines are maintenance jobs, one weeknightly and one weekly — “A schedule trigger runs every weeknight against your issue tracker via a connector. The routine reads issues opened since the last run, applies labels, assigns owners” — which is what a well-written script has done for twenty years.

(est.) What this argument gets right: the trigger is ordinary. Schedules, webhooks, mentions, and queues behave the same whether the consumer is a script or a model, and inherit the same failure modes. What it misses: the argument is about the wakeup, not the work. The question this note asks is narrower — once something wakes on a schedule, is there a step in the work that needs judgment a script cannot supply? For some task shapes there is not, and the honest answer is a script. For others there is, and it is always the same step: the one after the detection.

Six task shapes

The shapes below are the ones where the binding constraint is attention over time rather than thinking capacity. Two columns carry the test the counterargument demands: what the agent adds beyond a script, and where its output lands — because a standing agent that produces continuously delivers into a review queue that is not standing.

ShapeWhat the clock buysWhat the agent adds beyond a scriptWhere the output lands
Watch — detect a delta against a baselineSampling at times nobody is lookingNothing for the detection — a hash, a diff, or a threshold does that. The agent’s value starts after detection: triaging the delta and proposing the fix. Every scheduled example in Anthropic’s routines documentation is this shape: scan merged PRs, flag docs “that references changed APIs”, open “update PRs … for an editor to review”A list a human reads, a ticket, or a draft PR
Revisit — surface decay after a half-life elapsesRemembering when something is dueThe re-verification: re-reading a source, deciding whether a claim still holds, rewriting it. A script can only say “this is old”An edit a human reviews, or a report
Resolve — close predictions whose deadline has passedNoticing the deadlineThe judgment call on the outcome, and the written reasoning for it. A script can list what is due; it cannot say whether it came trueA log entry a human samples
Accumulate — build evidence no session can holdMany samples across weeksReading and summarising each sample into a running record; the state is the productA dossier a human reads at intervals
Wait — act on an external event when it arrivesBeing there when it happensInterpreting a natural-language event (a message, an issue, a review comment) and deciding what it asks forA pull request, a reply — something with an approver
Sweep — grind large-N work no session would finishEnough windows to get through the listThe per-item edit or judgment itself, when it is not mechanicalMany small changes, each needing review

(est.) Read the third column as a filter. Watch without triage is a script, and an agent that wakes on the clock to check for a delta spends tokens confirming nothing changed. Watch with triage, Revisit, Resolve, Accumulate, and Wait need an agent for the second half — detection is mechanical, but what follows detection is a reading-and-judging step, and that is what the model supplies. Sweep depends on the item: renaming is a script, rewriting is not.

That gives the corrected shape of the hypothesis: the clock buys the detection, the agent buys the judgment, and the two are separable. The mistake is putting the agent on the clock. Put the script on the clock and the agent behind the script — and at least one runtime already does exactly that: ✅ OpenClaw’s heartbeat reads a scratch file first; if it “is effectively empty,” the runtime “skips the heartbeat run to save API calls,” reported as reason=empty-heartbeat-file, with other pre-model gates marked “(no model call).” The gate fires only on a file that exists and is empty; the same page says that if no scratch file exists, the heartbeat still runs.

What continuous operation costs that a session does not

Four costs are specific to the standing shape. They are what an operating design has to answer, and they are the reasons the cron-job reduction is not the whole story.

1. An exit code is not a result. A cron monitor treats exit 0 as success. A standing agent can exit 0 having done nothing, or having decided nothing needed doing, or having produced a confident wrong answer. ✅ Anthropic’s routines documentation says this outright: “A green status in the run list means the session started and exited without an infrastructure error. It does not mean the task in your prompt succeeded.” ✅ One personal-agent runtime builds the empty case into its default heartbeat prompt: “If nothing needs attention, reply NO_REPLY.” (est.) That is a third run state that a cron monitor only sees if the run reports it as a metric, and nothing found on the agent side reports it by default. Liveness monitoring for a standing agent therefore needs a task-level assertion in the ping, not just the ping. The assertion has to be on something the task was supposed to change, or it passes forever.

2. The empty wake still spends — unless something cheaper runs first. A script that finds nothing costs a process spawn. A model that wakes to find nothing has paid for the context it loaded to find out, and the size of that context is a design choice: ✅ OpenClaw’s cost guidance says a fresh session per heartbeat takes the load “from ~100K tokens down to ~2-5K per run” against carrying the conversation history in. The floor is a few thousand tokens per wake, or zero if a pre-model gate decides there is nothing to look at. Where no such gate exists the cost is uncapped in aggregate. ✅ Anthropic’s scheduled deployments cap each run separately and say so: the budget “bounds every run separately rather than acting as a cumulative ceiling across runs: a deployment with a ‘2000’ cap can spend up to about $20 on every run.” ✅ The per-session SDK cap defaults to “No limit.” Per-period ceilings exist only at the account level — ✅ a daily cap on routines, ✅ per-user monthly limits on one workspace type, ✅ monthly hard limits that return a 429. (est.) Nothing found in this pass offers, as a default, a cumulative budget scoped to one standing agent across its runs. (est.) There is a workaround, an API gateway key per agent with a per-period cap, but it is a deployment the operator builds, and nothing found gives a lifetime ceiling that does not reset. The integral over time is the operator’s to compute.

3. Unattended means unapproved. ✅ “Routines run autonomously as full Claude Code cloud sessions: there is no permission-mode picker and no approval prompts during a run,” and included connectors can be used “including writes, without asking for permission during a run.” A session agent has a human at the prompt to say no; a standing agent has whatever scope it was given, for as long as it is given. (est.) This is the time-integrated form of the authority question agent-policy-enforcement-gap asks at session altitude: a control that merely wins during a session can be re-argued in the next one, while a key that locks is the only kind that holds at 03:00. And where the agent can install its own trigger, the scope includes the schedule itself: ✅ OpenAI’s scheduled-task documentation says “Skills can also create or update scheduled tasks.” ✅ The one counter-design found is a session-scoped recurring task that “automatically expire[s] 7 days after creation,” which its documentation justifies as bounding “how long a forgotten loop can run.” A trigger that dies on its own is the cheapest answer to authority that would otherwise integrate without limit.

4. The intake is a trust boundary. Work arrives at a standing agent through channels that outsiders can write to: an issue, a pull-request comment, a message in a channel. ✅ Anthropic’s own guidance for the GitHub integration warns that “External contributors may include hidden instructions through HTML comments, invisible characters, hidden attributes, or other techniques,” and for the Slack integration that Claude “may follow directions from other messages in the context.” ✅ A 2026 systematisation of 78 studies on prompt injection against agentic coding assistants reports “attack success rates against state-of-the-art defenses exceed 85% when adaptive attack strategies are employed.” A job queue with a trusted producer does not have this property. Intake design for a standing agent is who may write to it before it is what format the message takes.

The review queue is the ceiling

The fourth column of the shapes table is the load-bearing one. Every row lands its output somewhere that is not standing: a human, or a gate a human configured. (est.) The capacity a standing agent adds is the production cost of each item minus the cost of checking it — so where checking an item costs about what producing it would have, a 24/7 producer aimed at a 9-to-5 reviewer is a capacity transfer dressed as a capacity gain. That is the case for output that must be read in full, judged, and possibly redone. Where checking is cheap relative to producing, the gain is real, and that gap is the whole design lever.

Two things follow. First, any task shape adopted has to state where its output lands and who absorbs it, in the design, not afterwards. Second, the shapes that fit best are the ones whose output is machine-verifiable or sampled rather than read: a resolved prediction with a stated criterion, a drift report with a hash, a change with a test, a go/no-go posted to a channel. Where the output must be read in full, the standing agent’s cadence should be set by the reader’s cadence, not the clock’s. ✅ GitHub’s coding agent enforces a version of this at the approval step. “The person who created the issue can’t be the final approver” is separation of duties, and also an admission that the agent’s output is a review item, not a result.

hitl-progressive-autonomy holds the mechanism for lowering per-item review cost as trust accrues; delivery-org-agent-fit-matrix argues the missing axis in most task-fit judgments is verification cost and blast radius, which is exactly the axis the fourth column tracks. autonomous-agent-vs-decomposed-workflow settles a related question, who owns control flow inside a task. Its answer, keep the loop bounded and gate at seams, carries over: a standing agent’s schedule is a control-flow decision made once and then never looked at.

What would revise this note

  • A controlled comparison where a static-input task improves under scheduled operation at equal spend. The hypothesis is dead and the note is retitled.
  • A vendor shipping a cumulative budget scoped to a standing agent across its runs. Cost 2 becomes a configuration problem.
  • A cron-monitoring product adding a task-level assertion state distinct from “missed” and “failed.” Cost 1 becomes ordinary SRE.
  • Pre-model gating becoming the default in every scheduling product. Cost 2 shrinks to the gate’s false-negative rate, and the Watch row’s caveat goes.

Limits

  • Vendor documentation is the main evidence base. It describes what products do, not what practitioners experience; the practitioner sources here are ○ secondary and few. Several of the surfaces cited are in preview or being retired; the routines page carries a research-preview label and the Slack integration page a retirement notice, so the ✅ marks date faster than the arguments they support.
  • The six shapes are a partition chosen for this note, not a taxonomy found in the literature. A different partition would move some judgments; Anthropic’s own examples, for instance, are four event-triggered and two scheduled, which is Wait-heavy relative to this table.
  • “Equal spend and equal resets” is the pin that makes the hypothesis testable and also the reason no evidence was found: this pass found no such comparison, and did not search for one directly.
  • The only number found for the empty-wake cost is one vendor’s own “~100K tokens down to ~2-5K per run” figure, which measures conversation-history carry-in rather than the wake itself. The claim that the aggregate is material is (est.).
