Enterprise Agent Execution Architecture

The platform-agnostic layer under the Claude-Code-specific trio (agent-sandbox-isolation-tiers, agent-isolation-hardening, agent-policy-enforcement-gap). Those ask which boundary, whether it holds, and whether an org can mandate it for one tool. This asks what a production agent platform looks like when no single vendor’s feature set is assumed.

Provenance. Synthesized from an external AI-generated research report (dated 2026-07-31) supplied by oxzo, not from primary research by this vault. Four of its roughly forty checkable vendor and standards claims were verified against source before writing; those are marked ✅ below. The report’s own product-landscape section is deliberately not carried over — it is the part that rots fastest and the part least worth inheriting unverified. Structural claims here are argument, not measurement, except where this vault’s own probes are cited.

The thesis

A sandbox is necessary but insufficient. The sandbox should be assumed compromisable; its job is to limit the first blast radius.

The security objective is not “the agent cannot do anything harmful.” It is: no single model decision, prompt injection, sandbox process, dependency, credential, network path, or human approval can create an unbounded enterprise impact.

This is the same conclusion agent-policy-enforcement-gap reaches from the opposite direction — that note starts from one vendor’s policy system and finds it can’t bind a non-compliant endpoint; this one starts from architecture and concludes the endpoint was never the right place to put the guarantee.

Why agent execution is not ordinary application execution

A normal application runs developer-authored code on predefined inputs. An agent synthesizes new commands, interprets untrusted natural language as instructions, chooses tools dynamically, installs packages, retains state across long horizons, and can modify files that execute later somewhere else.

That produces three simultaneous problems, and most deployments solve only the first:

  1. Untrusted-code isolation — generated code may attack the kernel, runtime, parser, or helper services.
  2. Confused-deputy prevention — a perfectly isolated process can still misuse legitimate APIs, credentials, and repositories. Isolation does nothing here.
  3. Output and supply-chain containment — the agent plants changes in source, CI config, Git hooks, IDE tasks, skills, or lockfiles that execute later on a trusted machine, outside the boundary entirely.

A sandbox that protects the host kernel addresses (1) partially and does nothing about (2) or (3).

Trust assumptions

Assume adversarial: the model’s own output and trajectory; retrieved content, repository text, issues, documents, logs, and tool descriptions; packages and build scripts; the sandbox user including root inside the guest; outbound destinations reached via redirect, DNS change, or allowed SaaS APIs; persisted workspace, memory, snapshots, caches, and shared skills; other tenants; and a mistaken or malicious human request.

Protect: host and hypervisor; the orchestration plane; model and tool credentials; source, customer, and regulated data; cloud/K8s/CI/identity/secrets infrastructure; other tenants; the audit evidence and policy configuration themselves; and downstream consumers of generated artifacts.

The planes

The core structural claim is that these five planes must be separate, and that the agent sits inside only the second:

PlaneHoldsAgent’s access
Orchestration & policyModel gateway, deterministic policy engine, approval service, tool broker, credential exchange, budgets, kill switchNone — it proposes, the plane decides
ExecutionDisposable microVM/sandbox, no ambient identity, read-only input, ephemeral scratch, quotasThis is the agent
Capability brokersEgress proxy, package mirror, Git/DB/email/cloud brokers with destination and action policy, DLPOnly through typed calls
EvidenceAppend-only/tamper-evident run log, hashes of policy, image, inputs, actions, outputsWrite-only, out-of-guest
Verification & releaseClean image, hidden tests, scanners, exact-diff review, signingNone — cannot modify the verifier

Hard separation requirements: the sandbox cannot reach the hypervisor, container runtime socket, orchestrator API, cloud metadata service, secrets manager, policy store, evidence store, or approval database. The agent cannot modify its own network policy, identity, quotas, base image, verifier, hidden tests, audit sink, or termination conditions. The verifier consumes a content-addressed output — it never trusts a “tests passed” claim from the agent.

Policy enforcement lives outside the sandbox. An out-of-process reference monitor decides; the model only proposes. This is the architectural expression of the authority axis in agent-policy-enforcement-gap.

✅ Verified: kubernetes-sigs/agent-sandbox is real — a Sandbox CRD and controller under SIG Apps, supporting gVisor and Kata as isolation backends, with v0.2.1 moving to a “secure by default” networking architecture. It is the most direct standardization effort for this pattern.

A caveat from this vault’s own testing, relevant when layering: nested bwrap inside an unprivileged container fails to mount a fresh /proc, so an inner sandbox requires a documented weaker mode — see agent-sandbox-isolation-tiers. Layered isolation is defense in depth, not two independent boundaries.

Network is the most underestimated boundary

Default should be deny-all for both address families, no public ingress, enterprise-controlled or absent DNS, an immutable internal package mirror, and broker access only to named APIs. Block link-local, private ranges, node-local services, cloud metadata, cluster ranges, control planes, and other sandboxes.

Domain allowlists are structurally insufficient. Bypasses: compromised or user-content-hosting allowed services, redirects and alternate endpoints, DNS rebinding and raw-IP access, broad cloud API domains fronting many services, TLS/SNI vs HTTP Host ambiguity, non-HTTP protocols, QUIC/HTTP3, WebSockets, tunnels and CONNECT, and allowed APIs that themselves accept attacker-chosen destinations.

This vault has measured the claim rather than only citing it. Probing a replica of Anthropic’s published reference dev-container firewall found IPv6 traffic bypassing the entire IPv4-only policy, unrestricted DNS to any external resolver, and unrestricted TCP/22 to any host — with controls confirming the allowlist worked on IPv4/443. IPv6 is also what curl reaches for by default, so the unfiltered path was the default one. Details in agent-isolation-hardening. Three independent egress channels in an artifact whose shape is otherwise correct.

✅ Verified independently, from a different vendor: E2B’s documentation states internet access is enabled by default; domain filtering “only works for HTTP traffic on port 80 (via Host header inspection) and TLS traffic on port 443 (via SNI inspection)”; other ports use CIDR filtering only; “UDP-based protocols like QUIC/HTTP3 are not supported for domain filtering”; and “when both allow and deny rules are specified, allow rules always take precedence over deny rules.”

That last clause deserves attention on its own — allow-over-deny inverts the usual security default, so a broad allow silently defeats a narrow deny. Three sources now agree that hostname-based egress control leaks at the protocol edges. Treat “egress filtering: yes” in any product matrix as a claim to test, not a control to rely on.

Filesystem and persistence

Safe default: immutable base image; read-only content-addressed input; ephemeral writable scratch; an initially-empty export directory; no secrets mount; no host mount; no runtime socket.

Do not mount a developer checkout read-write into a high-risk sandbox. The agent can alter Git hooks, CI configuration, IDE tasks, build scripts, agent instructions, lockfiles, or generated binaries that later execute on a trusted host — problem (3) above. Prefer an immutable snapshot or private clone plus explicit patch export, and review hooks separately from ordinary diffs.

Interlock worth noting: sandbox-runtime implements exactly this defense as a mandatory deny list (.bashrc, .gitconfig, .mcp.json, .git/hooks/, .claude/agents/, …) — but on Linux it only blocks files that already exist, so a non-existent .git/hooks/pre-commit can still be created. A control this architecture treats as essential has a documented hole in at least one implementation. See agent-isolation-hardening.

Persist only what is required. Snapshots, caches, memories, package directories, browser profiles, and shared skill stores all carry state across runs; bind them to one tenant and never share writable state between trust domains.

Identity, brokered tools, and approval

Each run gets a unique short-lived workload identity, exchanged for narrowly scoped, audience-restricted, destination-bound credentials only when a permitted tool call occurs. That identity carries tenant, run/task ID, risk tier, data class, initiating human, approved tool set, expiry, and policy and image digests. Broad reusable credentials never enter the sandbox.

Prefer typed business tools over shell access to enterprise APIs. A git.create_pull_request tool taking a repository, base commit digest, patch digest, and branch lets the broker independently check tenant, branch pattern, changed paths, secret scan, policy, approval, and idempotency — then act with its own credential. The agent never holds the Git token.

Human approval is not a sandbox. Approvals are defeated by fatigue, misleading summaries, race conditions, and post-approval mutation. Bind approval to canonical bytes or a content digest, exact target, action, policy version, expiry, and maximum count; require re-approval when any bound field changes; show the reviewer the exact diff and an independently generated risk summary, not the agent’s own explanation.

The general form of a finding in agent-sandbox-isolation-tiers: boundaries stated conversationally (“don’t push”) are re-read from the transcript and can be dropped by context compaction. Durable authorization must be a rule, not a sentence.

Fail-closed conditions

For high-impact operations the orchestrator must deny, terminate, or quarantine when identity/attestation/tenant binding is invalid; a policy decision is deny, unavailable, timed out, indeterminate, or untraceable to a version; a tool request fails schema, canonicalization, or object-level authorization; approval is absent, expired, revoked, or doesn’t match the action digest; egress enforcement or destination validation is unavailable; classification/residency/DLP outcome is unknown for a sensitive sink; image or artifact signature, provenance, or SBOM is missing or invalid; the required runtime class or tenant boundary can’t be proven; the durable evidence sink is unavailable; the identity broker can’t mint the narrow scope; or persistent state lacks valid tenant and integrity metadata. It must never guess, retry through a weaker path, or fall back to a broader credential.

Availability exceptions must be preauthorized, named, and limited to low-risk read-only paths.

Risk tiers

TierExampleMinimum isolation and authority
0 AdvisorySummarize supplied documentsNo execution; scoped read-only retrieval; output filtering
1 Bounded developmentAnalyze trusted repo, draft a patchDisposable gVisor/microVM; read-only input or private clone; no secrets; restricted mirror; PR draft only
2 Untrusted code/dataExecute generated code or third-party reposmicroVM; no network by default; no persistent state; brokered tools; full audit; independent verification
3 Sensitive enterprise actionModify internal systems, regulated data, cloud resourcesTier 2 plus tenant-dedicated boundary, workload identity, typed tools, DLP, exact-action approval, separate release authority
4 Hostile evaluationCyber agents, malware analysis, containment testsOffline or one-way; dedicated hardware; no enterprise credentials or routes; tripwires; external kill controls; post-run rebuild

Authority should expand within a run only after objective evidence passes. Don’t provision a Tier-3 identity because a task might eventually need one.

Acceptance tests

The operational counterpart to “verify the boundary, don’t declare it.” The platform should fail closed against: host access via runtime sockets, device nodes, host namespaces, hostPath, or nested virtualization; egress via raw IP, IPv6, alternate DNS, DNS rebinding, redirects, QUIC/UDP, WebSocket, CONNECT, cloud metadata, or exfiltration through allowed code-hosting, logs, package names, or model APIs; identity attacks using expired/wrong-audience/replayed tokens, post-approval parameter changes, or splitting a denied transaction into permitted small ones; required-control outages; filesystem attacks via symlinks, path traversal, archive extraction, and writes to .git/hooks, CI config, or lockfiles; and evidence attacks — dropping or reordering events, making tests green by editing tests or fixtures, or closing a run as successful after a policy denial. Required-control outages cover: policy engine returning deny/timeout/stale, credential minting unavailable, egress enforcement disabled, and evidence sink dropping events — each must stop consequential work rather than degrade.

Two patterns worth extracting, because they recur across the set:

  1. Three of these are escapes from a correctly functioning sandbox. In 25725, 39861, and 55607, bubblewrap did its job; the escape came from the seam between sandboxed and unsandboxed components, or from a write exception granted deliberately. This is the strongest available evidence for the thesis that isolation is the first blast-radius limit and not the guarantee.
  2. Two independent attacks target the same configuration surface from opposite directions. CVE-2026-21852 is an attacker placing ANTHROPIC_BASE_URL in a repo to steal a key; the policy-detachment path in agent-policy-enforcement-gap is a user exporting the same variable to silently drop out of central policy. A config key that redirects the API endpoint is load-bearing in both threat models, which is a good general signal for where to look in any agent platform.

Not verified and therefore not cited above: aggregator claims of a specific total CVE count for Claude Code, and the frequently-repeated “two CVSS 10.0 sandbox escapes” — only CVE-2026-25725 reaches 10.0, and only under CVSS 3.1.

Where this framework is weak

Three criticisms of the source report, recorded because the note would otherwise read as endorsement:

  1. It is documentary, not empirical. Built from vendor documentation and standards; its own evidence caveats concede vendor pages “do not independently prove isolation” — a concession that applies to the report itself. It prescribes adversarial acceptance tests without running any. This vault’s egress probe is one small counterweight and covers a single artifact.
  2. It never prices anything. The “minimum viable secure configuration” — fresh microVM per run, deny-all egress, internal mirror, brokered identity, tamper-evident evidence, independent verifier — is a platform team, not a config file. Calling it “intentionally inconvenient” is honest but is not a degraded-but-real tier for an org with two engineers. The gap between Tier 1 and “nothing” is where most real deployments sit and the report is silent there.
  3. It assumes the org owns the execution substrate. Every architecture is a cluster or managed service. The dominant actual deployment — agents in developers’ local IDEs on machines the org only partly controls — is out of scope, and that is exactly where agent-policy-enforcement-gap finds the enforcement gap bites hardest.

Counterargument

The architecture is correct and mostly unaffordable, and an unaffordable control set has a predictable failure mode: it gets declared, partially built, and then relied upon at full strength. Consider an org that implements the microVM and the egress broker but skips the evidence plane and the independent verifier. It has covered problem (1) and left (2) and (3) — the ones isolation never addressed — while feeling considerably safer. On that reading, the highest-value first move is not the microVM at all but the verification plane: a clean-room CI the agent cannot write to, which catches bad output regardless of how the sandbox performed, and which most orgs already have.

The counter to that: the verification plane only catches what reaches it, and problems (2) and (3) include actions that never produce a reviewable artifact — a credential used, data exfiltrated, a ticket closed. Verification is the cheapest high-value plane, not a substitute for brokered authority.
