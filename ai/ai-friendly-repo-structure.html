AI-Friendly Repository Structure

How to structure code repositories so AI coding assistants (Claude Code, Cursor, GitHub Copilot, Aider, Codex, Gemini CLI, etc.) can contribute effectively. Covers instruction files, architecture, context management, documentation, testing, workflow, and anti-patterns.

Why it matters

The difference between a repo where agents produce good work and one where they create a mess comes down to structure, guardrails, and workflow design. AI agents now write a large share of new code — estimates range from 22% of merged code (DX Q4 2025 survey) to ~41% of generated code; generated ≠ merged, so pick the measure before quoting a number. And the quality gap is real: CodeRabbit’s “State of AI vs Human Code Generation” (Dec 2025, 470 open-source PRs) found AI-co-authored PRs carried 1.7x more issues overall, security issues up to 2.74× higher in the worst category (XSS), and 75% more logic/correctness issues than human-only PRs. This is not about making AI’s job easier — it is about making your codebase more maintainable and your AI output more reliable.

(Corrected 2026-06-10: previously “2.74x more security vulnerabilities and 75% more misconfigurations… 2026 industry data” — 2.74x is the ceiling category, the 75% was logic issues not misconfigurations, and the source is CodeRabbit Dec 2025.)

AGENTS.md emerged mid-2025 from Sourcegraph, OpenAI, Google, Cursor collaboration. Now maintained by the Agentic AI Foundation under the Linux Foundation. Supported by 20+ tools. Over 20,000 GitHub repos have adopted it. If you use multiple AI tools, keep shared instructions in AGENTS.md and tool-specific overrides in their native files.

What to include

High-value content:

  • Build/test/lint commands with exact flags (agents reference these constantly)
  • Technology stack with hard version constraints
  • Non-obvious project conventions and patterns
  • Boundaries: always/ask-first/never tiers
  • Non-standard tooling underrepresented in training data
  • Workflow rules (branch naming, PR conventions)
  • Developer environment quirks (required env vars)

What to exclude:

  • Code style enforcement (delegate to linters/formatters — “never send an LLM to do a linter’s job”)
  • Architecture overviews (agents discover these independently; removing them produces identical behavior at lower token cost)
  • Repository structure documentation (becomes stale, actively misleads)
  • Content the agent can figure out by reading code
  • Standard language conventions the model already knows
  • Auto-generated content (LLM-generated instruction files reduced task success by 0.5-2% while increasing costs 20-23%)

Critical constraints

  • Frontier LLMs can reliably follow ~150-200 instructions. Claude Code’s system prompt uses ~50. Your file gets the remainder.
  • Keep under 300 lines. A focused 50-line file outperforms a sprawling 1,000-line one.
  • The reported performance gain from human-curated files (~4% in instruction-file evals) is real but modest. The ROI comes from preventing specific, observed failure classes.
  • “Lost in the middle” — critical rules should go early in the file.
  • Treat instruction files like code: review when things go wrong, prune regularly, test by observing behavior changes.

Multi-tool strategy

Claude Code reads AGENTS.md as fallback. If you only use Claude Code, CLAUDE.md alone is sufficient.

Hierarchical organization

All major tools support nested instruction files. Root = universal rules, subdirectories = scoped context. Nested files take precedence on conflicts.

Progressive disclosure pattern

Don’t front-load everything. Create an agent_docs/ directory with focused files:

  • building_the_project.md
  • running_tests.md
  • code_conventions.md
  • service_architecture.md

Reference from CLAUDE.md using @agent_docs/building_the_project.md syntax. Claude reads on demand, keeping base context lean.

2. Repository Structure Patterns

Vertical slicing by feature (strongly preferred)

AI agents traverse codebases depth-first. Vertical/feature-driven organization keeps everything an agent needs for one task in one directory, minimizing tool calls and context consumption.

Preferred:

Avoid (horizontal slicing):

Horizontal slicing scatters feature logic across directories, forcing agents to jump between folders, consuming more tokens and losing coherence. One analysis found modularized, collocated files “improve recall by eliminating cross-cutting jumps between directories.”

Key structural principles

  1. Collocation: Keep implementation, tests, types, and utilities for a feature together
  2. Small, focused files: Avoid large “service” or “repository” files that mix unrelated operations — they pollute context with irrelevant code
  3. Focused test files: Match tests 1:1 with source files rather than monolithic test suites
  4. Clear module boundaries: Each module should have an explicit public interface (barrel exports, __init__.py, etc.)
  5. Self-contained modules: Dependencies between modules should be explicit and minimal

Functional Core, Imperative Shell (FCIS)

Separate pure business logic (deterministic functions: data in → data out, zero side effects) from I/O operations (database, network, filesystem). The “shell” orchestrates side effects around the pure “core.”

Why this matters for AI:

  • Pure functions map directly to LLM input-output reasoning — agents generate reliable tests without complex mocking frameworks
  • Side-effect-free code is safe for autonomous modification — no risk of accidental database mutations or network calls during agent execution
  • Sub-agents can operate exclusively within the functional core with minimal blast radius
  • When business logic is coupled with side effects, AI frequently hallucinates mocking frameworks or generates brittle, untestable code

Dependency hygiene

Circular dependencies (A → B → A) are catastrophic for AI reasoning. Transformers process information sequentially through attention — cyclical logic confuses the reasoning engine, causing hallucinated patches that deepen the tangle. One modified shared utility can cascade across dozens of files the agent doesn’t know about.

  • Extract shared types and interfaces into standalone neutral modules (Interface Segregation Principle)
  • Enforce acyclic dependencies with tooling (eslint-plugin-import, madge, deptry, Go’s built-in cycle detection)
  • Keep module boundaries explicit — each module has a clear public API
  • Consider code intelligence tools that build AST-based dependency graphs (see Section 3) so agents can query blast radius before modifying shared code

Monorepo vs polyrepo

Monorepos give AI agents a major advantage: cross-project context, pattern consistency, atomic multi-project changes, and no context loss at repository boundaries. Nx reports ~30% productivity improvement on cross-project work with agents.

However, monorepos introduce complexity. The meta-repo pattern offers a middle ground: a dedicated repo serving as the AI agent’s knowledge base for navigating a multi-repo codebase, containing:

  • AGENTS.md with repository map and conventions
  • repos.yaml with machine-readable repo definitions
  • structure/ for dependency graphs
  • conventions/ for cross-repo standards
  • workflows/ for step-by-step multi-repo operations
  • active-work/ for current multi-session epics

Using this pattern, one case study demonstrated an 8-merge-request fix across 6 repositories over 5 sessions without context loss.

Domain-driven layers

For larger projects, DDD layers (/domain, /application, /infrastructure) give agents predictable navigation: business rules in domain (no cloud dependencies), integrations in infrastructure. Agents can modify and test business logic independently.

3. Context Management

The core constraint

LLM performance degrades as context fills. The “40% rule” suggests quality drops noticeably past 40% context utilization. Everything in the repo structure should work to minimize how much context an agent needs to load for any given task.

Strategies

File-level discipline:

  • Keep files small and focused — under 300-400 lines is a good target
  • One concept/feature per file
  • Clear naming that describes contents without needing to read the file
  • Type exports and barrel files so agents don’t need to read implementation to understand interfaces
  • Whitespace, deep indentation, and formatting are parsed as distinct tokens by LLM tokenizers — keep formatting clean but avoid excessive nesting that burns tokens without aiding AI comprehension

Instruction-level discipline:

  • Use progressive disclosure: tell the agent how to find information, not all the information
  • Scope rules to file types using glob patterns (Cursor .mdc frontmatter, Copilot applyTo field)
  • Put critical rules early in instruction files (“lost in the middle” problem)
  • Customize compaction behavior: “When compacting, always preserve the full list of modified files and any test commands”

Session-level discipline:

  • Clear context between unrelated tasks (/clear in Claude Code)
  • Use subagents for investigation — they explore in separate context windows and report summaries
  • Scope investigations narrowly: “look at src/auth/” not “investigate the codebase”
  • After 2-3 failed corrections, start fresh rather than accumulating failed context

Architecture-level discipline:

  • Sub-agent architectures: specialized agents handle focused tasks with clean context, returning condensed summaries (1,000-2,000 tokens)
  • Claude Code Skills run in their own context window and can be parallelized
  • Context persistence through structured memory files (TODO.md, DECISIONS.log) rather than relying on conversation history

Tools for context packing and code intelligence

  • Repomix (20.9k GitHub stars): Packs codebase into AI-friendly single files with token counting and Tree-sitter compression. Has MCP server integration.
  • repo-map / llm-codemap: AST-based dependency graphs that give agents structural understanding of call chains, inheritance hierarchies, and cross-file relationships — a shift from “context packing” (blindly appending text) to “graph querying” (targeted structural lookups)
  • AI Distiller: AST-powered compression (90-98% reduction) via Tree-sitter — strips method implementations and internal variables, keeps public API signatures, types, and critical docstrings
  • gitingest / repo2txt: Bundle codebase excerpts for feeding to AI
  • Nx Polygraph: Connects multiple repos into a federated meta-repo for agent context
  • .aidignore: Like .gitignore for AI context — explicitly exclude generated code, vendor directories, build artifacts from agent analysis. Complementary to .repomixignore (Repomix’s own ignore file)

4. Documentation-as-Code for AI

What helps AI understand code

Type annotations are critical. Explicit types serve as machine-readable documentation. Agents parse function signatures, parameter types, and return types to understand intent without reading implementation. TypeScript strict mode, Python type hints for all functions, explicit interfaces over type aliases.

Naming conventions matter more than you think. When a codebase follows consistent naming patterns, AI becomes a “force multiplier.” When it doesn’t, AI becomes a “chaos amplifier.” Establish and document naming conventions explicitly, especially counterintuitive ones.

One real code snippet beats three paragraphs. In instruction files, demonstrate patterns with actual project code rather than prose descriptions.

Architecture Decision Records (ADRs):

  • Capture the why behind architectural choices — agents can discover what code does but not why decisions were made
  • New standard: AgDR (Agent Decision Records) extends ADR for AI-assisted development
  • ADRs become “executable intentions” for AI assistants — the agent reads the ADR and implements consistently with the recorded decision
  • AI can help generate ADRs from codebase analysis, but human review is essential
  • For machine readability, use explicit section tags in ADRs (<decision>, <context>, <consequences>) — lets LLMs parse decision boundaries reliably instead of guessing from prose structure
  • Embed capability manifests and authorization constraints in tabular format within ADRs — transforms passive records into active governance that agents can query

Inline documentation strategy:

  • JSDoc/docstrings on public interfaces: parameters, return types, edge cases, side effects
  • Comments for the “why”, not the “what” — AI reads code for what it does, comments for why
  • Gold standard file: one exemplar file that demonstrates all conventions applied together, functioning as an end-to-end test for AI style compliance
  • 64% of developers now use AI for documentation generation (Google DORA 2025)

What to make explicit:

  • Error handling patterns (how the project handles failures)
  • Non-obvious conventions (e.g., “all client API methods never throw — always return ApiResult”)
  • Domain terminology and jargon
  • Framework-specific idioms that differ from defaults

Machine-readable documentation formats

Standard README.md optimized for human consumption (badges, narrative tutorials) is inefficient for models. Emerging formats provide structured, token-efficient alternatives:

  • llms.txt: Sits at project root (inspired by robots.txt). Provides condensed representation of purpose, public APIs, and interaction rules. Increasingly adopted by documentation sites and library authors.
  • ReadMe.LLM: Acts like a header file — details how the model should use the library, what architectural patterns to respect, what dependencies are available in the execution environment.

Novel frameworks and internal libraries suffer from “The Great Ossification” — AI models default to popular, heavily-represented technologies from training data. If your project uses something niche or proprietary, explicit LLM-friendly documentation is essential for agents to use it correctly rather than hallucinating based on similar-but-wrong training data.

Practical tips for AI-readable docs:

  • Numbered code snippets let models reference explicit line numbers rather than guessing file locations
  • Avoid complex JSON in documentation examples — custom plain-text delimiters ([[code]]...[[/code]]) prevent quote escaping and line break issues during generation
  • Explicitly state operational rationale for constants (e.g., # Three retries balances reliability vs speed; most intermittent failures resolve by the second retry rather than just MAX_RETRIES = 3)

5. Testing and Guardrails

The verification principle

“Include tests, screenshots, or expected outputs so Claude can check itself. This is the single highest-leverage thing you can do.” — Anthropic best practices

AI performs dramatically better when it can verify its own work. Without verification, you become the only feedback loop.

Multi-layer validation stack

Layer 1 — Pre-commit hooks (deterministic, blocking):

Pre-commit hooks “aren’t about catching human mistakes anymore. They’re about keeping AI focused.” The agent gets the failure, adjusts, and tries again — no human intervention needed.

Layer 2 — Claude Code hooks (deterministic, lifecycle-attached): Unlike CLAUDE.md instructions (advisory), hooks guarantee execution. Key events:

  • PostToolUse: auto-format/lint after every file edit
  • PreToolUse: block writes to protected directories (migrations, generated code)
  • Stop: run final validation when agent finishes

Layer 3 — CI/CD pipeline:

  • Full test suite on PR creation
  • Security scanning (AI code shows ~50% vulnerability rate vs 15-20% human)
  • Architecture consistency checks
  • Performance profiling on critical paths

Layer 4 — Multi-agent review:

  • Writer/Reviewer pattern: one session writes, a fresh session reviews (no bias toward own code)
  • Adversarial review: second model or session critiques output
  • AI review first (style, common bugs, docs gaps) then human review (architecture, business logic, edge cases) — the “review sandwich” reduces human review time 30-50%

Hook and review tooling

  • Pre-commit framework: Multi-language hook management (Ruff, ESLint, Prettier, Mypy, tsc)
  • Husky: JS/TS hook management
  • CodeRabbit: AI code review with security scanning and architecture checks
  • Ellipsis: PR-level analysis with conversational context

Semantic linting for AI output

Traditional text-based linters miss structural anti-patterns common in AI-generated code. AST-based tools match code structure rather than text:

  • AST Grep: Lint rules that match structural intent (e.g., catch incorrect API usage regardless of variable naming). Catches semantic hallucinations that regex-based linters miss.
  • unparam (Go via golangci-lint): Detects function parameters consistently called with identical values — a common LLM anti-pattern of over-abstracting into generic functions
  • Security scanners (gosec, Snyk, Aikido, SonarQube): Critical given AI code’s ~50% vulnerability rate. Feed scanner output back to the agent via MCP or CI for automated self-correction loops.

The goal is a self-correcting pipeline: agent generates code → semantic linters + security scanners run automatically → failures feed back to the agent → agent iterates until standards are met.

Industry-validated mitigation stack

  1. Formal verification gates: Compiler passes, test suites, type checks, linting — things that can’t be faked
  2. Adversarial review models: Second AI session or different model critiques output
  3. Hierarchical agents: Separate planner, worker, and reviewer agents
  4. Low-stakes prioritization: AI for boilerplate, tests, docs, migrations. Humans for critical business logic.
  5. Spec-driven development: Specifications before implementation; specs as source of truth
  6. Knowledge transfer rituals: Require authors to explain AI-generated code in PRs/docs

6. Workflow Patterns

The four-phase pattern

  1. Explore (Plan Mode): Agent reads files and answers questions without changes
  2. Plan: Agent creates detailed implementation plan, human edits before proceeding
  3. Implement: Agent codes against the plan, running tests iteratively
  4. Commit/PR: Agent commits with descriptive message, creates PR

Skip planning for small, clear-scope tasks. Planning is most valuable when uncertain about approach, modifying multiple files, or unfamiliar with the code.

Task decomposition

  • Generate ultra-small tasks (1-2 hours, 4-8 hours max) with clear acceptance criteria
  • Atomic decomposition: no shared state between tasks enables parallel agent execution
  • Spec-driven development: write specs before AI implementation; specs become source of truth
  • Prompt plans: structured files containing sequential prompts for systematic execution

Branch and collaboration strategy

The trust gradient:

  1. Agent suggests changes, human applies manually
  2. Agent makes changes on branches, human reviews PRs
  3. Agent merges low-risk changes autonomously

Adjust based on track record and blast radius. Start conservative.

Parallel sessions:

  • Git worktrees for isolated parallel AI sessions on separate features
  • Writer/Reviewer split: one session implements, another reviews
  • Test-first split: one session writes tests, another writes implementation
  • Non-interactive mode (claude -p) for CI, scripts, and batch migrations

Commit discipline:

  • Ultra-frequent commits as “save points” for rollback
  • Never commit code you can’t explain
  • State checkpointing constantly to Git as an undo mechanism

The spec-first workflow

  1. AI conducts structured interview surfacing requirements, constraints, edge cases
  2. Collaboratively develop spec.md with architecture, data models, testing strategy
  3. Start fresh session for implementation (clean context focused on execution)
  4. Written spec serves as reference throughout

Agent bootstrapping

Autonomous agents can’t ask colleagues or manually troubleshoot setup. The repo needs a deterministic initialization sequence — an “agent bootloader” documented in CLAUDE.md or AGENTS.md:

  1. Sync: Exact git commands to get latest state
  2. Secrets: Secure injection of env vars and API keys (never hardcoded in prompts)
  3. Dependencies: Deterministic install (npm ci, poetry install, lock files enforced)
  4. Verify environment: Lint and test commands the agent runs to validate its own workspace before starting work

Without this, autonomous workflows are fragile — agents silently work against stale code, missing dependencies, or broken environments. The gap between “works on my machine” and “works in the agent’s session” is where autonomous execution fails.

7. Anti-Patterns

Repository anti-patterns

  • Horizontal slicing: Scattering features across controllers/services/models directories forces excessive context loading
  • Monolithic files: Large service/repository files pollute context with unrelated code
  • Monolithic test suites: Bundling tests forces agents to load irrelevant test context
  • Implicit conventions: Engineers absorb patterns tacitly; agents need explicit documentation
  • Stale structural references: Outdated directory maps in instruction files actively mislead agents

Instruction file anti-patterns

  • Auto-generating instruction files: LLM-generated rules reduced task success 0.5-2%, increased costs 20-23%. Hand-write every line.
  • Rule accumulation without pruning: Creates contradictions and bloat. Review and prune regularly.
  • Over-specification: If Claude already does it correctly without the instruction, delete it
  • Broad behavioral hotfixes: Vague instructions like “write better code” are useless
  • Architecture in instruction files: Agents discover architecture independently; documenting it wastes tokens and becomes stale

Workflow anti-patterns

  • Kitchen sink sessions: Mixing unrelated tasks in one session pollutes context
  • Correction spirals: After 2 failed corrections, start fresh — don’t accumulate failed approaches
  • Infinite exploration: Unscoped “investigate” prompts cause agents to read hundreds of files
  • Single-prompt architecture: Generating entire systems in one request eliminates iteration
  • Iterative AI debugging loops: “AI writes buggy code, AI fixes it, introduces new bugs” creates layers of uncomprehended fixes
  • Blind generation: “Create a complete system” produces over-engineered, untested code
  • Premature automation: Automating before understanding the problem space
  • Trust-then-verify gap: Accepting plausible-looking output without verification

Enterprise anti-patterns

  • Comprehension debt: Code that is more sophisticated than the team could independently create or maintain, creating fragility and AI dependency (see ai-code-latent-failure-modes for the full taxonomy)
  • Haunted codebases: Iterative drift where “the codebase slowly becomes something no one (human or AI) fully understands”
  • AI-only implementation, human-only testing: Developers get boring work; tests miss edge cases discovered during implementation
  • No audit trails: Missing prompt history, context, iteration records for AI-generated code
  • Skill atrophy: No tracking of what happens to team expertise over 2-3 years of AI delegation
