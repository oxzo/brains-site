Context Engineering for Claude 5-Generation Models

What it is

Anthropic’s July 24, 2026 statement that most prior context-engineering practice was scaffolding for weaker models, and can now be deleted. The headline, quoted exactly from the post:

We removed over 80% of Claude Code’s system prompt for models like Claude Opus 5 and Claude Fable 5 with no measurable loss on our coding evaluations.

Six named then→now reversals, plus a four-layer model for where context should live. Author: Thariq Shihipar, member of technical staff at Anthropic.

This is the prompt-layer instance of the thesis in harness-design-load-bearing — every component encodes an assumption about what the model can’t do. That note studied agent topology and found scaffolding relocating; this post studies a system prompt and reports it shrinking. The two are compatible observations at different layers rather than a disagreement — see Relation to “harness moves, not shrinks”.

Why it matters

Several notes in this vault codified 2026-Q1/Q2 prompting practice as durable principle. This post dates that practice and, in two places, reverses it. The reconciliation is recorded in What this supersedes in the vault so the corrections stay traceable to a source rather than becoming quiet drift.

The practical consequence for the seat: the default move on a misbehaving prompt has inverted. It was add a rule. It is now delete a rule and check whether the model already had the judgement.

Details

The six reversals

ThenNowWhat actually changed
Give Claude rulesLet Claude use judgementGuardrails written for worst-case avoidance were wrong for a subset of prompts; newer models handle the call unaided
Give Claude examplesDesign interfacesTool-usage examples constrain the exploration space; expressive parameters do the same work without the ceiling
Put it all upfrontProgressive disclosureVerification and code review moved out of the system prompt into selectively-invoked skills
Repeat yourselfSimple tool descriptionsInstructions live in the tool description, not duplicated in the system prompt
Memory in CLAUDE.md (# hotkey)Auto-memoryClaude saves relevant memories itself
Simple specsRich referencesHTML artifacts, test suites, a function in another codebase, rubrics — all valid specs

The rules→judgement row carries the post’s own worked example. The retired instruction was:

In code: default to writing no comments. Never write multi-paragraph docstrings or multi-line comment blocks — one short line max. Don’t create planning, decision, or analysis documents unless the user asks for them — work from conversation context, not intermediate files.

Its replacement is a single sentence: “Write code that reads like the surrounding code: match its comment density, naming, and idiom.” The post is explicit that the old version was a knowingly-accepted tradeoff — without it, “the comments Claude wrote would be incorrect in many cases” on older models.

Two rows deserve scope care:

  • Examples. The claim is about tool-usage examples constraining exploration. The post does not address output-format examples, and does not claim examples are bad in general. The Todo tool is the given counter-design: a pending | in_progress | completed enum plus a one-item-in-progress instruction communicates the usage pattern through the interface instead of through demonstrations.
  • Progressive disclosure. Applies to tools as well as skills. Deferred-loading tools require the agent to fetch full definitions via ToolSearch before use, so a large tool surface costs nothing until needed. Directly observable in this harness — the Task, Cron, and MCP tools load this way.

Where context should live

The post’s layer assignment, which no single existing vault note owns:

LayerAssignment
System promptProduct context — what product Claude is operating in and what it’s doing. Claude Code users will “likely never modify this”; harness builders should spend most of their effort here
CLAUDE.mdLightweight. A brief statement of what the repo is for, then most of the tokens on gotchas. Explicitly avoid “the obvious” — anything Claude can learn by reading the file system. Push detailed procedures into skills and reference them
SkillsLightweight guides for finding information when needed. Encode opinions and practices particular to you, your team, or your product. Avoid overconstraining “except in highly important areas.” Long skills split into many files
References@-mentioned files. Prefer code over description — “a HTML mockup of a design will generally produce better results than a description of the design or a screenshot”

Rubrics get a specific role: they let Claude verify your taste in a domain (the post’s example is what good API design looks like) by spinning up verifier agents carrying the rubric. That is the same generator/evaluator primitive harness-design-load-bearing documents, addressed at a subjective axis.

claude doctor

The post describes a command that helps simplify system prompts, skills, and CLAUDE.md files automatically. (Not verified locally — the behavior described here is the post’s claim, not an observation. claude doctor also predates this post as an install/diagnostics command, so confirm which behavior the local version has before relying on it.)

Relation to “harness moves, not shrinks”

harness-design-load-bearing quotes Anthropic’s March 24, 2026 engineering note: “the space of interesting harness combinations doesn’t shrink as models improve. Instead, it moves.” That note’s evidence was a harness that relocated — sprint decomposition became unnecessary at Opus 4.6 while the evaluator and planner stayed load-bearing.

This post reports the prompt layer shrinking by >80%. That is not a counterexample, and it is worth being explicit about why, because the surface reading (“one says moves, one says shrinks”) is wrong. The March claim is about the space of interesting harness combinations — agent topology. This post is about the token content of one agent’s system prompt. A shrinking prompt does not contradict a relocating topology; the two sources describe different layers and neither addresses the other’s.

What the two do share is the underlying mechanism, and this post refines it by showing that removed scaffolding has two distinct fates:

  • Relocated. Verification, code review, and tool instructions didn’t vanish — they moved into skills and tool descriptions, loaded on demand. This is the March note’s “moves,” observed at the prompt layer.
  • Deleted. The rules→judgement and repetition→consolidation reversals have no destination. That content is gone because the model no longer needs it.

Working synthesis: harness components relocate; harness guardrails get deleted. The March note only had occasion to observe the first, because topology components have somewhere to go. Neither source tests the other, and nothing here should be read as one Anthropic team contradicting another.

What the post does not establish

  • “No measurable loss” is scoped to Anthropic’s coding evaluations. Aggregate eval scores are the wrong instrument for detecting the failure class these guardrails were written against — the post says the original rules existed to avoid “worst case scenarios, such as deleting files,” which is tail behavior an averaged benchmark can miss. The claim is credible for typical coding work and untested for the tail.
  • Model-scoped, not universal. The reversals are asserted for Opus 5 and Fable 5. The post’s own reasoning implies the old rules remain correct for weaker models — anyone routing to Haiku or an older tier should not delete guardrails on the strength of this post.
  • Vendor guidance about its own product. Best possible source for what Anthropic did to Claude Code; weaker evidence for what you should do with a different harness, model, or domain. No independent replication documented.
  • Survivorship. The post reports the removals that held. Removals that were tried and reverted are not discussed, so the 80% is a success rate of unknown denominator.
