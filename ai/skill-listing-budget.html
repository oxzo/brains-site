The Skill Listing Budget — Why Skill Descriptions Silently Disappear

Skill-authoring guidance treats the description field as the skill’s whole trigger surface: Claude picks a skill from its description before the body is ever read (skill-quality-criteria). That holds only while the description is actually in front of the model. Past a certain catalog size, Claude Code stops showing some of them. The skill still loads and can still be called by name, but the model no longer sees what it is for.

Last verified: 2026-10-26 against the Claude Code docs (skills and settings reference) and Claude Code v2.1.310. Defaults and caps are FAST-decay.

The mechanism

Per the Claude Code skills docs:

  • Every name is listed; descriptions are budgeted. Each turn, the model sees a listing of all skill names with their descriptions. The listing “always contains every skill name, but if you have many skills, Claude Code drops some descriptions to fit the listing’s character budget.”
  • The budget is a share of the context window. The default is 1% (skillListingBudgetFraction: 0.01). It scales with the model, so the same catalog can fit for a large-context model and overflow for a smaller one. (That consequence is inferred from the scaling rule, not measured here.)
  • The least-used skills lose their descriptions first. “Claude Code drops descriptions starting with the skills you invoke least, so the skills you use most keep their full text.”
  • Each entry is capped too. Description plus when_to_use is cut at 1,536 characters regardless of the overall budget (skillListingMaxDescChars). This is separate from the 1,024-character validation limit on the description field in Anthropic’s skill best-practices.
  • The effect. The settings reference states it plainly: Claude “can still invoke those skills but is less likely to choose one on its own.”

A loop that entrenches itself (inference)

Usage decides who keeps a description, and a description is what gets a skill used. A new or rarely needed skill starts near the bottom of the usage ranking. In a crowded catalog it is listed name-only, so it rarely gets picked, so it stays at the bottom. The docs describe the ordering. The self-reinforcing loop is this note’s inference, though it follows directly. The way out is invoking the skill by name, which raises its rank. The practical result: once a catalog overflows, adding a skill won’t make it discoverable by its description on its own.

Measured in this vault (2026-10-26)

/skill-doctor (Claude Code v2.1.252+) reports each skill’s per-turn listing cost and its usage. Run non-interactively (claude -p "/skill-doctor") from the vault root:

  • The catalog: 65 vault-authored skills, carrying about 54,000 characters of description text (measured from the SKILL.md frontmatter). The report attributes 50 to the project and 15 to user-level copies of the same skills. Thirteen synced claude.ai skills and one plugin’s skills share the same listing.
  • At the default 1% budget, 33 of the vault’s project and user skills were listed name-only. That is the 26 never invoked plus the 7 invoked exactly once, consistent with the documented least-used-first ordering. They included lean-review, density-scan, readability-scan, reviewers-map, skill-output-eval, skill-trigger-eval, all six code-structure scans, and bias-scan-human.
  • At 2.5% (--settings '{"skillListingBudgetFraction":0.025}'), the same report showed 0 of them name-only.

Implication for the vault’s own audit tooling: /skill-trigger-audit and /skill-trigger-eval grade whether a description would match a query. For half the catalog, the description wasn’t in the listing at all, so live trigger behaviour was decided by the name alone. A clean trigger audit was measuring a surface the router couldn’t see.

Options, with their costs

The docs name these levers across the skills page’s “cut short” and /skill-doctor sections. Each trades something:

LeverEffectCost
Raise skillListingBudgetFraction (e.g. 0.02), or set SLASH_COMMAND_TOOL_CHAR_BUDGET to a fixed character countMore descriptions stay visibleMore context consumed every turn, by every session in that scope
Set low-priority skills to "name-only" in skillOverridesFrees budget for the restThose skills only fire when called by name, which suits user-invoked utilities
Turn unused skills off (/skills, skillOverrides: "off", removing the folder, or disabling a plugin)Shrinks the listingLoses the capability; plugin skills can’t be turned off individually (per /skill-doctor’s own output), only the whole plugin
Trim descriptions at the source, putting “the key use case first”Each entry costs less, and survives any cut at the 1,536 capRouting clauses (“distinct from X”) are usually the first thing trimmed, and they’re what prevents overlapping triggers

Which one is right depends on whether the catalog is a toolbox you mostly call by name (name-only and pruning) or a router you expect to choose for you (raise the budget). This vault is a skill lab whose skills are meant to fire unprompted, so it took the budget lever: "skillListingBudgetFraction": 0.025 in the project’s .claude/settings.json, verified by the rerun above. A side effect: the setting applies only inside this vault. A skill exported to another repo competes for that repo’s budget, often the default.

Consequences for writing skills meant to travel

  • Put the trigger first. If the listing is ever cut, the first clause is what survives. That’s the docs’ “key use case first” advice, and it’s the opposite of descriptions that open with a long account of the method.
  • The name is the last thing left. A skill that may be listed name-only in someone else’s catalog should have a name that states its job (lean-review) rather than a coined term.
  • Check the target catalog, not just the description. Before concluding a skill “doesn’t trigger”, run /skill-doctor in the session where it failed and check whether its description was shown at all.
