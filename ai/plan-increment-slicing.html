Plan-Increment Slicing — Vertical vs Horizontal

The plan-split-scan and /task-decompose answer how many pieces a plan has and whether each is well-sized. This note answers an orthogonal question they both lean on: which way the plan is sliced. A plan can pass every size and granularity signal — right concern count, shallow state-carry, no unresolved branch — and still be sliced wrong, because slicing is a different axis from size.

The distinction is old and well-established in software practice; what this note does is pin the rationale (why horizontal slicing defers risk), the carve-out (when horizontal is legitimate), and the detection tell in one place, so the two skills reference a single source rather than two copies that drift apart — /plan-split-scan carries the full check, /task-decompose a compressed restatement.

The two slicing directions

  • Horizontal slice (the failure mode): steps cut by architectural layer — all the schema, then all the API, then all the UI. Each step is individually well-scoped, but no step is independently demoable or verifiable end-to-end. The early steps are worthless until a later layer lands, and the first time the whole thing is exercised together is at the end — exactly when the accumulated integration risk is most expensive to discover and unwind.

  • Vertical slice (the target): each step is a thin end-to-end increment — a tracer bullet through every layer it touches — that can be demoed and verified on its own before the next is built. Risk surfaces early; each increment composes onto a working whole; a failed assumption is caught after one slice, not after the entire build.

The core asymmetry is about when integration risk is paid. Horizontal slicing front-loads the comfortable work (each layer in isolation) and back-loads the dangerous work (does it all actually fit together?). Vertical slicing inverts that: each increment forces an integration through the full stack immediately, so the riskiest unknowns are discovered while they are still cheap to fix — the seams between layers, the contract mismatches, the “the API doesn’t return what the UI needs” surprises.

Why this is a distinct axis from size

Size signals (concern count, state-carry depth, decision branches, verification seams, reversibility boundary) measure granularity — are the pieces the right size, in the right number? Slicing measures cut direction — are the pieces oriented along the layers or across them? The two are independent: a six-step plan with one clean concern per step and no unresolved branches passes every size signal and can still be a pure horizontal stack that defers all integration to the end.

This is why the check runs as a single orthogonal question, not as another size signal. It does not feed the concern-count math. It asks: is this cut vertically or horizontally, and if horizontal, is a vertical recut available?

The carve-out — some work is legitimately horizontal

Not every horizontal slice is a failure. The exception is a one-time foundational layer that genuinely has no thinner vertical expression:

  • a schema migration that must land whole before anything can read or write through it;
  • a shared library or framework that every later vertical slice consumes;
  • an irreducible infrastructure prerequisite with no demoable partial state.

These are not horizontal-slicing failures — they are irreducible foundations, and forcing a fake vertical recut onto them adds ceremony without surfacing risk earlier. The discriminating test: is a vertical recut actually available that would surface integration risk sooner? Flag horizontal slicing only when the answer is yes. When the layer is a genuine prerequisite consumed by everything downstream, leave it horizontal and spike it first (a quick exploratory probe) so its risk is still paid early, per the discipline of doing the riskiest work first.

Detection — the tell and the recut

The tell. The fastest diagnostic is the done-criterion test: look at what each step’s “done” looks like. If a step’s only honest done-state is “the code exists” — rather than “a user or a test can exercise this end-to-end” — that step is a horizontal layer with no observable value of its own. A vertical increment always has a behavioral done-state; a horizontal layer often cannot state one without referencing a later layer.

The recut. When horizontal slicing fires and a vertical recut is available, the corrective is to recut by capability, not by layer:

instead of (all schema → all API → all UI), slice as (one capability end-to-end → next capability end-to-end).

This recut frequently reduces total step count by collapsing parallel layer-steps into one vertical increment, so it composes with the over-decomposition direction rather than fighting it — recutting vertically can make a plan both better-sliced and smaller.

How the two skills use this

  • /plan-split-scan runs the slicing-axis check as an independent pass alongside its five size signals, and reports the result as its own output line (vertical / horizontal-but-carved-out / recut recommended). Severity is medium by default — the plan executes but defers integration risk and yields nothing demoable mid-flight. It escalates to high when a horizontal slice also places speculative work before a destructive step, because the deferred integration now compounds the reversibility-boundary signal.

  • /task-decompose applies the same principle at task-creation time: it decomposes into vertical slices from the start, uses the done-criterion test as the tell, and applies the same carve-out for irreducible foundational layers (spiked first). Where plan-split-scan audits an existing plan’s slicing, task-decompose produces a vertically-sliced list so the audit has less to catch.

Tradeoffs and limits

  • Not every plan has a meaningful slice direction. Pure research, exploratory analysis, and creative work often have no “layers” to cut across — the vertical/horizontal frame is load-bearing for build-shaped work (features, migrations, integrations) and weakens where the plan has no stack to slice through.
  • Vertical slices can carry setup overhead. A thin end-to-end increment may re-touch every layer, which costs more boilerplate per slice than batching a layer at once. The trade is deliberate: more per-slice setup in exchange for early, repeated integration. For genuinely trivial integrations where nothing can surprise, the horizontal batch may be cheaper — but that judgment should be explicit, not the default.
  • The carve-out can be abused. “This layer is foundational” is an easy rationalization for a horizontal cut that does have a vertical expression. The discipline is the availability test: a foundation is irreducible only when no thinner vertical slice exists, not when a vertical slice would merely be inconvenient.

Counterargument

The strongest objection: vertical slicing is folklore dressed as principle. “Tracer bullets” and “walking skeletons” are evocative metaphors, and for many small plans the layer-batched approach is obviously fine — the integration risk it “defers” is negligible because the layers are trivially compatible. Importing the vertical-slicing imperative wholesale risks ceremony: forcing thin end-to-end increments onto work where the seams were never in doubt.

The honest position: the slicing check earns its place precisely when integration risk is non-trivial and currently invisible — build-both-sides shapes, novel integrations, plans where “does it fit together?” is a real open question. There, deferring integration to the end is the expensive mistake, and the vertical recut is cheap insurance. Where the seams are known-safe (a CRUD form over a settled schema), the carve-out and the “is a recut actually available / worth it?” test should let the horizontal cut stand. The check is a prompt to ask the question, not a mandate to always recut.

Sources

Verified 2026-06-08 against widely-established software-practice literature; specific attributions below.

  • Hunt, A. & Thomas, D. (1999). The Pragmatic Programmer. Origin of “tracer bullets” / tracer code — building a thin end-to-end path through all layers first, then fleshing it out.
  • Cockburn, A. — “walking skeleton”: a tiny end-to-end implementation that exercises the full architecture before features are built. Also the “Elephant Carpaccio” exercise for slicing features into very thin vertical increments.
  • Freeman, S. & Pryce, N. (2009). Growing Object-Oriented Software, Guided by Tests. Popularized the walking-skeleton-first approach — write the first end-to-end test through a deployed thin slice before building outward.
  • The vertical-vs-horizontal user-story framing is standard agile story-slicing practice (e.g., the INVEST criteria for stories and the broad “slice the story vertically” guidance); no single canonical citation.
