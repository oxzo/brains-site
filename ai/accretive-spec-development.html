Accretive Spec Development

A development loop for one person and one AI coding agent in which the spec is a byproduct of building, not a prerequisite. You state an intent and what would prove it false, the agent builds the smallest thing that could falsify it, you react to the running artifact, and the agent harvests spec clauses from what survived — each clause pinned to a check that can fail. The spec grows by accretion, one verified clause per loop, and is periodically rewritten into a readable document.

What it tries to accomplish

Spec-first methods (Spec Kit, Kiro, OpenSpec and similar spec-driven development tooling) write requirements, plan, and tasks before code. That buys agreement before building, at the cost of momentum during exploration and of documents that lag the implementation. Building with no spec at all is fast but has no defence against the agent quietly solving a slightly different problem than the one you asked for.

The accretive loop sits between the two. It aims to:

  • Keep exploration fast. Minutes per loop, reacting to running code rather than to a document. No task list — the next probe is the task.
  • End with a spec you can trust. Every clause in the spec is an executable claim with a check that has been shown to fail when the behaviour is broken. A clause without a check is not a clause.
  • Keep the human’s intent as the anchor, not the agent’s reading of it. The agent writes the probe, the check, and the proposed clause, so left alone the check would only ever encode the agent’s own interpretation. Three independence rules put a human-owned falsifier ahead of the agent’s work, lock accepted checks, and demand a mutant rejection with a named failure before a clause is accepted; their normative form is rules 1 to 3 of clause-loop.
  • Separate what was observed from what is wanted. Harvest records what the artifact does. Promotion to spec is a separate human act, so accidental behaviour — especially in brownfield code — never becomes contract by default.
  • Know when to stop looping and plan. Hard gates stop irreversible work for permission, and planning heuristics send unstable work into a conventional plan before the expensive probe, not after five failed ones.
  • Earn a contract. A region of the spec whose clauses are all wanted and currently verified can be frozen, and a frozen region is a spec-driven-development-shaped contract other agents and services build against.

The honest scope of its guarantee, stated normatively in clause-loop: once a region is frozen, a contract guard rejects missing or failing required checks and unapproved changes to the region’s declared verification surface, and it does not prove that the checks express the requirement or the intent. Spec-to-intent drift is bounded — by the human-owned falsifier, the locked checks and the per-clause evidence rule — not prevented. An earlier version of this note called spec-to-test drift “impossible”; that overstated a guard which only sees the surface it was told about.

The loop

Step 0 — Ground

Before the first intent, hand the agent a screen or less of:

  • Context — prose about the project and its situation.
  • Constraints — hard facts the agent may never violate (“Node.js only”, “no external network calls”). Each enters the spec at Ground, born there, with a check attached where one is possible; a constraint with no attachable check is written as a guarded invariant (see Two tiers) from day one. A constraint the current code already violates enters as a wanted clause with an open exception — owner, scope, expiry — in the decisions log, rather than being pretended to hold.
  • Preferences — soft leanings the agent may trade off but must say when it does. A departure is logged as an amendment.
  • Irreversibility list — what is expensive to get wrong in this project (migrations, payment paths, public contracts, data deletion). It feeds the hard gates directly.

Output is GROUND.md. Probes are validated against it before you see them. Ground is a floor, not a plan: past roughly a screen you are sneaking upfront design back in.

1 — Intent

One sentence of what you want to be true next, plus one line of what would prove it false. That falsifier is the only oracle in the loop the agent did not write — the human owns it, written from scratch or substantively revised from candidate counterexamples the agent proposes — and it anchors the probe’s check before the agent’s reading of the intent exists. No acceptance criteria beyond that.

2 — Probe

The agent builds the smallest thing that could falsify the intent: code plus a runnable check. Before building, it declares an execution envelope and reads it against the hard gates and planning heuristics (below): a hard gate stops for the human’s permission on that action, a heuristic sends the work to a plan instead of a probe. On brownfield code the first probe is “harvest what is already true”.

The agent ends every probe with a short list of what the probe does not exercise. A running artifact shows presence, never absence, so failure-mode coverage has to be explicit.

3 — Confront

Run it. Before it runs, the agent drafts what pass and fail look like from your falsifier and you amend it if you disagree (/predict-then-compare). React to the working artifact and to the not-exercised list. Say what is wrong and what is missing.

4 — Harvest

The agent proposes one to three clauses capturing what you accepted or rejected. Each clause carries:

  • an oracle type — one of the seven clause-loop defines: test, property, guard, consistency, reader, walk or manual;
  • a pin — a stable id, its check id and the change it was born in;
  • a demonstration that the check rejects a deliberate mutant for a named reason — a one-line sabotage of the implementation that fails at the assertion the clause names, not a crash. A check that cannot fail is not a check, and one that fails for an unrelated reason proves nothing.

Clauses arrive in the observed state. You promote a clause to wanted only when you affirm it deserves to exist, not merely that its test passes. Observed clauses must be ruled on before the change closes; Close refuses while one is unruled. Rejecting one is three decisions on one DECISIONS.log line — not contract; whether the behaviour stays in the artifact; whether the check stays as characterization coverage — because “not promised” is not “not worth testing”.

Prune — this note’s name for what clause-loop reports as verification failing — lives inside Harvest: a clause whose check no longer passes is a stop. It stays wanted; a failing check is not a change of mind.

Once a clause is wanted, its check is locked: the agent may change the code but not that check inside the loop. Editing a locked check is a decision the human makes, and once the region is frozen it is recorded through an approval boundary the agent cannot write to. The normative form of this step is clause-loop rules 3 and 6.

5 — Freeze

A region is proposed for freezing when every clause in it is wanted and currently verified — not when it has merely gone untouched, and not on the strength of one recent probe that exercised a corner of it. Freeze and unfreeze are both decisions-log entries. Frozen means something in CI: a manifest written from the region’s pins names its clauses, checks and verification surface, and a contract guard fails the build on an unapproved change to that surface or on a required check that did not run and pass. The mechanism is defined in clause-loop. A frozen region is also exported as a contract test consumers run on their side; that export is what makes “other agents build against it” a mechanism rather than a sentence.

6 — Consolidate

Every ten or so archives, or at every freeze, the agent rewrites the region’s spec by domain structure: merges overlapping clauses, orders by concept rather than by birth iteration, keeps every pin, re-points any pin the rewrite breaks, and runs a clause-versus-clause conflict scan — two clauses whose checks exercise disjoint inputs can both pass while contradicting each other at intent level, and no per-check test can see that. The harvest order is a changelog; the consolidated form is the spec. Without this step the artifact converges on a test index with prose labels.

Clause states

A clause has two axes, defined normatively in clause-loop: acceptance — observed, wanted, retired — which is the human’s and changes rarely, and verification — passing, failing, stale, unknown — which is the run’s and is never hand-edited. A Ground constraint the current code violates is a wanted clause with an open, expiring exception rather than a state of its own. Only wanted clauses can freeze. Brownfield harvest therefore produces a visibly provisional characterization layer, not a contract.

Two tiers of spec

Tier one is executable clauses — the ones the contract guard covers once their region is frozen.

Tier two is guarded invariants: requirements you cannot cheaply attach a check to — negative (“never sends PII outbound”), cross-cutting (“degrades gracefully offline”), non-functional (“migration is reversible”). Each has a named manual check, an owner, and a review cadence. They live in the region’s spec file, labelled as tier two, and count as spec. They just do not get the drift guarantee; they get a scheduled re-check instead. Without this tier the executable-only rule would push the most important requirements out of the spec entirely.

Escalation gates

Planning is an escalation the loop expects to make. A cap of about five loops per intent is the backstop. The gates are defined normatively in clause-loop rule 4; they read an execution envelope the probe declares before building, and they are of two kinds:

  • Hard gates stop for the human’s permission on that specific action, whichever path the work is on: a write to production or a shared environment, a destructive operation, a credential, an externally visible action, anything on the Ground irreversibility list, an edit to a frozen region’s verification surface. Destructive work is never wrapped in a loop’s conditional.
  • Planning heuristics send the work to a plan instead of a probe, and are judged rather than computed: uncertainty the agent names about the approach; rework — the same region harvested and rejected twice, which is the intent being unstable, not the code, and which is where splitting an intent to dodge the cap shows up; growth — a probe whose budget exceeds the last three building loops combined, a design question wearing a probe’s clothes; cross-domain coordination — an intent spanning two or more regions with at least one under contract; a contract change — an intent that would modify or retire a wanted clause in a region under contract.

What the probe actually touched is compared to the envelope at every loop, because a rule that reads only the agent’s declared plan cannot see undeclared work.

Escalation has a defined target: a plan artifact in spec-driven-development shape (a Spec Kit plan, an OpenSpec change folder, or equivalent) that the next probes execute against. The loop escalates into that pipeline deliberately, because it is the right tool once the work is known to be expensive.

Command set

Four public actions — Start, Probe, Decide, Close — with eleven operations underneath — ground, intent, probe, confront, harvest, propose, archive, freeze, consolidate, explore, converge. Escalation is not an action; it is the gate check inside Probe. The runnable form — the actions, the operations, both paths, the folder layout, reader and walk oracles for non-code work, and a copyable starter kit — is clause-loop, and it is normative where this note and it differ.

When to use it

  • Good fit: one person, one agent, one repo; reversible work; exploratory or brownfield code where you learn what you want by seeing it run. It is the concrete instance of the verify-and-iterate unit of work in coding-with-agentic-loops, inside the agent-workflow-solo-practitioner niche.
  • What it is: an exploration-to-contract mode. Run the loop until a region freezes; a frozen region is a spec-driven-development-shaped contract, and change to it should go through a proposal-first process, which is the “agreement before building” guarantee the loop gives up everywhere else.
  • Relation to spec-driven development: not a replacement. The difference is direction of derivation (harvest from artifacts versus derive from requirements) and granularity (a clause per loop versus a document per phase). As of 2026-09, the mainstream tools also run evolving specs with executable checks, so executability and brownfield support are not what set this apart. How the two run as one system — which affirmation of a clause gates the build, the region transitions, and the mapping of these artifacts onto a Spec Kit or OpenSpec layout — is in spec-driven-development-operating-model.
  • Relation to intent engineering: the consolidated region spec is the durable, CI-enforceable contract layer intent-engineering-discipline argues for. This loop is one way to earn that artifact instead of drafting it.
  • Weak fit: multi-team contracts before anything has frozen; regulated audit trails (the log is the agent’s record of an approval; the approval itself lives at whatever boundary the repo host provides, and neither is a formal audit trail); any project where the first probe is itself the expensive part; handoff between sessions or parallel agents, where “no task list” stops holding and a plan file becomes the thread.

Beyond code: architecture and decisions

The loop transfers to design and decision work; the free re-running oracle does not. In code the check is a test. In architecture it is a spike, a fitness function, or a scenario walk, and only the first two re-run for free.

StepIn codeIn architecture design
Intent”X should be true next”, plus a falsifierA quality-attribute scenario — stimulus, response, measure: “under 10× load, checkout p95 stays under 300 ms”
ProbeSmallest code plus a checkA throwaway that could falsify it: walking skeleton, load or failure simulation, cost model, or a paper walk of the scenario through the candidate design. The probe is reversible even when the decision is not
ConfrontRun it, reactRun the spike where one exists; otherwise walk the scenario adversarially (second-order, red-team)
HarvestClause pinned to a testA constraint or invariant pinned to a fitness function where possible (“no imports from domain into infra”, a latency budget in CI) and to a dated scenario walk where not
PruneCheck fails, clause reported failingA fitness function fails, or a change touches a scenario’s assumptions and the walk is re-run by hand
FreezeFrozen region, contract guardAn accepted ADR. Unfreeze is a superseding ADR

Structure scans such as dependency-flow-scan, deepen-architecture and structural-trace serve as fitness functions here, so a harvested architecture clause can be pinned to one of them the way a code clause is pinned to a test. The same generalisation carried to documents and specifications — a reader oracle, where a fresh context is given the artifact alone and must complete a task from it — is defined in clause-loop.

For ADRs specifically (architecture-decision-records-ai): write the record after the probe, not before; carry the falsifier from Intent into the ADR as a pre-registered reversal criterion (“supersede this if the scenario fails at N users”); map ADR status onto clause state (proposed is observed, accepted is wanted, superseded is retired); and write the expected spike outcome before running it so the record does not become hindsight narrative.

Where it degrades: if the smallest falsifier of an intent is “build it in production”, the loop does not apply and the work is plan-first. Quality attributes are mostly tier-two guarded invariants, so “drift is bounded” shrinks to “drift is scheduled for re-check”. Decisions with no artifact at all (team topology, build-versus-buy) have no spike; there the loop collapses to intent, adversarial walk, and an ADR with a reversal criterion — a pre-registered decision journal, not accretive spec development.
