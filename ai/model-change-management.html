Model Change Management for LLM Features and Coding Agents

Vendor policy figures below were read at source on 2026-11-01. These pages change without notice, so re-read them before you rely on a number.

What it is

This note covers the work of moving a piece of software from one hosted model to another while it keeps doing its job. The software might be a user-facing LLM feature, a coding-agent harness or an LLM judge inside a pipeline. The work has three parts: tracking when the current model will stop being served, estimating what the swap breaks, and gating the swap on evidence rather than on the new model’s benchmark scores.

Model change is not optional for a team that uses hosted models. (The exits are self-hosting open-weight models, which has no forced retirement but carries its own operating cost, or a private arrangement with the platform; Bedrock mentions one for continued access.) Every major provider retires models on a published schedule. Some platforms also change the model or the serving stack behind a stable name. So the real question is how often a swap happens, how much notice you get and what a swap costs.

Why it matters

  • Swaps are forced and recur. Where a duration is stated, it is 12 to 18 months (Azure 18, or 12 for some partner models and 6 for Grok 4.7+; Google 12). Anthropic and Bedrock give per-model dates, and OpenAI states none. Recent Anthropic retirements came with about two months’ notice (details below). A product that runs on one pinned model should expect a forced migration roughly every 12 to 18 months for each model, sooner if it adopts a model late in its life (inference).
  • A swap is more than changing a model ID. Prompts, harness wiring, API parameters, judges and fine-tunes all carry tuning for one model. The measured studies below show that each of these can regress when the model changes, sometimes while the aggregate score improves.
  • A stable name does not mean stable behaviour. Aliases move to new snapshots. Some platforms upgrade deployments automatically. One vendor documents that serving infrastructure can change behaviour under a fixed model ID.
  • The cost term is unmeasured. No source found for this note reports engineer-hours or money spent per migration at any organisation. Planning numbers for migration effort are guesses until someone publishes one.

What the published histories show (figures marked derived are my arithmetic on dates printed at source):

  • Anthropic’s recent notices sit at the floor. The last five deprecation notices (December 2025 to September 2026) gave 60 to 62 days (derived). Earlier ones gave 63 to 189 days (the 2024 Claude 1/Instant notice gave 63; the four in 2025 gave 76 to 189), so short notice is not new. Measured from the snapshot date in the model ID to retirement, Sonnet 3.7, Sonnet 4, Opus 4, Opus 4.1 and Sonnet 4.5 (scheduled for 2026-11-30) lasted about 12 to 14 months. Haiku 3.5, Opus 3 and Haiku 3 lasted about 16, 22 and 25 months (all derived).
  • Observed notice can fall below a stated floor. OpenAI’s 2026-10-14 notice retires dated GPT-4o, GPT-4o mini, GPT-4.1 and GPT-4.1 mini snapshots on 2027-01-14. That is 92 days (derived), against a stated “at least 6 months” for GA models. The page gives no safety or compliance reason for this entry. The same page’s 2026-10-01 GPT-5.3-Codex / GPT-5.1 / GPT-5.4-Nano notice does give six months.
  • Retirement dates differ by platform. Anthropic’s page says Amazon Bedrock and Claude models on Google Cloud (Google managed) “set their own retirement schedules”. Bedrock says its dates “may differ from dates published by model providers”. Hosting the same model on two platforms buys calendar slack: Azure retires the same GPT-4o, 4o-mini and 4.1-mini snapshots on 2027-04-14, three months after OpenAI’s 2027-01-14. It does not buy independence from that model.
  • Azure picks the replacement late. Microsoft names the official replacement “approximately 90–120 days before the retiring model’s retirement date”, so migration testing against the named target cannot start earlier than that. Microsoft also tells customers not to wait for the named replacement before they start evaluating.
  • A dormant fallback can lose access. In Bedrock’s Legacy state (for models launched on or after 2026-09-07), “existing customers may lose access after 15 days of inactivity”. A rarely used backup model can disappear before its EOL date.
  • Vendor-hosted eval and prompt tooling has a lifecycle too. OpenAI is shutting down its Evals platform (read-only from 2026-10-31, dashboard and API off 2026-11-30) and its reusable prompt objects (v1/prompts, 2026-11-30). A golden set or prompt library kept only in a vendor’s console gets deprecated along with that console.

Programmatic monitoring exists, so retirement dates do not have to be tracked by hand. OpenAI’s GET /v1/models exposes an optional shutdown_date. Azure’s Models API exposes lifecycleStatus and deprecation.inference; note that Azure’s API value Deprecated means retired. Bedrock returns a modelLifecycle field. Anthropic offers a usage export by API key and model.

Pinning vs aliases

  • An alias is a moving target. The 2023 GPT drift study compared two snapshots behind the same gpt-4 and gpt-3.5-turbo names. The toxicity-classifier study notes that the update “is silent when a developer uses the main API gpt-3.5-turbo”. On the Claude API, short aliases for models before the 4.6 generation resolve “to the most recent dated snapshot for that minor version”.
  • A pinned ID fixes weights, not served behaviour. Anthropic states that weights are fixed per ID but “the serving infrastructure around the model can change over time”, including “the request router, safety classifiers, and sampling logic”. Its September 2025 postmortem describes three infrastructure bugs that degraded output on unchanged model IDs, with different exposure on each hosting platform.
  • The platform can change the model with no code change. Azure auto-upgrades Standard deployments at retirement by default. The alternative, NoAutoUpgrade, means the “deployment stops working at retirement”. Anthropic’s beta server-side fallback can answer a refused request with a different model, either one Anthropic recommends or up to three the customer names. In both cases the model that served a request can differ from the one the code asked for. Log the model reported in the response (response.model in Anthropic’s SDK examples) in the audit record, not just the requested ID. See agent-audit-trails-provenance.

Pin to prevent silent drift. Pinning does not prevent forced retirement or serving-side change, so it does not replace continuous evaluation.

The cost of a swap

The parts that carry model-specific tuning, roughly in order of how loudly they fail:

  1. The API contract breaks loudly. Within one vendor, a new generation can reject requests the old one accepted. Anthropic’s Sonnet 5.5 migration guide lists thinking budgets, sampling parameters, assistant prefill, forced tool choice and thinking: {"type": "disabled"} as settings that “return a 400 error”. Response shape changes too: “code that reads content[0].text breaks” because thinking blocks can come first. An API version can also remove a parameter for every model, as happened to temperature/top_p/top_k in Anthropic API version 2026-10-21. These are hard failures, and an integration test that exercises each request shape catches them.
  2. Prompts regress quietly and unevenly. Measured on 2023–24 models (details under Evidence strength): prompt-format optima transfer poorly across model series but well within a sub-series. One model update helped some prompts and hurt others, and it changed which prompt was best. OpenAI’s GPT-4.1 guide says getting the most from the model “will require some prompt migration”, and that existing prompts “may not immediately work” because the model follows instructions more literally. Prompts written to compensate for an older model can become harmful; context-engineering-claude-5-generation covers one vendor removing most of a system prompt for a newer generation.
  3. The harness is coupled to the model. An independent evaluator found that Claude Opus 4.5 scored 42% with its standard scaffold and 78% under Claude Code. For Opus 4.1 the standard scaffold was ahead “by almost 10 percentage points”. So the better scaffold for one generation was the worse one for the next. A 2026 study reports that open models fine-tuned under one agent scaffold “degrade substantially when deployed under any non-training scaffold”. Cursor states that “each model requires specific instructions and tweaks to our agent harness”, and lists tool names, explicit tool-use triggers and reasoning-trace passing as model-specific. See harness-design-load-bearing for which scaffolding to re-derive on each model change.
  4. Judges and their thresholds change with the judge. If the pipeline uses an LLM judge, reviewer or classifier, the measuring instrument changes too. A 2026 audit found that adjacent released versions of one judge differed by at most 0.022 accuracy and that none of the differences was significant. Position bias still changed 14.7% of verdicts on the latest release. Thresholds tuned on one judge version belong to that version. A toxicity-classifier case study found 63.8% of regressions on items the model was fully confident about, so a confidence threshold would have missed most of them (confidence measured as agreement across 20 samples).
  5. Fine-tunes expire with the base model. On OpenAI, fine-tunes follow the base model’s shutdown schedule. On Bedrock (models launched on or after 2026-09-07), no new fine-tuning jobs can start once the base model is Legacy. A fine-tune is a model-specific asset with the base model’s expiry date. Base-model updates also cause “negative flips” (previously correct, now wrong) in fine-tuned adapters, even when the fine-tuning procedure stays identical.
  6. Regulated settings may need re-approval. Under the EU AI Act, a high-risk AI system “shall undergo a new conformity assessment procedure in the event of a substantial modification” (Article 43(4)). A “substantial modification” is a change “not foreseen or planned in the initial conformity assessment” that affects compliance or the intended purpose (Article 3(23)). Article 43(4) exempts pre-determined changes documented at the initial assessment, but its text scopes that exemption to systems “that continue to learn”. Whether swapping a third-party foundation model counts as a substantial modification, and whether a documented swap procedure keeps it from counting, is an interpretive question that this note does not settle (unverified; needs legal reading). Other regulated domains have their own change-control regimes, which were not checked here.

What is not known: the size of the bill. No source found here reports hours or cost per migration. GitHub says only that “sometimes we need to make changes, for example modify some prompts”. Anthropic asserts that teams without evals “face weeks of testing” while teams with evals “upgrade in days”. That is a vendor claim with no comparator, and it should not be quoted as a measured effect.

Evaluation on model change

Building a golden set and running it as a CI gate is covered in eval-driven-llm-feature-development. Judge independence and cross-family grading are covered in llm-evaluation-methodology. A model swap adds the following:

  • Run the gate on the swap itself, not only on prompt edits. Anthropic’s evals essay places automated evals “on each agent change and model upgrade”. GitHub describes 4,000+ offline tests, about 100 containerised repos with deliberately broken tests that the model must fix, and internal users switched to the candidate model, “similar to canary testing”.
  • Report per-item regressions next to the aggregate. In the toxicity-classifier study, 10.9% of individual predictions flipped from correct to wrong across updates. In 87.9% of updates that improved overall accuracy, at least one previously correct prediction regressed. The gate should list newly failing items, not just a pass rate.
  • Run deterministic checks before judge checks. In the 2023 drift study, GPT-4’s directly executable code fell from 52.0% to 10.0% because the newer snapshot wrapped code in Markdown fences. Once the fences were stripped, correctness rose from 52% to 70%. Executing the code caught the change at once. The failure was in the format contract, not in capability, and only a deterministic check separates the two.
  • Pin the judge separately from the model under test, and audit it. GitHub uses “a model with known good performance” as its grader and “routinely audit[s]” its outputs. If the judge’s model changes during a migration, two variables move at once.
  • Keep evaluating after the swap. GitHub runs its tests “against our production models every day”. After its 2025 incident, Anthropic committed to running quality evaluations “continuously on true production systems” and added detection tests for unexpected character outputs. Both responses target drift on a model that has not been swapped, which pinning cannot catch.
  • Keep the swap point behind one indirection. GitHub routes completions through a proxy so it can “change which API the proxy server calls … without any sort of change on the client side”. Gateways such as those in agent-pipeline-tooling-landscape do the same. Indirection makes a swap cheap. Only the eval gate makes it safe.

Failure modes

How a model-change gate passes when it should fail, or fails when it should pass:

  • The aggregate hides flips. The pass rate holds or rises while specific cases break. This is measured (toxicity-classifier study and MUSCLE). Counter it with a per-item regression list.
  • Prompts get tuned until the golden set passes. If a team edits prompts for the new model until the fixed set goes green, the set stops measuring generalisation and becomes a training target. This is reasoning, not a measured result. A held-out slice that nobody tunes against is the obvious counter, and its value is untested here.
  • The judge moved too. A score change gets attributed to the model when the judge version also changed. This is measured for judges in general, but not yet for code-review judges.
  • A format contract is read as capability. A drop in a gate that mixes format and correctness gets read as “the new model is worse”, or a fix to formatting hides a capability drop. This is measured (2023 drift study).
  • Grading bugs penalise the new model. Rigid graders can reject valid answers. Anthropic’s essay reports that Opus 4.5 “initially scored 42% on CORE-Bench” until grading problems were found. The independent evaluator later reported 95% after fixes and a scaffold change. A new model that solves the task differently can look worse.
  • The agent games the grader. Anthropic’s essay warns that graders must be “resistant to bypasses or hacks” so the agent cannot “cheat” the eval, and it recommends reading transcripts. A more capable model is more likely to find a loophole in the grader.
  • A saturated suite gives no signal. A regression suite at 100% “tracks regressions but provides no signal for improvement” (Anthropic). It can confirm that nothing broke but cannot show that the new model is better for this workload.
  • Public benchmarks stand in for your workload. Microsoft’s lifecycle page advises comparing candidates on “your own application, prompts, and representative data … rather than relying on public benchmarks alone”. Scores depend on the scaffold (the 42% vs 78% result above), so a public number measured on someone else’s harness is weak evidence for yours.
  • The eval misses what users see. Anthropic’s postmortem: “The evaluations we ran simply didn’t capture the degradation users were reporting.” A gate on curated cases can stay green through real degradation.
  • A notice floor is read as a guarantee. Plans built on a stated floor can be undercut by an observed notice shorter than that floor (OpenAI’s GPT-4o/4.1 entry), or by an emergency retirement, which Microsoft explicitly reserves.

All the measured studies of prompt brittleness use 2023–24 non-agent models. The claim that 2026 agent prompts are equally brittle rests on vendor and practitioner statements, not on a measurement.

What needs more research

  • Engineer-hours per model migration at any named organisation, split by layer (API contract, prompts, harness, judges, fine-tunes).
  • Per-item verdict flip rates for an LLM code-review judge across versions of the same named model.
  • How much a harness tuned for one frontier closed model loses on another frontier model, measured with repeated runs.
  • Whether context files (CLAUDE.md, AGENTS.md) tuned for one model or agent lose effectiveness on another.
  • Whether eval gates, canary users or shadow traffic measurably reduce regressions that escape to users after a model upgrade.
  • How EU regulators and notified bodies treat a swap of the underlying foundation model in a high-risk system, and whether a documented swap procedure can be pre-determined. Also what other regimes (medical devices, financial model risk) require.
  • Why OpenAI’s GPT-4o/4.1 notice is shorter than its stated GA floor: an unstated exception, a classification difference, or a policy that postdates these models.
