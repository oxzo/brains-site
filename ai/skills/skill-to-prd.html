Skill: to-prd

Synthesize the conversation’s converged design into a structured Product Requirements Document and write it as a vault note under projects/. The skill is generative — it produces one agent-ready artifact and stops at the spec boundary: it does not pick the implementation approach (/plan-options), does not break the PRD into tickets (/task-decompose), and — its defining constraint — does not interview the user. If the session lacks a converged design, a context-sufficiency gate STOPS it and routes to /grill or /clarify-first instead of gathering requirements itself.

House-native port of Matt Pocock’s to-prd (see the source capture, tagged novel in the adoption pass): it keeps the three transferable mechanisms that note flags — no-interview synthesis, seam-first testing design (decide the test seams before any prose), glossary/ADR grounding — and the fixed seven-section template, but swaps the original’s issue-tracker-with-ready-for-agent-label publication for a vault note under projects/. It reuses in-house machinery rather than restating it: bias-aware-authoring rule 7 for the no-file-paths durability rule, /branch-resolve’s HITL/AFK split to classify each user story, and /intent-check + /falsifiability-scan as the verification companions the finished PRD routes to instead of self-grading.

When to use

  • The user wants to create a PRD, spec, or requirements doc from the current conversation (“turn this into a PRD”, “write up a spec from what we decided”)
  • A design or scoping conversation has converged and needs crystallizing into a trackable, agent-ready artifact
  • Handing a well-discussed feature off to an implementing agent rather than a human teammate
  • Capturing “what we just decided” as a durable spec before the session’s context is lost

Skip when:

  • The design isn’t converged — discovery/requirements-gathering belongs to /grill (stress-test an in-progress design) or /clarify-first (bounded burst on a vague request); re-invoke after
  • You need to choose how to build a settled feature — /plan-options (2–3 approaches, collapse to one)
  • You need to break a finished plan or PRD into implementation tasks — /task-decompose (the downstream step)
  • A PRD already exists and you want to audit it — /intent-check, /falsifiability-scan, or /red-team

Why it exists

A converged design conversation decays if it’s never crystallized: the decisions live only in a transcript that may not survive the context boundary, and the next agent (or the user next week) re-derives them from scratch. The original to-prd solved this with a no-interview synthesis that produces an agent-ready issue — a capability the adoption pass tagged novel against the owned set, which is almost entirely diagnostic scans that consume an artifact rather than produce one. The two failure modes it counters are interview-creep (sliding from “synthesize what’s known” into “ask what’s unknown”, which dissolves the skill into /grill) and the unstructured brain-dump (a PRD that’s a wall of prose with no testable user stories, no decided seams, and stale file paths baked into it). The context-sufficiency gate enforces the first; the fixed template plus rule-7 durability and seam-first ordering enforce the second.

In the develop-and-verify loop (intent-to-retrospective-loop) the PRD is the ① intent artifact that the downstream stages (/plan-options → /task-decompose → implementation → /intent-fulfilment-check) run against.
