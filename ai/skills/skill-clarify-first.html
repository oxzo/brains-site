Skill: clarify-first

Apply a four-phase protocol on a vague but load-bearing user request: research → grounded questions → clarify → execute. Every option offered to the user is either grounded in a real finding (file path, error message, function name, commit) or explicitly marked speculative; “Other (specify)” remains available. The skill exists to prevent ungrounded clarification — the failure mode where the assistant asks a clarifying question whose options were confabulated from training-data priors. The skill’s own anti-pattern is over-application: the protocol’s cost can exceed the cost of the failure it prevents, so the SKILL.md includes a “when the pattern itself is the wrong tool” section.

When to use

Invoke when all three hold:

  • The request has no named target, no named approach, or no named success criterion
  • Base-knowledge defaults would plausibly lead to wrong-direction work
  • The request is load-bearing — wrong-direction work has real cost

Skip when:

  • The request is already clear and specific
  • The deliverable is a single factual answer
  • Recent conversation already disambiguates
  • The user has explicitly bypassed clarification (“just pick one”)
  • The cost of getting it wrong is trivial

Why it exists

A clarifying question with confabulated options is worse than no question. The user is forced to mentally adjudicate between the model’s guesses, and a wrong-target choice silently anchors the rest of the work to the wrong frame. The protocol’s structural fix is: do the research first, then ask with options the user will recognise as their own context. Distinct shape from the rest of the catalogue — most skills produce a structured analytical output; this one prescribes a behavioural protocol before acting.
