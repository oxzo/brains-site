Skill: task-decompose

Decompose a chosen plan into implementation tasks with their specs attached — each task carries a falsifiable done-criterion written at creation, the interface it exposes and consumes, and a risk-rank that front-loads the project-killing unknown. The ④ stage of the intent-to-retrospective-loop and the produce-side sibling of plan-options (which picks the approach this skill then decomposes). It clears the ceremony bar by forcing the three disciplines the default task-breakdown skips: done-criteria at creation, the cross-task interface contract, and risk-ordering.

When to use

  • After the approach is chosen (e.g. via /plan-options), before issuing implementation work, on integration-heavy or novel material — build-both-sides-and-integrate shapes, hardware/firmware bring-up, cross-service wiring
  • When the seam between tasks is the real risk — a payload schema or protocol two tasks must agree on before either is built
  • When “is this task done?” is a non-trivial question for most tasks in the list
  • Upstream of /branch-resolve (branches) and /plan-split-scan (size); downstream of /plan-options (approach)

Skip when:

  • The work is routine and well-trodden, done-criteria write themselves, and nothing shares a contract (provisioning a standard service, a CRUD endpoint, a config change) — refuse, and say so
  • The approach isn’t chosen yet (use /plan-options)
  • You’re checking an already-drafted task list’s size (use /plan-split-scan)
  • You’re verifying a produced output (use /reviewers-map — post-hoc, not generation-time)

Why it exists

Silent-underspecification is the failure mode it counters: a plan gets broken into a narrative-ordered task list whose done-criteria are unstated (so “done” means “worked once”), whose cross-task contracts are discovered only at integration, and whose riskiest task is back-loaded behind cheap visible progress. None of the existing loop skills closes this at generation time — /plan-split-scan audits size, /branch-resolve operationalizes branches, and /reviewers-map verifies the output post-hoc, too late to shape the task.

The skill was the last buildable produce-side cell of the loop. Stage ④ was originally left native (2026-05-29) on the judgment that a task-generator couldn’t clear the ceremony bar; it was reopened the same day after walking the loop on two concrete cases that split the bar by case, not domain:

  • Pi-hole (routine, narrow): done-criteria write themselves (nslookup <ad-domain> → 0.0.0.0); the one non-obvious item (secondary-DNS bypass) is a branch for /branch-resolve. Task-generator = ceremony → correct refuse (the refuse-floor).
  • ESP32 + display Claude Code companion (novel, integration-heavy): native decomposition skipped all three disciplines — fuzzy done-criteria, the hook-payload-vs-device-parser contract built blind on both sides, and the project-killing unknown (does a Claude Code hook reach a LAN device at all?) sitting last instead of first. Task-generator clears the bar → pass (the pass-ceiling).

So the skill ships trigger-bounded: fire on integration-heavy/novel work where done-criteria are non-obvious and tasks share a contract; refuse on routine work. The refuse condition is what keeps it from competing with native decomposition everywhere — the same self-guard /plan-options carries against generating three plans for a one-approach task.
