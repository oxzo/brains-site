Skill: plan-split-scan

Scan a draft multi-step plan for structural over- or under-decomposition signals — concern count, state-carry depth, decision branches, verification seams, reversibility boundary — and recommend split, consolidate, or leave-alone per finding. Operates on the executor-side load axis: the plan’s shape against the executor’s capacity, before execution.

When to use

  • Before issuing a multi-step plan to an agent or subagent via the Agent tool
  • Before confirming an ExitPlanMode draft, especially across multiple concerns or production state
  • Before committing a projects/**/plan.md style document executed across sessions
  • Before a migration plan, a multi-file refactor, or any sequence mixing speculative and destructive operations

Skip when:

  • Plan is under ~5 steps, single concern, no destructive operation, no unresolved branch — monolithic execution is the right default and the scan refuses
  • Artifact is a description of a process rather than a prescription to execute
  • Throwaway / exploratory work, or the user has explicitly opted into monolithic execution

Why it exists

Under-decomposition produces attention drift, flattened branches, verification debt, and confabulated state-carry — the executor gets through it, but the output is unreviewable. Over-decomposition produces switching overhead, lost goal coherence, and plans of plans. Both failure modes are real and both are silent: fluent plans hide them. The scan names the structural signals (and the over-decomposition counter-signs) explicitly so the decision is auditable, not vibes-based. The refuse-to-scan floor exists because over-applying decomposition advice is itself an over-decomposition pattern.
