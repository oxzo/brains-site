Skill: deepen-architecture

Diagnose a codebase’s static module structure and rank deepening refactors — turning shallow modules (interface nearly as complex as the implementation) into deep ones (a lot of behaviour behind a small interface). Uses a fixed glossary and a three-test battery (deletion test, interface-is-the-test-surface, one/two-adapter rule), emits a markdown + Mermaid report of ranked candidates to the OS temp dir, and stops at the design boundary — it hands the chosen candidate to /grill and /plan-options rather than designing or writing code itself.

House-native port of Matt Pocock’s improve-codebase-architecture (see the source capture): it keeps the two transferable mechanisms that note flags — the fixed glossary (anti-synonym-drift) and the deletion test — translates his HTML report into a markdown+Mermaid one, makes the per-repo CONTEXT.md/ADR glossary optional-if-present, and delegates his hand-rolled grilling loop and “design it twice” pass to the owned /grill and /plan-options.

When to use

  • The user wants to improve architecture, find refactoring opportunities, or reduce tight coupling
  • Consolidating modules that leak across their seams; making a codebase more testable through its interfaces
  • Making a codebase more AI-navigable — fewer shallow modules to bounce between to understand one concept
  • The user names “shallow modules”, “deep modules”, “deepening”, or pure functions extracted only for testability

Skip when:

  • Behaviour recurs over time and the issue is standing structure, not static code shape — /structural-trace
  • You want a correctness review of a diff (/lean-review) or a merge call on an AI-authored diff (/ai-diff-judgment)
  • A candidate is already chosen and you want to design its interface — /grill (and /plan-options)
  • You want the refactor actually performed — this skill stops at the ranked report

Why it exists

A codebase drifts into many shallow modules — interfaces nearly as wide as the implementations behind them — that leak across their seams, can’t be tested through their declared interface, and force a reader (human or AI) to bounce between files to understand one concept. Nothing in the owned catalog diagnosed static code structure: the toolkit is thinking/verification-focused, /structural-trace diagnoses system behaviour over time, and the code-review skills judge a diff for correctness rather than the whole codebase for new structure. The source-skill capture tagged this capability “novel — no analogue in the owned set”; this skill fills that gap, prescriptively (ranked candidates with a recommendation badge) and with a reachable clean verdict so it doesn’t manufacture findings on an already-deep codebase.
