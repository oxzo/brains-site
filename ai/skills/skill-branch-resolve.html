Skill: branch-resolve

Operationalize each unresolved decision branch in a multi-step plan — route every branch to one of three resolutions in preference order: (1) resolve up front before issuing, (2) split into separate plans at the determinant, (3) express as a Gollwitzer implementation intention. Apply trigger criteria (observable, deterministic, falsifiable) and response criteria (specific, executable, bounded) when producing option 3. Force a hard split with a user-confirmation gate on any branch whose downstream contains a destructive or production-touching operation.

When to use

  • After /plan-split-scan flags a Signal-3 finding (unresolved branches) — this skill is the action step
  • Before issuing a multi-step plan that contains conditional syntax to an agent or subagent
  • Before confirming an ExitPlanMode draft with embedded “if X then Y otherwise Z” structure
  • Before committing a projects/**/plan.md document with run-time branches
  • Whenever a plan reads coherent but contains determinants whose evaluation falls to the executor at run time

Skip when:

  • The plan has no branches — nothing to resolve (run /plan-split-scan for structural audit instead)
  • Every branch is already in valid implementation-intention form (the skill will refuse)
  • The artifact is descriptive rather than prescriptive
  • Work is throwaway / exploratory

Why it exists

When an LLM encounters an unresolved if/then in a plan, it tends to pick one branch and proceed — usually the most training-data-typical one. The counterfactual branch is silently flattened. This skill exists to keep branches open and deterministic at execution time: by routing each unresolved branch to either an up-front resolution, a split into separate plans, or a Gollwitzer implementation intention with observable trigger and named response. The destructive-branch safety rule (never wrap a destructive op in conditional syntax) closes the asymmetric-cost case where a conditional firing produces irrecoverable state.
