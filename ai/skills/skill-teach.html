Skill: teach

Run a stateful, multi-session teaching workspace for a topic the user wants to learn. Each topic gets its own folder at learning/<topic-slug>/ inside the vault, persisting learning state across sessions in a fixed set of files: MISSION.md (why the user is learning — grounds every decision), RESOURCES.md (curated high-trust sources), ./learning-records/*.md (ADR-style records of what’s been learned, driving the zone of proximal development), ./lessons/*.html (the primary output — one beautiful, self-contained, single-topic lesson at a time), ./reference/ docs, an optional GLOSSARY.md, and NOTES.md (teaching preferences). Philosophy: knowledge (from trusted sources, never parametric guesses) → skills (interactive lessons with tight feedback loops) → wisdom (delegated to real communities).

Imported then vault-adapted. Based on Matt Pocock’s teach skill (mattpocock/skills, skills/productivity/teach). The upstream version treats the current directory as the workspace; this copy was modified to write into a dedicated learning/<topic-slug>/ folder under the vault so it works regardless of cwd and never scatters files across knowledge/. It is a generative productivity skill — a different genre from this vault’s verification-scan skills — and is manual-invoke only (disable-model-invocation: true).

When to use

  • The user says “teach me X” / “I want to learn X” and intends to learn it over multiple sessions, not get a one-shot explainer.
  • You want lessons grounded in a real-world mission and a curated resource list rather than ad-hoc parametric answers.
  • The topic benefits from persistent learning state — a record of what’s known, a glossary, reusable reference sheets.

Skip / reach for something else when:

  • The user wants a single quick answer — just answer in chat.
  • The request is “research topic X into a vault note” — that’s normal vault note authoring under knowledge/, not a teaching workspace.
  • You want to build a skill (/write-a-skill) or audit one (/skill-quality-audit, /skill-trigger-audit).

How it sits in the vault

Outputs land in learning/<topic-slug>/ — a workspace area, exempt from the vault’s note conventions (lessons are HTML; learning records use the teach format, not templates/concept.md). Do not run /bias-scan-* or note-template linting against files under learning/. The skill keeps learning/_index.md current and, when a lesson surfaces durable reusable knowledge, offers to promote it to a proper knowledge/ note and link it back. Because the workspace path is fixed, /teach can be invoked from anywhere in the vault — no cd dance.

Why it exists

Default LLM teaching collapses to disconnected, ungrounded explainers: abstract, untethered from why the learner cares, drawn from parametric memory, and forgotten between sessions. teach counters that with three structural commitments — mission-grounding (no lesson without a concrete real-world reason), trusted-source knowledge (resources curated in RESOURCES.md, never parametric guesses), and persistent learning state (learning records + glossary that let each session pick up at the learner’s actual zone of proximal development). The unit of teaching is one tightly-scoped, beautiful lesson tied to the mission — a tangible win, not a wall of text.
