Agent Isolation Hardening

agent-sandbox-isolation-tiers picks the tier. This note is the next step: making the boundary you picked actually hold. Verified against Claude Code 2.1.220, the reference dev container at anthropics/claude-code@main, and @anthropic-ai/sandbox-runtime as of 2026-07-31.

The recurring failure mode is not a missing boundary — it’s a boundary with one rule that voids it. Everything below is an instance of that.

The reference firewall has three egress holes — tested, not inferred

The published .devcontainer/init-firewall.sh is the artifact most people copy for unattended work. Its shape is sound: ipset allowlist, iptables -P OUTPUT DROP, explicit REJECT tail, and a self-verification step. Three rules undercut it.

I replicated its rule structure in a rootless container and probed it, with the allowlist deliberately narrowed to api.anthropic.com so the results are unambiguous:

ProbeResultMeaning
curl -4 https://github.com (off-allowlist, 443)blockedcontrol — the allowlist works as designed
curl -4 https://example.comblockedcontrol
curl -6 https://example.comREACHABLEIPv6 bypasses the entire policy
curl https://example.com (default family)REACHABLEand IPv6 is what curl picks by default
dig @1.1.1.1 <name>SUCCEEDEDarbitrary external resolver reachable
ssh -4 git@github.com (off-allowlist)reached sshdport 22 egress to anywhere

Hole 1 — the policy is IPv4-only

The script calls iptables and never ip6tables. In the test container, ip6tables -S showed -P OUTPUT ACCEPT with global IPv6 present, so every allowlist rule was void for IPv6 traffic — and since curl prefers IPv6 when available, the default path was the unfiltered one.

Fairness point: the script’s own verification step catches this. It exits 1 if https://example.com is reachable, so on a dual-stack container it aborts loudly rather than running wide open. The danger is copying the rules without the check, or running where the resolver happens to return IPv4 first — then the hole is silent.

Fix: mirror every rule to ip6tables (including a v6 ipset, hash:net family inet6), or disable IPv6 in the container outright and assert it — the second is easier to get right and easier to verify.

Hole 2 — unrestricted DNS to any resolver

iptables -A OUTPUT -p udp --dport 53 -j ACCEPT is added before the restrictions and never narrowed. Any host, any resolver. DNS is a well-worn covert channel: data encodes into query names sent to a nameserver the attacker controls, and no allowlist rule ever sees it.

Fix: allow UDP/53 only to the container’s own resolver address, not 0.0.0.0/0. Under Docker that is 127.0.0.11; other runtimes expose their own resolver address. Everything else falls to the REJECT tail.

Hole 3 — unrestricted TCP/22 to any host

iptables -A OUTPUT -p tcp --dport 22 -j ACCEPT gives full outbound SSH anywhere. Confirmed: ssh -4 git@github.com reached GitHub’s sshd while curl -4 https://github.com was blocked. SSH is a general-purpose tunnel, so this is not “git over SSH works” — it is an arbitrary egress channel with encryption included.

Fix: drop the blanket rule. Git-over-SSH to GitHub already works via the api.github.com/meta ranges in the ipset, matched on destination rather than port.

Hole 4 (not tested, structural) — the host /24

HOST_NETWORK is derived by rewriting the last octet of the default gateway to .0/24, then allowed in both directions. That is a whole subnet, reachable in both directions, granted by a line whose apparent purpose is “let the container talk to its host.” In a corporate network segment it is the adjacent infrastructure — internal registries, admin interfaces, other build agents; in a flat network it is considerably more. Narrow it to the specific host address, if host access is needed at all.

The reference allowlist is stale for claude.ai auth

The script resolves: registry.npmjs.org, api.anthropic.com, sentry.io, statsig.anthropic.com, statsig.com, and three VS Code hosts. Compared against the current documented network requirements, it is missing claude.ai, platform.claude.com, downloads.claude.ai, and mcp-proxy.anthropic.com.

Consequence: a container built from this script can reach the API but cannot complete a claude.ai OAuth sign-in, since token exchange and refresh go to platform.claude.com. Conversely sentry.io and the two Statsig hosts no longer appear in the documented requirements at all.

The current required set is api.anthropic.com, claude.ai, claude.com, platform.claude.com, mcp-proxy.anthropic.com, downloads.claude.ai, storage.googleapis.com, bridge.claudeusercontent.com, and raw.githubusercontent.com, plus optional telemetry (http-intake.logs.us5.datadoghq.com, browser-intake-us5-datadoghq.com, disabled together by CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC). Note that variable also disables Remote Control’s feature-flag fetch.

Better pattern than resolve-once: the script digs each domain at boot and pins the returned IPs. CDN-backed hosts rotate addresses, so the allowlist rots during a long session, and pinning a shared CDN edge IP incidentally allows every other tenant on that edge. Prefer a filtering HTTP proxy that decides on hostname over an IP-set firewall — that is what both the built-in sandbox and sandbox-runtime do — and keep iptables as the backstop that forces traffic through it.

sandbox-runtime, done well

Why it fails closed on Linux

On Linux srt removes the sandboxed process’s network namespace entirely; the only egress is HTTP and SOCKS5 proxies on the host, reached over bind-mounted Unix sockets bridged by socat. This is the architectural reason it is a real boundary and not a convention.

A misreading worth pre-empting: the README’s future-work section carries a heading “Linux proxy bypass”, which reads like an escape vector. The body says the opposite: srt uses HTTP_PROXY/HTTPS_PROXY/ALL_PROXY to point tools at the proxies, and a program ignoring those variables ends up “unable to connect to the internet”. With no netns there is no path around the socket. So: fail-closed (breakage), not fail-open (escape). The same section lists proxychains/LD_PRELOAD as future work to make “bypass more difficult”, so treat it as architecturally fail-closed with the authors reserving some doubt — not as a known escape.

Mandatory deny paths, and the Linux gotcha that defeats them

srt always blocks writes to a fixed set regardless of allowWrite: .bashrc, .bash_profile, .zshrc, .zprofile, .profile, .gitconfig, .gitmodules, .ripgreprc, .mcp.json, and the directories .vscode/, .idea/, .claude/commands/, .claude/agents/, .git/hooks/, .git/config. That list is precisely the self-escalation surface — write any of them and you own the next session.

The gotcha: on Linux these are enforced by bind-mount, so they only block files that already exist. A non-existent .git/hooks/pre-commit cannot be blocked and can be created. macOS uses glob patterns and blocks both.

This exact bug class has been exploited in Claude Code’s own sandbox. CVE-2026-25725 (< 2.1.2, CVSS 3.1 10.0 / v4.0 7.7, CWE-501 Trust Boundary Violation, GHSA-ff64-7w26-62rf): bubblewrap protected .claude/settings.local.json read-only, but .claude/settings.json was not protected when it did not exist at startup. Sandboxed code created the file, injected SessionStart hooks, and those executed with host privileges on the next run. Same shape as the srt gap above — a protection expressed as a constraint on an existing path silently does not apply to a path that isn’t there yet. Treat “pre-create the deny-path files” as a mitigation with a CVE behind it, not a fussy precaution.

Fix: pre-create the deny-path files as empty placeholders in any repo you hand to an unattended srt session, so the bind-mount has something to cover. Also note mandatoryDenySearchDepth defaults to 3 — files deeper than three levels inside an allowed write path are not scanned; raise it (max 10) or keep write scope shallow.

Config skeleton

Deny-all by default, so an under-specified file means a session that cannot start. Minimum viable shape:

Two asymmetries that are easy to get backwards, and are intentional: for reads it is deny-then-allow with allowRead winning, so you can carve a readable workspace out of a denied /home. For writes it is allow-only with denyWrite winning, so you can carve protected files out of a writable tree. Domain entries take an optional :port suffix; without one they match any port.

Claude Code also needs write access to ~/.claude and ~/.claude.json — the latter sits outside the directory, and missing it is the usual cause of a wrapped session that won’t hold auth.

Syscall-level enforcement, and its edges

The bundled apply-seccomp binary (static, x64/arm64) blocks AF_UNIX socket creation, and also io_uring_setup/enter/register — because IORING_OP_SOCKET on Linux 5.19+ would otherwise route around the socket() rule. That second block is a good sign that its authors take the threat model seriously; it is the kind of gap most homegrown seccomp policies miss.

Two edges to know: it does not stop operations on descriptors inherited from a parent or passed via SCM_RIGHTS, and on architectures without a pre-built filter you must fall back to allowAllUnixSockets: true, which removes the protection entirely.

Rollout note: srt is distributed via npm, so the effective install location depends on the fleet’s npm prefix. Where that prefix is unusual — a per-application runtime, a version manager, a locked-down image — the binary can land off the login shell’s PATH, which turns “the wrapper is installed” into a false assumption. Pin the invocation (npx, or an absolute path) rather than relying on PATH resolution in any automated context.

Container tier

What the reference Dockerfile does that is worth keeping, independent of Docker:

  • Non-root remoteUser. Not cosmetic: --dangerously-skip-permissions refuses to start as root or under sudo, so a root container blocks the very thing the container exists to enable.
  • Narrow sudoers. node ALL=(root) NOPASSWD: /usr/local/bin/init-firewall.sh — exactly one root command, so the agent can raise the firewall at start but cannot lower it afterwards. Copy this precisely; a blanket NOPASSWD hands the agent the ability to flush its own policy.
  • Firewall at postStartCommand with waitFor set to it, so the container is not usable before the policy is up.
  • CLAUDE_CONFIG_DIR pointed at a named volume together with mounting ~/.claude there — because ~/.claude.json lives outside ~/.claude, mounting the directory alone loses auth on rebuild.

Runtime portability: none of this requires Docker specifically. --cap-add=NET_ADMIN --cap-add=NET_RAW is sufficient for the iptables/ipset approach under a rootless runtime — verified — so the pattern ports to rootless OCI runtimes without a privileged container. What does not port automatically is the address-family assumption: the rootless container used for these probes had global IPv6, which is what exposed Hole 1. Docker’s default bridge commonly does not. Assert the address families your runtime actually gives the container instead of inheriting the reference script’s IPv4-only assumption.

Layering the built-in Bash sandbox inside the container requires sandbox.enableWeakerNestedSandbox: true, because nested bwrap cannot mount a fresh /proc unprivileged — tested, with the trade-off in agent-sandbox-isolation-tiers.

The caveat that survives all of this: a container does not stop a malicious project from exfiltrating what is inside the container, including the Claude Code credentials in ~/.claude. Don’t mount ~/.ssh or cloud credential files in; prefer short-lived, repository-scoped tokens.

VM tier

The VM is the only tier that gives kernel-level separation, and it is the documented recommendation for genuinely untrusted code. Two things determine whether it is available rather than theoretical:

  • Hardware virtualization exposed to the workload. Present on bare metal, frequently absent on cloud instances that don’t offer nested virtualization — and cloud instances are where CI runners live. A VM-tier policy that CI cannot satisfy will be quietly downgraded to a container by whoever has to make the pipeline pass.
  • A hypervisor stack in the image. On image-based and immutable fleets this is a base-image decision made long before the security review, not something a developer installs later.

Neither is a reason against the tier; both are reasons to verify it on the actual target class before mandating it, since the failure mode is a policy that only holds on the machines that were used to write it.

Cross-cutting: verify the boundary, don’t declare it

Every hole above was found by probing, and three of the four contradicted what reading the script suggested. Minimum acceptance test for any boundary before an unattended run:

  1. Negative control, both address families — an off-allowlist host must fail on IPv4 and IPv6, tested with the family forced (curl -4 / curl -6), not the default.
  2. Positive control — api.anthropic.com must succeed, or you have built a boundary that also blocks the work.
  3. Protocol sweep, not just 443 — try DNS to an external resolver and TCP/22 to an off-allowlist host. Both were open in the reference config.
  4. Self-escalation probe — attempt a write to ~/.bashrc, .git/hooks/pre-commit, and the relevant settings.json. Under srt on Linux, create-then-check, since non-existent files aren’t covered.
  5. Re-run after any allowlist edit. Resolve-once designs rot silently.

Counterargument

The holes above are real, but the threat model that makes them urgent is hostile code inside the boundary — a poisoned dependency, an injected instruction acting on the agent. For unattended work on your own repository, the dominant risk is still the agent doing something wrong-but-permitted, and none of this touches that: a perfectly sealed container will happily let the agent rewrite your project’s history. Hardening egress is necessary for the untrusted case and close to irrelevant for the careless case, which is the more common one. If the realistic worry is “it ran overnight and made a mess”, the effort belongs in deny rules, a scratch branch, and reversibility — not in ip6tables.

The counter-counter: egress hardening is cheap and one-time, and it’s the only one of these controls that still works after the agent has been successfully manipulated.
