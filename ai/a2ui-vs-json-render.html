A2UI vs json-render — Generative UI Protocol vs Framework

Last verified: 2026-08-25 (a2ui.org + its renderers reference, json-render.dev + its docs, the json-render repo README, GitHub API, and the npm registry all fetched and read the same day). Both projects move fast; version, star, and status claims below decay quickly.

One claim in the 2026-06-12 version of this note was wrong

It said json-render was “React and React Native only”. It was not, even then — the Vue, Svelte, and Solid renderers were on npm from February and March 2026, months before that verification. The error came from reading the marketing homepage (which still says only “React & React Native”) and not the repo README or the docs sidebar. Corrected throughout below; see bias-aware-verification-protocol for the general failure — verifying against the most prominent source rather than the most complete one.

Two prominent answers to the same problem — letting an LLM/agent produce interactive UI safely, by emitting constrained declarative JSON instead of executable code. They sit at two different layers of the stack, and are not rivals: one is a cross-platform protocol, the other a multi-framework rendering library. As of 2026-08 they explicitly interoperate — see Do they actually compose? below.

What each one is

A2UI (a2ui.org)

A protocol created by Google, with contributions from CopilotKit and the open source community (the site states this outright). Agents emit declarative JSON messages describing UI structure and data; a client-side renderer maps them onto native components — no arbitrary code crosses the trust boundary. The site frames the purpose as a single question: “how can AI agents safely send rich UIs across trust boundaries?”

  • Spec versions (per the site’s own table): v1.0 “Candidate”, v0.9.1 “Current production release”, v0.9 “Stable”, v0.8 “Legacy”. Unchanged since 2026-06-12 — v1.0 has now sat as a candidate for 2.5+ months. The site notes v1.0 was “previously designated as v0.10 when in draft”.
  • Maintained renderers: React, Lit, Angular, Flutter (GenUI SDK) — each ✅ Stable for v0.8 and v0.9.1, 🚧 Planned for v1.0. SwiftUI (iOS/macOS) and Jetpack Compose (Android) are listed as Planned only — no shipping spec support. (The homepage prose also names a Markdown renderer; it is not in the maintained-renderers table.)
  • Ecosystem renderers (community): json-render, A2UI-Android (~15★, v0.8), a2ui-react-native (~9★, v0.8), Lynx A2UI (v0.9), AGenUI — cross-platform iOS/Android/HarmonyOS (v0.9).
  • Transport: the site names A2A directly — “Transports like A2A which communicate A2UI messages between agents and clients.” (In the 2026-06 version of this note the A2A pairing was flagged as unverified background; it is now verified at source, and the relationship is specifically transport, not sibling branding.)
  • Repo: a2ui-project/a2ui, 16.2k stars, Apache-2.0, created 2025-09-24, pushed 2026-08-24
  • Notable: still no formal GitHub releases — only v0.9 and v0.8 tags, and no tag for the v0.9.1 the site designates as current. The release process stays looser than the website’s version table implies.

json-render (json-render.dev)

A framework/library from Vercel Labs. The developer defines a catalog of allowed components and actions with Zod schemas; the LLM streams constrained JSON matching the catalog; the renderer paints progressively as the stream arrives. Can export a generated UI as standalone React code — or as a whole standalone Next.js project.

  • Renderers — far wider than the homepage advertises. The README’s own summary: “React, Vue, Svelte, Solid (web), React Native (mobile) from the same catalog”. All four web renderers plus React Native are published at 0.20.0.
  • Non-DOM renderers too: @json-render/next (routes, layouts, SSR), react-three-fiber (3D scenes), remotion (video), react-pdf, react-email, ink (terminal TUIs), image (SVG/PNG via Satori). The same spec format drives all of them.
  • Integrations with their own docs pages: AI SDK, A2UI, Adaptive Cards, AG-UI, OpenAPI. Plus @json-render/mcp — “MCP Apps integration for Claude, ChatGPT, Cursor, VS Code” (see generative-ui-security for what hosting MCP-supplied UI entails).
  • Component counts — two different numbers, often conflated: the homepage catalog demo shows 41 components and 6 actions; the README advertises 36 pre-built shadcn/ui components in @json-render/shadcn. Different things.
  • npm @json-render/core at 0.20.0 (published 2026-08-16), 30 versions total. 29 of those landed between 2026-01 and 2026-05; only one minor since. The churn has slowed sharply — that’s the single most decision-relevant change since June.
  • Repo: vercel-labs/json-render, 16.0k stars, Apache-2.0, created 2026-01-14, pushed 2026-08-19. Unlike A2UI, it does cut formal GitHub releases (v0.20.0, v0.19.0, …).
  • Vercel AI SDK fit is real and documented: the AI SDK integration page pairs useChat with useJsonRenderMessage, in Standalone and Inline modes (see ui-for-ai-products for that surface).

Do they actually compose?

The 2026-06 version of this note speculated that the layers “can even compose”. As of 2026-08 both projects say so in their own docs — with a caveat worth knowing before planning around it.

  • A2UI’s side: its renderers reference lists json-render under “Ecosystem Renderers” — “Vercel’s React library for rendering A2UI catalogs via Zod schemas”.
  • json-render’s side: ships a docs/a2ui page showing how to define an A2UI-shaped catalog (BoundValue, adjacency list, surfaceUpdate) against the schema-agnostic core.
  • The caveat: that page is labelled “Concept: This page demonstrates how json-render can support A2UI. The examples are illustrative and may require adaptation for production use.” There is no @json-render/a2ui package on npm. This is a documented pattern, not a shipped adapter — budget integration work accordingly.

Cross-organization by design — the agent and the client can be built by different vendors, which is the case no library solvesMore moving parts: protocol + per-platform renderer + agent integration

Production readiness (as of 2026-08-25)

Neither is boring-mature; both are credible with eyes open. Two months of extra evidence moved them closer together, not further apart.

  • A2UI’s designated production release (v0.9.1) is stable across all four maintained renderers, which is the real readiness signal. The v1.0 stall is the thing to watch: a candidate that hasn’t landed in 2.5 months, with every renderer still marking v1.0 “Planned”, means pinning to v0.9.1 is the only sane choice today — and that a v1.0 migration is deferred work you are taking on, not avoiding.
  • json-render is fine for internal tools, prototypes, and products that pin versions. The slowed release cadence (one minor in ~3 months against 29 in the prior five) reads as stabilization rather than abandonment — the repo was pushed 2026-08-19 — but 0.x plus Labs status remain real risks for a long-lived customer-facing product, softened meaningfully by code export, which limits lock-in.

Rule of thumb, revised. The old version of this rule said “multiple platforms → A2UI”. That no longer separates them, because json-render covers five UI frameworks plus six non-DOM targets. The axis that actually separates them:

  • Different organizations on each end (your client renders UI from someone else’s agent), or native mobile without React Native → A2UI. This is the case a library genuinely cannot cover.
  • You control both ends and you’re in the JS ecosystem → json-render, whatever your framework. Faster, and the code-export escape hatch caps the downside.
  • Both → viable, via json-render’s A2UI catalog pattern — but that’s a recipe you implement, not a package you install.
