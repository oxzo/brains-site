Buying Verifiability by Constraining Shape

deterministic-gates-agent-loop takes the code as given and asks which gates to run against it. This note is the inverse move: change the shape of the code until the gate you want becomes cheap.

The observation underneath it is that analysis cost is a property of the representation, not only of the question. “Can control reach the payment handler without passing an authorization check?” is an interprocedural data-flow problem in free-form async TypeScript — you need CodeQL or equivalent, the analysis is unsound in practice, and it takes minutes. The identical question against an explicit state machine is graph reachability over a finite edge set: milliseconds, and complete rather than merely sound.

Completeness is the part worth pausing on. deterministic-gates-agent-loop’s four-property table notes that practical linters are neither sound nor complete. Constraining the representation is one of the few moves that buys the upgrade outright, because the state space stops being an approximation and starts being an enumeration.

What a state machine makes mechanical

Once a subsystem’s states and transitions are declared rather than implied, a set of questions that were judgment calls become graph queries:

  • unreachable states — dead code the type checker cannot see;
  • missing transitions — the enumerable version of “did it handle the error case?”, which is otherwise unanswerable without knowing what the cases are;
  • terminal states with no exit — deadlock, as a query rather than an incident;
  • invariant violations — “no transition into charging except from authorized” as a graph assertion instead of an AST heuristic hoping the call is reachable.

The last one matters because it repairs a specific weakness the gates note names: an AST rule can verify a call is present but not that it is reached. Declared transitions collapse that gap.

The oracle payoff

The larger prize is test generation. oracle-problem-verification argues the scarce resource in verification is not analysis but oracles — something that decides whether an output is correct. A finite machine is an oracle generator: enumerate the paths, and each path is a test case with an expected state sequence you did not have to author.

In XState this is getSimplePaths from @xstate/graph. The path set is derived from the machine, so it is not co-authored with the implementation in the way an LLM-written test suite is — which is precisely the independence failure the oracle note catalogs.

Caveat on maturity: as of 2026-08-21 xstate itself is healthy (v5.32.5, ~22M downloads/month, actively pushed), and @xstate/graph is at v3.0.4. But @xstate/test, the model-based-testing package, sits at v0.5.1 and was last published 2026-01-19 while core moved on. The path-generation primitive is solid; the ergonomic wrapper around it is the least-maintained part of the stack, so expect to write the harness yourself.

Why an executing model beats a modeled model

TLA+, Alloy, and the bounded model checkers in the gates note all carry the same structural liability: you verify a model, and model-to-code correspondence is manual. A proof about the model says nothing about the code if the two have drifted, and nothing mechanical prevents that drift.

A statechart in application code does not have this gap, because the machine is the runtime artifact rather than a description of one. That is a meaningful advantage over heavyweight formal methods for exactly the mid-tier properties most web systems care about, and it is the reason to reach for this before reaching for TLA+ — not because the logic is stronger, but because the correspondence is free.

The trade is expressiveness: TLA+ can state properties about unbounded concurrent systems that a statechart cannot.

”Forced” has to mean a gate, not a convention

A convention that the team uses state machines is advisory, and claude-code-enforcement-hooks draws the relevant line: advisory rules describe intent, gates deny actions. An agent under deadline writes an if chain next to the machine, and every individual diff looks locally reasonable.

Making it binding means a layer-2 AST rule in the sense of the gates note: within a designated directory, transitions of the relevant domain type may only be declared in a machine definition, and a handler that mutates that state outside one fails the PR. That is a ast-grep or Semgrep rule, and without it the constraint erodes in the direction of least resistance — which for a generative model is whatever shape its training data made most probable.

Where it earns its keep, and where it is ceremony

Worth it where the domain is genuinely state-shaped and the consequences are asymmetric: authentication and session lifecycle, checkout and money movement, multi-step onboarding, retry/backoff and circuit breakers, connection and subscription lifecycle, and agent loops themselves (functional-agent-architecture).

Not worth it for CRUD endpoints, rendering, data transformation, or anything whose “state” is just the value of a variable. Modeling those as statecharts produces ceremony that makes the code harder to read while verifying nothing anyone doubted.

The test is whether you can name the states without inventing them. If the states are obvious to a domain expert and currently implied by scattered booleans, the machine is recovering structure that already exists. If you have to invent state names to fit the formalism, you are adding structure rather than revealing it.

The general family

Statecharts are one instance of a recurring trade — narrow what can be expressed, and a checkable property falls out:

ConstraintExpressiveness given upProperty bought
SQL instead of arbitrary traversal codeimperative control flowquery planning, optimization, static analysis of access
Declarative IaC instead of setup scriptsarbitrary side effectsdiffable plans, drift detection, policy-as-code
Schemas instead of ad-hoc payloadsstructural freedomvalidation, compatibility diffs, codegen

Recognizing the family is the useful part: when a property keeps being expensive to check, the productive question is often not “which analyzer is strong enough” but “what would have to be true about the code’s shape for this to be trivial”.

The case against

  • It relocates the oracle problem rather than solving it. The machine definition becomes the specification. A machine that models the domain wrongly gets verified confidently and completely, which is a worse failure than an unverified implementation because it carries more authority. Everything oracle-problem-verification says about circular specifications applies unchanged.
  • State explosion under composition. Parallel regions and nested machines multiply states. “Finite” stops implying “small”, and the exhaustive path enumeration that made this attractive becomes intractable at exactly the complexity where you wanted it most.
  • Ecosystem risk is real. XState’s v4→v5 transition was a substantial breaking change, and the model-based-testing surface is the least-maintained part today. Constraining architecture around a library is a bet on that library.
  • The strongest version of the objection: most defects in web systems are not illegal-state-transition defects. They are wrong business logic inside a legitimate transition, and no amount of state-machine rigor touches those. The gain is real but narrower than the ceremony implies, and it is concentrated in the specific subsystems listed above rather than distributed across the codebase.
