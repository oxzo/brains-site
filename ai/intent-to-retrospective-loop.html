The Intent-to-Retrospective Loop

The development lifecycle this vault’s tooling serves runs from a stated intent through to a retrospective, and it is a loop, not a line: the retrospective feeds the next intent. Each stage has two distinct operations — produce the artifact (generative) and check the artifact (evaluative) — and when this loop was first mapped, the skill catalog was rich in checks and nearly empty of produces (gaps since closed — see Build order below). This note defines the loop, maps each stage to its skill (or names the gap), and specifies the data contract that lets the loop close. It is the conceptual anchor for the lifecycle-skill family, the way knowledge-base-entropy anchors the corpus-scan family.

The loop

The front half (① → ④) is production; the back half (⑤ → ⑦) is verification; ⑦ closes the loop by converting the cycle into lessons and scored predictions that inform the next ①.

The produce / check split

Every stage can be acted on two ways. The split is the whole point of this note, because it locates the thin side. (Design-time snapshot — the GAP cells were filled the same day; see Build order.)

The two keystones

Stages ⑥ and ⑦ were the missing pieces (both since built — see Build order), and they are the ones that make the ①–⑦ spine a loop rather than a line.

⑥ Intent-fulfilment check (proposed /intent-fulfilment-check)

Nothing currently asks “does this output actually serve the intent we started from?” intent-check audits the intent’s quality at the start; reviewers-map audits the output’s correctness at the end; neither connects the two. The check: take the originating intent (the ① artifact — an intent: line, a project Goal, a spec objective), take the produced output, and assess whether the output advances that target. The check flags silent goal-substitution (the work drifted to an adjacent, easier, or more interesting target) and partial fulfilment (correct but addresses only part of the intent). Distinct from intent-check (intent quality, no output) and the corpus-level intent-drift-scan backlog candidate (body-vs-stated-intent drift across many notes; this is one cycle, output-vs-intent).

⑦ Retrospective (proposed /retrospective)

The one genuinely generative skill on the spine — it produces lessons, it doesn’t evaluate an artifact. Its mechanism is resulting separation (Annie Duke, Thinking in Bets, 2018): separate decision-quality from outcome-quality so the cycle’s “lessons” don’t encode luck as validated process. The dangerous quadrants it surfaces:

  • good outcome / bad process — luck mistaken for skill; must not be encoded as a repeatable lesson
  • bad outcome / good process — a sound process wrongly abandoned after one bad roll

This is also where the loop pays its biggest dividend: the retrospective is the natural place to harvest predictions into the calibration log, which directly attacks the dormant-calibration-loop problem (the loop’s single empirical feedback mechanism currently holds one prediction). See the data contract below.

The ceremony trap (stages ② and ④)

“Generate a plan” and “generate tasks” look like generative gaps, but Claude already does both natively. A skill there is ceremony unless it forces a discipline Claude skips. When planning, Claude reliably skips two things: it collapses to one plan without generating alternatives, and it loses the thread back to ①. So a stage-② skill is worth building only if it forces option-generation + intent-traceability — produce 2–3 candidate plans, each explicitly traced to the intent, then collapse to one with the reason recorded (the judge-panel pattern). Decided 2026-05-29: build the disciplined stage-② generator on exactly this bar (proposed /plan-options); stage ④ (task-generation) stays native — its size is already covered by plan-split-scan and a separate task-generator would not clear the same bar. This applies the anti-sprawl guard from the catalog: a generative skill must force a discipline the default skips.

Stage ④ reopened 2026-05-29. The same-day call above (“stage ④ stays native — a separate task-generator would not clear the same bar”) was over-general: it settled the bar by domain when the bar is actually case-dependent. Walking the loop on two concrete cases — provisioning Pi-hole, and building an ESP32 + display Claude Code status companion — split cleanly:

  • Pi-hole (routine, narrow): done-criteria write themselves (nslookup <ad-domain> → 0.0.0.0); the one non-obvious item (a secondary DNS resolver letting clients silently bypass Pi-hole) is a branch → branch-resolve. A task-generator here is ceremony. The original “native is adequate” call holds.
  • ESP32 companion (novel, integration-heavy): native decomposition reliably skips three disciplines — (1) a falsifiable done-criterion per task written at creation time (reviewers-map checks this only post-hoc on the output, too late to shape the task); (2) the cross-task interface contract (the Claude Code hook’s payload schema vs. the device’s parser — built on both sides independently, the mismatch surfaced at integration); (3) risk-ordering (the one task that can kill the project sits last in narrative order instead of first as a spike: does a Claude Code hook reach a LAN device at all?). None of these has a home in plan-split-scan (size), branch-resolve (branches), or reviewers-map (post-hoc).

So ④ does clear the ceremony bar — but as a trigger-bounded skill (task-decompose), not a blanket one: fire on integration-heavy or novel work where done-criteria are non-obvious and tasks share a contract; refuse on routine, well-trodden work where native decomposition is already adequate. The Pi-hole case is the refuse-floor; the ESP32 case is the pass-ceiling — both halves of the Phase-0 dogfood gate fall out of this single walk.

The data contract

The loop only closes if ⑦ writes to the artifacts that feed the next ①. The contract:

  • Reads: the cycle’s intent (① artifact), the plan/tasks, the mechanical-verification result (⑤), and the intent-fulfilment readout (⑥).
  • Produces:
    1. Lessons — transferable claims phrased for reuse (not “this specific bug” but “this class of mistake”), each linked to where it would next apply.
    2. Resulting verdict — decision-quality vs outcome-quality per notable call, flagging the two dangerous quadrants.
    3. Calibration entries — any forward-looking claim the cycle made that is now resolvable, or any new bet worth tracking, formatted in the exact calibration-loop record schema (claim / resolves-by / criterion / confidence / domain / rationale / Resolution: PENDING).
  • Writes to: journal/calibration-log.md directly (auto-write, decided 2026-05-29) — the retro appends new PENDING prediction entries autonomously, no confirmation gate. The one safety property: it only appends new entries, never edits or resolves existing ones (the log is append-only by its own contract; resolution stays with calibration-loop resolve), and it echoes every appended entry in its output so the write is auditable. Optionally also appends to journal/commitments-log.md (overlap with commitment-ledger — the retro is the learning layer above the ledger’s accounting layer; they compose, the retro does not replace the ledger).

This contract is the load-bearing design decision: it is what turns “what we learned” from prose that evaporates into a scored prediction that compounds. Without the calibration write, ⑦ is just a nicer journal entry; with it, the loop has a memory.

Build order

All three built 2026-05-29 (SKILL.md + reference note under knowledge/ai/skills/ + decoupled /skill-trigger-audit dogfood each; all verdicts trigger-clean):

  1. ⑦ retrospective — the generative learning gap; revives the dormant calibration loop via the auto-write data contract. Built first; pinning its contract made ⑥ fall out.
  2. ⑥ intent-fulfilment-check — the loop-closer (output-vs-intent).
  3. ② plan-options — the disciplined plan-generator, built on the ceremony bar (option-generation + intent-traceability).
  4. ④ task-decompose (2026-05-29, reopening — see ceremony trap) — the disciplined task-generator, scoped by a refuse-on-routine trigger boundary; forces done-criterion + interface-contract + risk-ordering at generation time. Dogfooded on the Pi-hole (correct-refuse) and ESP32-companion (pass) cases; closes the last buildable produce-side cell.

The loop’s check stages were already in the catalog: ① intent-check, ③/④ plan-split-scan + branch-resolve, ⑤ reviewers-map. The loop is now fully instrumented end to end — produce side at ②④⑦, check side at ①③④⑤⑥. The only produce cells left empty (① intent-generation, ⑤ mechanical-verification) are empty by category: the human owns the intent, and verification is intrinsically a check.
