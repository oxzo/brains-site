Generative UI — Runtime Landscape and Evidence Base

Last verified: 2026-08-25 (npm registry + GitHub API queried directly; arXiv metadata via the arXiv API; spec, vendor, and ACM pages fetched same day, with paywalled ACM abstracts via tools/snapshot). Version, star, and status claims below decay fast. The libraries in the table shipped releases the same week this was written.

The vault already holds two narrow slices of this: a2ui-vs-json-render (one head-to-head, re-verified 2026-08-25) and ui-for-ai-products (streaming and failure affordances). Neither covers the field, and neither carries the research. This note is the anchor: the two axes that organize the space, the current runtime options, and what the evidence actually shows.

Scope boundary, kept sharp throughout: design-time builders (v0, Bolt, Lovable — a human prompts, a human reviews, code lands in a repo) are a different problem from runtime generative UI (an agent produces interface for an end user, live, with no human in the loop). They share a name and almost nothing else. Most confusion in this space is the two being discussed as one thing.

Two axes, not one

Every runtime approach answers what crosses the trust boundary. But what a failure costs depends on what the host is holding — and that second question does more predictive work than the first. Treating this as one axis is the common mistake, and it produces guardrail advice that is either ignored or over-applied.

Axis 1 — what crosses the boundary. CopilotKit’s 2026 developer guide splits it three ways (vendor-authored, and it positions CopilotKit as the answer at all three tiers); restated around the boundary rather than around their product:

TierWhat crossesThe model choosesCharacteristic failure
StaticNothing. A tool-call name + validated args.Which of your components to show, and with what dataWrong component; bounded and inspectable
DeclarativeA JSON tree naming components from a fixed catalogComposition and layout, within the catalogCatalog too narrow → generic output; too wide → unbounded surface
Open-endedHTML/CSS/JS, or a whole UI surfaceEverythingArbitrary code from a probabilistic source; XSS, exfiltration, silent side effects

Axis 2 — what a compromise costs. A browser tab in your own web app is a low-privilege host: the web’s threat model already assumes hostile content, and an escape costs you that tab. An IDE, a desktop AI client, or an agent shell is a high-privilege host holding SSH keys, tokens, and repo write access; an escape costs all of it.

Risk is the product of the two, not either alone:

Low-privilege host (browser tab, your web app)High-privilege host (IDE, desktop client, agent shell)
StaticThe baseline. Your components, your app.Agent shell rendering components you already audited.
DeclarativeCatalog-constrained genUI in a product.A2UI across a vendor boundary — catalog is the contract.
Open-endedGoogle Gemini’s generative UI. Presentational, no privileged actions. Survivable.MCP Apps in an IDE. The worst cell in the grid.

A third property sits on neither axis and decides whether that bottom-right cell is survivable at all: isolation quality. It is a mitigator, available at any tier, and it is where the real engineering is — see generative-ui-security.

This grid dissolves what otherwise looks like a contradiction later in this note: MCP Apps is the most open-ended thing here and has the most careful safety design in the space. Both are true because it occupies the worst cell. Predeclared reviewable resources, mandatory sandboxing, and auditable JSON-RPC are what that cell costs.

What this means for the guardrail everyone repeats

Practitioner guardrail lists near-universally open with “give the model a whitelisted component registry, not arbitrary HTML or JavaScript” — stated flatly, as a rule. The condition is what matters, and it is almost always omitted.

Google ships open-ended code generation to consumers and violates nothing: presentational surface, low-privilege host, no privileged actions. That is not a counterexample to the rule; it is the rule’s scope, made visible. Two failure modes, and they are opposite. Repeating the guardrail unconditionally gets it ignored, because a very large visible counterexample exists. Abandoning it because Google does otherwise throws away the cases where it holds. The grid above is the condition. Know which cell you are in before you decide the rule applies.

Version numbers carry more signal than stars here:

  • Tambo at 1.3.0 and CopilotKit at 1.69.0 are the only options here past 1.0. (142 and 1,120 published versions respectively.) Everything else is 0.x or a pre-1.0 spec. If a stable semver contract matters, that is the whole shortlist — and the two are not equivalent: Tambo is a dedicated generative-UI SDK, CopilotKit a broader agent-UI framework that includes generative UI.
  • AG-UI at 0.0.58 is a 0.0.x protocol despite Google/LangChain/AWS/Microsoft/Mastra/PydanticAI adoption claims and 15.5k stars. Adoption breadth and interface stability are independent; do not read one as the other.
  • A2UI’s v1.0 is still a “Candidate” — the same status it held at the 2026-06-12 verification in a2ui-vs-json-render. v0.9.1 remains the designated production release. A release candidate that has not landed in ~2.5 months is a mild negative signal, not a fatal one.
  • json-render moved 0.19.0 → 0.20.0 in that same window — one minor in ~2 months, against 29 versions in its first 5 months. Either the API is settling or attention moved. Still 0.x, still Vercel Labs.
  • json-render is not a React library, despite its own homepage. The site advertises “React & React Native”; the repo README and the published packages cover React, Vue, Svelte, Solid, and React Native from one catalog, plus non-DOM renderers for Next.js, PDF, email, Remotion video, React Three Fiber, terminal (Ink), and Satori images — all at 0.20.0, with Vue/Svelte/Solid on npm since Feb–Mar 2026. It also ships @json-render/mcp for MCP Apps hosts. Treating it as React-only understates its reach and is the specific error a2ui-vs-json-render carried until 2026-08-25; the marketing page is the least complete source about it.
  • CopilotKit is the mature one by age and volume (publishing since 2023) and is now the largest by stars. It also authored AG-UI, so “CopilotKit + AG-UI” is one vendor’s stack, not two independent endorsements.

Vercel AI SDK is at v7, not v6 — released 2026-06-25, a correction to what ui-for-ai-products currently states. v7 is positioned as an agent-runtime upgrade (typed per-tool contextSchema + toolsContext, WorkflowAgent durability, approvals, telemetry, first-class timeout config at total/step/chunk/tool granularity). Migration is npx @ai-sdk/codemod v7. Generative UI in the SDK remains the tool-call→React-component binding, i.e. the static tier.

MCP Apps — the one with a finished spec

SEP-1865 reached Final status on the Extensions Track (created 2025-11-21; authored by Ido Salomon, Liad Yosef, Olivier Chafik and six others; shipped as the first official MCP extension, per secondary sources, on 2026-01-26 — a date the ext-apps repo path specification/2026-01-26/apps.mdx corroborates).

It sits in the grid’s worst cell, open-ended content in a high-privilege host. The design answers that directly:

  • UI ships as predeclared resources under a ui:// URI scheme, typed text/html;profile=mcp-app — not embedded in tool results. The SEP is explicit that this was chosen over MCP-UI’s embedded-resource approach specifically so hosts can prefetch, cache, and security-review the HTML before anything runs.
  • Bi-directional traffic reuses MCP’s JSON-RPC, so every UI→host message is loggable and auditable rather than a bespoke postMessage channel.
  • Mandatory iframe sandboxing; hosts may require explicit user consent for UI-initiated tool calls.
  • Optional, negotiated, backwards-compatible.

The provenance is worth keeping. It unifies two prior systems, community MCP-UI (adopters cited in the SEP: Postman, HuggingFace, Shopify, Goose, ElevenLabs) and OpenAI’s Apps SDK (launched November 2025). This is the “UI runs inside someone else’s AI client” case, and it is the only one here with a finalized standard.

What the research actually shows

Six papers, all metadata confirmed against the arXiv API on 2026-08-25. A community index at awesomegenerativeui.com tracks ~28 and is a better entry point than any single reading list.

The capability is real — and it’s shipped

“Generative UI: LLMs are Effective UI Generators” (arXiv 2604.09577, Leviathan et al., Google; arXiv metadata reports 2026-02-24 — note the 2604 ID prefix would normally imply April, an inconsistency left unresolved. Author count is not stated here: the arXiv API returns 13 author nodes while the abstract page lists 12). Claims, verbatim from the abstract: results are “overwhelmingly preferred by humans over the standard LLM markdown output”; worse than human experts but “at least comparable in 50% of cases”; the capability is “emergent, with substantial improvements from previous models.” Releases PAGEN, an expert-crafted evaluation dataset.

The important part is not the paper — it is that Google shipped this before publishing it. The Google Research blog post (2025-11-18) predates the arXiv posting and describes it live in the Gemini app (dynamic view, visual layout) and in Search AI Mode for AI Pro/Ultra subscribers in the US. The implementation: Gemini 3 Pro, a server exposing tools (image generation, web search), heavy system instructions, and post-processing to fix common issues — generating HTML/CSS/JS that runs in the user’s browser. Stated limitation: generation “can sometimes take a minute or more.”

So the most visible consumer deployment of runtime generative UI is raw code generation with a post-processing cleanup pass — bottom-left cell of the grid above. Not a violation of the registry guardrail; outside its scope. Worth stating what is inference rather than fact: Google does not say “we ship this because the surface has no privileged actions.” That reading is mine, and it is the load-bearing assumption behind treating this deployment as safely replicable in a low-privilege host.

Two independent corroborations, so the capability claim does not rest on Google evaluating Google:

  • “Generative Interfaces for Language Models” (arXiv 2508.19227v3, Chen, Zhang, Zhang, Shao et al. — SALT-NLP; ACL 2026 Findings). LLMs respond by generating a task-specific UI rather than prose, via structured interface representations plus iterative refinement. Reports up to 72% improvement in human preference over chat, across a multidimensional framework covering functional, interactive, and emotional dimensions. Independent team, independent evaluation, same direction as Google’s result.
  • “The Keyhole Effect: Why Chat Interfaces Fail at Data Analysis” (arXiv 2602.00947, Mohan Reddy, 2026-02-01) is the mechanistic case, and the most useful framing here for anyone who has to justify the work. It argues chat degrades multi-step analytical tasks through five named mechanisms — content displacement defeating spatial memory, hidden state exceeding working memory (~4 chunks under load), forced verbalization triggering verbal overshadowing that degrades visual pattern recognition, linear text blocking epistemic action and cognitive offloading, and serialization penalties scaling with data dimensionality. Generative UI appears as one of eight proposed remedies. Note what this reframes: the argument for generative UI is not “prettier than markdown” but “markdown is a cognitive bottleneck for state-dependent work.” That is a falsifiable claim about tasks, which tells you where generative UI earns its cost — and by implication where it does not. It also connects the whole axis to cognitive-load-theory-for-ai and how-much-information-at-once.

The explanations are unreliable — measured

“Design Theater: Evaluating the Gap Between User-Facing Design Reasoning and Implementation in Generative UI Tools” (arXiv 2607.22928v2, Imteyaz et al., 6 authors, 2026-07-24, accepted at AAAI/AIES). The strongest result in the set and the one to actually act on.

24 benchmark tasks × 5 tools = 120 interfaces. Tools evaluated: ChatGPT, Claude, Firebase Studio, Vercel v0, and Bolt. Findings:

  • ~25% of user-facing design rationales are not implemented in the interface produced.
  • 34% for functional requirements.
  • Tools recognize roughly half the UX principles embedded in prompts (mean = 0.54).
  • Four of the five tools implemented ≤6% of functional principles.
  • Interfaces converge across tools in appearance and layout, varying mainly in color.

“Design Theater” names the failure precisely: “plausible and confident design rationales that have little relationship to the actual implementation.”

Note the scope carefully — these are design-time builders, not the runtime frameworks in the table above. The paper does not measure json-render or Tambo. What transfers is the mechanism, not the number: an LLM’s stated reasoning about its own UI output is not evidence about that output. That indicts one specific workflow, reading the rationale instead of testing the interface. It is the same generation-vs-verification asymmetry as cognitive-burden-of-ai-use and the oracle-problem-verification framing. The convergence finding also lands squarely on visual-ai-slop-fingerprints.

”Good UI” has no single ground truth

“Efficient Personalization of Generative User Interfaces” (arXiv 2604.09876, Peng, Das, Bigham, Wu — CMU/Purdue, 2026-04-10). 20 trained designers made pairwise judgments over the same 600 generated UIs. Average kappa = 0.25 — substantial disagreement among trained designers, and written rationales show they diverge on how they define and prioritize shared concepts like “hierarchy” or “cleanliness.”

This is the quiet load-bearing result for anyone building evals here. A fixed design rubric encodes one designer’s preferences and calls it quality. Their method instead represents a new user in terms of prior designers, and beat both a pretrained UI evaluator and a larger multimodal model. Direct read-through: an LLM-as-judge for UI quality inherits whichever designer population its rubric was written from. But do not over-read the disagreement — the paper’s actual contribution runs the other way. Low inter-rater agreement did not mean preference was arbitrary; their model learned it from sparse feedback and beat both baselines. The lesson is that “good UI” is learnable but not universal: a single fixed rubric asserting global quality is the thing that fails, while a judge calibrated to a named population can work. Pairs with llm-evaluation-methodology.

Accessibility — two separate bodies of work, deliberately not merged

There are two literatures here. They are often cited together as if one answered the other. They do not: they use different tools, tasks, output artifacts, metrics, and populations, and neither is positioned to confirm or contradict the other. Kept apart on purpose.

(a) Generation used as a remediation layer over existing pages

“Generative UI as an Accessibility Bridge: Lessons from C2C E-Commerce” (arXiv 2604.25455, Bektur Ryskeldiev, Mercari R4D / Univ. of Tsukuba, 2026-04-28) synthesizes six studies (2022–2025) with blind, low-vision, and older-adult users. Its ASSETS ‘25 browser extension used GPT-4o to restructure existing e-commerce HTML for screen-reader users; 15 screen-reader users rated three conditions:

ConditionOverall browsing experience (5-pt Likert)
Fully regenerated, text-only5.0
Tag-level reorganization (visual layout unchanged)4.57
Original Mercari site3.14

Median task-completion time fell from ~130 s to ~25 s. Semantic similarity between original and regenerated pages averaged 96.3% (range 91.60–99.36%), so content meaning was largely preserved. Scope: n=15 on one site class, and the author states the wider program’s samples run 8–15. This is a promising result on a narrow task, not a general finding about accessibility.

What makes this case tractable is structural and worth naming: the system has a source document to be faithful to, so fidelity is measurable, and it inherits content rather than inventing it. That property does not transfer to generation from a prompt.

(b) Accessibility of interfaces generated from a prompt

Three results, and they need their scopes attached — the headline number in particular is weaker than it reads:

  • “Generated Inaccessible: Measuring WCAG Violations in AI UI Design Tools” (W4A 2026). Reports 29.0% compliance across 21,880 assessments (color contrast 26.8%, use of color 19.2%), and 39% of AI violations needing “major redesign” versus 22% for manual. Read the scope before quoting the number: the tools are design-mockup tools (Figma Make, Google Stitch, Visely, UXPilot, Banani, SketchFlow AI) — not runtime generative UI and not code generation; the 54 participants were “primarily students and early-career designers”; and the five WCAG criteria were chosen because participants lacked the background to assess code-dependent criteria like semantic structure, keyboard operability, or ARIA correctness. So this is what novices could see by visual inspection of mockups, not a WCAG audit. It is real evidence about a real tool class, and it is not evidence about generated code.
  • “Measuring the Semantic Accessibility Gap in LLM-Generated Web UIs” (CHI 2026 EA, Calò et al.). The stronger result for our purposes, because it works at code level: 300 UIs from three frontier models (Claude, Gemini, GPT) yielded 541 semantic violations that pass automated checks — alt="image", “Click here” links. Detection by LLM-as-judge, validated by controlled fault injection at 80–92% recall, triangulated against four expert annotators over 324 components.
  • A11YN (arXiv 2510.13914, Yoon et al., Yonsei/SNU, 2025-10-15). RL (GRPO) against an axe-core-severity-weighted reward cut a Qwen2.5-Coder-7B baseline inaccessibility rate from 0.38 to 0.15 on RealUIReq-300, reportedly beating GPT-4.1 and Claude Sonnet 4. Those baselines are two model generations old — treat the comparison as historical and the method (severity-weighted automated signal as an RL reward) as the transferable part.

The one claim that survives from both

Not a synthesis of the two literatures — a finding each reaches separately about the same instrument. The automated accessibility gate is the wrong gate here. From (a): “every test page passed some automated audits while still failing real users.” From (b): an image with alt="image" “passes every check yet conveys nothing.” Axe-core’s ~30–40% WCAG coverage is already noted in ai-augmented-ui-development; the semantic-gap paper is direct code-level evidence that generated UI fails predominantly in the uncovered remainder. A green axe run on generated UI is weak evidence. See visual-verification-ai-ui and design-system-accessibility.

And one counterintuitive result, scoped to its tool class: in the W4A mockup-tool study, explicitly specifying accessibility requirements in the prompt decreased compliance — prompts naming 4.5:1 contrast, 44×44px touch targets, and no-color-alone did worse than prompts that did not. The authors read it as misalignment between how designers express accessibility and how these systems operationalize constraints. Whether it generalizes to code-generating models is untested. Within that tool class, “just put it in the prompt” is falsified.

The definitional work

“The GenUI Study” (arXiv 2501.13145v3, Chen, Knearem, Li — UCLA/Google/DeepMind, DIS 2025): 37 UX professionals across four roles, week-long mini-projects with journals and interviews. The field’s main empirical account of practitioner adoption, which is the axis relevant to design-side-ai-adoption-stall and designer-seat-under-ai.

“Towards a Working Definition of Designing Generative User Interfaces” (arXiv 2505.15049, Kyungho Lee, DIS 2025 companion): 127-publication review + 18 expert interviews + 12 case studies. Its definition is the useful export — humans and AI collaborate at design time to generate interfaces; users interact with AI-generated interfaces at runtime. That is the boundary this note opens with, and the reason to trust it is that a 127-publication review landed on it, not that this note asserts it.

The security surface

Extracted to its own note: generative-ui-security — the isolation stack flag by flag, what the MCP Apps spec actually mandates versus leaves to hosts, A2UI’s double-iframe pattern, and a review checklist. The short version, because axis 2 depends on it:

Where the host-privilege axis comes from. Backslash Security’s analysis of the 2026-07-28 MCP spec (published 2026-05-28), on MCP Apps rendering in IDE iframes:

“A sandbox escape in a tab costs you that tab. A sandbox escape here is a full IDE compromise.”

Vendor blog, architectural analysis, no disclosed exploit. The framing is the origin of axis 2; the mechanics are independently checkable and carry more weight.

The one mechanism to remember: the question is not whether allow-same-origin is set, it is whose origin the frame has. allow-scripts plus allow-same-origin gives no containment when the frame shares the embedder’s origin — it can reach the parent DOM or delete its own sandbox attribute. On a different origin the same pair is fine, and MCP Apps requires exactly that: “The Host and the Sandbox MUST have different origins”, and the Sandbox “MUST have the following permissions: allow-scripts, allow-same-origin.”

The spec is also more prescriptive than “mandates sandboxing and leaves the rest to hosts” — it specifies the sandbox-proxy contract, a mandatory CSP built from declared domains, and a restrictive default policy (default-src 'none', connect-src 'none') when an app declares none. On confirmation the Final spec is blunt: a View-initiated tool call is governed by a bare “MAY … subject them to further user approval.” A server cannot assume the host prompts. (An agent-invokes-app-tool direction with stronger language exists only in the draft — it is not in the shipped standard.) Either way, do not use the host’s confirmation UI as your authorization boundary; that is guardrail 3.

One scope trap worth carrying: the sandbox-proxy contract binds “if the Host is a web page” — so it does not bind for the Electron desktop hosts that make up the high-privilege case, where the spec prescribes nothing beyond “sandbox the iframe” and Electron’s own process controls do the real work. Detail and a corrections log in generative-ui-security.

Evaluating generated UI — what actually exists

“Evaluate task success, not screenshot plausibility” is easy to say. Three things now make it doable.

  • PAGEN — Google’s released dataset of expert-crafted reference results, from the Leviathan paper. Reference set, not a metric.
  • FlowEval (arXiv 2605.04165, Wu, Vaithilingam, Schoop, Nichols — Apple-affiliated, 2026-05-05). The most useful idea in the set. It measures whether a generated UI supports realistic interaction flows, by driving a computer-use agent through validated tasks on a real site and its generated analog, then comparing navigation traces with reference-based similarity metrics (e.g. dynamic time warping). Expert-evaluator study reports strong correlation with human judgment and better-aligned rankings than an MLLM-judge baseline. This is the closest thing to “task success, measured, at scale” — and note it evaluates behavior under interaction, not appearance, which is precisely the axis Design Theater found tools failing on.
  • LLM-as-judge, validated by fault injection — the semantic-accessibility method above: inject known faults, measure recall (80–92%), then trust the judge proportionally on unmodified samples. Worth stealing as a general technique for any LLM judge, well beyond accessibility. Pairs with llm-evaluation-methodology.

The constraint on all of it remains the kappa = 0.25 ceiling: trained designers agree with each other weakly, so a judge aligned to “human preference” is aligned to some humans. FlowEval partly sidesteps this by measuring flow support rather than design quality — a reason to prefer behavioral metrics where the task allows.

Cost and latency — the constraint nobody’s guardrail list mentions

Hard numbers, from the bridge paper’s ASSETS ‘25 study: full-page HTML regeneration took one to five minutes per page and consumed roughly 220,000 tokens per session. Google’s own blog concedes generation “can sometimes take a minute or more.”

The author’s conclusion is the one to carry: “For a screen reader user browsing quickly, minute-scale latency is a regression, not an improvement.” Practical deployment needs caching, smaller specialized models, or regeneration only on first visit. The companion failure from the same program runs the other way — an object-detection loop at every 100 ms for responsive audio framing, bounded by battery and thermal headroom, not by tokens.

Two design consequences:

  1. Generative UI has a latency floor that conventional UI does not, and it lands in exactly the range where interactive use breaks. This is a stronger argument for the static tier than any safety argument — the static tier renders your components at component speed.
  2. Output tokens are the expensive ones. A UI response is billed as output. Full-page HTML regeneration at ~220k tokens per session is not a rounding error, and it recurs per user per session. llm-cost-optimization applies directly.

Guardrails, and which ones survive contact

The standard list is sound but under-specified about when each item is load-bearing. Sharpened:

  1. Whitelisted component registry, not arbitrary markup. Non-negotiable when the generated surface can trigger actions, and non-negotiable when the host is high-privilege (IDE, desktop AI client, agent shell) regardless of actions — that is the trust inversion above. Google’s consumer deployment shows the rule is negotiable for a purely presentational surface in a browser tab; neither exemption transfers to an IDE. Be able to state which case you are in.
  2. Validate every prop (Zod / JSON Schema) at the render boundary. Cheap, catches malformed and partial streams, and is the mechanism structured-output-json-mode already covers.
  3. Separate rendering from authorization. The single most important item. Generated UI must never be the thing that authorizes a side effect — see vibe-coding-authorization-flaws for what this looks like when it fails. Confirmation gates on purchases, deletion, publishing, account changes.
  4. Deterministic fallback, on a latency budget. Text or conventional UI when generation fails, times out, or validates badly. Measured generation is one-to-five minutes for a full page — set the timeout from a real interaction budget and fall back, rather than letting the user watch a spinner. This is an availability requirement, not an error path.
  5. Persist the spec, the tool calls, the validation result, and the user’s action. Without it, a generative UI bug is unreproducible by construction. This is agent-audit-trails-provenance applied to the render path; MCP Apps’ JSON-RPC choice bakes it into the protocol.
  6. Test the stream, not just the output — malformed, partial, delayed, duplicated, out-of-order.
  7. Evaluate task success and workload, not screenshot plausibility. Design Theater and the kappa = 0.25 result are the two reasons: convincing-looking output and unreliable self-reported reasoning are exactly what these systems produce well. FlowEval’s trace-comparison approach is the concrete method; an MLLM judge scoring screenshots is the thing it beat.
  8. Do not treat a green accessibility audit as evidence. The load-bearing measurement is the code-level one: 541 semantic violations across 300 UIs from three frontier models, all passing automated checks. Automated a11y tooling covers the syntactic layer; generated UI fails predominantly in the semantic layer beneath it. Manual assistive-tech testing is not optional here in the way teams have learned to pretend it is elsewhere. (The 29.0%-compliance figure is about design-mockup tools assessed visually by novices — real, but not about generated code; don’t use it to carry this guardrail.)
  9. Give untrusted UI an origin that is not yours — either opaque (omit allow-same-origin) or a separate real origin behind a sandbox proxy, which is what MCP Apps mandates. With allow-scripts on your origin there is no containment at all. Full checklist in generative-ui-security.

Guardrail 7 deserves its own line: do not accept the model’s design rationale as evidence. It is the specific thing that was measured and found ~25–34% detached from implementation.

The failure record, such as it is. One documented content-integrity failure in a deployed system: the bridge paper’s HTML-regeneration extension silently dropped a link to an extended-warranty option on an Amazon product page while condensing promotional sections (the author’s own disclosure; mitigated with a semantic-similarity threshold and targeted link re-insertion). Plus a substantive security-analysis literature on the MCP Apps surface, architectural, with no disclosed exploit. This pass found no public post-mortem of a runtime generative-UI system attacked or failing at scale, and no CVE against MCP Apps or A2UI; that is a statement about what one search pass found, not about what exists.

The dropped-warranty-link failure is worth holding onto as the canonical shape: not a crash, not a refusal, not a visible error — a silent omission inside output that looked entirely correct. That is what generative UI failure looks like, and it is invisible to every automated gate in the stack.

How to choose

Answer the two axis questions first — they narrow the field faster than any feature comparison.

1. What must cross the boundary? If your components can express the output, nothing needs to. 2. What is the host holding? If it holds credentials, treat every open-ended option as a security project, not a UI project.

The static tier is the default, and the burden of proof is on leaving it. That is a claim about the state of the field on 2026-08-25 — generation latency measured in minutes, an unresolved security surface in privileged hosts, and a measured accessibility regression. Each is a thing the field is actively optimizing. Re-examine the default when any one of them moves, rather than treating it as a principle; it is a reading of current evidence, not a law.

The version-dependent claims decay fastest of anything here, and they drive several rows above: which projects are past 1.0, which specs have landed, which npm majors are current. Re-query npm and the spec sites before relying on them. A single release changes the answer.
