Three-Level Repository Documentation: docs, ADR, intent

A plan for layering three kinds of documentation into a code repository, each answering a different question at a different altitude. Two of the three — docs and ADR (architecture decision records) — are established practice; the third, per-file intent, is an explicit hypothesis being tested here, not a settled standard. This note is the methodology and the rollout plan; it is language-agnostic and meant to be adapted per repo.

It assembles existing vault material rather than inventing new theory: clear-intent-as-anchor (the four-axis test for whether an intent does real work), intent-engineering-discipline (the same anchoring move at repo scale), architecture-decision-records-ai (the ADR layer), ai-friendly-repo-structure §4 (the docs layer), and the intent-to-retrospective-loop / /intent-fulfilment-check machinery (the drift check).

The three levels

Each level answers a distinct question. The unifying idea (clear-intent-as-anchor): state the target so the rest can be checked against it — at three altitudes.

LevelQuestion it answersAltitudeLifetimeLives where
docsWhat does it do, and how do I use/build/operate it?repo / packageliving, present-tenseREADME, llms.txt/AGENTS.md, agent_docs/, API docs
ADRWhy was this decision made, over which alternatives?one decisionpoint-in-time, append-only statusdocs/adr/NNNN-*.md
intentWhat is this file for — what would be lost if it vanished?one fileliving, edited with the filea marker inside each source file

The gap intent fills: code shows what it does; docs explain how to use it; ADRs explain why a choice was made. Nothing at the file level states what this unit is supposed to accomplish, such that drift away from that purpose can be noticed. That missing fine-grained anchor is the hypothesis this plan tests.

How the three stay distinct (anti-duplication):

  • intent ≠ docs. Intent is the file’s one-line target, for drift-checking and navigation — not usage instructions. Usage goes in docs.
  • intent ≠ ADR. An ADR is written once and records a decision; a file’s intent is read every session and moves with the file. A file’s intent may cite an ADR (implements ADR-0003) but does not restate it.
  • docs stays durable. Describe behavior and interfaces, not file paths or line numbers (.claude/rules/bias-aware-authoring.md rule 7); paths rot on the next refactor, behavior survives it.

The file-intent hypothesis (the unsettled part)

Hypothesis: a one-line intent on (nearly) every source file produces enough value — agent navigation, drift detection, a forcing function against dead/bloated files — to justify the authoring and maintenance cost.

Why it might pay off:

  1. Agents see code, not intent — the same argument that makes ADRs matter more in AI-assisted repos (architecture-decision-records-ai §1), pushed down to the file. A file-intent tells an agent what a file is for before it spends context reading 400 lines.
  2. Drift detection at file grain. /intent-fulfilment-check asks “does this output still serve its stated intent?” Run per-file, it catches scope creep, god-objects, and files that quietly became something else.
  3. A deletion test. If you can’t write a non-trivial intent for a file, that is evidence the file shouldn’t exist (the deletion test from /deepen-architecture).
  4. Navigation. Grepping intents finds “the file that does X” faster than reading directory trees.

Why it might not (failure modes, surfaced deliberately):

  • Intent theater. Most file intents on trivial files will restate the filename — @intent: handles auth on auth.ts. That is noise, and noise trains readers to ignore the marker that matters (clear-intent-as-anchor “Theater” failure mode). Intent theater is the dominant risk of the all files choice, and the main reason the layer is a hypothesis rather than a recommendation.
  • Granularity mismatch. Many files are too small to have an intent distinct from their module’s. Per-file may be the wrong unit; per-module may be right. (This is the open question — see Phase 5.)
  • Drift / rot. The intent goes stale as the code moves. Mitigation: phrase it as a durable target, not an implementation description (rule 7 again).
  • Distributed maintenance cost. Every substantive file edit may need an intent edit; the cost is small but paid constantly, and the benefit is diffuse and hard to attribute back.

Form discipline (from the four-axis test, clear-intent-as-anchor): an intent is a target, not a description. “the file that resolves a raw config blob into a validated, typed settings object” works; “config code” does not. Run the Form axis on a sample of intents during the hypothesis review — if they read as filename restatements, the layer is theatrical and the pre-registered fork in Phase 5 fires.

How to implement file-intent

Mechanism — in-file header marker (recommended). A single canonical, greppable token at the top of each file:

Compared against the alternatives:

MechanismCollocationSurvives refactorCI-greppableDrift risk
In-file header marker (recommended)✅ with the code✅ moves with the file✅ one regex finds allmedium
Docstring / KDoc / JSDoc tag✅✅✅medium
Sidecar file (foo.ts + foo.intent.md)✗ scatters, doubles file count✗ orphans easily✅high
Central registry (INTENTS.yaml)✗ far from code✗ stale on any rename✅ easiesthighest

The header marker wins on the axes that matter for AI-assisted repos: collocation (keep what an agent needs in one place — ai-friendly-repo-structure §2), durability (it moves when the file moves, unlike a path-keyed registry), and greppability (the presence gate is a single regex). Use one token across all languages so a single scan finds every intent regardless of comment syntax. A docstring tag is a fine variant where the language’s doc tooling should pick it up; sidecars and registries are not recommended — they drift worst and fight collocation.

Enforcement — presence + drift (the chosen level). Two gates, deliberately split by cost and trust:

  1. Presence gate — deterministic, cheap, blocking. A script scans tracked source files; any non-exempt file missing the marker fails CI (and a pre-commit hook). This is grep-level and maps to the deterministic Layer-1/Layer-3 gates in ai-friendly-repo-structure §5. Maintain an explicit exemption list: generated code, vendored/third-party, config, test files, barrel/index files, and trivially short files. The exemption list is itself a load-bearing artifact — record its rules in the establishing ADR.
  2. Drift gate — LLM judgment, periodic, advisory. A scheduled job (not per-commit — too costly) runs /intent-fulfilment-check at file granularity over files changed since the last run: does the file still serve its stated intent? It flags Drifted / Over-built / Substituted and emits a report or PR comment for a human to triage. It is advisory, not blocking, because LLM judgment is not a deterministic oracle (oracle-problem-verification). Scope it to changed files to bound token cost (agent-context-budget-as-admission-control).

Sequence matters: stand up presence first, add drift once the marker is habitual. The drift gate is the expensive, less-proven half — and it is also the instrument that falsifies or validates the whole hypothesis, so it is where the evidence comes from, not where you start.

Phased rollout

PhaseDeliverableRisk
0 — Decide & dogfoodWrite ADR-0001 establishing this system: the canonical @intent token, the exemption rules, the per-file granularity bet and its fork condition. This ADR is the gold-standard example for the ADR layer.low
1 — docs layerREADME (human), llms.txt or AGENTS.md (machine), agent_docs/ progressive-disclosure files, an empty docs/adr/ with template.md. Mostly known practice (ai-friendly-repo-structure §1, §4).low

3 — intent presence gateConvention doc + exemption list + presence-check script wired into pre-commit and CI. Apply to new and changed files first; backfill existing files opportunistically rather than in one big-bang pass.medium
4 — intent drift gateScheduled per-file /intent-fulfilment-check over changed files, advisory output. This is the hypothesis’s measurement instrument.medium
5 — review the hypothesisAfter a set period / N PRs, run the validation signals below and decide: keep all-files, fall back to per-module, or restrict to public-interface files. Record the outcome as a new ADR.—

Validating the hypothesis (Phase 5 criteria)

Pre-register what would change the decision, so the review is evidence-driven rather than vibes (clear-intent-as-anchor axis 2; /calibration-loop):

  • Falsified if: a Form-axis sample shows intents are mostly filename restatements; the drift gate rarely fires meaningfully; authors route around it; the intents are demonstrably never read.
  • Validated if: the drift gate catches real scope-creep / dead-file cases; agents demonstrably navigate faster; the deletion test removes real cruft.
  • Pre-registered fork: if per-file proves theatrical on small files, fall back to per-module intent (one per package/directory) plus per-file intent only on public-interface files. Both fallbacks were live options at the start; the bet is that all-files beats them, and Phase 5 is where that bet resolves.

Authoring the docs themselves

ADRs and docs are a high-stakes hallucination surface — written once, read for years (architecture-decision-records-ai, solo-developer-ai-stack). Any AI-drafted ADR gets /bias-scan-ai before commit; load-bearing decisions (auth, persistence, deployment topology) get /red-team. See .claude/rules/bias-aware-authoring.md.
