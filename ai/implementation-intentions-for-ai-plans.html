Implementation Intentions for AI Plan Execution

An implementation intention is a conditional plan in the form “if situation Y occurs, then I will initiate response Z” — distinct from a goal intention, which specifies the desired outcome (Gollwitzer, 1999). The framework was developed in self-regulation research to explain why goal intentions on their own often fail to produce action: the unresolved gap between intention and execution is closed by binding the when, where, and how of the response to an explicit environmental cue.

This note ports the framework to AI plan design. Implementation intentions are the structural upgrade for Signal 3 of the plan-split-scan (decision branches): an unresolved branch in a plan should be either resolved up front, split into its own plan, or expressed as an implementation intention. Anything else is a bet that the executor will figure out the branch correctly at run-time — a bet that loses more often than the planner expects.

The framework (Gollwitzer)

Two distinct planning constructs, working at different levels:

ConstructFormFunction
Goal intentionI intend to achieve XNames the desired end state. Necessary but not sufficient for action.
Implementation intentionIf situation Y occurs, then I will initiate response ZSpecifies the conditional execution. Binds behavior to a trigger.

Implementation intentions are subordinate to goal intentions — they don’t decide what to do, only when/where/how to execute it. In human self-regulation, the mechanism is offloading the moment-of-decision from deliberative control to environmental cues: when the trigger fires, the response is initiated automatically, without re-deliberation.

Empirically, supplementing a goal intention with implementation intentions produces meaningful behavior-change effects. Gollwitzer & Sheeran’s (2006) meta-analysis of 94 studies reported a medium-to-large effect size (d ≈ 0.65) for goal attainment when implementation intentions were added — across health behaviors, academic tasks, prejudice-control, and other domains. The effect is robust enough that implementation-intentions interventions are now standard tools in clinical behavior-change practice.

Why this matters for AI plans

LLMs and agents don’t have willpower failures, but they have structural cousins: context drift, branch-collapse, and default-policy fallback. The same conditional-binding move that solves the human intention–behavior gap addresses these for AI execution.

Context drift

On long plans, the executor’s attention erodes (lost-in-the-middle / position bias). Decisions that depend on plan-level reasoning made early in context can be silently lost by step 10. An implementation intention binds the decision to a local trigger at the point of use rather than relying on the executor to maintain global state.

Branch-collapse

When an LLM encounters an unresolved if/then in a plan, it tends to pick one branch and proceed — usually the most common or training-data-typical one. Counterfactual branches are silently flattened. An explicit implementation intention forces the branch to remain open and deterministic at execution time (if X, then route to subagent Y with payload Z; if not-X, then return to user for confirmation).

Default-policy fallback

Underspecified responses (“handle the error appropriately,” “deal with the edge case”) collapse onto the model’s training-data prior for that phrase — which may bear no relation to your actual intent. The implementation-intention form forces the response to be operationalized as a specific action against a specific trigger.

The conditional template

IF <trigger>: <observable, deterministic, falsifiable signal>
THEN <response>: <specific action, named tool, named subagent, or explicit return-to-user>

Both halves must pass strict tests:

Trigger criteria. The trigger must be:

  • Observable by the executor at the moment of decision (not a future state, not a global property)
  • Deterministic — same input maps to same trigger-firing decision
  • Falsifiable — a clear “yes the trigger fired” or “no it did not” verdict, not a feel

Vague triggers (“if something feels off,” “if the result looks wrong”) are not implementation intentions — they’re verbal hedges. Re-formulate or drop.

Response criteria. The response must be:

  • Specific — named action, named tool call, named subagent, named output
  • Executable by the executor as currently configured (don’t reference a tool the agent doesn’t have)
  • Bounded — has a clear termination, so the response doesn’t recursively expand into its own plan

A response that is itself a multi-step plan should not be smuggled into a then-clause. Either inline it, or have the response be escalate to a separate plan.

Worked examples

Bad (un-operationalized branch)

If the existing migration works, modify it; otherwise rewrite it.

The trigger (“works”) is not observable until the executor checks; the response (“rewrite”) is itself a plan. This is Signal 3 of the plan-split-scan in pure form — an unresolved branch the executor cannot collapse without doing the check first.

Better (resolved up front)

Run the check before issuing the plan, decide which branch, and issue the resolved plan. Eliminates the conditional entirely.

Better (implementation intention)

Step 1: Run pytest tests/migration_test.py. IF all tests pass: continue to step 2 (modify migration in place, see spec section A). IF any test fails: STOP. Return the failing test names to the user and request a decision (modify-with-fix or rewrite path B).

The trigger is observable (test exit code), deterministic (same input → same verdict), and falsifiable (pass/fail is binary). The response is specific (named tool, named output, explicit return-to-user on the negative branch). The branch remains open until the trigger fires.

Better (split into separate plans)

Issue the test-run as its own plan. Receive the result. Issue the appropriate downstream plan (modify or rewrite) based on the result. Highest verification leverage, highest coordination overhead — pick this when the branch is high-stakes or the two downstream paths are large.

Mapping to the plan-split-scan signals

Implementation intentions interact with multiple signals of the plan-split-scan:

  • Signal 3 (decision branches) — the direct mapping. Every unresolved branch should be: resolved up front, split into its own plan, or expressed as an implementation intention. “We’ll figure it out when we get there” is none of those. Prefer the first two as defaults; the conditional form is the fallback (see the corrective under Counterargument).
  • Signal 2 (state-carry depth) — implementation intentions reduce state-carry by binding the decision to a local trigger rather than a global decision made earlier in the plan.
  • Signal 4 (verification seams) — a well-formed implementation intention is itself a verification seam (the trigger evaluation is a natural pause point).
  • Signal 5 (reversibility boundary) — never wrap a destructive operation in an implementation intention. The conditional-form invites the executor to fire it without the explicit user-confirmation gate. Destructive operations remain hard splits.

Failure modes specific to LLM execution

In human self-regulation, implementation intentions work through an automatic, cue-driven response; that mechanism translates imperfectly to LLM context. Four concrete failure modes:

Trigger ambiguity. The trigger is observable in principle but ambiguous in execution. “If the build fails” — what counts as failing? Non-zero exit code? Warning count above threshold? Both pass and known-flaky test list non-empty? Either pin the trigger precisely or expect non-deterministic branching.

Response under-specification. “Then handle the error” collapses onto the model’s training-data prior for error-handling, which may be silent-swallow, retry-forever, or some other default that doesn’t match intent. Name the action.

Compound conditionals as deferred planning. A chain of if A then if B then if C then … is not an implementation intention — it’s a plan with branches the planner failed to resolve, hidden in conditional syntax. Each nested branch should resolve to a single trigger/response pair or split into its own plan.

Run-time trigger evaluation drift. The LLM evaluates the trigger differently than the user intended (e.g., evaluates “passes” more loosely on a test the planner cared about being strict). If the trigger evaluation is itself load-bearing, instrument it externally (run the test, capture exit code, pass it back into the plan) rather than asking the LLM to evaluate.

Related cognitive-science context

The Gollwitzer framework sits in a broader literature on goal hierarchies:

  • Goal intentions (what to achieve) are necessary but insufficient. Studies find that goal-intention-only conditions produce significantly less follow-through than goal-intention-plus-implementation-intention conditions across many domains.
  • Distal goals are protected from intention–behavior gap erosion by proximal implementation intentions. This pairs with the concrete-subgoals pillar (Locke & Latham 1990; Bandura 1977) — concrete subgoals provide the what; implementation intentions provide the when/how of executing them.
  • Self-regulation depletion (Baumeister’s ego-depletion line of work) was the original problem the framework solved; the framework’s empirical robustness has held up better than ego-depletion itself, which suffered replication issues (Hagger et al. 2016, multi-site replication finding no significant depletion effect). The if-then mechanism’s empirical base is independent of whether ego-depletion as a construct survives.

Tradeoffs and context-dependence

  • The cost is up-front planning effort. Implementation intentions move work forward in time — you have to anticipate triggers and pre-specify responses. This is real cost; it’s worth paying when the consequences of the branch are non-trivial.
  • They are not universal. For plans with one concern, deterministic flow, and no branching, implementation intentions add nothing but ceremony. Use them where Signal 3 fires.
  • They compose with the falsifiability scan. A well-formed implementation intention is essentially the operationalization checklist (falsifying observation, measurement, deadline) packaged as a conditional. The two skills can fire together: /falsifiability-scan on the trigger phrasing, /plan-split-scan on the structural placement.

What this doesn’t cover

  • Trigger detection by the LLM itself. This note assumes the trigger evaluation is reliable. For triggers where the LLM might mis-evaluate (vague natural-language conditions, subjective quality judgments), externalize the trigger evaluation to a deterministic check (exit code, test result, schema validation) before relying on the if-then form.
  • Multi-agent if-then routing. When the response is “route to subagent Y,” the question of which subagent is itself a planning problem this note doesn’t address. The named subagent or named tool is the boundary — picking it is upstream.
  • State machines and finite-state plans. When a plan grows beyond ~3 independent conditionals, it’s a state machine and should be modeled as such. Implementation intentions are the syntax for single conditional choices; they don’t replace formal state-machine specification for genuinely stateful workflows.

Counterargument

The strongest objection: if-then conditionals can become a syntactic veneer that hides un-resolved planning rather than resolving it. A plan with twelve nested conditionals is not “twelve implementation intentions” — it’s an unresolved plan with branches the planner failed to think through. The framework’s empirical strength in human self-regulation depends on the conditionals being few and cue-driven; ported to AI plans, the same constraint holds. If implementation intentions become a way to avoid the discipline of resolving branches up front, they have failed in the same way that always-breaking-it-down-further can produce over-decomposition (see the over-decomposition counter).

The corrective: prefer resolved up front and split into separate plans over implementation intention as defaults; reach for the conditional form only when neither alternative is feasible (the trigger genuinely cannot be evaluated up front, and the two downstream paths are similar enough in scope that splitting would duplicate setup).
