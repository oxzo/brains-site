BDI Architecture for Coding Agents

Belief-Desire-Intention (BDI) is a cognitive architecture for rational agency from late-1980s/early-1990s AI research. Its enduring contribution is the separation of deliberation from means-ends reasoning — deciding whether the current goal is still the right goal is a different activity from deciding the next step toward it, and conflating them is a known failure mode. That separation is directly relevant to LLM coding agents, which routinely either re-deliberate constantly (losing forward momentum) or commit to stale plans (continuing past the point where the goal no longer holds).

This note ports the BDI vocabulary to LLM coding agents and flags what doesn’t transfer cleanly. It is not a claim that classical BDI systems should be rebuilt — they were planning systems, not natural-language ones. The vocabulary is the value: it gives precise names to four moving parts in an agent loop that are otherwise lumped together.

The four parts

The classical BDI decomposition, mapped to a coding agent:

BDI constituentClassical definitionCoding-agent realisation
BeliefsInformational state — what the agent takes to be true of the worldRepository state (AST, dependency graph, file contents), retrieved documentation, observed tool outputs
DesiresMotivational state — outcomes the agent is oriented toward, possibly conflictingGoals from the user / spec (“refactor X to use Y”; “maintain backwards compatibility”)
IntentionsCommitted-to subset of desires the agent is actively pursuingActive execution threads, the current plan, scheduled tool invocations
EventsExternal triggers for belief revisionTest failures, lint errors, compilation errors, user redirection, file watcher signals

The agent loop, classical-BDI flavour:

  1. Observe environment → update beliefs.
  2. Evaluate desires against current beliefs → select an intention via deliberation.
  3. Use means-ends reasoning to pick the next action toward the selected intention.
  4. Execute. New observations and events feed back to step 1.

Most LLM agent loops today collapse all of this into a single autoregressive turn. The BDI lens is useful precisely because it names where the collapse happens.

Why the deliberation / means-ends split matters

Deliberation answers: is the currently committed intention still the right one given updated beliefs?

Means-ends reasoning answers: given the currently committed intention, what’s the next step?

Two failure modes when the split collapses:

  • Plan staleness. The agent commits to a plan, executes step-by-step, observes that the underlying belief that justified the plan no longer holds (e.g., a test it relied on was deleted), and continues anyway because nothing triggered re-deliberation.
  • Decision thrash. The agent re-deliberates on every step, never building forward momentum, often switching plans on noisy signals (one flaky test, one unhelpful tool result).

Classical BDI handles this trade-off with commitment strategies (Rao & Georgeff): blind, single-minded, open-minded — corresponding to never re-deliberate, re-deliberate when blocked, re-deliberate when anything changes. LLM coding agents face the same trade-off without typically naming it. The choice is a tuning parameter.

The hallucinated-beliefs problem

The single most important failure mode when porting BDI to LLM agents: beliefs formed from parametric memory are not grounded.

A classical BDI agent’s beliefs were a structured knowledge base — the agent literally could not believe something not in the KB. An LLM agent’s beliefs leak from training data: it will confidently assert that a library exists, a function is named X, an internal API accepts argument Y — none of it true for the actual repository. Those beliefs then become preconditions for intentions, and the intentions become plans, and the plans fail in ways downstream of the original ungrounded belief.

The structural fix is to decouple belief formation from parametric weights and tether it to verified retrieval:

  • AST-derived facts (the actual call graph, the actual import tree) — not LLM-summarised descriptions of code.
  • Metadata-filtered retrieval over docs, not raw vector search (which returns semantically similar but possibly outdated/wrong material). fine-tuning-vs-rag discusses the broader retrieval choice.
  • Capability-checked tool invocations — if the agent’s “belief” is that tool T exists, the runtime confirms or rejects this before the intention forms. See functional-agent-architecture on typed effects and capability tokens.

In other words: beliefs that are load-bearing for an intention must come from a source the system can verify, not from the model’s internal continuation.

Where BDI vocabulary helps in a real coding-agent pipeline

The BDI separation suggests questions worth asking of any agent design:

  • Where do beliefs come from? If the answer is “the model decides,” the system is one ungrounded continuation away from a hallucinated belief becoming an intention becoming an action.
  • Are conflicting desires resolved up front, or at execution time? Resolving at execution time means the agent might pick either branch depending on which retrieved chunk hit attention first. Up-front resolution is what a good intent spec does (see intent-engineering-discipline).
  • What triggers re-deliberation? “Never” → stale plans. “Anything” → thrash. Pick deliberately. Test failures, lint errors, and user interrupts are the usual concrete triggers; everything else stays in means-ends.
  • What is an intention’s commitment level? A single tool call? A multi-step plan? Until the next observation? Until the user redirects? This is the commitment-strategy question, and the answer shapes the whole loop.

What BDI doesn’t solve

  • Deterministic reasoning — LLM token sampling is stochastic; BDI vocabulary doesn’t change that. It only helps name where stochasticity becomes a problem.
  • Belief grounding by itself — BDI says beliefs should be grounded; it doesn’t say how. The how lives in retrieval, verification, and capability systems (functional-agent-architecture, fine-tuning-vs-rag, ai-verification-stack-web).
  • Multi-agent coordination — BDI was originally single-agent. Distributed-BDI (dMARS, d’Inverno et al. 1998) extended it, but the topology choices in multi-agent-coordination-topologies aren’t pre-decided by adopting BDI vocabulary.
  • The empty middle of LLM reasoning — BDI assumes the means-ends reasoner can compute “the next action to achieve intention I.” For complex coding tasks, the LLM is the reasoner, and its competence at that step is the central question — BDI doesn’t answer it.

Tradeoff: vocabulary vs. ceremony

The risk in adopting BDI vocabulary for LLM agents is ceremony — wrapping a normal tool-calling loop in B/D/I/E labels without changing behaviour. The vocabulary is worth carrying only if the labels make a real distinction visible:

  • A field labelled beliefs should be grounded by mechanism, not just renamed context.
  • A field labelled desires should expose conflicts; if there’s only one desire, just call it the goal.
  • A field labelled intentions should be revisable on events; a frozen plan is just a script.
  • An events channel that doesn’t actually trigger re-deliberation is decoration.

When the labels stop adding distinction, drop them.

The recent (2026) literature on BDI-LLM hybrids is emerging and not yet citation-settled (e.g., grounding LLM beliefs via retrieval, hallucinated-belief problem). Treat compound-named “BDI + X” frameworks in current AI writing with the same scepticism as other fingerprints of AI-synthesised text — the underlying questions (where do beliefs come from, what triggers re-deliberation) are real; the specific named methods often are not.
