Cognitive Load Theory for AI Prompts and Plans

Cognitive Load Theory (CLT) decomposes the mental effort demanded during learning or problem-solving into distinct sources, against a fixed working-memory bottleneck (Sweller, 1988; Sweller, van Merrienboer & Paas, 1998). The framework originates with John Sweller’s work in the late 1980s and was developed for instructional design; this note ports its diagnostic vocabulary to AI prompt and plan design.

The bridge is not literal — LLMs do not have a Baddeley-style working memory; the binding constraint is attention dilution within the context window rather than a separate short-term store. But the three-load taxonomy is structurally portable: AI executors face load from the inherent difficulty of the task, from the form in which the task is presented, and from the productive synthesis work itself. Naming the three lets prompt and plan designers diagnose which kind of load a failure traces to and apply the right corrective.

The three load types (canonical formulation)

TypeSourceProperty
IntrinsicThe inherent difficulty of the task or material — irreducible, set by the problem itself given the executor’s prior knowledgeCannot be eliminated; can only be staged or scaffolded
ExtraneousThe form, presentation, or organization of the task — load that does not contribute to solving the problemEliminable; the primary target of prompt and plan improvement
GermaneThe productive cognitive effort dedicated to schema-building, pattern-recognition, and integrationProductive; the load you want the executor spending capacity on

Working memory capacity is bounded — the classical figure of ~7±2 items (Miller, 1956) has been revised downward to ~4±1 for unrelated items (Cowan, 2001). When the sum of intrinsic + extraneous + germane load exceeds capacity, performance collapses non-gracefully.

Important note on the framework. Sweller and collaborators substantially revised the three-load formulation in later work (Sweller, Ayres & Kalyuga, 2011; Sweller, 2010 onward), reconceptualizing germane load as a redistribution of working-memory resources to intrinsic-load processing rather than a separately measurable third type. This note uses the three-type vocabulary because it remains the most useful descriptive frame for design decisions, while flagging that the underlying construct is contested even within CLT research. Treat the categories as diagnostic labels for design, not as separately quantifiable load measurements.

The LLM mapping

The structural analogs hold. The mechanism differs.

Intrinsic load → problem difficulty for the executor

The task’s irreducible complexity given the LLM’s pre-trained capabilities and the in-context information available.

  • Asking GPT-4 / Claude / equivalent to do arithmetic on six-digit numbers is high intrinsic load (the operation is poorly represented in training)
  • Asking the same model to summarize a paragraph is low intrinsic load (well-represented operation)
  • A reasoning task that requires holding three independent constraints simultaneously is high intrinsic load on attention-allocation

You cannot reduce intrinsic load by reformatting the prompt. You can stage it (chain-of-thought, multi-step plans, scratchpads) — which converts what looked like high intrinsic load into a sequence of lower-load steps each within capacity.

Extraneous load → load from prompt form, not content

The portion of working-memory / attention budget consumed by how the task is presented, not by the task itself. Sources:

  • Repetition — the same context restated multiple times across a plan, forcing the executor to re-parse it each time
  • Irrelevant ceremony — boilerplate, system-prompt cruft, retrieval noise, verbose XML markup that doesn’t carry task information
  • Bad ordering — task statement after the context it operates on, or task scattered across the prompt
  • Format mismatches — natural-language description of what should be a table; code presented as prose
  • Position-bias-vulnerable layout — load-bearing instructions in the middle of a long prompt where lost-in-the-middle applies

Extraneous load is the primary actionable target of prompt engineering. Most “the model didn’t follow my instructions” failures trace here.

Germane load → productive synthesis

The cognitive work that actually produces the output — pattern recognition, integration of context with the task, generation of the answer. For LLMs, this is the next-token-prediction process operating over the active context.

You want maximum capacity available for germane load. The path is: reduce extraneous load aggressively, stage intrinsic load when it exceeds capacity, don’t try to “increase germane load” — that’s not a thing you control directly; you control what capacity remains for it.

Chunking — pre-existing schemas expand effective capacity

In human CLT, chunking — organizing disparate elements into a single Gestalt — is the mechanism by which experts process material that overwhelms novices. A grandmaster sees a chess position as a few high-level structures (open file, weak square, attacking formation) where a novice sees 32 individual pieces. The chunk is a single working-memory item; the schema is the long-term-memory structure that produces the chunk.

The LLM analog is well-established empirically: prompts that cue an existing model schema (named pattern, well-known framework, canonical example) execute better than prompts that describe the same structure from scratch. “Apply the Strategy pattern to this code” cues a pre-trained schema; “Create classes such that…” forces the model to reconstruct the same structure from primitives. The first prompt has lower extraneous load not because it’s shorter, but because it leverages a chunk the model already holds.

The corollary: a prompt that uses vocabulary the model doesn’t have a chunk for pays extraneous load for the same task. Stylistic conventions specific to your codebase, jargon from a narrow domain, or invented framework names all force the model to reconstruct schemas from primitives — extraneous load that should have been eliminated. Either use the canonical vocabulary, or lift the schema definition once at the top of the prompt rather than implicitly assuming it.

The granularity paradox

The same load decomposition explains why both under-decomposition and over-decomposition fail — they fail through different load types.

Decomposition stateFailure load sourceSymptom
Monolithic (zero decomposition)Intrinsic load exceeds capacityAttention drift, confabulated state-carry, “the agent did the wrong thing on step 8”
Optimal (intermediate)Germane load maximized for capacityClean execution; verification checkpoints land at natural seams
Hyper-granular (over-decomposition)Extraneous load exceeds capacityEach step re-establishes context; coordination overhead exceeds task work; “plans of plans” syndrome

This is the load-theoretic restatement of the task-decomposition note’s over-decomposition counter: there is no single “more granular = better” axis. The right granularity is where intrinsic load per step fits the executor’s capacity and the cumulative extraneous load of orchestration doesn’t dominate the productive work.

Diagnostic moves for the three load types

When a prompt or plan is failing, classify the dominant load type before reaching for a fix.

If failure traces to intrinsic load

Symptom: the executor competently follows the structure but produces a wrong answer on the substantive question. Re-prompting in the same shape produces the same wrong answer. The model “doesn’t know” or “can’t reason about” the problem.

Fixes:

  • Stage the work — split the high-intrinsic step into a chain where each link is within capacity
  • Add scaffolding — chain-of-thought, scratchpad, intermediate artifacts
  • Provide the missing schema — example, definition, named pattern reference
  • Accept and escalate — if intrinsic load exceeds the executor’s reach even after staging, escalate to a more capable executor (larger model, human review, external tool)

Anti-pattern: rewriting the prompt with more emphasis or threatening tone. Intrinsic load isn’t a compliance problem.

If failure traces to extraneous load

Symptom: the executor follows part of the instruction, misses or contradicts another part, or seems to “lose track” mid-execution. The instructions are correct but the executor doesn’t act on them coherently.

Fixes:

  • Cut repetition — state shared context once, lift it to the top
  • Drop ceremony — verbose markup that doesn’t carry task information
  • Reorder — task statement first or last (avoid middle), with position-bias mitigated
  • Use chunked vocabulary — leverage pre-trained schemas instead of inventing terminology
  • Run density-scan on the prompt — the six levers there target extraneous-load patterns specifically

Anti-pattern: adding more instructions hoping one will stick. Each addition is more extraneous load.

If failure traces to germane-capacity exhaustion

Symptom: the executor handles each individual instruction correctly but produces a shallow or incoherent synthesis. Surface compliance, missing depth.

Fixes:

  • Reduce extraneous load to free capacity for synthesis (the primary lever)
  • Break the synthesis into named sub-syntheses that the executor produces in sequence
  • Use intermediate artifacts that capture early synthesis output, then feed it back as input to later steps

Anti-pattern: asking for “deeper analysis.” This often increases intrinsic load without freeing germane capacity.

What this does and doesn’t translate from human CLT

Translates well:

  • The three-load diagnostic vocabulary — useful for naming what kind of failure you’re seeing
  • The capacity-is-bounded principle — different substrate, same shape: attention dilution as the LLM analog of working-memory capacity
  • Chunking and schema-leverage — pre-trained patterns reduce extraneous load
  • The granularity paradox — under- and over-decomposition fail through different load mechanisms

Translates with caution:

  • Specific numeric capacity claims — “4±1 items” is a human result; LLM equivalents would need entirely separate measurement
  • The germane-load construct itself — contested within CLT research (Sweller’s own later revisions); use as a label, not a measurement
  • Worked-example effect, expertise reversal effect, redundancy effect — empirically grounded in human studies; plausibly applicable to LLM prompts but the specifics may differ. Treat as design hypotheses to test, not laws

Does not translate:

  • The motivational and self-efficacy mechanisms layered on top of CLT in the goal-setting literature — LLMs do not have motivation, fatigue, or affect
  • “Cognitive overload as protective shutdown” — humans avoid overwhelming tasks; LLMs typically generate confabulated output instead of refusing, which is a different failure shape that CLT does not predict

Composition with related skills

  • /density-scan on prompt prose — operates on the surface patterns that drive extraneous load (surprisal spikes, monotony, long dependencies). The skill is what you reach for when you suspect extraneous load is the dominant failure source.
  • /plan-split-scan on multi-step plans — operates on plan structure (concern count, state-carry, branches). The load-theoretic lens is the why behind the signals: each signal flags a structural pattern that drives extraneous load at the orchestration layer.
  • /reviewers-map on AI output — operates on the receiver side. Where CLT-for-AI is about executor load, reviewers-map is about the load the AI output places on the human reviewer.

The three are non-overlapping in target (prompt prose, plan structure, output verification) and complementary in lens (CLT explains what kind of load each scan addresses).

Tradeoffs and context-dependence

  • The framework is a diagnostic vocabulary, not a measurement instrument. Don’t try to assign numeric loads to prompt components — the construct doesn’t support that even in human CLT.
  • Intrinsic load is executor-dependent. What’s intrinsically hard for a 7B local model is intrinsically easy for Claude Opus. The same prompt may need different staging for different executors. The executor declaration in the plan-split-scan (Step 0) is the entry point.
  • Some “extraneous load” is intentional. Examples, worked solutions, and reference material look extraneous if you measure by token count but are productive scaffolding for intrinsic load. The distinction is functional: does this content help the executor build a schema that reduces total load downstream? If yes, it’s germane scaffolding, not extraneous noise.

What this doesn’t cover

  • Worked-example effect in detail. The CLT literature has a substantial body on worked examples, expertise reversal, and faded guidance. The plausibility of these transferring to LLMs is high but unmeasured; a separate empirical note would be needed to claim more.
  • Multi-modal load. Human CLT has substantial work on visual + auditory split-attention effects. LLM analogs (text + image, text + code) are an open area; this note does not address them.
  • Cross-executor calibration. “How much intrinsic load can model X handle in step Y?” — there is no general answer; calibrate against your own failure data.

Counterargument

The strongest objection: the three-load decomposition is a useful framing, but importing it from human educational psychology to LLM prompt design risks dressing prompt-engineering folklore in scientific vocabulary. The fixes recommended above (“cut repetition,” “use named patterns,” “stage hard problems”) are practitioner consensus anyway; the CLT lens doesn’t add new fixes, it just relabels existing ones.

The honest position: the lens adds value at the diagnostic layer, not the prescriptive layer. The fixes are what they are; the value of CLT-for-AI is letting you say “this failure is extraneous-load-driven, not intrinsic-load-driven” — which changes which fix to reach for. If a designer already knew which fix to apply, the lens is overhead. If they were applying intrinsic-load fixes to an extraneous-load failure (or vice versa), the lens corrects them.

The framework is also vulnerable to the narrative-coherence failure mode — CLT sounds explanatory because it has named categories and authoritative citations. Treat it as a working hypothesis for AI design, not as established science applied to LLMs. The empirical work has not been done.
