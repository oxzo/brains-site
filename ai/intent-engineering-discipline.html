Intent Engineering as a Discipline

“Intent engineering” is an emerging (mid-2026) framing that positions a third discipline alongside prompt engineering (per-query syntax) and context engineering (which information enters the window, with what relevance / sufficiency / isolation / economy / provenance). Where those two address the information and surface layers, intent engineering addresses the strategic layer: what the user/org wants the system to produce, what counts as done, and what must never happen — encoded durably enough that any agent can be run against the same contract, whether local or remote, current model or next quarter’s.

This is the same operation as the one in clear-intent-as-anchor (state the target so the rest can be checked against it), at the artifact altitude: instead of a one-line intent: frontmatter on a note, it’s a repository-resident, machine-readable spec that the CI pipeline can validate.

Why the framing exists

Single-prompt engineering treats AI generation as a query problem: get the wording right, get the output you want. Context engineering treats it as an environment problem: the model is fine if you put the right facts and shape in front of it. Both are necessary; neither covers what happens when an autonomous agent runs for thirty minutes across forty tool calls and quietly drifts off the user’s actual goal.

The 2026 “vibe coding” phase made the gap visible — products shipped fast, but with no traceable answer to what was supposed to be built once the conversation that produced them scrolled off. The agentic IDEs (Cursor, Windsurf, Claude Code, etc.) operate multi-step. Their failure mode is not “wrong token” but “right-looking code, wrong intent.” That’s the failure intent engineering is reaching for.

The discipline borrows its analogy from intent-based networking (Cisco / IETF, mid-2010s), where the operator declares a desired network state and the controller reconciles reality to match. Applied to coding agents: declare the desired user outcome and the strict constraints; let the agent execute against the declaration rather than a procedural prompt.

The three layers

A useful decomposition (synthesised from the emerging literature, not a settled standard):

LayerWhat it isWhat goes wrong when missing
IntentionRaw unstructured signal — a user friction, a complaint, a feature requestNothing to build from
StructureFormalised, falsifiable specification of what success means and what is prohibited”Right-looking” output that misses the actual ask
ProjectionExecution into code, UI, API documentationThe visible artifact; only this layer is usually reviewed

Most teams jump Intention → Projection and skip Structure. Intent engineering is the explicit name for the missing middle layer.

Position relative to existing vault concepts

  • Upstream cognitive principle: clear-intent-as-anchor — the why; the four-axis test (form, completion-falsifiable, navigable, altitude) for whether any intent statement is doing real work. Intent engineering is that principle operationalised as a repository artifact rather than a one-line frontmatter.
  • Tactical primitive: implementation-intentions-for-ai-plans — Gollwitzer’s if-then conditionals are the form most “what should the agent do under situation Y” rules in an intent spec take. Use that note’s trigger/response criteria when authoring those rules.
  • Architectural enforcement: functional-agent-architecture — once the intent spec exists, it’s enforced by typed effects, capability tokens, snapshot isolation, and property-based behavioural contracts. The spec says what counts as compliance; the architecture is how non-compliance is physically prevented.
  • Adjacent durable artifacts: architecture-decision-records-ai — ADRs and AgDRs (Agent Decision Records) capture the why of decisions; an intent spec captures the what must hold of an ongoing capability. They overlap but don’t substitute (an ADR explains the choice once; the intent spec is read every session).
  • Output containment: structured-output-json-mode — JSON-mode and grammar-constrained generation are the lowest-level enforcement of structural constraints stated in the spec.
  • Spec-first design loop: ai-system-design-workflow — the upstream activity that produces material for an intent spec; this is intent engineering at the codebase scale.

What an intent specification typically contains

Reconstructed from the cross-section of the emerging literature; treat as a starting shape, not a standard:

  • Objective and target components — what is being changed, named.
  • Belief grounding — where the agent’s worldview comes from (which docs, with what metadata filters), so it doesn’t form beliefs from parametric memory. The actual ground-truth side of bdi-architecture-for-coding-agents.
  • Desires — the goal intentions, possibly conflicting; the spec resolves the conflict up front (e.g., “non-blocking I/O and strict backwards compatibility — backwards compatibility wins on conflict”).
  • Implementation intentions — explicit if-then rules for foreseeable situational cues (see implementation-intentions-for-ai-plans for the trigger/response criteria).
  • Invariants — properties that must hold across the execution. Often split into hard (zero tolerance — e.g., no plaintext secrets) and soft (tolerated transient violation with a bounded recovery window).
  • Governance — allowed and prohibited tools / capabilities (cf. functional-agent-architecture capability tokens).
  • Recovery mechanisms — what happens on violation; typically tiered (lightweight critique → autonomy reduction → human escalation).
  • Success criteria — CI-enforceable verification commands (pytest, ruff, type checks, mutation thresholds — see ai-verification-stack-web).

Failure modes

Theatrical spec. The artifact exists, is structured, and anchors nothing — the same failure mode clear-intent-as-anchor flags at the one-line frontmatter scale, scaled up. A well-formatted YAML with vague success criteria (“system should be reliable”) is theatre. Apply the four-axis test to every load-bearing field.

Premature solution lock-in. clear-intent-as-anchor’s altitude axis warns against specifying the implementation (use library X, route through framework Y) before the right shape is known: it closes off option space. For early/exploratory work, prefer need-level statements; commit to solution-level only when the implementation is the actual subject of the work.

Spec drift without re-check. The original spec was right at write-time; the work has moved; the spec has not. No current tooling forces a re-check. Treat the spec like a long-lived ADR — visible review when the work substantively shifts.

Smuggled fabrication. The 2026 literature on intent engineering is dense with AI-synthesised compound terms (“Constraint-Checked RAG”, “Triples-to-Beliefs-to-Triples”, “Drift Bounds Theorem”) whose specifics do not consistently trace to citable work. The source material for this note is part of that literature. Verify named methods before encoding them in a spec or a vault note. The real underlying ideas — constraint-filtered retrieval, structured-output grammars, property-based behavioural contracts — are well-established in their non-renamed forms and already live in functional-agent-architecture and structured-output-json-mode.

Maturity caveat (as of 2026-05)

The term intent engineering is emerging. The underlying ideas — declarative specs, contract-first design, intent-based networking, behaviour-driven development — are not. What is genuinely new is the synthesis: the proposal that LLM-agent IDEs need a durable, repo-resident, CI-enforceable contract layer, distinct from per-session prompts, distinct from context selection, distinct from architectural decisions. Whether the discipline settles around this name or another (intent specs, agent contracts, system specs, spec-driven AI) is open. The operation — state the target so the rest can be checked against it — is the part to track, not the label.
