Evaluating AI-Generated Code Beyond Tests

A decision rubric for “green CI, now what?” When every automated gate passes, what do you actually check next — and how do you decide whether to ship, return to the agent, or escalate to human review?

Extends ai-verification-stack-web, which enumerates the tools. This note covers the judgment layer that sits on top.

Why green CI isn’t enough

Green pipelines prove the code doesn’t break the things you thought to test. For AI-authored code, the gap between “tests pass” and “behaves correctly” is wider than for human code:

  • Hollow tests. Test suites can hit 100% line coverage with only a 4% mutation score — Wang et al.’s mutation-guided test-generation study found exactly such suites (arXiv 2506.02954, IEEE TSE 2025; “some test suites achieve 100% coverage but only 4% mutation score”). The tests exist to satisfy the CI contract, not catch bugs. (Attribution corrected 2026-06-10: previously credited to “Meta LLM mutation research” — Meta’s ACH paper (arXiv 2501.12862, FSE 2025) is a different work and does not contain this figure.)
  • Spec drift. The AI implemented what it inferred from context. Tests check the inferred spec, not the actual spec.
  • Local correctness. A change can be internally consistent — types align, tests pass, linter clean — while violating an invariant the test suite doesn’t encode.
  • Novel failure surface. AI-co-authored PRs carry 1.7× more issues than human-only PRs, with security issues up to 2.74× higher in the worst category and improper password handling 1.88× more likely (all CodeRabbit, Dec 2025); Veracode’s Spring 2026 GenAI report separately finds ~45% of AI-generated code fails security checks absent explicit security guidance. Familiar review intuitions undercalibrate. (Corrected 2026-06-10: 1.88× was previously stated as the overall vulnerability rate co-attributed to Veracode — it is CodeRabbit’s password-handling figure.)

Trust signals

Before reading the diff line-by-line, scan for signals that raise or lower the prior that this change is safe.

Positive signals (lower skepticism)

  • Small, focused diff. <50 LOC, <3 files, single concern.
  • Uses existing patterns. Imports established helpers instead of reinventing them.
  • No new abstractions. No new classes, interfaces, hooks, middleware, or utility modules.
  • Tests behavior, not implementation. Assertions are on observable outputs, not internal calls.
  • Touches non-critical code. No auth, permissions, payments, persistence, or public API surface.
  • Agent expressed uncertainty where appropriate. The reasoning log flags edge cases and asks clarifying questions rather than confidently guessing.
  • Clear mapping from spec to diff. Every changed line traces to a line in the spec or ticket.

Negative signals (raise skepticism)

  • Large diff, scope creep. Touches files unrelated to the stated task.
  • Fresh abstractions. New classes, wrappers, adapters, or “utility” modules.
  • Defensive code without reason. try/catch blocks that swallow errors, null checks on values the type system guarantees, fallback values for impossible states.
  • Test edits without behavior change. Test assertions weakened or deleted without a corresponding code change. This is the single strongest tampering signal.
  • Parallel implementations. A second function that does what an existing function already does.
  • Over-confident reasoning. The agent declares the change “complete” without flagging edge cases that obviously exist.
  • Layer violations. Business logic in UI components, DB access in route handlers, presentation concerns in domain code.
  • New dependency added. Especially unfamiliar packages. Check ai-supply-chain-risks.

Architectural-risk heuristics

Where AI-generated web code goes wrong architecturally. Use these as a checklist when the change is non-trivial.

  1. Premature abstraction. AI reaches for classes, factories, and generics before the duplication justifies them. Three similar lines is better than a hook.
  2. Inventing types. Introduces a new User or Order type parallel to the existing one because it didn’t grep for the existing one.
  3. Error-handling theater. Wraps everything in try/catch and returns null or a stringified error, turning compile-time guarantees into runtime mysteries.
  4. Implicit coupling. Module A reads from a context or store that Module B writes to, without either side declaring the relationship.
  5. Wrong layer. Fetch calls in components, validation in routes, formatting in domain models. AI will match whatever layer the request mentioned, not the layer the logic belongs in.
  6. Fake convergence. Tests edited until they pass rather than code fixed until tests pass. Especially suspect when both tests and code changed in the same pass.
  7. Deleted invariants. Assertions, type constraints, or validation removed “to make the test pass” without a comment explaining why the invariant was wrong.

The tiered decision rubric

Think of review as a cascade. Each tier is cheaper than the next. Escalate only when lower tiers leave uncertainty.

Tier 1 — Mechanical gates (cost: seconds)

Type check, lint, unit tests, mutation score threshold, bundle size, dependency audit. See ai-verification-stack-web layers 2–3 and 5. Non-negotiable; failure blocks everything.

Tier 2 — Semantic automated gates (cost: minutes)

Schema/contract validation, visual regression, fitness functions (import boundaries, perf budgets), E2E smoke. Catches whole classes of “green CI but wrong behavior” bugs.

Tier 3 — AI critic review (cost: cents to dollars)

A separate agent with the spec and the diff, prompted as a skeptical reviewer. Useful for scanning for the negative signals above at scale. Not a replacement for human review — collusion risk is real (see multi-agent-failure-modes).

Two operational details that make the difference between a critic that catches bugs and one that rubber-stamps:

  • Sprint contracts. Where possible, the critic is grading against an explicit contract the generator agreed to before coding — scope, acceptance criteria, behavior to demonstrate. This is the upstream-prevention move from harness-design-load-bearing: a critic with a contract verifies; a critic without one improvises. Without a contract, the critic ends up grading whatever the diff happens to do, which means spec drift slips through.
  • Iterative critic tuning. Early versions of any critic agent identify legitimate issues and then dismiss them (“yes it’s broken, but the code looks reasonable so I’ll pass”). Treat the critic prompt as a stateful artifact: read its logs, compare verdicts against your own on a sample, and rewrite the prompt when the verdicts diverge. The critic that ships PR #100 should not have the same prompt as the one that shipped PR #1. See harness-design-load-bearing for the operational pattern.

Both moves attack self-evaluation bias from different angles — sprint contracts make the critic’s job mechanical enough to short-circuit the bias; iterative tuning calibrates the critic against ground truth.

Tier 4 — Human spec review (cost: minutes)

Not line-by-line code review. The question: does this change match what I asked for? Read the spec, then the PR description, then the diff summary. If they tell the same story, the code is probably close. If the diff touches files the spec didn’t mention, stop and ask why.

Tier 5 — Human architectural review (cost: 15+ minutes)

Required for any change that trips an escalation trigger below. This is where the lead dev’s judgment pays off — read the diff with the mental model of “what will this look like in six months when the next AI change touches it?”

Escalation triggers

Any of these force Tier 5 review, regardless of what lower tiers said:

  • Change crosses a module boundary or touches a shared interface
  • New runtime dependency added
  • Modifies auth, permissions, persistence, payments, or PII handling
  • Introduces a new abstraction (class, interface, hook, middleware, service)
  • Diff exceeds 200 LOC or 10 files
  • Mutation score below threshold for the file’s tier (70% business logic, 50% UI, 30% utilities)
  • Test files edited in the same pass as implementation files without new behavior added
  • Public API surface changes (exports, route shapes, event payloads)
  • Agent’s own reasoning log expresses uncertainty about correctness
  • Fitness function / architectural rule warning suppressed rather than resolved

Review protocol for AI diffs

When you do pull up the diff, the order matters. Humans reviewing AI code with human-code habits miss the AI-specific failure modes.

  1. Read the spec or ticket first. You’re checking the diff against intent, not against your aesthetic preferences.
  2. Read the PR description / agent reasoning log. Note any hedges, flagged assumptions, or “I chose X because Y” decisions. Those are the places to focus.
  3. Look at the test diff before the code diff. If tests were weakened or removed, stop and investigate. This is the highest-signal check for AI self-deception.
  4. Grep for new abstractions. Search the diff for class , interface , function , export const, type . Every new abstraction should have a justification.
  5. Check cross-file consistency. If the change modifies a shared type or function, verify callers still make sense. AI often updates the definition and misses one caller.
  6. Run the feature. Not just the tests. See ai-verification-stack-web layer 3 for visual verification. Human perception catches regressions tests miss.
  7. Cross-check the diff against the escalation trigger list. If any trigger fires, route to architectural review.

Decision outputs

Every review ends with one of these. Pick explicitly — “LGTM” is not a decision.

  • Ship. All gates green, no escalation triggers, trust signals positive.
  • Ship with monitoring. Green but non-trivial. Add observability; review metrics post-deploy.
  • Ship behind a flag. Risky area, bounded blast radius. Gradual rollout.
  • Return to agent with specific feedback. Cite the failing gate or signal. Vague feedback produces vague fixes.
  • Escalate to human architect. A trigger fired. Not a judgment on the code — a policy requirement.
  • Reject. Fundamental mismatch with spec, security concern, or architectural violation that can’t be fixed by iteration.

Anti-patterns

  • Rubber-stamping after green CI. The whole point of this note. Green CI is a floor, not a ceiling.
  • Line-by-line review of every AI diff. You’ll burn out and miss the patterns. Use signals to triage, then deep-read the suspicious changes.
  • Accepting “all tests pass” as the agent’s completion signal. Tests passing is table stakes; the agent should also report what it verified beyond tests.
  • Letting the agent edit its own tests unchecked. The single highest-leverage guardrail is: test changes require stronger justification than code changes.
  • Suppressing a fitness function rather than resolving the violation. If the ESLint rule or bundle budget complains, the rule is usually right.
  • Trusting AI critic reviews as independent. Same model family = correlated blind spots. Critic agents catch surface issues; they don’t replace Tier 4/5.
