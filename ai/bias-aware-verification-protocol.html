Bias-Aware Verification Protocol

What it is

A concrete, runnable protocol for bias-aware AI interaction. It treats every non-trivial exchange as having two bias layers — one in the user’s prompt, one in the model’s output — and applies explicit passes to each. It then adds two adversarial passes (disagreement drill and red-team) on the resulting answer.

This is the synthesis note. The two atomic layers are documented separately:

  • prompt-bias-diagnostics — input side (what’s biased in the prompt, and how to reframe)
  • ai-output-bias-fingerprints — output side (what bias signatures to detect in the response)

Why it matters

The hardest thing about verifying AI output isn’t spotting a wrong answer — it’s deciding when to scrutinize at all. A protocol gives you a cost-calibrated default: which checks to run at which stakes, without having to re-derive the question each time.

For anyone whose role is “the human who verifies AI work” (see ai-verification-stack-web), this protocol is a first-class skill. It sits orthogonally on top of the verification stack — not a new layer, but a discipline that improves every layer’s signal-to-noise.

The four passes

Pass 1 — Input (prompt) triage

Goal: neutralize framing bias before the model sees the prompt.

Trigger: any prompt that will shape a decision with real consequences — production code, specs, research that changes your mind, user-visible outputs, prompts going to a subagent fleet.

What to do: run the prompt-bias-diagnostics triage (under 30 seconds):

  1. Leading question? → reframe to neutral
  2. Embedded estimate? → ask for independent estimate first
  3. Single anecdote? → add base-rate request
  4. Dispositional framing of behavior? → ask for situational first
  5. Hot emotional state? → delay or add cold-state reframe
  6. Alternatives ruled out? → ask for alternatives explicitly

Automation: the /bias-scan-prompt slash command runs this triage on a prompt (file path or literal text) and returns findings plus a suggested rewrite. Use it for prompts that will shape a decision or be baked into a spec.

Cost: 30 seconds of attention, or a cheap auto-prompt-triage subagent ($0.001/prompt with Haiku-tier).

Pass 2 — Output fingerprint scan

Goal: detect bias signatures in the model’s response before acting on it.

Trigger: any output that will be acted on, published, or propagated (committed code, vault notes, PR descriptions, emails, agent decisions).

What to do: run the ai-output-bias-fingerprints detection checklist:

  1. Strip fluency — list load-bearing factual claims
  2. Frame-test for sycophancy
  3. Entity check — every named person, paper, URL, API, number
  4. Gap test — what assumptions did the model make?
  5. Mainstream check — is the popular answer right for your case?
  6. Failure-mode probe — were tradeoffs acknowledged?
  7. Context fit — did training-register assumptions leak in?

Automation: the /bias-scan-ai slash command runs this checklist on a file and returns structured findings plus a PASS/REVIEW/FAIL verdict.

Cost: under a minute for short outputs; selective for long outputs (apply to load-bearing sections).

Pass 3 — Disagreement drill (inversion)

Goal: use the model’s own variance under reframing as a calibration signal.

Trigger: decisions with significant downside, or where the model’s first answer felt suspiciously clean.

What to do: ask the model to argue the opposite position as strongly as it argued the first. Compare.

  • Large gap (two substantially different answers) → the question is genuinely contested or the model is unreliable here; go to Pass 4 or escalate to human judgment
  • Small gap (model hedges both ways with the same evidence) → the first answer was probably noise-dressed-as-confidence; treat as uncalibrated
  • Zero gap (model refuses to engage with the opposite) → strong signal of a value-locked or RLHF-constrained topic; seek independent sources

This is inversion applied to model outputs.

Automation: the /disagree slash command runs this drill on the most recent substantive assistant response.

Cost: one additional model call, plus a minute of reading and comparison.

Pass 4 — Red-team pass

Goal: surface failure modes the primary pass missed.

Trigger: high-stakes outputs — production architecture, security-relevant decisions, public-facing content, automated actions with non-trivial blast radius.

What to do: a second prompt or second agent whose only job is to find the first answer wrong. Concrete prompt patterns:

  • “Here is an answer: <first output>. Give me the three strongest reasons this is wrong or will fail in practice.”
  • “A skeptical senior engineer is reviewing this. What is their first objection?”
  • “Pre-mortem: assume this decision turned out to be a disaster six months from now. List the causes.”

Use a different model if you can — cross-model disagreement is a stronger signal than same-model disagreement. Document the red-team findings; if the primary answer survives them, you have earned trust in it. If not, revise.

This is red teaming operationalized for AI outputs.

Automation: the /red-team slash command runs this pass on a file or artifact and returns three strongest objections, a pre-mortem, and the weakest load-bearing claim.

Cost: one to three additional model calls plus human review time. Not cheap — reserve for high-stakes decisions.

The protocol is not “run all four every time.” It is “run the right ones for the stakes.” Overhead unmatched to stakes is the main reason verification protocols get abandoned.

Orthogonal: human-authored artifact scan

The four-pass protocol above is about AI interactions — it assumes there’s a prompt and a model-produced output to check. A separate scan exists for artifacts whose reasoning is the author’s own:

  • /bias-scan-human <path> — runs against a human-drafted decision note, journal entry, plan, retrospective, or synthesis note
  • Checks the full cognitive-bias catalog: sunk cost, confirmation, anchoring, planning fallacy, fundamental attribution error, self-serving bias, narrative fallacy, survivorship, loss aversion, automation bias, etc.
  • Draws on cognitive-biases, probability-judgment-biases, social-attribution-biases, ../general/consumer-valuation-biases, ai-automation-biases, debiasing-mental-models

This scan is orthogonal to the four-pass AI protocol — not a fifth pass. The two sets of checks are largely non-overlapping: /bias-scan-ai asks “did the model hallucinate or sycophant,” /bias-scan-human asks “did the author sunk-cost or confirmation-bias.” When an artifact is mixed (human draft + AI edits), run both; their findings typically don’t duplicate.

Existing layers check the artifact. The bias protocol checks the reasoning that produced the artifact — both yours (input) and the model’s (output). Neither substitutes for the other.

Templates

Bias-aware code review prompt

Use when reviewing an AI-generated PR:

You are reviewing AI-generated code. Before line-by-line review, perform a bias-fingerprint pass:

1. Are there hallucinated APIs, imports, or function signatures? List any you can't verify.
2. Do the tests exist to test behavior, or to pass CI? Identify tests with low mutation value.
3. Was the simplest, most mainstream solution chosen when a better-fitting niche solution exists?
4. Are there confident-looking claims in comments or commit messages that don't match what the code does?
5. What assumptions did the AI make that the spec did not supply? Which are wrong?

Report findings as a bulleted list. Do not proceed to normal review until the fingerprint pass is complete.

Bias-aware research synthesis prompt

Use when asking for a summary of evidence you’ll act on:

Before summarizing, run an input-side check:

1. Did my question embed an answer I'm expecting? Restate it neutrally.
2. Am I asking about a case where the mainstream answer tends to be wrong? Flag this.

Then produce the summary with:
- Load-bearing claims listed as bullets (no prose hiding)
- Base rates where relevant
- At least two counterarguments or failure modes per major claim
- Explicit list of assumptions and information you'd need to verify

End with the strongest argument against your own summary.

Disagreement-drill one-liner

You just gave position A. Now argue position not-A with equal rigor, as if that's what I'd asked. Note where the evidence genuinely supports both and where it only supports one.

Red-team one-liner

Here is a proposed [decision/plan/answer]: <paste>. A hostile but honest reviewer finds three specific ways this fails. What are they?

Anti-patterns

  • Protocol theater. Running all four passes on every interaction regardless of stakes. Burns budget and attention; erodes the discipline’s credibility when the overhead stops paying off.
  • Self-serving framing audits. Using Pass 1 to rewrite prompts toward a preferred conclusion rather than toward neutrality. If you know what answer you want before asking, no amount of framing hygiene will save you.
  • Trusting the red-team output. The red-team pass is itself an AI output and is subject to the same bias fingerprints. Skepticism doesn’t bottom out.
  • Treating passes as proof. Running the protocol produces better-calibrated reasoning; it does not produce correctness. The output still requires ordinary verification for facts, specs, and contracts.
  • Skipping Pass 1 because the output scan exists. Biased prompts produce biased outputs that the output scan is less likely to catch (because the output looks internally consistent with the biased question). The cheapest correction is upstream.

Why it stays valuable as models improve

The protocol stays valuable even as models get stronger — because stronger models produce more convincing biased outputs, not fewer. This protocol is part of the verification skill stack that compounds over time (see ai-verification-stack-web). The oracle problem is irreducible; someone has to decide what “correct” means, and bias-aware verification is part of how that judgment is exercised and trusted.

The protocol also addresses the specific failure mode in the personal CLAUDE.md rule (trust-but-verify subagent meta-claims): the incident behind that rule is a textbook Pass 2 miss — a confident, coherent, narrative-consistent subagent output that went un-entity-checked and got relayed.
