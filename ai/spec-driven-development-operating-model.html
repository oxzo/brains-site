Spec-Driven Development and the Accretive Loop as One Operating Model

Tool specifics verified 2026-09-04 against Spec Kit’s evolving-specs guide, Kiro’s specs and correctness docs, and the OpenSpec README, concepts and existing-projects docs. The combined model is original to this vault.

accretive-spec-development positions the loop beside spec-driven development (SDD) as a different mode: agree-then-build versus build-then-harvest. Under both, every clause ends up affirmed twice by a human — once as a requirement (this is what we want) and once as a check (this is how we would know). The models differ in which affirmation comes first and which one gates the build. This note gives the rule for that, the region transitions that follow from it, and how the loop’s artifacts sit inside a tool’s layout without a second set of books. It is also the vault’s SDD note: it carries only the SDD mechanics the combination needs, not a tool comparison. The runnable method built on this reasoning is clause-loop, which also carries it to prototypes, specifications and documentation and which is normative — where this note and it differ, it wins; this note stays the why.

One shape, two orders

The three verified tools share a core: specify or propose → design or plan → tasks → implement. Spec Kit and OpenSpec wrap it with a clarify or explore step in front and a consistency or verify step behind, and OpenSpec archives at the end. Spec Kit runs it as /speckit.specify, /speckit.clarify, /speckit.plan, /speckit.tasks, /speckit.analyze, /speckit.implement, /speckit.converge; Kiro as requirements.md, design.md, tasks.md; OpenSpec as /opsx:explore, /opsx:propose, /opsx:apply, /opsx:archive, with /opsx:verify (“check implementation matches specs”) optional in its expanded profile. The loop’s shape is intent plus falsifier → probe → confront → harvest → freeze → consolidate.

What differs:

  • Which affirmation gates the build. SDD gates on the requirement — “Agree before you build”, in OpenSpec’s words. The loop gates on the check: it pre-registers a falsifier, builds, and affirms the harvested clause afterwards.
  • What the human authors upstream. A requirement with WHEN/THEN scenarios bounds many failure directions; one falsifier line bounds one. Both are agent-drafted otherwise, so this is the only place independence enters — which is why the loop asks the human to own the falsifier at every outcome boundary, not to type one per task.
  • A design gate. SDD puts a design.md or plan.md in front of the human before the build. The loop has no design step: “how” is the agent’s probe choice, seen first at Confront.
  • Enforcement point. SDD checks its artifacts against each other before implementation (/speckit.analyze across spec, plan and tasks). The loop enforces after, in CI, through the contract guard on a frozen region’s manifest.
  • Granularity. A change per SDD cycle; a clause per loop.

What does not differ is accumulation or brownfield fit. OpenSpec’s openspec/specs/ “starts nearly empty and accumulates”; “you write specs only for what you’re about to change”; “the spec for auth/ becomes thorough only after you’ve made several auth changes”. That is accretion at change granularity — a design claim from the tool’s own docs; no non-vendor evidence on brownfield behaviour is cited here. The loop is accretion at clause granularity with an executable pin. So “SDD for frozen regions, the loop for open ones” is the wrong cut: OpenSpec runs on regions that have no spec yet by design, and the loop already sends work in regions without a contract to a plan when a heuristic fires. Region state is an input to the rule below, not the boundary between the models.

The operating rule

Which affirmation gates the build. The requirement gates it — agree, then build — when a planning heuristic fires on the envelope the probe declares: uncertainty about the approach, rework in the region, growth past the last three building loops, cross-domain coordination with at least one region under contract, or a contract change that would modify or retire a wanted clause in a region under contract. Separately, a hard gate — an irreversibility-list item, a production or shared-environment write, a destructive operation, a credential, an externally visible action, or an edit to a frozen region’s verification surface — stops for the human’s permission on that action whichever affirmation is gating, and a bare surface edit needs a permit, not a proposal. Otherwise the check gates it — build, harvest, then promote. The heuristics and gates are defined normatively in clause-loop rule 4; this note only places them. The surface gate is the pre-build half of test-tamper protection; a code-only probe that breaks a listed check without editing its surface is caught after the fact by the execution guard (the failing row below). Under this rule, “spec is the source of truth, code is a regenerable artifact” (writing-loops-not-prompts) is true of a region under contract and false of a region that is harvesting, where the running artifact is the truth and every clause is provisional.

Three honest notes on the rule. Its output drifts: as regions go under contract, the cross-domain heuristic and the surface gate fire more often, and a mature project is requirement-first by construction — the loop is the on-ramp, not the steady state. And the growth heuristic has a cold start: after three trivial probes, any real one is longer than the previous three combined. Read it against the last three probes that built something. And the model has not been run: what would show the rule wrong is the heuristics or the gates firing on most probes within the first month, so harvesting never happens, or DECISIONS.log going unwritten after a few sessions.

Region states and transitions

A region is the unit a manifest covers: a domain folder under openspec/specs/ (a feature directory in Spec Kit). An intent that spans two folders is two regions and hits the cross-domain heuristic once either is under contract. Three states:

  • open — no clauses.
  • harvesting — the loop is running; clauses are observed or wanted; checks may well run in CI, but no manifest guards them.
  • under contract — frozen: every clause wanted and verified, a manifest written from the pins naming clauses, checks and the verification surface, a contract test exported to consumers — other agents, future sessions, downstream services.

Two rows need a note. A requirement-first change does not suspend the loop: inside it, every task is intent plus falsifier, and the mutant gate still runs before a scenario counts as pinned. And retiring is not failing. A failing clause’s check fails; a retired requirement’s check still passes, so retirement is a deliberate decision at archive — a retire entry saying whether the behaviour stays and whether the check stays as characterization coverage — rather than an automatic deletion, and a check is deleted only when its purpose is obsolete. The first is clause-loop rules 1, 2 and 4; the second is rule 3.

Artifacts: one layout, three additions

The rule that prevents a second set of books: the region’s spec file is specs/<region>/spec.md and there is no other. The loop’s files map onto the tool’s layout, inside its root; nothing lives beside it. Three additions carry the loop’s guarantees, because no verified tool has them in this form:

  1. The pin — under each #### Scenario:, one trailing line with a stable id, acceptance, oracle type, check id, birth change and evidence. Whether OpenSpec’s tooling tolerates the extra line is unverified.
  2. The manifest written from the pins, the contract guard and the contract-test export — the CI mechanism behind “under contract”.
  3. DECISIONS.log — nine kinds, defined in clause-loop, written by the agent from the human’s decisions.

Reference layout, OpenSpec-shaped; + marks the additions:

Spec Kit is feature-keyed (specs/<feature>/spec.md). Treat a feature directory as a region when the feature is one. When a feature spans regions, the per-feature directories stay as the historical record the guide wants and the region file is consolidated from them; the two will diverge, and the region file wins.

The vault’s own skill chain is this pipeline without the name: to-prd is specify or propose, plan-options is plan or design, task-decompose is tasks with a falsifiable done-criterion per row, the loops are implement, intent-fulfilment-check is converge’s completion assessment at intent level, and pr-contract is the archive-time record.

Which Spec Kit persistence model, when

Spec Kit’s guide names three ways to keep specs/ aligned with code. The combined model uses two of them, by phase, and declines the third:

  • Flow-back while harvesting. The guide lets “the first useful edit … happen wherever the insight lands” and then realigns the artifact set, with /speckit.analyze to check for gaps; its discipline is “do not leave a lower-level change in tasks.md or code if spec.md still says something different and the spec is meant to remain trustworthy”. An observed clause is that first edit, captured in the artifact closest to the work. The loop adds what the guide does not have: the clause is not trustworthy until promoted, and promotion needs the pin, the locked check and the mutant gate — this vault’s additions, not the guide’s.
  • Living spec under contract. “Revise the existing spec.md first. Then regenerate or manually revise downstream artifacts so they match”, with /speckit.analyze before implementation resumes and /speckit.converge to assess completion. A change to a region under contract starts in the delta spec, which is this model.
  • Flow-forward, declined. “Each feature directory should remain a historical record” — a new directory per follow-up change. That conflicts with one spec file per region; the model keeps the per-change record in the archive folder instead, which is OpenSpec’s mechanism, not Spec Kit’s.

The oracle bridge

Kiro extracts properties from EARS-formatted requirements during design, before implementation, and calls the result “a clear, traceable link between your requirements and the tests that validate them”. The loop builds the same link in the opposite order: probe, then check, then clause. In both, the agent authors the check, so independence comes only from what the human authored upstream — a requirement in one direction, a falsifier in the other, and the requirement reaches further. That is oracle-problem-verification’s circular-spec row stated as a workflow rule.

The completeness rule that makes either order acceptable: a clause is complete only when it has both a requirement form and a pinned check shown to reject a mutant for a named reason, whichever was born first. Requirement-first clauses have the form and must earn the pin; harvested clauses have the pin and must earn the form before promotion.

Kiro’s on-failure choice — fix the implementation, adjust the tests, or refine the requirements — maps onto the loop’s rules one to one: fixing code is free inside the loop; adjusting a test is an edit to a locked check and needs the human’s permission — through the approval boundary once the region is under contract; refining a requirement is a change to a wanted clause and needs a decision, or a proposal if the region is under contract. The mutant gate is the addition: Kiro’s docs name neither it nor the test library that runs the properties.

Two critique gates

A falsifier is a pre-registration — how we would know it is not working — not a critique. The critique asks whether this is the wrong thing to build, and it sits where the cost is:

  • Before the build, red-team on proposal.md and design.md, because a requirement-first change is expensive by definition. The output has a destination: the strongest objection becomes a #### Scenario: in the delta or a rejection in DECISIONS.log. A red team whose findings go nowhere is theatre.
  • After the probe, Confront: the human reacts to the running artifact and to the not-exercised list, after committing to what pass and fail look like — pre-registered criteria, predict-then-compare. Cheap probe, cheap gate. OpenSpec’s optional /opsx:verify is the tool slot for this; the loop makes it mandatory.

Failure modes of running both

  • Double bookkeeping. A SPEC.md beside openspec/specs/. The one-file-per-region rule exists for this.
  • Theatrical proposal. A proposal structured to pass the gate that anchors nothing. Run a four-axis intent audit (intent-check) on the SHALL lines; a proposal with no falsifiable scenario is rejected, not improved.
  • Independence collapse. The agent writes the proposal, the design, the tasks and the properties, and the human only approves. The floor is a human-owned falsifier at every outcome boundary — the change’s intent, and any task that introduces a new assumption, trade-off or visible behaviour — with the other tasks inheriting it and saying so; below that, every check encodes the agent’s reading of the intent — intent-engineering-discipline’s “theatrical spec” with tests attached.
  • Harvest-only SDD. Building on a region under contract and back-filling a proposal from the harvest. The surface gate stops it before the build when the envelope names the edit; the surface guard fails CI when it does not, and the execution guard when a listed check breaks without its surface being touched.
  • Converge as the gap oracle. Letting /speckit.converge’s generated tasks replace the not-exercised list removes the human falsifier from failure-mode coverage — the agent then names both the gap and its fix.
  • Consolidate and archive drifting. An archive-merge can break pins the same way a consolidate rewrite can. Re-point any pin the rewrite breaks — the consolidate rule — applies to both.
  • Undefined regions. The cross-domain heuristic, the manifest and the spec file are all keyed on the region. If auth/ is one region to one person and three to another, the heuristic fires on everything. Fix the folder taxonomy in Ground.
  • Retirement handled as failure, or a rejected clause’s check deleted by reflex. A passing check silently kept, or useful characterization coverage thrown away; see the transition table.
  • Too heavy for one person. Per clause: a pin, an evidence record, a decision; per proposal: a red team; plus the contract guard. The public surface is four actions and a packet the human answers in chat, which is the thinning already applied. The likeliest failure is not a bookkeeping error but dropping the model. If it must be thinned further, keep the pin, the evidence rule and the manifest and relax the rest first.

When not to combine

  • Multi-team contracts before anything has frozen: SDD alone.
  • Regenerate-from-spec practice, where code is rebuilt from the spec rather than edited: harvest is idle; SDD plus the mutant gate.
  • Work where the first probe is itself the expensive part: plan-first, as the loop already says.
  • Regulated audit trails: permit and freeze lines carry an approval reference from the boundary, but the log is agent-written and the boundary is whatever the repo host provides; add a formal approval step at archive.
  • Parallel agents or session handoff: a plan file is the thread and “no task list” stops holding.
