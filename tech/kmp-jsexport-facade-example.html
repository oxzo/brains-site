Worked Example — The DTO-Flattened @JsExport Facade

The code companion to kmp-js-interop-boundary. That note ends on a design consequence: you don’t expose idiomatic Kotlin to the web team — you build a deliberately designed, DTO-flattened, annotation-disciplined facade, and that facade is the public API the React/TS app consumes. This note shows what that actually looks like in code.

Compile- and runtime-verified 2026-07-06 with Kotlin 2.3.20 / Gradle 8.14.5 / JDK 21: this facade was built as a real Kotlin/JS library (binaries.library() + generateTypeScriptDefinitions()), published to a local npm consumer, typechecked under strict TS, and exercised at runtime (Promise, Flow bridge, precision round-trip). Corrections the build demanded are folded in below and listed in §5. Flag names and stability remain time-sensitive — re-check against kmp-js-interop-boundary. As of 2026-07.

The shape of the problem

Two layers, one boundary:

┌─ commonMain (idiomatic Kotlin) ─────────┐
│  rich domain model: sealed classes,     │   ← internal, NOT exported
│  List/Map, Long, Flow, suspend fns      │
└──────────────┬──────────────────────────┘
               │  mapping / flattening
┌──────────────▼─── jsMain (the facade) ──┐
│  @JsExport DTOs: Array, Double/String,   │   ← the public API surface
│  Promise, observer callbacks, @JsName    │      .d.ts is the contract
└──────────────┬──────────────────────────┘
               │  npm package (.js + .d.ts)
┌──────────────▼─── React / TypeScript ────┐
│  import { ... } from '@org/core'         │
└──────────────────────────────────────────┘

1. The idiomatic core — what you do NOT export

This is normal, rich Kotlin. It lives in commonMain, serves the native Android/iOS clients directly, and is never annotated with @JsExport.

Every line here has at least one feature from the “does NOT cross cleanly” list in kmp-js-interop-boundary: Long, Map/List, a sealed hierarchy with an object case, a suspend function, and a Flow. Hand this to @JsExport as-is and you get name-mangled symbols, KtMap/KtList views the TS team must convert by hand, an invisible Pending case, and broken Long typing.

2. The facade — flattened, annotated, the actual public API

This lives in jsMain. It is the only thing marked @JsExport. Every boundary-hostile type is converted to something a TS consumer reads as native.

The when on the sealed interface is exhaustive — if someone adds a new PaymentResult case in the core, the facade fails to compile until the mapping is updated. That compile error is the feature: it forces the boundary contract to stay in sync with the domain instead of silently dropping a case.

3. What the web team actually consumes

Gradle’s generateTypeScriptDefinitions() emits a .d.ts from the facade. The React/TS app imports it as an ordinary npm dependency — but the import shape depends on the module format (both verified 2026-07-06):

  • Default (UMD): the Kotlin package becomes a nested TS namespace — a facade in package core.facade emits export declare namespace core.facade, and the consumer reaches types as core.facade.Money.
  • With useEsModules() (recommended for Vite/modern bundlers): the distribution becomes .mjs + .d.mts with flat root-level named exports even from a nested Kotlin package — idiomatic import { Money } from ..., as below. Vite consumes it with zero config; bundle economics are in kmp-js-interop-boundary. Short version: ~28 KB gzip floor after minification, and tree-shaking across the boundary is effectively zero, so the facade’s dependency graph — not the consumer’s import list — sets the cost.

No KtMap/KtList views, no BigInt surprises, no mangled symbol names, no missing union case. The TS team sees idiomatic TypeScript because the facade did the flattening — not because Kotlin exports cleanly (it doesn’t).

4. Why the facade is a versioned contract

That generated .d.ts is the public API. Two practices follow, and they are the “semver + .d.ts-diff review” half of the design consequence:

  • Semver the facade, not the core. The internal domain model can churn freely; what the web team pins is the DTO surface. A change that alters a DTO field is a breaking change even if the domain logic is untouched.
  • Diff the .d.ts in review. A .d.ts diff is the precise, mechanical record of what changed at the boundary. Treat an unexpected .d.ts diff the way you’d treat an unexpected public-API change in any published library — because that is exactly what it is. A renamed DTO field is a silent break for the consumer unless the diff is read.

The facade is small surface area on purpose: the smaller and flatter it is, the cheaper the .d.ts diff is to review and the less the web team is exposed to the experimental @JsExport friction documented in kmp-js-interop-boundary.

One caveat the generated contract adds (verified 2026-07-06): the .d.ts is noisier than the facade source suggests. Every exported data class leaks copy(), toString(), hashCode(), equals() and a deprecated $metadata$ namespace into the public surface, plus module-level Nullable<T>/KtSingleton helpers. The .d.ts-diff reviewer must learn to read past these Kotlin-isms — and consumers can call copy() even though the facade never advertised it.

5. What the build actually demanded (verification log, 2026-07-06)

Built and run with Kotlin 2.3.20 / Gradle 8.14.5 / JDK 21 / TS 5.9 strict. The §1–§2 code compiled essentially as written; the full delta from illustration to working library:

  • Opt-ins: @file:OptIn(ExperimentalJsExport::class, DelicateCoroutinesApi::class) (both warning-level), plus ordinary imports (kotlin.js.Promise, kotlinx.coroutines.promise, etc.). No experimental compiler flags were needed for this facade — the GlobalScope.promise path avoids -Xenable-suspend-function-exporting.
  • A factory is mandatory. internal constructor becomes private constructor() in the .d.ts, so TS cannot instantiate AccountFacade; the facade must export a factory function (the snippet as originally drafted showed no construction path).
  • Package placement decides the import shape — see §3.
  • Runtime behavior confirmed: authorize() awaits to the flattened DTO; the observer bridge delivers values and unsubscribes; the tagged union switch sees all three cases.
  • The precision trap is real and the flatten defeats it: the demo balance 2^53 + 1 (9007199254740993) survived Kotlin Long → String → TS end-to-end exactly, while Number("9007199254740993") rounds to 9007199254740992 — the silent corruption the Security section warns about, observed.
  • Bundle cost of this facade and its stdlib/coroutines floor: measured in kmp-js-interop-boundary — ≈296 KB raw / ≈51 KB gzip as shipped in the library dist, collapsing to ≈90 KB raw / ≈28 KB gzip after a consumer Vite build (minification does the work; tree-shaking contributes nothing).
  • ESM follow-up (same date): with useEsModules() the library was consumed by Vite 7 and webpack 5 production builds with zero config and typechecked strict under moduleResolution: bundler (TS 6.0); the .d.mts exports are flat, so §3’s idiomatic imports work as written. Tree-shaking is zero by default, but the combination of per-file granularity + hand-added sideEffects: false prunes a DTO-only consumer to <1 KB gzip in both bundlers — each lever alone does nothing. The full flow was re-run correctly under that aggressive config; details and caveats in kmp-js-interop-boundary.

Security implications

The facade discipline argued for on maintenance grounds is also the security lever. Most of the implications below are general frontend-security truths — but KMP’s “share the core across platforms” value proposition actively pulls you toward the mistakes, because logic that is genuinely protected in a native app feels like it’s still protected once the same core compiles to browser JS. It isn’t.

The facade is a convenience boundary, NOT a trust boundary

Anything in the shared core that compiles to web ships to the browser, where the user can read and modify it. So validation, authorization, pricing, limits, and fraud rules enforced in the core are advisory on web — an attacker calls the server API directly or edits the running JS and the checks evaporate. The core shares a rule’s implementation across platforms; it cannot share the rule’s authority. The server must re-validate everything the core “already validated.” The real-world failure is cognitive: a green account.authorize(...) tempts teams to weaken the server check that is the actual enforcement point. This is why kotlin-multiplatform-web-enterprise keeps regulated logic server-side (counterfactual c).

Keep the @JsExport surface minimal — it’s also the XSS-reachable surface

Everything exported is callable by any script on the page, including injected script. A minimal facade is therefore least-privilege, not just cheaper to review. Exporting an internal or admin operation “because it was convenient” hands it to an XSS payload. Name mangling (hello_sv8swh_k$) is not obfuscation and must not be treated as a protection.

Don’t ship secrets or production source maps

  • Embedded constants ship verbatim. Any key, salt, internal endpoint, or fraud threshold baked into the shared core lands in the public JS bundle — a grep away in devtools. A constant that felt “buried in the core” on Android is exposed on web.
  • Source maps leak the original Kotlin. The .js.map files that make debugging work (per kmp-js-interop-boundary) reconstruct your Kotlin source, names, and comments. Gate them out of production builds, or restrict who can fetch them.

Flatten 64-bit values to String, never Double (integrity)

This is why §2 flattens Money.amountMinor: Long to a String, not a Double. A JS Double is exact only to 53 bits, so a 64-bit amount or account/transaction ID flattened to Double silently loses precision — wrong amount, wrong account, a corrupt-integrity bug that no exception flags. The DTO-flattening step is where a type-safety guarantee the Kotlin core had can be quietly destroyed at the boundary; treat every numeric flatten as a correctness decision.

Provenance gap across the language boundary

  • Two supply chains converge. The Kotlin stdlib + kotlinx libraries are pulled into the bundle, then re-packaged as npm. The Gradle dependency- verification story covers the inputs (see kotlin-multiplatform-web-enterprise); the emitted npm artifact needs its own SBOM/provenance, and SBOM tooling is weaker across the Kotlin→JS boundary.
  • Reproducible build is unestablished. No confirmed reproducible-build / SLSA-provenance story for transpiled-Kotlin frontend artifacts (open condition 5 in kotlin-multiplatform-web-enterprise) — so you cannot cleanly attest that the shipped .js corresponds to the audited Kotlin source.

Checklist

  • Server re-validates every rule the core enforces; core checks treated as UX only
  • Exported facade is minimal — no internal/admin operations reachable from page scripts
  • No secrets/keys/thresholds in any code path that compiles to web
  • Production builds strip or gate .js.map source maps
  • 64-bit numerics and IDs flattened to String, not Double
  • npm artifact has its own SBOM; provenance gap to Kotlin source acknowledged in the risk register
