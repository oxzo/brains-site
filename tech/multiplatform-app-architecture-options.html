Web + iOS + Android + Backend: The Architecture Option Space

As of 2026-08-26. Version numbers and stability tiers are the fastest-moving claims in this note; re-verify before citing.

The framing correction

“Which cross-platform framework?” is the wrong first question, and it is the one every comparison article answers. It collapses five decisions that are actually independent:

  1. UI sharing — how much of the rendered interface is one codebase
  2. Logic sharing — how much non-UI code (domain, validation, networking) is one codebase
  3. Client↔server contract — how the three clients talk to backend services
  4. Data and state topology — request/response versus a local store that syncs
  5. Delivery cadence — how you ship to three platforms whose release gates differ by orders of magnitude

You can pick independently on each axis. React Native + REST + no offline + weekly releases is a valid combination; so is native Swift/Kotlin + shared Kotlin core + GraphQL + local-first. Most “framework wars” content only argues axis 1 and silently assumes defaults for the rest.

The five-axis split is an authored frame, not a standard taxonomy — no source in this research pass proposes it. Its claim to usefulness is only that it separates decisions that can be made independently; if a real project finds two of these axes genuinely coupled, the frame is wrong for that project.

Axis 5 is the one that distinguishes this problem from ordinary web architecture, and it is the most under-discussed. See design-tokens for the cross-platform consistency layer that sits orthogonal to all five.

Axis 1 — UI sharing

A spectrum, not a binary. Ordered by how much UI code is shared:

(a) No UI sharing — native Swift/SwiftUI + Kotlin/Compose + a web SPA

Three UI codebases, three teams (or three hats). Still a legitimate default, and the correct answer more often than framework marketing admits.

  • Wins on: platform fidelity, day-zero OS feature access, hiring in each silo, no framework-abandonment risk, no interop tax.
  • Loses on: 3× UI cost, three-way feature drift, design-system enforcement becomes a governance problem rather than a code problem (see design-system-failure-modes).
  • Pairs naturally with heavy sharing on axis 2, which is where most of the reuse value actually lives.

(b) Shared mobile UI, separate web — Compose Multiplatform or Flutter for iOS+Android

One mobile UI, a web app built with web tooling. This is the sweet spot for a lot of products, because the iOS/Android pair are far more similar to each other than either is to the web.

  • Compose Multiplatform is Stable for Android, iOS, and desktop as of the current supported-platforms table (kotlinlang.org, checked 2026-08-26). Its web target (Kotlin/Wasm) is Beta.
  • Flutter covers both plus web and desktop from one codebase. Its 2026 roadmap states “On the web, we intend for WebAssembly (Wasm) to become the default,” and commits to completing the Impeller migration on Android by “removing the legacy Skia backend on Android 10 and above,” plus “day-zero support for Android 17 and upcoming iOS releases” (flutter.dev).

(c) Shared across all three — React Native + React Native Web (Expo), or Flutter Web

One UI codebase for web, iOS, and Android. The most-shared option, and the one with the sharpest hidden costs.

Expo is the mainstream path here. Verified against primary sources on 2026-08-26:

  • Expo SDK 57.0.0 targets React Native 0.86, React 19.2.3, react-native-web 0.21.0; iOS 16.4+ (Xcode 26.4+), Android 7+ (compileSdkVersion 36), Node 22.13.x minimum (docs.expo.dev).
  • npm registry, queried 2026-08-26: expo latest is 57.0.16 (published 2026-08-24); react-native latest is 0.87.0 (published 2026-08-11). React Native’s own release line therefore runs ahead of the SDK’s pin — an SDK upgrade, not a package bump, is how you move.
  • Expo’s docs describe web output as statically rendered “for SEO and performance, or client-rendered for a more app-like experience,” and note React Native Web is optional but recommended “when building across platforms as it maximizes code reuse” (docs.expo.dev).

The caveat that matters: the web output is not a normal web app. RNW renders <View>/<Text> primitives to DOM. You inherit a component model designed for mobile, and web-native concerns (semantic HTML, CSS-native layout, third-party web widget ecosystems) get harder, not easier. React Server Components are “[e]xperimentally available. This is a beta release and subject to breaking changes,” with EAS Update not yet supporting them and production deployment explicitly not recommended (docs.expo.dev).

The honest version of option (c) for most teams: share the mobile pair, treat web as a first-class separate surface, and take the sharing on axis 2 instead. Which is option (b) with extra steps.

(d) Web-first wrapper — Capacitor / PWA

Ship one web app; wrap it in a native shell for the stores. The web build is the product; the native projects are packaging.

  • Cheapest path to three platforms if you already have a web app and mobile is a companion surface, not the primary one.
  • Cost is a WebView, which means the performance ceiling and platform-idiom ceiling are both lower. For content, forms, dashboards, and internal tooling this is frequently fine and frequently under-considered.
  • Capacitor produces standard native projects, so store submission is a normal native submission (Xcode/Android Studio or CI), whereas Expo’s EAS Submit handles it from CI without a local macOS requirement — (secondary sourcing; verify against current EAS docs before relying on the macOS claim).

(e) The .NET lane — MAUI + Blazor Hybrid

Relevant only if the org is already C#/.NET end to end, in which case a single language from UI through API is a real advantage. Outside a .NET shop it has no pull. Treat 2026 status claims for MAUI as (unverified) — I found no primary Microsoft roadmap source in this pass.

Axis 2 — Logic sharing (usually the higher-value axis)

Independent of the UI decision. The reusable mass in most products is domain models, validation, API clients, auth flows, offline queueing, formatting, feature flags, and analytics — not pixels.

  • TypeScript shared core in a monorepo. The default when web is React and mobile is React Native. Zero FFI, zero binding layer, one toolchain. Structurally the same “share core, native UI” shape as KMP, and it dominates KMP if mobile is already RN.
  • Kotlin Multiplatform core, native UI on each platform. The strongest option when mobile is true-native and the backend is JVM. Stable on Android, iOS, JVM server, and Kotlin/JS for web (kotlinlang.org). The mobile pair is solid; the web consumption path still goes through the experimental @JsExport, and Swift Export is still pre-stable — JetBrains’ August 2025 roadmap lists it as experimental with a stable release targeted in 2026 (JetBrains). (A secondary summary described it as moving Alpha→Beta; the primary post says experimental. Check the current tier before planning around it.) This option has its own cluster: kotlin-multiplatform-web-enterprise for the decision view, kmp-js-interop-boundary for what actually crosses the boundary, kmp-enterprise-adoption-evidence for who runs it in production.
  • Rust core + generated bindings (UniFFI/Wasm). Strongest web story of the compiled-core options, highest learning tax. 1Password’s headless Rust core under thin native UI across desktop, mobile, and browser is the standing production reference; Mozilla’s UniFFI generates the Kotlin/Swift bindings for this shape.
  • Share nothing on the client; put the logic on the server. The classic and still-underrated answer — thin clients, generated API clients, all rules enforced server-side. Costs you offline capability and client-side latency; buys you a single place to audit and change behavior. Worth remembering that anything compiled to a client is readable and modifiable by the user, so client-side validation and limit checks are advisory no matter which sharing option produced them — the server re-validates or it isn’t enforced.

Monorepo tooling follows from language mix, not preference: Turborepo or Nx if the shared code is JS/TS; Bazel/Buck2/Pants if the repo is genuinely polyglot and large. Remote caching is the feature that pays for the migration, not the task graph. (Tool-to-scale mapping here is from secondary comparison articles — treat specific package-count thresholds as unverified.)

Axis 3 — the client↔backend contract

Three clients means the contract is the integration surface that breaks. Options:

  • REST + OpenAPI, contract-first, with generated clients. Generate TypeScript, Swift, and Kotlin clients from one spec so a backend breaking change fails the client build rather than production. This is the boring answer and it survives client-framework churn better than anything else — the spec outlives the framework you picked on axis 1.
  • GraphQL (+ Federation for multi-service backends). Earns its complexity when clients genuinely need different shapes of the same graph and you would otherwise proliferate endpoints. Federation composes domain subgraphs into one schema.
  • tRPC. End-to-end type safety with no codegen step, but only inside TypeScript. If iOS/Android are Swift/Kotlin, tRPC cannot serve them — it is a web+RN answer, not a three-platform answer. Easy to mis-select, because tRPC’s DX is genuinely excellent inside the half of the problem it covers.
  • gRPC / Connect. Strong typing and streaming across polyglot clients; browser support needs a proxy layer.
  • BFF per client. Orthogonal to the above: one thin service per client surface, shaping responses for that client’s needs. Buys independent evolution and per-client caching; costs you N services to keep alive. Worth it when the web and mobile clients want genuinely different payload shapes; wasteful when they want the same data.

The BFF also solves an auth problem, which is why it keeps reappearing: web and native have different correct token stories. Native apps store tokens in the iOS Keychain / Android Keystore, which are hardware-backed and unavailable to other apps. Browsers have no equivalent — anything in localStorage is readable by any XSS that achieves execution. So the standard shapes diverge: OAuth 2.0 + PKCE with OS secure storage on native, versus a BFF/token-handler pattern that keeps refresh tokens server-side and hands the SPA only a short-lived access token in memory. (Sourced from secondary security write-ups in this pass; verify against the current OAuth 2.0 for Browser-Based Apps BCP before implementing.)

Axis 4 — data and state topology

  • Request/response with a cache (TanStack Query and equivalents). Right for most products. Cheapest to reason about.
  • Local-first / sync engine. A local database on each client with a sync protocol to the server. Buys real offline, instant interactions, and conflict handling as a designed feature rather than an incident. Costs you a hard distributed-systems problem inside your product.
    • Current contenders: PowerSync (Postgres → client SQLite with a write-back path; the most mobile-mature of the three), ElectricSQL (Postgres sync with “shapes” defining what reaches which client), Zero from Rocicorp (query-based sync; Replicache was sunset in its favor). (All characterizations here come from secondary comparison articles, not vendor docs or hands-on use — treat maturity rankings as unverified.)
  • The decision driver is not “would offline be nice.” It is whether a user in a tunnel, a warehouse, or a hospital basement is a real user. If not, this axis costs more than it returns.

Axis 5 — delivery cadence, the constraint web developers underestimate

Web ships continuously. Mobile ships through a review gate, and users on old versions persist for months. Any architecture spanning both has to answer: how do we change the product without a store release?

Options, roughly by power and risk:

  • Just ship native releases. Fine at low change frequency. Version skew becomes the API’s problem — you now support every client version in the wild.
  • Server-driven UI. The server sends UI structure, not just data; clients render generically. Airbnb (Ghost platform), Netflix, and Lyft are the canonical references, and Shopify reported escaping a weekly release cadence with it. The cautionary half is equally well documented: Spotify’s HubFramework, the earliest serious generic SDUI at scale, was deprecated, with engineers describing debugging it as archeology. (Both halves are from secondary write-ups — the Shopify and Spotify specifics are unverified.) The lesson in that pairing: SDUI works when scoped to a surface that genuinely needs frequent change, and rots when generalized into a whole-app rendering framework. Note also that every named reference here is a company with a dedicated platform team to maintain the renderer and its tooling — that standing cost is the part of the economics that doesn’t transfer to a small team.
  • JS bundle OTA updates (EAS Update and equivalents). Push a new JS bundle without a store review — available only if axis 1 put you on a JS runtime.
  • Sidestep the store entirely. If the audience is employees or a known enterprise customer base, MDM/managed distribution (and Apple’s business-focused distribution programs) removes App Review from the critical path and with it most of axis 5’s difficulty. Worth checking before designing around a constraint that may not apply — (programme names and current terms unverified in this pass).

Get the Apple rule right, because it is widely misquoted. App Store Review Guideline 2.5.2 reads, verbatim:

“Apps should be self-contained in their bundles, and may not read or write data outside the designated container area, nor may they download, install, or execute code which introduces or changes features or functionality of the app, including other apps. Educational apps designed to teach, develop, or allow students to test executable code may, in limited circumstances, download code provided that such code is not used for other purposes. Such apps must make the source code provided by the app completely viewable and editable by the user.” — App Review Guidelines, retrieved 2026-08-26

Note what is not there: the widely-cited “code run by WebKit or JavaScriptCore is exempt” carve-out. That language lives in the Apple Developer Program License Agreement §3.3.2, not in the review guidelines — several secondary sources attribute it to 2.5.2, and they are wrong. The substance of the permission is that downloaded scripts must not change the app’s primary purpose or add functionality inconsistent with what was reviewed. (The §3.3.2 wording and the reported June 2017 rewrite to engine-agnostic language are from secondary sources; read the current DPLA text directly before betting a release strategy on it.)

Guideline 4.7 is a separate provision covering “HTML5 and JavaScript mini apps and mini games, streaming games, chatbots, and plug-ins” — it is about hosting third-party software inside your app, not about updating your own. Don’t conflate them.

Practical read: bug fixes, copy, and UI iteration within the reviewed purpose are the safe zone; shipping a materially different app post-review is the violation.

How to choose — the drivers that actually decide it

Ordered by how often I’d expect each to be the binding constraint. That ordering is an authored judgment, not a measured one — but note that every driver on it outranks the benchmark numbers that comparison articles lead with:

  1. Who you can hire and retain. The clearest documented shared-core failures — Dropbox abandoning its C++ mobile core around 2019, and Slack hitting the same wall — were killed by hiring, retention, and custom-tooling overhead rather than by the technology failing on its own terms (InfoQ, 2019-11). Whether that generalises to most failures is unmeasured; it is placed first here as a judgment, not a statistic. This driver is really Conway’s law surfacing in the option space — each archetype implies a team shape you have to be able to staff and fund; multiplatform-team-topology works that through per archetype.
  2. How different the three products really are. If web is a marketing site + dashboard and mobile is the app, sharing UI across all three is solving a problem you don’t have.
  3. Whether offline is a requirement or a wish. Decides axis 4 outright.
  4. How often you need to change the product. Decides axis 5, and axis 5 can retroactively decide axis 1.
  5. Regulatory posture. If client-side logic can’t be trusted as enforcement, axis 2 collapses toward thin clients regardless of what’s technically shareable.
  6. What the backend already is. A JVM backend makes KMP nearly free on axis 2; a Node backend makes TS sharing nearly free.

Framework benchmark numbers are near the bottom of that list, and near the top of every comparison article.

Evidence quality warning

Searching this topic in 2026 returns an unusually high proportion of SEO content-farm output — “X vs Y vs Z 2026” articles that recycle each other’s numbers without primary sourcing. Adoption statistics in this space (KMP “7%→23%”, Flutter 46% vs React Native 35%) circulate widely with no traceable methodology and should not be used as decision inputs.

Claims in this note traceable to primary sources: Expo SDK/RN version pins, npm registry versions, KMP/Compose stability tiers, the Flutter 2026 roadmap quotes, Expo’s RSC status, and the verbatim Apple guideline text. Everything else is labeled inline.

Also unfound in this pass: credible recent postmortems of teams abandoning a cross-platform framework. The 2018-era Airbnb React Native writeup is still the most-cited example, which is itself a signal — either the failure mode has genuinely receded with the New Architecture and Compose MP stabilizing, or failures simply stopped being published. Treat the absence as unknown, not as evidence of safety.
