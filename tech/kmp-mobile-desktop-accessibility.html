KMP Accessibility on iOS, Android and Desktop — What Compose Multiplatform Bridges

As of 2026-11-10. Researched that day by a subagent reading official docs, release notes and the JetBrains tracker; the tracker states marked ✓ below were re-queried by hand the same day. Fast-moving: re-verify before citing. The web target is a separate story with a weaker bridge, covered in kmp-web-accessibility.

The split that decides everything

“Is KMP accessible” depends on who draws the UI.

Shared logic, native UI (SwiftUI/UIKit on iOS, Jetpack Compose on Android). The shared Kotlin never builds a view, so assistive technology meets the native toolkit and nothing else. This is an inference from the architecture: no primary source was found that states it, and none that contradicts it.

Shared UI with Compose Multiplatform. Compose draws its own pixels and must translate its semantics tree into each platform’s accessibility API. The quality of that bridge differs per platform, and the rest of this note is about it.

iOS

What the iOS accessibility page (dated 22 July 2025) states:

  • “Screen readers and VoiceOver can access the content of the Compose Multiplatform UI”, and the UI “supports the same gestures as the native iOS UI for navigation and interaction.”
  • Semantics map to native accessibility objects; “for most interfaces built with Material widgets, this should happen automatically.”
  • AssistiveTouch and Full Keyboard Access work: “You can navigate with keys like Tab and activate items using Space.”
  • Material3’s ColorScheme “currently lacks out-of-the-box support for high-contrast colours.” The app must detect Increase Contrast itself and supply its own palette.
  • testTag becomes the element’s accessibility identifier, and performAccessibilityAudit() in XCUITest audits a Compose screen “just as the Accessibility Inspector does.”

The tree is built lazily. Since the 1.8 line, “the tree is fully loaded after the first request from the iOS accessibility engine and is disposed of when the screen reader stops interacting with it”, which per the 1.8 what’s-new page “allows fully supporting iOS Voice Control, VoiceOver, and other accessibility tools”. The same release added container traversal semantics, the editable trait on text fields, page-scroll announcements and right-to-left support, and stopped exposing fully transparent components.

The iOS page contradicts the release notes. It still documents the experimental AccessibilitySyncOptions setting, which the 1.8 notes say “has been removed as no longer necessary.” Trust the release notes: advice from before 1.8 to force the sync mode on, for UI-test tools or for VoiceOver, describes a setting that no longer exists.

What the page never mentions: Dynamic Type, Reduce Motion, Bold Text and Switch Control. The tracker fills in part of that:

  • Dynamic Type: live font-scale updates fixed 2026-08-25 (CMP-10365 ✓).
  • Reduce Motion: the 1.13.0-beta02 notes say “Fixed an issue where Compose content ignores the Reduce Motion accessibility setting.” A separate report that animations hard-cut under Reduce Motion is still open (CMP-10284 ✓); whether the fix covers it was not checked.
  • Bold Text: a fix for CJK text resolved 2026-08-31 (CMP-10193).
  • Smart Invert inverting images is open (CMP-7939).
  • Switch Control: no documentation and no tracker issue found. Untested, not known-good.

Views embedded through UIKitView have native accessibility off by default (isNativeAccessibilityEnabled), according to a 2024 droidcon NYC talk; that source predates the lazy tree, so confirm against current docs before relying on it.

Open iOS issues worth knowing before an audit

All Open on 2026-11-10; filed dates in brackets.

  • CMP-10695 ✓ (Major): SecureTextField exposes password content to VoiceOver [2026-08-25]. The iOS sibling of the web password leak in kmp-web-accessibility, which is fixed in the 1.13 pre-releases; this one is not.
  • CMP-10691 ✓ (Major): SemanticsProperties.Error is not announced [2026-08-24]; CMP-10773: TextField isError is not announced [2026-09-10]. Form validation errors are silent to VoiceOver.
  • CMP-10804 (Major): incorrect RadioButton state [2026-09-16]; CMP-9055: Checkbox and Tab roles ignored [2025-10-09]; CMP-8887: CollectionInfo not working [2025-09-03].
  • Keyboard: CMP-10566 (Major) Tab does not move focus between text fields [2026-07-24]; CMP-10817 (Major) Full Keyboard Access skips text-field trailing actions [2026-09-17]; CMP-9859 (Major) focus jumps to the top of a lazy column [2026-03-04].
  • VoiceOver quality: rotator stops working after a focus change (CMP-10420, Major), focus latency on scroll (CMP-11022), noisy announcements in lazy lists (CMP-10735).

Recently fixed, which shows the direction: live regions (CMP-7602 ✓, 2026-04-27), Snackbar messages not being read (CMP-9046), incorrect state reading (CMP-9677), the toggle “off” state (CMP-10834, 2026-09-29).

Desktop

From the desktop accessibility page:

  • Windows goes through Java Access Bridge, which is off by default. Someone has to run jabswitch.exe /enable, and a packaged app must add the jdk.accessibility module to its native distribution. The page names JAWS and NVDA only as tools for checking speech output; it gives no list of supported screen readers and mentions neither Narrator nor Microsoft UI Automation.
  • macOS is listed as fully supported, tested with Accessibility Inspector.
  • Linux is listed as not supported.

Tracker, all Open: accessibility does not work in a Windows native distribution (CMP-373 ✓, Major, filed 2023-09-05); Narrator support (CMP-7161 ✓, filed 2024-11-29); Linux support (CMP-2167) and Orca over AT-SPI (CMP-8236 ✓, filed 2025-05-23); custom actions and action labels unsupported (CMP-2118); marking a component as a heading has no effect (CMP-2119).

The dependency on Java Access Bridge is the structural point. It means a Windows user’s screen reader works only if a setting most users have never heard of is enabled, and Narrator, the screen reader that ships with Windows, is not served at all.

Android

On Android the shared UI is Jetpack Compose, so TalkBack, Switch Access and the platform’s testing tools apply as they would to any Compose app. The closest statement in the docs is that Compose Multiplatform “builds on top of Jetpack Compose, making most accessibility features available in common code across all platforms.” No source was fetched that says outright that the Android target is unmodified Jetpack Compose. Resources for the Android side are in android-kmp-security-performance-resources.

Writing accessible shared code

The general accessibility page presents contentDescription, role, stateDescription, testTag, traversalIndex and isTraversalGroup as common-code APIs and points to Jetpack’s semantics reference for the rest. No per-platform support matrix exists. The docs flag nothing as unsupported on iOS or desktop, yet the tracker shows properties that compile everywhere and reach assistive technology only on some platforms (error state and collection info on iOS, headings and custom actions on desktop). The only way to know is to test each property on each target.

Automated checks

  • Android only: enableAccessibilityChecks() in Compose UI tests (labels, contrast, touch-target size, traversal order).
  • iOS: performAccessibilityAudit() through XCUITest, run against the built app, not from shared test code.
  • Shared code: nothing. Accessibility checks for the multiplatform ComposeUiTest are an open request (CMP-6719 ✓, filed 2024-09-20), and the accessibility test artifacts are not published for multiplatform (CMP-7843 ✓, filed 2025-03-26).

This is what rule UI-2 in kmp-quality-rules already assumes: two platform-specific checks, not one shared one.

How much weight the tracker deserves

A query for unresolved issues in the tracker’s UI. Accessibility subsystem returned 79 ✓ on 2026-11-10; roughly 54 are tagged iOS or desktop and roughly 16 web (the per-platform split is approximate). Forty-two issues in that subsystem were resolved between 2026-05-01 and 2026-11-10.

Read that number carefully. It has no baseline: UIKit, SwiftUI and Jetpack Compose have accessibility bugs too, and their trackers are not public in the same way, so 79 open issues does not show that Compose Multiplatform is worse than native. What the list does show is which behaviours to test first, and that fixes are landing at a steady rate.

Evidence that is missing

  • No independent audit of a shipped Compose Multiplatform app on iOS or desktop was found for 2025–2026, positive or negative.
  • No VPAT or Accessibility Conformance Report from JetBrains for the framework, and none from a company shipping an app built on it.
  • No published comparison against Flutter or React Native on iOS.
  • The only practitioner material opened was a 2024 droidcon NYC slide deck, which lists “accessibility complexity” among the costs and predates the lazy tree.

Absence here reflects one search session, not proof that none exists.

Regulatory context

  • WCAG2Mobile is still a W3C Group Draft Note dated 6 May 2025 (w3.org); such notes “are not endorsed by W3C nor its Members.”
  • EN 301 549 V4.1.1 now exists: ETSI’s delivery directory lists it with a 2 September 2026 timestamp ✓, after V3.2.1 from 2021. Vendor blogs say it adopts WCAG 2.2 AA and that V3.2.1 remains the presumption-of-conformity baseline until V4.1.1 is cited in the Official Journal (unverified: read from search summaries only, and no Official Journal notice was found).
  • European Accessibility Act: application from 28 June 2025 (the directive page did not load in this session; the date is consistent with the vault’s earlier sourcing).

What this means for a decision

  • Shared logic with native UI carries no accessibility risk from KMP as far as the evidence goes. Accessibility is a reason to prefer it only if the alternative’s gaps matter to you.
  • Compose Multiplatform on iOS is a supported, actively maintained bridge with real holes. For a regulated consumer app, the password exposure and the silent error states are the two to test before anything else, and a manual VoiceOver and Full Keyboard Access pass per release stays mandatory (kmp-quality-rules, UI-5).
  • Compose Multiplatform on Windows desktop depends on Java Access Bridge. Where the user population includes Narrator users or unmanaged machines, that is a planning constraint, not a bug to wait out.
  • Linux desktop has no assistive-technology support.

The counterargument to reading this as “avoid shared UI”: the iOS gaps are individual bugs in a bridge whose vocabulary is otherwise present, and several closed within months of being filed. The web target was in a worse position until the 1.13 pre-releases, with whole classes of state never reaching the browser, and it still has structural gaps (text sizing, contrast preferences) that no bridge fix addresses.

What would change this

  • CMP-10695 or CMP-10691 closes, or a release note names the fix.
  • The iOS docs page is rewritten to drop AccessibilitySyncOptions and to cover Dynamic Type, Reduce Motion and Switch Control.
  • Windows gains UI Automation or Narrator support (CMP-7161), or CMP-373 closes.
  • CMP-7843 ships a multiplatform accessibility-check artifact.
  • A vendor conformance report or an independent audit of a shipped app appears.
  • EN 301 549 V4.1.1 is cited in the Official Journal.

Not verified

  • That shared-logic-plus-native-UI has no KMP-specific accessibility constraint (inferred, no primary source).
  • Switch Control on iOS; Dynamic Type and Bold Text beyond the individual fixes above.
  • What runComposeUiTest can assert about accessibility, and whether third-party multiplatform tooling exists.
  • Whether the Reduce Motion fix in 1.13.0-beta02 resolves CMP-10284.
  • How content-description strings from shared resources behave per platform.
