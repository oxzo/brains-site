How the pieces fit

Four layers, each building on the one before it:

  1. Kotlin the language. Null safety, sealed types, coroutines. Quality here means idioms plus a written error-handling policy, enforced by tooling.
  2. Android + Jetpack Compose. Google publishes an opinionated, current architecture (UI and data layers, unidirectional data flow, screen-level ViewModels, offline-first) and a reference app, Now in Android, that implements it. Most “how should we structure this” questions have an official default.
  3. Kotlin Multiplatform. The same Kotlin compiled for Android (JVM), iOS (native) and web (JS/Wasm). Most of Android’s architecture transfers, but some of the Android defaults stop working: Hilt can’t enter shared code, SwiftUI can’t observe Flows without a bridge, Navigation 3 is Compose-bound, and Room has no web target. The enterprise-specific decisions live in these gaps.
  4. Enterprise non-functionals. Build health at many modules, test strategy across targets, security standards (OWASP MASVS), accessibility law (the European Accessibility Act covers consumer banking), and observability on iOS.

Sources to treat with caution

  • Pre-2023 Compose and Android tutorials — they pre-date Material 3, Navigation 3 and the Compose compiler moving into Kotlin. Google’s own Compose course is still dated August 2022.
  • Medium-hosted Android blogs (ProAndroidDev) — active but not editorially filtered; check claims against official docs.
  • AI-generated “converter” and “skill” pages, interview-question SEO sites — topic checklists at best.
  • Tutorials that assume Hilt-only, XML/Fragments or RxJava as the default stack — wrong defaults for a KMP target.
  • Archived reference apps — Tivi, Fenix — are snapshots of older practice.

Evaluating skill levels

No company publishes an Android- or Kotlin-specific engineering ladder (searches found only job ads). A workable proxy: a generic ladder such as Etsy’s, with competencies drawn from Google’s architecture recommendations, Effective Kotlin’s items, and the KMP docs on source sets and expect/actual.

Counterargument — is “learn the Android canon first” the right path?

The plan routes through Android before KMP. The strongest objection: the target app shares ViewModels and navigation across Android, iOS and a native web UI, and several Android defaults (Hilt, Navigation 3, Room, collectAsStateWithLifecycle) don’t survive that move. Weeks 3–6 partly teach things the team will deliberately not use.

Why the order stands anyway: Google’s architecture vocabulary (UDF, single source of truth, screen-level state holders, offline-first) is what the KMP ecosystem, its libraries and its hiring pool speak, and the vault’s own shared-ViewModel proposal is written in it. Knowing the Android default is what lets you see why the shared-code version must differ. Mitigation: in weeks 3–6, mark each Android-only API you meet and check it against the gaps listed in android-enterprise-architecture-resources (“Where the sources disagree”).
