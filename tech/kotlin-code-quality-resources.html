Kotlin Code Quality — Resources and Principles

The best resources for writing enterprise-grade Kotlin, the language itself (Android and KMP specifics live in sibling notes), plus the principles they agree on. Part of kotlin-android-kmp-learning-hub.

As of 2026-10-18. Links, versions and dates were checked by a research subagent on that date; items it could not open are marked (unverified). Coroutine basics are in the learning track’s resource list; only coroutine quality material is here.

Where the language is (2026-10)

  • Latest stable: Kotlin 2.4.21 (2026-10-08). Cadence: a language release (2.x.0) roughly every 6 months, a tooling release (2.x.20) about 3 months later, bug-fix releases unscheduled. 2.5.0 is planned for December 2026 — Kotlin releases.
  • K2 is the only compiler. Stable since 2.0.0 (2024-05-21); 2.4 drops -language-version=1.9 — What’s new in 2.4.
  • Stable in 2.4: context parameters (except explicit context arguments), explicit backing fields. Experimental: collection literals, name-based destructuring, the unused-return-value checker. Rich errors / union types are “Exploration and design” (KEEP-0462, public discussion) — don’t plan around them — Language features and proposals.
  • At 1M LOC, every experimental feature adopted is a migration you pay for later. Default to stable-only in shared modules.

Official sources

  • Coding conventions — JetBrains. The style baseline your formatter should encode; its “Idiomatic use of language features” section and library rules (explicit visibility, explicit types, KDoc on public API) matter most. Beginner→intermediate.
  • Idioms and Kotlin tour — fastest orientation; the tour runs in the browser. Better fit for a TS developer than Kotlin Koans, which were written for Java developers.
  • Kotlin Tips videos — short idiom videos, mostly Sebastian Aigner.
  • Language pages worth reading in full, because each carries an enterprise warning:
    • Null safety — the only NPE sources are explicit throws, !!, init inconsistency, and Java interop (platform types).
    • Sealed classes — exhaustive when for UI state and closed error types. KMP caveat: subclasses must share a source set; expect sealed hierarchies still need else.
    • Value classes — UserId over String cheaply; boxes when generic/nullable/interface-typed, and mangles names (matters for Swift/Java interop). typealias gives no type safety.
    • Scope functions — official warning: “avoid overusing them… avoid nesting scope functions and be careful when chaining them.”
  • Library authors’ guidelines — JetBrains. Written for library authors, but at 1M LOC your shared modules are internal libraries with many consumers. Key sub-pages: Simplicity, Minimizing mental complexity, Backward compatibility. Intermediate→advanced.
  • Explicit API mode (explicitApi() in Gradle) — forces visibility modifiers and explicit types on public declarations.
  • Kotlin Roadmap — what’s in focus; the page itself disclaims delivery commitments.
  • Kotlin blog — release posts and, in 2026, KMP and payments-domain case studies.

Books

  • Effective Kotlin — Marcin Moskała (Leanpub, last updated 2026-06-12). Rules of thumb with reasoning, in 8 chapters (Safety, Readability, Reusability, Abstraction design, …). The most direct “write reviewable Kotlin” book — use its item names as the team’s review vocabulary. Doesn’t teach basics. Intermediate→advanced.
  • Kotlin in Action, 2nd ed. — Aigner, Elizarov, Isakova, Jemerov (Manning, 2024). Written by the Kotlin team; the “why” behind the language, now with coroutines and Flow chapters. Beginner→intermediate. Start here.
  • Kotlin Coroutines: Deep Dive — Moskała. Use parts 2 (cancellation, exceptions, scopes, testing) and 4 (best practices) for coroutine quality. Advanced.
  • Advanced Kotlin — Moskała. Variance, delegation, contracts, multiplatform, KSP, compiler plugins. Advanced; later reading.
  • Older and skippable once you have Kotlin in Action: Atomic Kotlin (v1.1, 2021, Kotlin 1.5-era), Programming Kotlin (2019, pre-K2).

Error handling — the decision to make first

Kotlin has four error mechanisms and no enforced default; a large codebase needs one written policy before the first shared module.

  • Result KEEP — the official design rationale: “The Result class is not designed to represent domain-specific error conditions.” Result is for capturing arbitrary failures in general-purpose plumbing. Use nullable types or domain sealed classes for failures callers must handle; exceptions for logic errors and broken invariants handled centrally.
  • Signatures, be true — Sergey Chernov, guest post on the Kotlin blog (2026-08-19). Argues expected failures belong in the signature. Guest post, not a JetBrains position; only partially read.
  • Arrow typed errors — Either and the Raise DSL. Composable and explicit, but adds bind discipline and a new vocabulary; arrow-core 2.2.3 stable. Advanced.
  • Kotlin and Exceptions — Roman Elizarov, Medium (2020). Widely cited, existence confirmed, body not read (Medium returned 403) — (unverified content).

Coroutine quality (not basics)

  • Best practices for coroutines in Android — Android Developers. Inject dispatchers; make suspend functions main-safe; ViewModel creates coroutines; don’t expose mutable types; avoid GlobalScope; make blocking work cancellable; never swallow CancellationException. Most rules transfer to shared KMP code.
  • Coroutine exceptions handling — JetBrains. launch vs async propagation; CoroutineExceptionHandler only handles uncaught root failures and can’t recover; a child failure cancels the parent unless under supervisorScope.
  • Community “coroutine mistakes” posts (ProAndroidDev and similar) are uneven; check each claim against the two pages above.

Recommended order for a JS/TS developer

  1. Kotlin tour + Idioms in the browser (an evening or two).
  2. Kotlin in Action 2nd ed. for the language model.
  3. Coding conventions → Null safety, Sealed classes, Value classes, Scope functions. Pick the formatter and wire CI before writing much code.
  4. Effective Kotlin, a chapter a week, items used in review.
  5. Error-handling set (Result KEEP, Signatures, be true, Arrow) → write the error policy.
  6. Coroutine quality: Android best practices + exceptions page → Deep Dive parts 2 and 4.
  7. Enforcement: formatter + detekt + Compose Rules + Konsist; explicit API mode and ABI checks on shared modules.
  8. Library authors’ guidelines before the first internal shared-module release.

JS/TS mappings that help: sealed interface ≈ a TS discriminated union, but checked nominally and exhaustively by the compiler; value class ≈ a branded type that actually exists at compile time; Kotlin nullability ≈ strictNullChecks without the any escape hatch — except at Java interop, where platform types reintroduce it.

Principles the sources agree on

  1. Explicit visibility and types on every public declaration — an inferred return type change silently breaks binary compatibility (Backward compatibility).
  2. Never add a parameter to an existing public function, even with a default — compiled clients fail with NoSuchMethodError; add an overload (same).
  3. Avoid data class in public APIs — adding a property changes copy and componentN signatures (same).
  4. Expected domain failures in the type (sealed / nullable / Either), exceptions for the exceptional, Result for plumbing (Result KEEP).
  5. Exhaustive when over sealed types, no else — so adding a case breaks the build where it should (Sealed classes).
  6. Domain IDs as value classes, not raw String/Long (Value classes).
  7. !! and platform types are where NPEs come from — treat both as review flags (Null safety).
  8. Don’t nest scope functions (Scope functions).
  9. Never swallow CancellationException; inject dispatchers; no GlobalScope (coroutine best practices).
  10. Small API surface built on a small core, reusing standard types like Duration (Simplicity).
  11. Automate conventions instead of arguing in review — deterministic formatter + linter with a baseline (Block).

Tradeoffs and open questions

  • ktlint vs ktfmt. ktfmt is faster and unarguable; ktlint is configurable and closer to the official style but can fight the IDE. Don’t run two formatters; if you adopt ktfmt, disable detekt’s ktlint-backed formatting rules.
  • detekt’s version gap against Kotlin 2.4 — stable is old, current is alpha. Whether 1.23.8 runs cleanly on 2.4 is (unverified).
  • BCV vs built-in ABI validation — both maintained, the built-in one experimental; neither page says which replaces the other. Check before committing, especially for KMP klibs.
  • Arrow vs plain sealed classes. Arrow buys composability at the cost of team vocabulary and discipline; sealed hierarchies carry less machinery. A large team with mixed Kotlin experience is an argument for the simpler option until a concrete need appears.
  • Android-flavoured guidance. Many quality rules assume an Android ViewModel lifecycle; check them against shared code, where that lifecycle may not exist (see 2026-10-10-kmp-shared-viewmodels-navigation).
