The Kotlin → JS / Wasm / React Interop Boundary

What crosses cleanly from a shared Kotlin core to a web-native React/TypeScript consumer, what doesn’t, and how the library is packaged and debugged. Companion to kotlin-multiplatform-web-enterprise and kmp-enterprise-adoption-evidence. For the Compose-renders-the-UI alternative and its accessibility ceiling, see kmp-web-accessibility.

As of 2026-06 (packaging, bundle-size, bundler-consumption, and Wasm sections locally verified 2026-07-06 against Kotlin 2.3.20). This boundary moves fast — @JsExport is experimental and several limitations were only addressed in late-2025 Kotlin releases. Re-verify version-pinned facts before relying on them.

Target choice: Kotlin/JS, not Kotlin/Wasm

For a logic-only core handed to a JS frontend, JetBrains recommends Kotlin/JS: it “is the better fit because it provides a better interop experience” (JetBrains, 2025-05). Kotlin/Wasm’s strengths are near-native compute, faster UI rendering, and smaller binaries — all UI/compute-oriented, and largely irrelevant when you only ship a library that must hand rich typed objects across the boundary.

Stability (as of 2026-06):

  • Kotlin/JS web target — Stable; Kotlin/Wasm (wasmJs) web target — Beta, in the KMP supported-platforms table (kotlinlang.org).
  • Kotlin/Wasm’s wasm-js target reached Beta with Kotlin 2.2.20 (Sept 2025); Kotlin/Wasm overall is Beta with Stable expected late 2026 (InfoWorld, 2025-09; the “Stable late 2026” date is not in that source but is not contradicted). WasmGC reportedly reached all major browsers including Safari in late 2024 (the Safari 18.2 / Dec 2024 specifics are (unverified) — no source was fetched for this sentence).

The @JsExport mechanism — experimental, top-level only

The current JS-export path is built on the experimental @JsExport annotation. JetBrains acknowledges its constraints “make it challenging to use in enterprise applications” (verbatim, JetBrains 2025-05). JetBrains is working to let the “majority of Kotlin declarations” be exported and to stabilize the annotation — not yet done.

  • Note: the dossier attributed stabilization to ticket KT-80310, but that ticket number could not be confirmed against the cited blog or YouTrack — (unverified), treat the ticket number as unconfirmed even though the stabilization plan is confirmed.

What crosses cleanly on Kotlin/JS

Per the official js-to-kotlin-interop doc (as of 2026-06, kotlinlang.org) and Touchlab’s guides:

  • Exports reasonably: data classes, regular classes, objects, nullability, enums (since 1.6.20), interfaces (since 1.6.20).
  • Anything not marked @JsExport is not supported across the boundary.

What does NOT cross cleanly (per-API friction)

Confirmed against the official doc and Touchlab’s dev.to @JsExport guide:

  • Collections. List/MutableList/Map/Set are not exported as native JS arrays/objects — they surface as KtList/KtMutableList/KtMap/KtSet views needing conversion methods (asJsReadonlyArrayView/asJsArrayView). Must be flattened to Array / plain JS objects for a clean TS consumer.
  • Long. Non-exportable with no JS equivalent; breaks TS typing unless skipLibCheck = true. Exporting as BigInt requires experimental compiler flags -Xes-long-as-bigint and the language feature +JsAllowLongInExportedDeclarations (-XXLanguage:+JsAllowLongInExportedDeclarations). Kotlin 2.3.0 added experimental BigInt/BigInt64Array representation.
  • Unsigned integer types. Explicitly not supported.
  • Suspend functions. Only experimentally exportable since Kotlin 2.3.0 behind -Xenable-suspend-function-exporting (consumed as JS async functions). Before that, manual Promise wrapping via GlobalScope.promise was required.
  • Flow / StateFlow. No clean export; require hand-written wrappers (FlowObserver/StateFlowObserver-style), per kt.academy (Kotlin 1.8.21 reference). No clean export path was confirmed from a primary source for the callbackFlow→callbacks/Observables pattern.
  • Sealed-class hierarchies. Export buggily — data/regular-class subclasses export, but object subclasses are invisible.
  • Default parameters. Not preserved across the boundary (not confirmed by an authoritative source for either target — treat as (unverified)).
  • Name mangling. The compiler mangles names (e.g. hello_sv8swh_k$) unless @JsName is used.
  • TypeScript union types cannot be expressed in Kotlin (kt.academy, 1.8.21).

Net effect: the shared-core team must design a DTO-flattened, annotation-disciplined facade — not expose the rich idiomatic domain model. That facade is the public API the web team consumes, and it is the contract that needs semver and .d.ts-diff review.

Late-2025 / 2026 improvements (Kotlin 2.3.x)

Confirmed against whatsnew23. Kotlin 2.3.0 (released 2025-12-16) added:

  • Experimental @JsExport of suspend functions (-Xenable-suspend-function-exporting)
  • LongArray as BigInt64Array (under -Xes-long-as-bigint)
  • Unified companion-object access across all module systems
  • @JsStatic in interfaces
  • @JsExport.Default

Kotlin 2.3.20 (released ~2026-03) added the ability to implement Kotlin interfaces from TypeScript and experimental SWC compilation support.

Several of these remain Experimental behind flags. The broad shape of the friction persists.

Wasm boundary is more restrictive

If Kotlin/Wasm is chosen anyway: only primitives, strings, function types, JsAny subtypes, and opaque JsReference<T> handles may cross — arbitrary Kotlin classes/objects/collections cannot (Touchlab, 2024-03; kotlinlang wasm-js-interop). A Kotlin object reaches JS as e.g. fun createUser(...): JsReference<User> — awkward for a React/TS consumer wanting real typed objects.

Locally verified 2026-07-06 (Kotlin 2.3.20, same spike, wasmJs { binaries.library(); generateTypeScriptDefinitions() }):

  • The restriction has NOT loosened. @JsExport on a class is a hard compile error on wasmJs: “This annotation is not applicable to target ‘class’. Applicable targets: function” (verbatim). The JS-target facade cannot be reused; the Wasm facade is top-level functions only.
  • What works, at runtime too (Node 22 / V8 WasmGC): primitives and String cross; function types cross with real TS signatures (onNext: (p0: string) => void, unsubscribe as () => void); JsReference<Account> round-trips correctly but surfaces as unknown in the generated .d.mts — the TS consumer loses all type information for handles. Long→String flattening stays exact (2^53 + 1 verified end-to-end).
  • TS-declaration generation and npm packaging work on wasmJs despite the Experimental label: .d.mts, ESM glue (auto-detects browser/Node/Deno/standalone VMs), and package.json with main/types wired, at build/dist/wasmJs/productionLibrary.
  • Warts hit in one afternoon: the ExperimentalWasmDsl opt-in moved to org.jetbrains.kotlin.gradle (old FQN is an error, removal scheduled 2.4); an incremental-compilation internal compiler error after adding an export to an existing build (ArrayIndexOutOfBoundsException in WasmIrFileMetadata.fromByteArray) — a clean build fixes it; and the JS-side per-file granularity property breaks the wasmJs compile in the same module (“Per-file compilation can’t be used with any moduleKind except es”) — the JS tree-shaking recipe above conflicts with a co-hosted wasmJs target.

Two structural differences from the JS target:

  • DCE is automatic and whole-program. The logic-only build contains zero coroutines symbols even though commonMain depends on kotlinx-coroutines — unused domain surface just vanishes at link time, no sideEffects hand-assertion, no granularity recipe. This automatic whole-program DCE is the opposite of the Kotlin/JS default, where everything in the module graph ships.
  • Size verdict flips by workload. Logic-only: Wasm total (~8 KB gzip) is ~3× smaller than the JS target’s minified floor (~25–28 KB gzip). With coroutines reachable: rough gzip parity (~25 KB both). The old “Kotlin/JS larger bundles, Kotlin/Wasm smaller binaries” folklore is directionally right for lean cores, but the JS glue (~3 KB gzip) and coroutines dominate the difference.

Caveats: one local datapoint, tiny facade, library-mode distribution; browser WasmGC support and streaming-instantiation behavior not re-tested here. Interop friction (no classes, unknown handles) still makes Kotlin/JS the JetBrains-recommended and practically saner target for a rich typed facade — the size win only matters if the exported surface is genuinely function-shaped.

Packaging / build / npm

Locally verified 2026-07-06 (Kotlin 2.3.20, Gradle 8.14.5, JDK 21 — spike built from kmp-jsexport-facade-example): configure js { binaries.library(); generateTypeScriptDefinitions() } (the IR argument is no longer needed; IR is the only compiler). The jsBrowserProductionLibraryDistribution task is real and emits per-module .js files (facade + kotlin stdlib + each kotlinx dependency), .js.map source maps, one .d.ts, and a package.json with main/types wired — at build/dist/js/productionLibrary, not the build/productionLibrary in older Touchlab docs. npm install <path> and a strict-mode tsc typecheck against the emitted .d.ts both worked. The build also runs a jsProductionLibraryValidateGeneratedByCompilerTypeScript validation task.

Two consumer-relevant surprises from the same spike, both UMD-specific (see the ESM section below for the fix):

  • Output is UMD, not ESM, by default for a browser library. useEsModules() in the js target DSL switches the distribution to .mjs + .d.mts with real import/export statements and main/types re-pointed accordingly (verified 2026-07-06).
  • Under UMD, the Kotlin package becomes a nested TS namespace. A facade in package core.facade produces export declare namespace core.facade { ... }, so the consumer writes import { core } from '<lib>' and reaches types as core.facade.Money. Under ESM the nesting disappears: the .d.mts emits flat root-level named exports (export declare class Money) even from a nested Kotlin package, so consumers get the idiomatic import { Money } from '<lib>' (verified 2026-07-06).

ESM + bundler consumption and tree-shaking (measured 2026-07-06, both bundlers)

Same spike, useEsModules(), consumed by a Vite 7.3.6 production build (Rollup + esbuild-minify) and a webpack 5.108.4 production build (terser); typechecked strict with moduleResolution: bundler. Both bundlers consumed the library with zero configuration. Measured bundle sizes:

Conclusions (item 2 corrects the first pass of this section, which tested the levers only one at a time and wrongly concluded no lever works):

  1. Minification, not tree-shaking, sets the default cost. The ~278 KB of unminified per-module .mjs collapses to ~85–90 KB raw / ~25–28 KB gzip once either bundler minifies it — the honest consumer-side floor for stdlib + coroutines is ~25–28 KB gzip, not the raw-dist ~50 KB in the table below.
  2. Tree-shaking is zero by default but fully recoverable — the levers only work in combination. Each lever alone does nothing: at per-module granularity the whole facade plus its imports is one module, so sideEffects: false has nothing separate to prune (byte-identical in both bundlers); per-file granularity alone still ships everything because each generated file runs initMetadataFor* calls at module scope that bundlers must assume are side effects. Per-file granularity + a hand-added sideEffects: false prunes almost everything in both bundlers: the one-DTO consumer drops from ~85–90 KB to ~2 KB raw / <1 KB gzip, with all coroutines machinery gone.
  3. The recipe has real costs, which is why the default conclusion still stands for most teams: (a) sideEffects: false is a hand-made post-build assertion Gradle doesn’t emit — it declares every Kotlin module initializer droppable. That assertion held at runtime for this facade (full flow re-run and correct under the aggressive config) but is not a general guarantee for code relying on module-init registration; (b) per-file mode ships a dangling types path (package.json points to a root .d.mts that per-file mode doesn’t emit — declarations land per-file, e.g. <module>/core/facade/Facade.export.d.mts), so the post-build step must also fix that; (c) full-facade consumers pay a per-file wrapper overhead (~8% raw vs per-module).
  4. So: bundle cost is set by the library’s dependency graph — unless you adopt the per-file + sideEffects recipe, in which case it’s set by what consumers import. For a facade whose web consumers use only a slice (DTO validation, a rule engine), the recipe is worth the post-build packaging step; for full-surface consumers, stick with the default per-module granularity.

Bundler note: webpack ran ~6% smaller raw / ~10% smaller gzip than Vite on identical inputs (terser vs esbuild-minify) — a minifier difference, not a KMP finding.

Debugging

Source maps ship (.js.map, auto-generated since Kotlin 1.3.60), so web devs debug minified Kotlin-origin JS that maps back to Kotlin sources — workable but unfamiliar.

What we couldn’t establish

  • No concrete KB/MB measurement of Kotlin stdlib overhead in JS or Wasm library output — resolved 2026-07-06 by local measurement for both targets (JS: Packaging section, ~163 KB raw / ~27 KB gzip stdlib floor, ~25–28 KB gzip after bundler minification; Wasm: its own section, 8.4 KB gzip logic-only / 25.4 KB gzip with coroutines, glue included). No independent published benchmark was found. The load-time/UI-speed half of the reported JS-vs-Wasm tradeoff remains (unverified): ~0.25–0.5s faster initial JS load; ~3× faster Wasm UI (kmpship.app).
  • Vite and webpack consumption, tree-shaking, and dead-code-elimination behavior — resolved 2026-07-06 by local measurement, both bundlers (see the ESM/bundler section): both consume the useEsModules() output cleanly with zero config; minification cuts the bundle to ~25–28 KB gzip; tree-shaking is zero by default but recoverable via per-file granularity + hand-added sideEffects: false (one-DTO consumer: <1 KB gzip), with the caveats listed there.
  • Browser devtools debugging quality with the generated source maps (stepping into Kotlin, variable inspection) — asserted via .js.map, not independently evaluated.
  • Whether the Wasm interop restriction loosened by 2026 — resolved 2026-07-06: it has not. Exporting a class on wasmJs is still a hard compile error in Kotlin 2.3.20 (see the Wasm section for the verbatim error and what does cross).
  • Default-parameter handling — not confirmed by an authoritative source.
  • A clean Flow-to-JS export path — none confirmed.
