Characterization Testing for Legacy Code

What it is

A characterization test records what a piece of code does now, not what it should do. Michael Feathers named the technique in Working Effectively with Legacy Code (2004). In a 2016 post he states its purpose as “to document your system’s actual behavior”, and says such tests are “descriptions of what we have rather than statements of correctness.”

The same idea goes by several names, each with a slightly different emphasis:

  • Characterization test (Feathers): the general idea, often written one assertion at a time.
  • Golden master: capture a large chunk of output once and compare later runs against it. The Wikipedia entry on characterization tests treats this as a variant name.
  • Approval test: the tooling form. ApprovalTests describes itself as “taking a snapshot of the results, and confirming that they have not changed.” A run writes a received file, the test compares it with the approved file, and you approve a change by copying received over approved.
  • Snapshot test: the same mechanism in JavaScript test frameworks such as Jest, usually applied to rendered UI or serialised data.

All four are change detectors. A red result means “behaviour changed”. It does not mean “bug”.

Why it matters

Legacy code is often hard to refactor safely because nobody can say what it is supposed to do. The original intent is gone, the documentation is wrong or missing, and production behaviour has become the specification. Feathers puts it this way: “When a system goes into production, in a way, it becomes its own specification.” He adds: “We need to know when we are changing existing behavior regardless of whether we think it’s right or not.”

Hyrum’s Law gives the reason correctness is the wrong standard: with enough users, “all observable behaviors of your system will be depended on by somebody.” An odd rounding rule or an undocumented field order may be load-bearing for a downstream system. A suite that pins only intended behaviour misses exactly these behaviours, and a rewrite most easily breaks them.

Characterization tests are a cheap way to get a net under code you do not understand, because they do not require you to understand it first. You learn its behaviour by running it.

How to do it

The basic loop

Feathers’ recipe, as quoted by Mark Seemann from chapter 13 of the book:

  1. Use a piece of code in a test harness.
  2. Write an assertion that you know will fail.
  3. Let the failure tell you what the behaviour is.
  4. Change the test so that it expects the behaviour the code produces.
  5. Repeat.

In his 2016 post Feathers calls the process simple: “The hardest part is breaking dependencies around a piece of code well enough to be able to exercise it in a test harness.” In legacy systems that is usually most of the work. Database calls, clocks, static singletons, file I/O and network calls have to be cut at a seam before the code can run in a test at all.

Where to aim

Feathers’ heuristics, as quoted in a 2007 InfoQ summary: write tests for the area you will change, then for the specific things you will change, and if you are extracting or moving functionality, write tests that verify those behaviours still exist and are still connected. The aim is a net under the change, not full documentation of the system.

Golden master in bulk

When outputs are large or the input space is wide, assert on the whole output in one go instead of field by field. ApprovalTests’ combination approvals (“automatically testing all combinations of a set of inputs”) generate the input matrix and record every input→output line in one approved file. The documentation calls it “a powerful way to quickly get very good test coverage.”

Check the net, not just the code

A characterization test usually passes on its first real run, because it was written to match existing behaviour. A test that passes immediately proves nothing about whether it can fail. Seemann notes that “It happens with surprising regularity that you inadvertently write a tautological assertion”. His remedy is to sabotage the code under test, confirm that the intended assertion fails on the intended line, then revert. This is manual mutation testing.

The Helsinki TDD MOOC’s legacy-code exercise, based on Emily Bache and Terry Hughes’s Gilded Rose kata, mechanises the same idea. Use line coverage first “to find non-tested lines”, and once all lines are tested, “switch to using mutation coverage” (mutation-testing-ai-generated-code).

Failure modes and tradeoffs

Non-determinism

Timestamps, generated IDs, random values, hash-map ordering and platform-dependent formatting all change between runs. A golden master that includes them fails every time, and the team learns to ignore it. Jest’s documentation is direct: “You’re responsible for making sure your generated snapshots do not include platform specific or other non-deterministic data”. It offers property matchers that replace volatile fields with type placeholders such as Any<Date>. ApprovalTests calls the same mechanism scrubbers: they “clean output to help remove inconsistent pieces of text, such as dates”. Its Java options apply no scrubbing by default.

The tradeoff is over-scrubbing. Every scrubbed field is behaviour you have stopped pinning. A 2026-10-22 Stack Overflow blog piece (Panda, discussed below) advises ignoring only specific noisy fields, not broad categories. Where possible, control the source (inject the clock, seed the random generator) instead of hiding the output.

Locking in bugs

This is by design, and also a real cost. Feathers’ advice: “if you haven’t determined that the behavior you’ve uncovered is a bug, it’s often a good idea to leave the test in place.” The pin makes any later change to that behaviour a visible decision. The risk comes later, when the pinned bug reads as specified behaviour to someone who did not write the test. Jest’s docs give the snapshot form of the same warning: fix an unintentional bug “before re-generating snapshots to avoid recording snapshots of the buggy behavior.”

Mitigation: mark suspicious pins as observed, not confirmed in the test name or a comment, and send each one to someone who can rule on it. clause-loop builds this into its method: harvested behaviour arrives as observed and becomes contract only when a human promotes it, so accidental behaviour never becomes contract by default.

Brittle and unreadable snapshots

Large snapshots fail on harmless changes, and a big diff is hard to judge. Victor Cruz’s 2024 UFMG master’s thesis reviewed 50 grey-literature documents on snapshot testing. It found the technique popular because it is easy to implement and prevents regressions, but that “fragility and lack of context can lead to false positives, making it challenging for developers to interpret test failures”. The recommended practices were to treat snapshot results as part of the codebase and to keep snapshots “small” and “focused”. Fujita et al. (ICSME 2023), in a preliminary study, report that about 8.2% of commits in the projects they studied update snapshot files. That gives a sense of how much churn a snapshot suite carries.

The behavioural failure that follows is reflexive re-approval. Updating a snapshot is one command (jest -u), and approving is one file copy. Jest’s docs explicitly ask teams to “fight against the habit of regenerating snapshots when test suites fail instead of examining the root causes of their failure”, and to review snapshot files in code review like any other assertion.

Coverage gaps

A characterization test pins only the inputs you thought to try. Behaviour on untried inputs, and side effects outside the captured output (database writes, messages sent, files touched), stay unpinned. Jest notes that a snapshot is “directly scoped to the data you render”, so a component can pass its snapshot while a caller misuses it. High line coverage from a golden-master sweep also overstates protection: a line can be executed without its result reaching anything that is compared. That is why the coverage-then-mutation order above matters.

What it cannot tell you

Wikipedia states that golden-master testing “does not imply correctness of the results”. Characterization tests protect a refactor, meaning same behaviour with a new structure. On their own they do not support an intentional behaviour change. When the requirement changes, the pins on the changed behaviour have to be deliberately re-approved or replaced by intent-based tests. Otherwise the suite either blocks the change or gets bulk-regenerated, and the bulk regeneration throws away the rest of the net too.

With coding agents

Characterization tests suit agent-driven changes to legacy code because the baseline is captured before the agent acts, from the running system. It therefore does not share the agent’s assumptions. The Stack Overflow blog piece (2026) frames the risk this guards against: an assistant that “drafts a big refactor and updates the tests in the same go”. When the producer writes both the change and its expected values, the test is a co-authored oracle and inherits the producer’s misunderstanding (oracle-problem-verification).

Several practices follow from that, though the sources are thin:

  • The legacy system is the oracle, not the model. A 2026 SFEIR (consultancy) method essay on migrating WinDev applications states the rule as “aucun test dont le LLM a écrit les valeurs attendues” (no test whose expected values the LLM wrote). It attributes the formulation “le LLM génère les ENTRÉES. Le code legacy, lui seul, génère les SORTIES” (the LLM generates the inputs; the legacy code alone generates the outputs) to Hamadi Jabloun. The model may propose inputs, which helps with the coverage problem. Only the running legacy code fills in the expected values. The essay pairs this with shadow runs of both implementations on live traffic and a feature-flagged cutover once divergence reaches zero. It reports no measured results.
  • Divergences go to a human who can rule on them. In the same essay, each divergence is either a defect in the new code or a legacy bug that the business decides to fix. The agent lists suspicious cases and does not correct them.
  • Lock the baseline against the agent. If the agent can regenerate snapshots, edit approved files or disable tests, it can always reach green. A secondary account (InfoQ, 2026) of a Spotify QCon talk reports that, early in the project, agents “would take shortcuts to make builds pass, such as commenting out failing tests or downgrading Java versions.” Approved files and snapshot directories belong on the list of paths the agent may not write (deterministic-gates-agent-loop).
  • Know what the vendor gate actually is. Amazon Q Developer’s Java upgrade documentation (as read 2026-11-01) says it “re-builds and runs existing unit tests” while iterating, then presents a diff that the developer accepts. On a legacy codebase with thin coverage, that gate is only as strong as the tests that already exist. Characterization tests are how you strengthen it before the run (ai-driven-legacy-migration covers agent-generated test nets and their no-mock constraint).
  • Check the agent-built net with mutation. If an agent writes the characterization tests, as opposed to only the inputs, the tautological-assertion risk Seemann describes applies at scale. A mutation pass is the cheap check on whether the net can catch anything.

In this note’s view, legacy integration constraints matter mainly through the harness problem. A legacy system bound to a proprietary runtime, a database or a mainframe interface may only be observable end to end. In that case the golden master lives at the system boundary (recorded requests and responses, shadow traffic) rather than at the unit level. Coarser pins localise failures less precisely, and they pick up more non-determinism.

What needs more research

  • No measured evidence for the agent case. As of 2026-11-01 this review found no first-party, measured account of characterization or golden-master tests gating a real agent-driven legacy migration, and no study comparing defect escape with and without them. The practices above are reasoning plus method essays.
  • LLM-generated characterization tests. Agent-written test nets are reported in practice (see ai-driven-legacy-migration), but no study was found of how often LLM-written characterization assertions are tautological or quietly wrong. UnitTenX (arXiv 2510.05441, 2025) combines LLM agents with bounded model checking (ESBMC) to generate unit tests for legacy C; its abstract reports no figures.
  • Triage cost. LLMShot (arXiv 2507.10062, 2025) uses vision-language models to classify failing UI snapshots as regressions or intended changes. The abstract reports 84%+ recall for its 12B variant on an iOS dataset. Whether model triage of golden-master diffs helps or simply automates re-approval is open.
  • Snapshot evidence beyond Jest. The empirical work found (Cruz 2024; Fujita et al. 2023) is centred on frontend snapshots (Cruz’s corpus is Jest; the Fujita et al. summary does not state language scope), not on backend or legacy golden masters.
