Effective Code Review

Synthesis of preliminary deep research (2026-06-05) on what makes code review effective: empirical findings, the Google eng-practices standard, author-side discipline, reviewer hierarchy, review psychology, communication conventions, and the human/machine split. Captured to feed a future code-review skill — see Implications for a code-review skill.

What review is actually for

  • Developers say the goal is defect detection, but only ~15% of review comments point to actual defects (Microsoft research: Bacchelli & Bird 2013; the 15% figure is usually cited from Czerwonka et al. 2015, “Code Reviews Do Not Find Bugs”).
  • The dominant real outcomes: knowledge transfer, team awareness of changes, and alternative-solution discussion. Understanding the rationale behind a change is the hardest and most valuable part.
  • With CI, tests, and static analysis catching mechanical defects, human review has moved up the abstraction gradient: from code-centric (is this line correct?) to intent-centric (does this solve the right problem maintainably?). Humans are poor compilers but good architectural validators.

Cognitive limits (SmartBear/Cisco study)

Source: SmartBear’s study of a Cisco team, ~10 months / ~2,500 reviews (Cohen, Best Kept Secrets of Peer Code Review). Caveat: vendor research (SmartBear sells a review tool), not peer-reviewed — treat thresholds as calibrated folklore, not law. They are nonetheless the most-cited numbers in the field.

MetricThresholdBeyond it
Review size200–400 LOC per sessionDefect discovery drops sharply; ≥1,000 LOC → rubber-stamping
Duration≤60 min uninterruptedAnalytical fatigue, missed edge cases
Velocity<500 LOC/hourSuperficial reading
Defect yield70–90% when within limitsDecays as size/speed/duration grow
  • Ego Effect: the expectation of review improves submitted code. Spot-checking 20–33% of changes lowered defect density across the whole codebase — a 1-in-3 chance of scrutiny is enough.
  • Lightweight asynchronous tool-based review found as many bugs as formal Fagan-style inspection in ~20% of the time. Heavyweight inspection meetings are empirically dead.

The standard: code health strictly improving

From Google’s eng-practices (google.github.io/eng-practices):

  • Senior principle: approve once the change definitely improves overall code health, even if not perfect. There is no perfect code, only better code.
  • Two failure modes it balances: gatekeeping perfectionism (disincentivizes incremental improvement) vs. permissive approval (death by a thousand cuts).
  • Only hard exception: feature appropriateness — a reviewer may reject a well-built feature they don’t want in the system.
  • Conflict resolution: technical facts and data overrule opinion; the style guide is absolute authority on style; anything not in it is personal preference → stay consistent with local code, else author wins. Equally-valid design alternatives → author wins. Stuck threads escalate to synchronous discussion, with the decision recorded on the change.

Author-side discipline

The review is only as good as the artifact. Author obligations:

Small, atomic changes

One logical change per CL/PR; ~100–250 lines is the commonly cited sweet spot, 400 the hard ceiling. Include tests in the same change. Splitting strategies for large work:

StrategyMechanism
Stacked changesBranch the next change off the previous one while it’s in review — author never blocks
File-basedOrthogonal pieces to different domain experts in parallel
HorizontalSlice by layer (API stub / data model / client)
VerticalSlice by feature, full stack per micro-interaction
Refactoring separationMechanical moves/renames reviewed separately from behavioral changes — never hide logic in a movement diff

Horizontal × vertical compose into a matrix: each cell is one reviewable unit.

The description is a first-class artifact

The PR description is the permanent public record of why; future readers (and AI tools) navigate history through it. Shape:

  • Title: imperative, stands alone (“Delete the FizzBuzz RPC and replace it with X”).
  • Why / context: bug, feature, or debt — the semantic frame the reviewer judges against.
  • How: approach taken, alternatives considered and rejected (pre-empts the reviewer re-proposing them).
  • Risks / trade-offs: points the reviewer’s limited attention at the vulnerable spots.
  • Testing instructions: how to validate manually.

The reviewer hierarchy

Evaluate top-down, broadest first — never line-by-line from the top:

  1. Design / system integration — does the change belong here, does it couple things it shouldn’t, is it over-engineered (solving hypothetical future problems instead of today’s)?
  2. Functionality, security, user impact — edge cases, race conditions, deadlocks (the things deterministic tests miss); injection/XSS/CSRF, input sanitization, sensitive-data handling; demo/screenshot for UI changes.
  3. Complexity — “too complex” = a peer can’t understand it quickly, or a future modifier will likely introduce a bug. Cleverness is not a defense.
  4. Tests — present in the same change, meaningful (not coverage theater), deterministic, fail only on real breakage. Error handling: graceful failure, useful messages, logging.
  5. Naming, comments, docs — names communicate purpose; comments explain why, never what (a what-comment is a refactoring signal); READMEs/docs updated in tandem.

Psychology: egoless programming

Weinberg, The Psychology of Computer Programming (1971): programmers fuse identity with output, turning review into perceived personal attack. Operative commandments for review:

  • You are not your code — a defect is an artifact to fix, not a verdict on the author.
  • Mistakes are statistically certain; a found problem is the system working, not a failure.
  • Critique code, not people: “this function lacks a null check,” never “you forgot again”; “we” over “you”.
  • Respect and patience — reviews are the highest-leverage mentoring channel; include genuine praise for elegant work.

Communication: Conventional Comments

conventionalcomments.org — machine-parseable label prefix per comment: <label> [decorations]: <subject>.

LabelMeaningBlocking?
issue:Bug/security/structural problem; pair with a suggested fixYes
suggestion:Concrete improvementPer decoration
question:Reviewer lacks context — burden on reviewer, softens critiqueUsually no
nitpick:Trivial style preferenceExplicitly no
thought:Architectural musing, seed for laterNo
chore:Process task (ticket, CI run)Process-level
todo:Small necessary follow-upMinor
praise:Sincere positive — aim for ≥1 per review—

Decorations: (non-blocking), (blocking), (if-minor) — give the author explicit autonomy.

Anti-patterns this counters

  • Bikeshedding: arguing trivia while architecture rots. Counter: nits explicitly optional, or “no nits” during the core pass.
  • Priority inversion: days of typo rounds, then “by the way, the design is wrong — rewrite.” Counter: the hierarchy above — verdict on design first, nits only after the foundation is approved.

Speed and emergencies

  • Slow review compounds: context evaporates, feedback loops stretch to weeks, pressure builds to approve junk. Maximum first response: one business day; healthy teams complete multiple round-trips per day. Track time-to-review.
  • But never interrupt flow state to review — batch at natural breakpoints. The speed of the individual response matters more than time-to-approval: if you can’t review now, say when, suggest someone else, or approve with non-blocking comments.
  • Real emergencies (production-down, zero-day, rollback-avoidance, legal) reduce review to one question — does this safely fix the emergency? — with retroactive full review after. Fake emergencies (sprint deadlines, Friday deploys, “I’ve worked on it so long”) get no bypass; that bypass is a primary technical-debt vector.

Human/machine split

  • Deterministic layer (linters, formatters, SAST: ESLint/Prettier, SonarQube, Semgrep, Codacy): hard CI gates. Humans must never spend cycles on what these catch — formatting arguments are automation failures.
  • Semantic layer (LLM reviewers: CodeRabbit, Greptile, Qodo, GitLab Duo, Devlo (last one unverified)): understand context and intent, catch cross-caller logic issues, draft summaries. Non-deterministic → unusable as compliance gates; quality is capped by how much repo context they see beyond the diff (the “monorepo problem”; enterprise tools add codebase-wide retrieval).
  • Human layer: final architectural validation and accountability. “An AI reviewed it” is not an auditable position in regulated industries; a human owns the merge. Emerging pattern: adversarial AI review — one model writes, a different model attacks, human arbitrates both.
  • 2026-typical pipeline: AI feedback at draft time → static gates in CI → human architectural pass.

Implications for a code-review skill

What the research says a Claude code-review skill should encode (vs. what /lean-review and built-in /code-review already do):

  1. Altitude-ordered output — verdict on design/approach before any line-level findings; never emit nits if the design verdict is “rewrite” (priority-inversion guard).
  2. Label taxonomy — emit findings as Conventional-Comments-style labels with explicit blocking status; issue: requires a suggested fix.
  3. Net-improvement verdict semantics — the approve/request-changes call is “does this improve code health,” not “is this perfect”; minor items are non-blocking by default.
  4. Size guard — flag diffs beyond ~400 changed LOC as needing decomposition and name the applicable splitting strategy, rather than pretending one pass covers them.
  5. Don’t duplicate the machine layer — skip anything a linter/formatter/SAST gate would catch; spend tokens where automation is weak: logic edge cases, concurrency, intent-vs-implementation drift, coupling.
  6. Description review — review the PR description as an artifact (imperative title, why, rejected alternatives, risks); a missing description is itself a finding.
  7. Hunt where tests can’t see — race conditions, swallowed errors, invariants the suite doesn’t encode; check tests for coverage theater (connects to evaluating-ai-code-beyond-tests’s hollow-tests finding).
  8. Tone rules are cheap to encode — comment-the-code-not-the-author phrasing, ≥1 praise when warranted.
