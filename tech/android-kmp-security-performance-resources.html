Security

Standards — the vocabulary auditors use

  • OWASP MASVS — the mobile security verification standard: 8 control groups (STORAGE, CRYPTO, AUTH, NETWORK, PLATFORM, CODE, RESILIENCE, PRIVACY). Baseline for audits and pen-test scope in regulated sectors. Start here. v2.1.0 is current (its release year is not shown on the page).
  • MAS Testing Profiles — replace the old L1/L2/R levels: MAS-L1 Essential, MAS-L2 Advanced (extends L1), MAS-R resilience, MAS-P privacy. Pick one per app; L2 is the natural target for banking.
  • OWASP MASTG (v2 — the first stable release of the refactored guide) and MASWE (78 weaknesses) — the chain is MASVS control → MASWE weakness → MASTG test. For security testers.
  • OWASP Mobile Top 10 (2024) — M1 Improper Credential Usage, M2 Supply Chain, … M10 Insufficient Cryptography. A risk list for briefings, not a verification standard.
  • Mobile Application Security Cheat Sheet — the best short first read for a web engineer.

Android platform

  • Security checklist — entry point for an Android security review: Credential Manager, Play Integrity, storage, explicit android:exported, WebView, API keys, IPC.
  • Mitigate security risks — 44 named risks grouped by MASVS category, each with mitigation; good source for review checklists and lint rules.
  • Android Keystore — hardware-backed keys, StrongBox (Google advises it only for high-threat models), attestation, auth-bound keys. Biometric-bound keys invalidate on new enrolment by default. The core of secure storage now that security-crypto is deprecated.
  • BiometricPrompt — BIOMETRIC_STRONG + CryptoObject for crypto-backed auth; per-operation auth for payments.
  • Credential Manager and passkeys — one API for passkeys, passwords and federated sign-in; passkeys on Android 9+.
  • Play Integrity + standard requests — bind the token to the request with requestHash; decode server-side.
  • Network security config — declarative SPKI pinning; the page warns a mistake “can block all connections to that domain until an app update is released”.
  • R8 app optimization — full mode default since AGP 8.0; the docs frame obfuscation as size reduction, not a security guarantee.
  • App security improvement program — Play scans uploads; some warnings carry remediation deadlines. Make zero open alerts a release gate.

iOS side, as it affects KMP

App Transport Security, Keychain services and App Attest are the iOS counterparts of network config, Keystore and Play Integrity. Page bodies (unverified) — JS shells.

Secure storage from shared Kotlin — a real gap

  • Multiplatform Settings — the standard KMP key-value abstraction. Its default does not encrypt (NSUserDefaults on Apple); KeychainSettings is marked experimental.
  • KVault — Keychain + “encrypted SharedPreferences”; maintenance unclear, and the Android side likely sits on the deprecated library (unverified).
  • Touchlab’s encrypted KV pattern (2021) — sound shape, but its Android half uses the deprecated library.
  • Implication: for tokens and secrets, define an expect/interface in common code and implement it directly on Keystore (Android) and Keychain (iOS), with a documented encryption scheme, rather than adopting a wrapper library.

Supply chain

  • Gradle dependency verification — verification-metadata.xml with sha256 + PGP; checksums give integrity, signatures give provenance; generated entries need review.
  • Dependency locking — committed gradle.lockfile, strict mode.
  • CycloneDX Gradle plugin — SBOM generation; README doesn’t mention KMP or Android and doesn’t see Swift/SPM deps — spike it on the real module graph.

Performance

  • Android vitals — the source for every Play threshold. “Bad behavior” (28-day window): user-perceived crash rate 1.09% overall / 8% per phone model; ANR rate 0.47% / 8%; excessive partial wake locks 5%. Exceeding them can reduce Play visibility.
  • Baseline Profiles — AOT-compile critical paths; “about 30%” faster code execution as a typical, not guaranteed, result. Non-Play distribution may not apply them.
  • Macrobenchmark (startup, jank; physical devices, release-like build) and Microbenchmark (hot loops).
  • App Startup — one initializer replacing per-SDK content providers, with explicit ordering. A big app with many SDKs needs it.
  • Perfetto — system tracing for startup, jank, ANRs, memory.
  • Compose performance best practices — release build first; then remember, derivedStateOf, lazy-list keys, deferred state reads.
  • Reduce app size — AAB, R8 + resource shrinking, strip native symbols.
  • Kotlin/Native memory manager — tracing GC (concurrent mark-and-sweep by default); Instruments integration via VM Tracker and enableSafepointSignposts. Memory fixes ship in compiler releases — track Kotlin versions.
  • We built the same app in KMP and React Native — Software Mansion (2026-07-02). One app, vendor-authored: KMP much smaller and 2–4× faster to start on Android; near-parity on iOS size and startup, but higher iOS RAM (~157–251 MB vs RN’s ~44–131 MB). A reality check, not a verdict — measure your own.

Accessibility (mobile)

  • Accessibility in Compose and Semantics — the semantics tree is the ARIA-tree equivalent; custom low-level composables must supply their own semantics.
  • Testing Compose accessibility — automated checks since Compose 1.8 via enableAccessibilityChecks() (labels, contrast, touch targets, traversal). Wire into CI.
  • Accessibility testing guide + Accessibility Scanner — “isn’t a replacement for manual testing” (TalkBack, Switch Access, Voice Access, real users).
  • Accessibility foundations — 48 dp touch targets, 4.5:1 text contrast, 3:1 non-text, sizes in sp.
  • Compose Multiplatform iOS accessibility — VoiceOver reads Compose semantics; performAccessibilityAudit() works in XCUITest. Gaps: no built-in high-contrast Material3 scheme; the tree syncs lazily. No formal stability label for accessibility itself — audit with real VoiceOver users.
  • W3C mobile accessibility — no separate mobile guidelines; WCAG 2.x applies, mapped by the draft WCAG2Mobile note.
  • European Accessibility Act (Directive 2019/882) — consumer services provided after 28 June 2025 must comply; consumer banking is in scope. The harmonised standard commonly linked is EN 301 549 (V3.2.1 — whether a newer version is in force is (unverified)). Confirm scope with counsel.

Privacy

  • Play Data safety and Apple App Privacy Details — you declare third-party SDK collection too; Google doesn’t verify accuracy.
  • Privacy manifest for KMP iOS apps — App Store Connect rejects undeclared required-reason APIs (ITMS-91053). Compose Multiplatform touches stat/fstat and mach_absolute_time; JetBrains ships a finder script and a Gradle plugin. See also Apple’s third-party SDK list.

Release checklist

Security

  1. MAS profile chosen (L1 baseline; L2 for finance) and controls mapped to MASVS groups.
  2. Threat model covers the Mobile Top 10 2024, especially M1 credentials, M2 supply chain, M7 binary protection.
  3. R8 on in release with narrow keep rules; obfuscation treated as friction, not protection.
  4. No secrets in the client; key material in Keystore/Keychain.
  5. No new security-crypto; migration plan if present.
  6. Hardware-backed keys; auth-bound keys for high-value actions.
  7. iOS secrets in the Keychain — and the KMP abstraction doesn’t silently default to unencrypted storage.
  8. BIOMETRIC_STRONG + CryptoObject for sensitive operations.
  9. Credential Manager + passkeys for sign-in.
  10. If pinning: SPKI pins, backup pin, tested rotation, no user bypass.
  11. Server-side attestation (Play Integrity with requestHash; App Attest on iOS) with a per-risk fail-open/fail-closed policy.
  12. Verification metadata + lockfile committed; SBOM generated in CI.
  13. Zero open Play ASI alerts; every component sets android:exported.
  14. ATS exceptions per-domain only.

Performance 15. [ ] Perf claims only from release/benchmark builds; Macrobenchmark startup + jank on physical devices in CI. 16. Privacy 27. [ ] Data safety form and Apple labels cover every SDK. 28. [ ] PrivacyInfo.xcprivacy declares Kotlin/Native and Compose required-reason APIs; each SDK ships its own manifest.

Tradeoffs

  • Certificate pinning. OWASP calls it a last resort (“almost no situation where you should consider pinning”); a mistake blocks connectivity until an app update ships, and corporate TLS-inspection proxies break it. Many banks pin anyway for compliance — if so, plan rotation as an operational process.
  • Root/jailbreak detection and RASP. MASVS-RESILIENCE: “The absence of these measures does not in itself constitute a vulnerability.” False positives exclude legitimate users; attestation adds platform lock-in. Never the primary control — server-side validation comes first.
  • StrongBox — stronger than the TEE but slower and algorithm-limited; Google advises it only for high-threat models.
  • Play Integrity verdicts are risk signals, not an allow-list, and tie you to Google Play.
  • Compose Multiplatform on iOS — stable, but higher memory than alternatives in one benchmark and accessibility gaps; regulated products should audit, not trust labels.
  • Crash reporting — third-party SDKs support KMP; Crashlytics needs CrashKiOS with caveats.
