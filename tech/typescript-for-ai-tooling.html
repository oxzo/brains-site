TypeScript for AI Tooling

What it is

Patterns and practices for building AI-powered tools, agents, and integrations in TypeScript. TypeScript has become the de facto language for AI application development — the Anthropic SDK, OpenAI SDK, Vercel AI SDK, and MCP SDK are all TypeScript-first, and the type system maps naturally onto tool schemas and structured outputs.

Why it matters

Building AI tools requires handling complex, semi-structured data flows: tool schemas, streaming responses, multi-turn conversations, and error recovery. TypeScript’s type system catches schema mismatches at compile time, and its async/streaming primitives fit the event-driven nature of LLM APIs. If you’re building agents, MCP servers, or AI-enhanced CLIs, TypeScript is the most productive choice.

Agentic loops

The core pattern for an agent: send messages, check for tool use, execute tools, feed results back:

Key design decisions:

  • Max iterations: always cap the loop to prevent runaway costs. 20 is a reasonable default; adjust based on task complexity.
  • Error as tool result: return errors back to the model as is_error: true tool results so it can self-correct. Never throw from a tool handler — the agent loop should keep running.
  • Retry logic: the SDK handles 429 retries automatically. For your own transient failures (network, database), add retry logic in the tool handler itself.

Token management and context windows

Large agent conversations can exceed context limits. Strategies:

  • Summarize older messages: periodically ask the model to summarize the conversation so far, replace old messages with the summary.
  • Truncate tool results: large tool outputs (file contents, search results) can dominate the context. Truncate or summarize before pushing into messages.
  • Track token counts: use the usage field from each response to track cumulative context size.

For precise counts, use the Anthropic token counting endpoint or the @anthropic-ai/tokenizer package.

  • Mock API responses: create fixtures of Anthropic.Message objects and stub the client. The SDK types make this straightforward:

  • Snapshot testing: snapshot tool schemas to catch accidental changes. Zod schemas make this easy since they serialize to JSON Schema deterministically.

  • Integration tests: use a cheap model (e.g., Haiku) with real API calls for end-to-end agent loop tests. Set low max_tokens to keep costs down.

  • Deterministic seeds: not yet available in the Anthropic API, so integration tests will have some variance. Assert on structure, not exact text.

  • Vitest/Jest setup: for projects using tsx, configure Vitest with globals: true and use vi.mock() to stub the Anthropic client.

Common pitfalls

  • Forgetting "type": "module" in package.json: the MCP and Anthropic SDKs use ESM. Without this, you get ERR_REQUIRE_ESM errors.
  • Not handling stop_reason: "max_tokens": if the model hits the token limit mid-response, it stops abruptly. Check for this and either increase max_tokens or prompt the model to continue.
  • Mutating the messages array outside the loop: the agent loop owns the messages array. If you modify it from another part of your code, you can corrupt the conversation state.
  • Huge tool results: returning a 100KB file as a tool result wastes context window. Truncate, summarize, or paginate large outputs.
  • Not validating tool input: always parse tool inputs through Zod (or equivalent) before using them. The model can send malformed data, especially with complex schemas.
