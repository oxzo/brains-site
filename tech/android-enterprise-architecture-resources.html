Official Google guidance — read in this order

  1. Guide to app architecture — two required layers (UI, data), optional domain layer; single source of truth, unidirectional data flow (UDF), DI. Mandatory baseline.
  2. Architecture recommendations — the best single review checklist. “Strongly recommended” items include: repositories even for one source; coroutines + Flow between layers; UDF; collectAsStateWithLifecycle; don’t send events from ViewModel to UI — model them as state; single activity with Navigation 3; no Context in ViewModels; ViewModels at screen level only; prefer fakes to mocks; R8 full mode + Baseline Profiles.
  3. UI layer and Producing UI state — “State is; events happen.” combine + stateIn(WhileSubscribed(5_000)); don’t launch coroutines in init.
  4. Domain layer — optional; warns against pass-through use cases. A useful brake on over-layering.
  5. Data layer and Offline-first — repositories own the source of truth; local DB as truth for offline; write strategies (online-only / queued / lazy), sync (pull / push / hybrid), conflict resolution.
  6. Modularization guide — benefits (reuse, visibility, ownership, build time) and the pitfall of modules too fine or too coarse.

Compose:

  • State and Jetpack Compose — remember, rememberSaveable, hoisting rules. Read first.
  • Side-effects — LaunchedEffect, DisposableEffect, derivedStateOf, snapshotFlow, rememberUpdatedState.
  • Compose architecture — pass each composable the least it needs.
  • Stability + strong skipping — unstable params compare by ===, stable by equals; lambdas auto-memoized. Removes most @Immutable folklore.
  • Compose performance — measure in release mode with R8 and Baseline Profiles before tuning code.
  • API Guidelines for Jetpack Compose and for @Composable components — the rules for an internal component library: modifier as first optional param, emit or return never both, slots over CompositionLocal.
  • Design systems in Compose — custom design systems and theme anatomy; pairs with design-system-component-apis.

Navigation and ViewModel:

  • Navigation 3 overview — you own the back stack as a list of keys; NavDisplay renders it.
  • Nav2 → Nav3 migration — doubles as a statement of Nav3’s limits: Compose-only, no more than one level of nested navigation, no shared destinations across back stacks.
  • ViewModel overview and ViewModel in KMP — no Hilt in common code; SwiftUI can’t observe Flows directly (needs SKIE or KMP-NativeCoroutines).

Reference apps worth studying

  • Now in Android — Google. The map of current recommendations. Offline-first, fakes instead of mocking libraries, Roborazzi screenshots. Read its Architecture and Modularization learning journeys: feature modules split into api/impl; impl may depend only on other features’ api; core never depends on features. Its build-logic is the convention-plugin template. No evidence yet of a Nav3 migration.
  • Bitwarden Android — ARCHITECTURE.md — the best production write-up found: data sources → managers → repositories; BaseViewModel with one StateFlow, an action channel and a one-shot event flow; Hilt. Security-sensitive domain, so close to an enterprise context.
  • android/nav3-recipes — modular navigation with Hilt, Koin and Metro variants, results, deep links, multiple back stacks. Points to terrakok/nav3-recipes for Compose Multiplatform.
  • Pocket Casts Android — real app mid-migration (Compose and Views coexist), feature/service modules. Study for migration reality.
  • Signal Android — study for build/tooling layout (build-logic, baseline-profile, microbenchmark, lintchecks, reproducible builds); architecture not assessed.
  • android/architecture-samples — simple to-do app; good for basics, not enterprise-scale.
  • Don’t study for current practice: Tivi (archived 2024-11-12, a 2022–24 KMP snapshot), Fenix (archived).

Architecture patterns beyond MVVM

  • Circuit — Slack. Presenter (Compose runtime emitting state) + Ui + Screen key; “used in production at Slack”. Still 0.x.
  • Molecule — Cash App (2022). Presenters as composable functions — imperative if/when instead of chained Flow operators. Repo.
  • Decompose — Arkadii Ivanov. Lifecycle-aware components with shared navigation whose UI is pluggable (Compose, SwiftUI, Kotlin/React). The option that doesn’t tie navigation to Compose — relevant when the web UI is native DOM.
  • Redwood — Jake Wharton, Cash App (2023). Compose-the-language driving native UI per platform; beta at the time.
  • Workflow (Square, Kotlin + Swift), Mavericks (Airbnb), RIBs (Uber, 2018 — pre-Compose but still the clearest argument for strict structure at ~200 engineers and 40+ sub-teams; plugin points behind flags so non-core features can fail without stopping the core flow).

Modularization at scale — case studies

  • Scaling Slack’s mobile codebases: modularization (2022-03-28) and modernization (2022-05-04) — every module has an owner; Feature/Service/Library module types; they deliberately did not mandate api/impl pairs because doubling subprojects costs configuration time. Reported “92% Modularized”, p95 time-to-merge down 30%.
  • Gradle modularization delivers 3x faster Android builds — Automattic (2025-09-08). Rare controlled experiment: 37 modules vs a merged monolith. Incremental builds 1.3–3.6× faster with modules, CI ~3× faster — but IDE sync ~5× slower (0.8 s vs 4.0 s).
  • Square’s 3,500→4,400-module Gradle posts are in android-kmp-testing-build-ci-resources.
  • GitHub CODEOWNERS — the mechanism that makes “every module has an owner” enforceable.

Books

  • Jetpack Compose Internals — Jorge Castillo (last updated 2022-11-20). Slot table, composer, recomposer, snapshots. Good mental model, but pre-dates strong skipping and the compiler moving into Kotlin — don’t trust it on current compiler behaviour.

Study order for a JS/TS developer

  1. Kotlin + coroutine basics (see kotlin-code-quality-resources).
  2. Guide to app architecture → recommendations. UDF is Redux/React’s state-down, events-up.
  3. Compose state → side-effects. mutableStateOf ≈ useState, remember ≈ useMemo/useRef. Where it breaks: recomposition tracks the state a composable reads — there’s no dependency array — and LaunchedEffect keys act like useEffect deps but launch coroutines.
  4. Stability and strong skipping — automatic React.memo; === vs equals is the re-render pitfall to review for.
  5. ViewModel + state production. A screen-scoped store that survives rotation. Process death (SavedStateHandle) has no web analogue.
  6. Now in Android and its two learning journeys, then Bitwarden’s architecture doc.
  7. Data layer + offline-first — like a normalized client cache, except the database is the truth and the UI never reads the network directly.
  8. KMP layer — the Jetpack KMP matrix, the KMP ViewModel guide, the Nav3-on-CMP page.
  9. DI — Hilt concepts first (graph, scope, binding), then Metro/Koin. Closest JS analogy is NestJS/InversifyJS, but resolution happens at compile time.
  10. Case studies — Slack’s two posts, Square’s Metro migration, Automattic’s benchmark, Uber RIBs.

Principles the sources agree on

  • Data and UI layers always; a domain layer only when it earns its keep.
  • One source of truth per data type, exposed immutably.
  • State down, events up — no ViewModel→UI event streams, model them as state.
  • ViewModels are screen-level and never hold Context; reusable components use plain state holders.
  • Hoist state to the lowest common owner; pass composables the least data they need.
  • Fakes over mocks; test ViewModels and data layers.
  • Module dependencies point one way: features → other features’ api only; core never → features.
  • Every module has an owner and a small public surface.
  • Don’t over-modularize — fine-grained modules cost configuration and IDE-sync time.
  • Make non-core features flaggable and removable so they can fail alone.
  • Measure performance in release mode before tuning code.

Where the sources disagree

  • Shared navigation on KMP. Google recommends Nav3, but the multiplatform port is JetBrains’, covers navigation3-ui only, and is bound to Compose. With a native DOM web UI, shared navigation state has to come from elsewhere — Decompose, Circuit, or an in-house back-stack model (the approach in 2026-10-10-kmp-shared-viewmodels-navigation). None was found proven in a native-web setup. Browser history on web is not in Nav3’s base library.
  • MVVM vs presenters. Google says screen-level ViewModels; Circuit/Molecule argue Compose-runtime presenters are easier to write and test. Neither side has independent benchmarks; Circuit is 0.x.
  • Hilt vs KMP DI. Hilt is official but can’t enter shared code; Metro is young but has the Square data point; Koin’s compile safety is new.
  • Domain layer. Google calls it optional and warns against pass-through use cases; NiA uses one. Pick a rule early.
  • api/impl everywhere? NiA does it; Slack avoided it for configuration cost. At 1M LOC these pull in opposite directions — measure.
  • Compose Multiplatform web. The only primary statement says Beta. Verify with JetBrains before committing a web UI to it (this vault’s current direction is a native web UI anyway — see kmp-web-accessibility for why).
