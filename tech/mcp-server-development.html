MCP Server Development

What it is

The Model Context Protocol (MCP) is an open standard for connecting AI agents to external tools, data sources, and services. An MCP server exposes tools (functions the agent can call), resources (data the agent can read), and prompts (reusable prompt templates) over a simple JSON-RPC transport. Building an MCP server lets you give any MCP-compatible AI client (Claude Code, Claude Desktop, Cursor, etc.) access to your own systems.

Why it matters

MCP solves the “N x M” integration problem: instead of building custom integrations between every AI client and every tool, you build one MCP server and it works with all MCP clients. This is the same pattern that LSP brought to editors. For personal infrastructure — like this Obsidian vault’s “brains” MCP server — it means your AI assistant can read, search, and write your notes through a well-defined interface.

Details

Architecture

MCP uses a client-server model over two transport types:

  • stdio: the client spawns the server as a subprocess and communicates over stdin/stdout. Best for local tools. This is what Claude Code and Claude Desktop use.
  • Streamable HTTP: the server runs as an HTTP endpoint using Server-Sent Events for server-to-client streaming. Best for remote/shared servers. Replaces the older SSE transport (deprecated in the 2025-03 spec revision).

The wire protocol is JSON-RPC 2.0. Messages are newline-delimited JSON over stdio, or HTTP POST/SSE over Streamable HTTP.

The protocol defines three capability types:

CapabilityDirectionPurpose
ToolsClient calls serverFunctions the AI can invoke (search, write, compute)
ResourcesClient reads serverData the AI can browse (files, DB records, API data)
PromptsClient reads serverReusable prompt templates with parameters

Defining tools

Each tool has:

  • name: unique identifier (snake_case by convention)
  • description: natural language description the AI reads to decide when to use the tool
  • inputSchema: JSON Schema or Zod schema defining the parameters
  • handler: async function that receives validated input and returns content blocks

Write descriptions as if explaining to a human colleague what the tool does and when to use it. The AI relies heavily on this description for tool selection.

Tool description best practices:

  • Explain when to use the tool, not just what it does
  • Mention what it returns and common failure modes
  • Keep it under ~200 words — the AI reads every tool description on every call
  • Use examples in the parameter descriptions (e.g., “e.g., ‘knowledge/tech/mcp.md’“)

The filesystem MCP server pattern

A common pattern is wrapping a local directory (like an Obsidian vault) with an MCP server that provides:

  • read_file / write_file / edit_file — file CRUD
  • search_files — content search (grep-like)
  • list_directory / directory_tree — navigation
  • get_file_info — metadata (size, modified date)

This is exactly what the “brains” MCP server does for this vault. It constrains access to allowed directories and provides a safe interface for the AI to interact with the filesystem.

Anthropic provides @anthropic-ai/mcp-filesystem as a ready-made implementation of this pattern.

Security considerations

MCP servers run with the privileges of the user who starts them. Critical safeguards:

  • Path traversal prevention: resolve all paths against an allowed root and reject anything that escapes it. Use path.resolve() and verify the result starts with the allowed prefix. Watch out for symlinks — use fs.realpath() to resolve them before checking.
  • Input validation: validate all tool inputs against their schemas before processing. Never trust that the AI sent valid data. Zod schemas in server.tool() handle this automatically.
  • Allowlisting: explicitly list which directories or operations are permitted. Deny by default.
  • Rate limiting: for remote servers, rate-limit tool calls to prevent abuse. Use middleware on the HTTP transport.
  • No secrets in tool outputs: be careful not to leak environment variables, credentials, or sensitive file contents through tool responses. Filter out .env files, *credentials*, etc.
  • Command injection: if your tool runs shell commands, never interpolate user input into command strings. Use execFile (not exec) and pass arguments as an array.

Common pitfalls

  • Forgetting ESM setup: the MCP SDK is ESM-only. Ensure "type": "module" in package.json and "module": "Node16" in tsconfig.json. See typescript-for-ai-tooling for details.
  • Writing to stdout: any console.log in an stdio server corrupts the transport. Use console.error or file logging instead.
  • Tool descriptions too vague: “Searches files” is not enough. The AI needs to know what kinds of files, what the query format is, and what the output looks like.
  • Not handling large outputs: if a tool can return megabytes of data (e.g., reading a huge file), truncate or paginate. Large responses waste the AI’s context window.
  • Missing error context: "Error occurred" is useless. Return "File not found: path/to/file. Available files: [list]. Use list_directory to browse." — give the AI enough context to self-correct.
  • Synchronous operations blocking the event loop: all tool handlers should be async. Use fs/promises (not fs), and avoid CPU-heavy synchronous work.
