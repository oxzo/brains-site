KMP Web Accessibility — WCAG Under a Canvas-Rendered UI

As of 2026-08-31 (second pass; first pass 2026-08-26). Fast-moving: source claims below were read against jb-main on that date, tracker state against the YouTrack REST API on that date. Re-verify before citing.

Second-pass summary. The WCAG verdict below is unchanged and re-verified against live jb-main: no aria-checked, aria-valuenow, aria-live, aria-level, or tabindex is emitted, so 4.1.2 and 4.1.3 still fail at the framework level. What changed is the investment reading, in both directions. JetBrains merged three web-a11y PRs in August 2026 — two of them after 1.12.0 shipped, so they are queued for the next release and invisible in any release note. One of them resolves an open question this note raised. Meanwhile the near-complete fix for the ARIA gap exists as an unmerged external draft PR, stale since May. See What changed since the first pass, below.

“Does KMP web support WCAG” is two questions, because “KMP web” names two architectures with opposite accessibility profiles. Getting the split right is most of the answer.

The split — which architecture are you asking about

(1) Shared Kotlin core + web-native DOM UI. Kotlin compiles to a JS/Wasm library; React (or any DOM framework) renders the UI. This is the architecture evaluated in kotlin-multiplatform-web-enterprise, with the boundary detailed in kmp-js-interop-boundary.

Here KMP is invisible to assistive technology. The compiled Kotlin never touches the DOM — it returns values that your React components render as real HTML. Accessibility is exactly the accessibility of your component layer: the same problem, the same tools, the same answers as any React app. See design-system-accessibility. WCAG imposes no KMP-specific constraint in this architecture, and this note’s findings do not apply to it.

(2) Compose Multiplatform for Web (Kotlin/Wasm). Compose renders the entire UI into a single <canvas> via Skia. To a browser and to a screen reader, the app is one opaque graphic. Accessibility exists only insofar as the framework synthesizes a parallel DOM that mirrors the semantics tree.

Everything below is about (2).

Status of the target itself

  • Compose Multiplatform 1.12.0 released 2026-08-25 (GitHub releases).
  • Web is still Beta on both stability tables — “Web based on Kotlin/Wasm: Beta” for core KMP and for the Compose UI framework (kotlinlang.org supported-platforms; that page’s own footer reads 10 September 2025, so it may lag the 1.12 release).
  • Web accessibility first shipped in 1.9.0 (2025-09-16) via PR #2188, merged 2025-07-07, closing CMP-7675. The umbrella request CMP-5937 (“Compose Multiplatform Web / Wasm support accessibility”) was resolved 2025-11-17.
  • 1.12.0 is still the latest release as of 2026-08-31 (no 1.13.x, no newer prerelease). Two of the three August accessibility merges below postdate it, so the shipped artifact lags jb-main.
  • It is on by default; ComposeViewport(configure = { isA11YEnabled = false }) turns it off (What’s new in 1.9.0).

How it actually works

Verified by reading compose/ui/ui/src/webMain/kotlin/androidx/compose/ui/ on jb-main, 2026-08-26.

The DOM ComposeViewport builds (comment block in window/ComposeWindow.web.kt):

<container>
  <positioning_container>
    <shadow_container.shadow>      ← open shadow root
      <style/>
      <app_container>
        <canvas/>                  ← tabindex="0" role="generic" draggable="true"
        <a11y_container/>          ← the mirror, position:absolute, 100%×100%
      </app_container>
    </shadow_container>
    <interopContainer/>
  </positioning_container>
</container>

platform/accessibility/ComposeWebSemanticsListener.kt walks the Compose semantics tree and mirrors each node into a position: fixed <div> inside a11y_container, sized and placed to overlay the canvas pixels it represents. Screen readers read the mirror; clicks on the mirror are forwarded to Compose. Architecturally this is the same trick Flutter Web uses.

Two properties of the sync worth knowing:

  • It is debounced. DEBOUNCE_MS = 100, MAX_TIME_IN_DEBOUNCE_MS = 1000 — the tree syncs 100 ms after changes settle, or is force-synced if changes have been arriving continuously for 1 s. Under sustained animation or typing the accessible tree can trail the visual UI by up to a second.
  • Reordering was destructive; it no longer is. Until 2026-08-28 a child-order change called removeAllChildrenOf(htmlNode) and re-appended — by its own comment, chosen because “the code is more simple with this approach.” PR #3349 (“Update the Web A11Y DOM without rebuilding unchanged nodes”, JetBrains, merged 2026-08-28) replaced this with insertBefore-based reconciliation that leaves unchanged nodes in place; removeAllChildrenOf survives only for full teardown of the root. Verified on jb-main 2026-08-31. Not in any release yet — 1.12.0 shipped 2026-08-25, three days before the merge.

The exact semantics vocabulary that crosses

This is the most useful finding, and it is checkable in one grep. Across both web accessibility source files, the properties read are exactly eleven (was ten on 2026-08-26; LinkTestMarker added by PR #3331, merged 2026-08-27):

ContentDescription · Text · EditableText · TestTag · Disabled · Role · Heading · IsDialog · CollectionInfo · LinkTestMarker · SemanticsActions.OnClick

Links now render as interleaved <div role="link"> children inside the text node’s div, with the surrounding text split around them so a screen reader doesn’t read the link text twice — a genuine quality improvement, and a narrow one.

SemanticsProperties.kt on the same branch defines 87 capitalised properties and actions. Everything else is silently dropped on web, including:

StateDescription · ToggleableState · ProgressBarRangeInfo · Selected · SelectableGroup · LiveRegion · Error · Password · IsSensitiveData · Focused · TraversalIndex · IsTraversalGroup · HideFromAccessibility · PaneTitle · MaxTextLength · ContentType · ImeAction · HorizontalScrollAxisRange / VerticalScrollAxisRange · CollectionItemInfo · CustomActions

Silently is the operative word — Modifier.semantics { stateDescription = "…" } compiles, runs, is correct on Android/iOS/desktop, and produces nothing on web. There is no warning.

Re-verified 2026-08-31 on jb-main: StateDescription, ToggleableState, ProgressBarRangeInfo, and LiveRegion are still absent from both files, as are the strings aria-checked, aria-valuenow, aria-live, aria-level, and tabindex. The attribute set written is unchanged: aria-modal, aria-disabled, aria-label, role, contenteditable, plus innerText, id, and inline bounds.

Role map (A11YImplementationUtils.kt): button · checkbox · switch · radio · tab · img · menu · heading · textbox · list · grid · dialog. Role.ValuePicker and Role.Carousel map to nothing, both marked // TODO: Any web alternative?. Anything clickable with no role defaults to button under an in-source acknowledgement: // TODO: Not everything with OnClick is a button!

Two mapping choices are questionable on their face (my reading, not a filed issue): Role.DropdownList → role="menu" where ARIA would want listbox or combobox; and role="heading" is emitted with no aria-level, so every heading is level 2 by default and heading-level navigation carries no structure.

No aria-checked. No aria-valuenow/aria-valuemin/aria-valuemax/aria-valuetext. No aria-expanded, aria-selected, aria-pressed, aria-current, aria-haspopup, aria-required, aria-invalid, aria-describedby, aria-live, aria-level, aria-setsize/aria-posinset. No tabindex on mirror nodes. No landmark roles.

What changed since the first pass (2026-08-26 → 2026-08-31)

3. The near-complete fix exists, unmerged, and has been stale for three months. PR #3016 “Revamp A11y for Web platform” rewrites the whole web accessibility layer (+1522/−384, 8 files). It adds, in one PR, almost everything this note lists as missing:

  • aria-checked (true/false/mixed), aria-valuemin/-valuemax/-valuenow/-valuetext, aria-live (off/polite/assertive), aria-selected, aria-invalid, aria-readonly, aria-orientation, maxlength, tabindex set/remove, and the grid set (aria-rowcount/-colcount/-rowindex/-colindex/-rowspan/-colspan)
  • reads for StateDescription, ToggleableState, ProgressBarRangeInfo, LiveRegion, Selected, TraversalIndex, Focused, Error, MaxTextLength, HideFromAccessibility, CollectionItemInfo, and both scroll-axis ranges, plus the SetProgress, ScrollBy, and RequestFocus actions
  • slider and progressbar roles, and Role.DropdownList → combobox — which fixes the mismapping flagged below as my own reading

Why it hasn’t landed, and why that matters more than what it contains. The author is ApoloApps, author_association: NONE — an external contributor, not JetBrains. The PR is a draft, mergeable_state: dirty (conflicted), and untouched since 2026-05-27, when the author wrote: “I’m still doing changes to fix to rough edges with the PR and I might open a new one replacing.” No replacement PR has appeared — that contributor’s subsequent PRs are all performance and UiMediaScope work. Two reviews exist, both COMMENTED, neither approving.

So the state of web accessibility is not “unsolved problem.” It is “solution drafted by a volunteer, not staffed to completion.” That is a different risk, and a worse one for planning purposes: the technical path is known, so the gap is not a research question anyone can wait out, but the timeline is owned by nobody with a delivery commitment.

Two things PR #3016 does not fix, which is worth knowing before treating it as the answer: it never touches Password or IsSensitiveData (the leak below survives it), and it adds no aria-level and no landmark roles (so 1.3.1 and 2.4.1 stay broken).

A security wrinkle, for the finserv reading

CMP-10652 “Compose Web accessibility-DOM password leak” — open, filed 2026-08-11, subsystem UI. Accessibility, platform Web, affected 1.11.1. The claim: the accessibility DOM writes a password-marked field’s live text into innerText, so anything with DOM access reads the unmasked value.

The mechanism is confirmed in source. syncNodeProperties executes htmlNode.innerText = config[SemanticsProperties.EditableText].text with no guard, and neither SemanticsProperties.Password nor IsSensitiveData appears anywhere in the web accessibility layer. And JetBrains has reproduced it. The single tracker comment, from a JetBrains engineer, reads: “Thanks, reproduced. […] document.body.shadowRoot is null, but the problem can be observed from accessibility tree.” That both confirms the leak and corrects the ticket’s repro line — the shadow root is attached to an inner div, not body, exactly as the source shows. The issue remains Open with priority Normal as of 2026-08-26. I have not run the reproduction myself.

Adjacent and also open: CMP-7553 “[Web] SecureTextField. Clipboard operations are allowed” (2025-02-04).

This sharpens the point already made in kmp-jsexport-facade-example: anything Compose puts on screen it also puts in the DOM, in plain text, by design.

Why “the audit passed” won’t save you

Automated scanners are actively misleading on canvas-rendered apps. axe and Lighthouse grade the DOM; a canvas app has almost no DOM to fail, so it scores well while being unusable. The Flutter community has written this up directly — “Lighthouse gives your Flutter app a perfect accessibility score. It’s lying”. The same logic applies here, with an extra twist: WCAG 1.4.3 contrast has to be measured from rendered pixels, not from CSS, because there is no CSS.

If you evaluate this, evaluate it manually: NVDA + Firefox/Chrome, VoiceOver + Safari (desktop and iOS), TalkBack + Chrome, keyboard-only, 200% browser zoom, browser text-size-only zoom, Windows High Contrast. Inspect the mirror by opening the shadow root and reading the a11y_container divs.

The escape hatch, and its limit

HtmlElementView (renamed from WebElementView in 1.11.0, PRs #2636, #2641; moved to webMain in #2614) embeds real, absolutely-positioned HTML inside a Compose Web app. The original request, CMP-6858, was motivated in the reporter’s own words by “the Compose Web canvas accessibility is not great.”

But interop is one of the two areas the official docs name as unsupported: “Accessibility for interop and container views with scrolls and sliders” and “traversal indexes.” So the escape hatch is real for rendering and not yet covered for accessibility. Using it at scale also means writing the accessible parts of your UI in HTML — at which point the honest question is why the shell is a canvas.

The documentation gap worth naming

kotlinlang.org/docs/multiplatform/compose-accessibility.html states that the framework “enables the design of applications that comply with the requirements of the European Accessibility Act (EAA) and the Web Content Accessibility Guidelines (WCAG).”

That page then links per-platform deep dives for iOS and desktop only. There is no web section on it, and compose-web-accessibility.html returns 404. The sole web accessibility documentation is a short section in the 1.9.0 what’s-new page. A compliance claim sits on the general page; the platform with the largest gap has no page.

Regulatory stake, for the finserv framing in kotlin-multiplatform-web-enterprise: the European Accessibility Act has applied since 2025-06-28 and covers consumer banking services, with EN 301 549 as the harmonized standard referencing WCAG 2.1 AA. (EAA date, banking scope, and the EN 301 549 → WCAG 2.1 AA reference are from secondary compliance-vendor sources — Level Access, Deque — not read from the directive or the standard text; confirm with counsel before relying on the specifics.)

The outside view

This is not a “wait two releases” problem. Flutter Web has shipped the same canvas-plus-semantics-overlay architecture for years longer, with far more resourcing, and screen-reader support on canvas-rendered content is still the standard caveat in 2026 practitioner writeups. The reference class says the overlay approach asymptotes below DOM-native accessibility rather than converging on it — because the overlay only ever carries what the framework chose to mirror, while real HTML carries browser-native behaviour the framework never has to reimplement.

That does not make CMP Web unusable. It makes the accessible-surface decision architectural rather than schedulable.

Verdict

  • Shared Kotlin core + React/DOM UI: WCAG is unaffected by KMP. Counterweight, so this doesn’t read as motivated reasoning: that verdict is not really evidence for the chosen architecture. Architecture (1) was picked on interop, hiring, and bundle grounds long before accessibility came up, and its accessibility profile is simply “React’s” — a wash, not a win. What this note actually does is close off the alternative some reader will eventually propose (“why not just share the UI too?”) and put a price on it.
  • Compose Multiplatform for Web, consumer-facing and regulated: not viable at WCAG 2.1/2.2 AA today. Stateful widgets fail 4.1.2 at the framework level; there is no framework path to 4.1.3 (you would have to mount your own live region through HtmlElementView and drive it yourself); text sizing and high-contrast are structurally out of reach.
  • Where it is defensible: internal tools with a known user population and a documented accommodation path; prototypes; surfaces outside EAA/Section 508 scope; apps whose accessible surface is entirely HtmlElementView.
  • Beware the middle case — a mobile-first CMP app growing a web target “for free”. iOS and desktop get first-class semantics support and visible ongoing investment (they carry open a11y tickets of their own — CMP-7939, CMP-9360, CMP-10207, CMP-10640 — but the vocabulary is there); the web build silently doesn’t, and the same Modifier.semantics block that works on mobile is dropped on web without a warning. The parity assumption is the trap, not the framework.

What would change this — falsifiable conditions

  • The July-2025 QA batch (CMP-8612, CMP-8619, CMP-8621, CMP-8624, CMP-8627, CMP-8628, CMP-8629, CMP-8630, CMP-8634) closes. CMP-8627 went In progress 2026-08-31 — the leading indicator to watch.
  • aria-checked, aria-valuenow, and aria-live appear in ComposeWebSemanticsListener.kt — grep the file; this is a one-minute recheck. (Still absent 2026-08-31.)
  • PR #3016 merges, or JetBrains opens a staffed replacement. This is now the single highest-information signal, because it converts the question from “will this be solved” to “will this be shipped.” Watch for either the draft flag clearing on #3016, or a new webMain/.../accessibility PR authored by a MEMBER account. Its author said on 2026-05-27 they might open a replacement; as of 2026-08-31 they have not.
  • The ten-property read set grows to include StateDescription, ToggleableState, ProgressBarRangeInfo, and LiveRegion.
  • A dedicated web accessibility documentation page ships (currently 404).
  • JetBrains publishes a VPAT / Accessibility Conformance Report or an EN 301 549 statement for CMP Web. None found as of 2026-08-26 — and the absence is informative rather than incidental, because JetBrains does publish ACRs against EN 301 549 for other products (IntelliJ IDEA, TeamCity). The capability and the template exist; the framework hasn’t been put through them.
  • A third-party audit of a shipped CMP Web app reports AA conformance. None found.
  • CMP-10652 moves off Open — it is vendor-reproduced but unfixed as of 2026-08-26.

Open questions

  • Does the destructive child re-ordering disrupt an in-progress screen-reader traversal? Moot as of PR #3349 (merged 2026-08-28) — reconciliation now leaves unchanged nodes in place. Whether it did disrupt traversal in 1.9.0–1.12.0 was never tested by me; the fix’s existence is suggestive but not proof that it did.
  • Does the 100 ms/1 s debounce produce audible staleness with NVDA during typing? Untested.
  • Is there any production CMP Web app with a published accessibility audit? None found — consistent with kmp-enterprise-adoption-evidence, where web-target production use is already the rare exception.
  • Does CMP-8619 still reproduce? Source maps Role.Switch → "switch", yet the ticket says Switch has no role attribute. Either Material’s Switch doesn’t set SemanticsProperties.Role on web, or the ticket predates a fix and was never retested. Needs a runtime check.
