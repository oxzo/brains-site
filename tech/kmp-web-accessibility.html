KMP Web Accessibility — WCAG Under a Canvas-Rendered UI

As of 2026-11-10 (third pass; earlier passes 2026-08-26 and 2026-08-31). Fast-moving. Source claims were read against release tags and jb-main of JetBrains/compose-multiplatform-core on that date, tracker state against the YouTrack REST API. Nothing here was tested with a screen reader. Re-verify before citing.

Third-pass summary: the verdict changed, and it now depends on the version. The stable release, 1.12.2, still has every gap the earlier passes described, including the password leak. The 1.13.0 pre-release line (alpha02 onward; beta02 is current) closes the largest ones: checkbox and switch state, slider and progress values, live regions, selection state, and password masking in the accessibility DOM. Heading levels, landmarks, expanded and pressed state, error state, browser text sizing and contrast preferences are still missing in every version. The earlier passes predicted this would not be fixed on a release-or-two timescale; for the stateful-widget gap that prediction was wrong. See What the earlier passes got wrong.

“Does KMP web support WCAG” is two questions, because “KMP web” names two architectures with opposite accessibility profiles. Getting the split right is most of the answer.

The split — which architecture are you asking about

(1) Shared Kotlin core + web-native DOM UI. Kotlin compiles to a JS/Wasm library; React (or any DOM framework) renders the UI. This is the architecture evaluated in kotlin-multiplatform-web-enterprise, with the boundary detailed in kmp-js-interop-boundary.

Here KMP is invisible to assistive technology. The compiled Kotlin never touches the DOM — it returns values that your React components render as real HTML. Accessibility is exactly the accessibility of your component layer: the same problem, the same tools, the same answers as any React app. See design-system-accessibility. WCAG imposes no KMP-specific constraint in this architecture, and this note’s findings do not apply to it.

(2) Compose Multiplatform for Web (Kotlin/Wasm). Compose renders the entire UI into a single <canvas> via Skia. To a browser and to a screen reader, the app is one opaque graphic. Accessibility exists only insofar as the framework synthesizes a parallel DOM that mirrors the semantics tree.

Everything below is about (2). For the same framework on iOS, Android and desktop, see kmp-mobile-desktop-accessibility.

Status of the target itself

  • Stable: 1.12.2, tagged 2026-10-15 (1.12.0 was 2026-08-25, 1.12.1 2026-09-22). Pre-release: 1.13.0-beta02, tagged 2026-11-04, after alpha01 (2026-09-09), alpha02 (2026-10-06) and beta01 (2026-10-23). Dates are git tag dates in JetBrains/compose-multiplatform; the changelog headers agree on the months.
  • Web is still Beta on both stability tables (supported-platforms).
  • Web accessibility first shipped in 1.9.0 (2025-09-16) via PR #2188. It is on by default; ComposeViewport(configure = { isA11YEnabled = false }) turns it off (What’s new in 1.9.0).

How it works

ComposeViewport builds a shadow root that holds the canvas and, beside it, an accessibility container. A semantics listener walks the Compose semantics tree and mirrors each node into an absolutely positioned <div> in that container, sized and placed over the canvas pixels it represents. Screen readers read the mirror; clicks on the mirror are forwarded to Compose. Architecturally this is the same approach Flutter Web uses. (Structure read from source on 2026-08-26, not re-read in this pass.)

Two properties of the sync:

  • It is debounced. The tree syncs 100 ms after changes settle, or is force-synced once changes have been arriving continuously for 1 s. Under sustained animation or typing the accessible tree can trail the visual UI by up to a second. Unchanged in 1.13.0-beta02.
  • Reordering no longer rebuilds the subtree. Up to and including 1.12.2, a child-order change removed and re-appended every child. From 1.13.0-alpha01 the mirror is reconciled in place (PR #3349).

Role map (1.13.0-beta02)

button · checkbox · switch · radio · tab · img · menu · heading · textbox · list · grid · dialog · link · progressbar · slider. Role.ValuePicker and Role.Carousel still map to nothing, both marked // TODO: Any web alternative?. A clickable node with no role still defaults to button under the in-source note “Not everything with OnClick is a button!”

Three mapping choices remain questionable (my reading, not filed issues):

  • Role.DropdownList → role="menu", where ARIA would want listbox or combobox.
  • role="heading" with no aria-level, so every heading defaults to level 2 and heading navigation carries no structure.
  • Radio buttons probably still expose no checked state. The layer writes aria-checked from ToggleableState and aria-selected from Selected. Compose radio buttons carry Selected, and ARIA defines aria-checked, not aria-selected, for the radio role. That would explain why CMP-8621 (checkbox, switch and radio lack aria-checked) is still Open while the checkbox half is in source. Not runtime-tested.

The July-2025 ticket batch

Nine screen-reader issues were filed against 1.9.0-beta01 in July 2025. On 2026-08-31 eight were Open. On 2026-11-10:

  • Fixed: CMP-8612 (slider and progress values), CMP-8619 (slider, progress and switch roles), CMP-8627 (VoiceOver scroll), CMP-8628 (mobile VoiceOver skips elements).
  • Answered as already fixed: CMP-8624 (mergeDescendants).
  • Open: CMP-8621 (aria-checked), CMP-8629 (alpha(0f) nodes still highlighted), CMP-8630 (isTraversalGroup), CMP-8634 (VoiceOver with text fields).

Also still Open: CMP-10457 (context menus), CMP-10679 (no way to assert focus state in web tests), CMP-10692 (OS and browser preferences), and two filed 2026-10-05: CMP-10894 (VoiceOver focus not set on the first element, In progress) and CMP-10895 (desktop VoiceOver does not outline elements, Open). The collector epic CMP-9678 carries 27 linked issues, 8 unresolved; on 2026-08-31 it was 23 and 14.

How the gap closed

The 1.13.0-alpha02 changelog lists six web accessibility items: scrolling through accessibility tools (#3366), aria attributes for sliders and progress indicators (#3382), text-field value sync and password obfuscation in the accessibility tree (#3401), read-only, max-length and selection state (#3381), and LiveRegion mapped to aria-live (#3428). Alpha01 had already shipped the August work on aria-disabled, links and in-place reconciliation.

In the jb-main commit history, all of these but one carry the same author as the August work, whose GitHub account the second pass recorded as a JetBrains member; the exception, #3381, carries the name of the external contributor who wrote the earlier draft rewrite, PR #3016. That draft was therefore not merged as one piece: its contents landed in parts, some from its author and some rewritten by JetBrains. (Authorship is read from commit author names, and matching the name on #3381 to the draft’s author is an inference; GitHub’s PR metadata was not reachable in this pass, so the open-or-closed state of #3016 itself is unknown. Its branch head is unchanged since 2026-05-27.)

A security wrinkle, for the finserv reading

CMP-10652 “Compose Web accessibility-DOM password leak” was filed 2026-08-11 and reproduced by JetBrains: the accessibility DOM wrote a password field’s live text into the mirror, so anything with DOM access could read the unmasked value.

  • Fixed in the pre-release line. The ticket was resolved Fixed on 2026-09-14. From 1.13.0-alpha02 the layer checks Password and IsPasswordObfuscated and writes one bullet per character instead of the text.
  • Not fixed in stable. At the v1.12.2 tag the listener still writes the field’s text with no password check. Anyone shipping 1.12.x is exposed until they move to 1.13.
  • IsSensitiveData is still not read, so non-password sensitive fields get no such treatment.

I have not run the reproduction on either version. Adjacent and still unresolved: CMP-7553, clipboard operations allowed on a secure text field.

This sharpens the point made in kmp-jsexport-facade-example: anything Compose puts on screen it also puts in the DOM, in text, by design. The password case now has an exception; nothing else does.

Why “the audit passed” won’t save you

Automated scanners are actively misleading on canvas-rendered apps. axe and Lighthouse grade the DOM; a canvas app has almost no DOM to fail, so it scores well while being unusable. The Flutter community has written this up directly — “Lighthouse gives your Flutter app a perfect accessibility score. It’s lying”. The same logic applies here, with an extra twist: WCAG 1.4.3 contrast has to be measured from rendered pixels, not from CSS, because there is no CSS.

The 1.13 changes raise the stakes on this point. More attributes in the mirror means more for a scanner to approve, and none of it shows whether NVDA or VoiceOver reads the result sensibly. Evaluate manually: NVDA + Firefox/Chrome, VoiceOver + Safari (desktop and iOS), TalkBack + Chrome, keyboard-only, 200% browser zoom, browser text-size-only zoom, Windows High Contrast. Inspect the mirror by opening the shadow root and reading the accessibility container.

The escape hatch, and its limit

HtmlElementView embeds real, absolutely positioned HTML inside a Compose Web app. The original request, CMP-6858, was motivated in the reporter’s own words by “the Compose Web canvas accessibility is not great.”

Interop is one of the two areas the 1.9.0 docs name as unsupported: “Accessibility for interop and container views with scrolls and sliders” and “traversal indexes.” Source has moved past that list (sliders and scrolling are handled in 1.13 pre-releases, traversal indexes on jb-main), and the page has not been updated, so which interop cases are covered today is not documented anywhere. Using the escape hatch at scale also means writing the accessible parts of your UI in HTML — at which point the honest question is why the shell is a canvas.

The documentation gap

kotlinlang.org/docs/multiplatform/compose-accessibility.html states that the framework “enables the design of applications that comply with the requirements of the European Accessibility Act (EAA) and the Web Content Accessibility Guidelines (WCAG).”

That page links per-platform deep dives for iOS and desktop only. There is no web section on it, and compose-web-accessibility.html still returns 404 on 2026-11-10. The sole web accessibility documentation remains a short section in the 1.9.0 what’s-new page, now out of date in both directions. The 1.12.2 and 1.13.0-beta02 what’s-new pages do not mention web accessibility at all, so a year’s most significant accessibility work on the target is recorded only in the changelog.

Regulatory stake, for the finserv framing in kotlin-multiplatform-web-enterprise: the European Accessibility Act has applied since 2025-06-28 and covers consumer banking services, with EN 301 549 as the harmonized standard referencing WCAG 2.1 AA. (From secondary compliance-vendor sources — Level Access, Deque — not read from the directive or the standard text. ETSI now also lists EN 301 549 V4.1.1, dated September 2026; whether it has replaced V3.2.1 as the harmonized version is unverified. Confirm with counsel.)

Verdict

  • Shared Kotlin core + React/DOM UI: WCAG is unaffected by KMP. Counterweight, so this doesn’t read as motivated reasoning: that verdict is not evidence for the architecture. It was picked on interop, hiring and bundle grounds, and its accessibility profile is simply “React’s” — a wash, not a win.
  • Compose Multiplatform for Web on stable 1.12.x, consumer-facing and regulated: not viable at WCAG 2.1/2.2 AA. Stateful widgets fail 4.1.2 at the framework level, there is no framework path to 4.1.3, and the password leak is unpatched.
  • Compose Multiplatform for Web on 1.13 once it is stable: the framework-level blockers on 4.1.2 and 4.1.3 are mostly gone in source. What remains is a narrower list: radio state, expanded, pressed and error state, heading levels and landmarks, keyboard focus movement, and the structural items no mirror can fix (browser text sizing, text spacing, forced colors, reduced motion). A conformance claim still needs a manual screen-reader audit that nobody has published. “Not viable” becomes “unproven, with known holes.”
  • Where it is defensible today: internal tools with a known user population and a documented accommodation path; prototypes; surfaces outside EAA/Section 508 scope; apps whose accessible surface is entirely HtmlElementView.
  • Beware the middle case — a mobile-first Compose app growing a web target “for free”. The same Modifier.semantics block that works on mobile is partly dropped on web without a warning, and which part depends on the version. The parity assumption is the trap, not the framework.

The outside view, revised

Flutter Web has shipped the same canvas-plus-semantics-overlay architecture for years longer, and screen-reader support on canvas-rendered content is still a standard caveat in practitioner writeups. An overlay only ever carries what the framework chose to mirror, while real HTML carries browser-native behaviour the framework never has to reimplement. That argument still holds for the structural rows in the table above.

It does not hold for the attribute gap. That was ordinary engineering work, and it was done in about five weeks once staffed.

What the earlier passes got wrong

Kept because the note made falsifiable claims and several fired.

  • “This is not a ‘wait two releases’ problem.” For checked state, values and live regions it was exactly that: Open on 2026-08-31, in a pre-release on 2026-10-06.
  • “The timeline is owned by nobody with a delivery commitment.” The second pass read the stale external draft as evidence that the fix was unstaffed. JetBrains-authored fixes for sliders, live regions and the password leak merged between 2026-09-07 and 2026-09-18, days after that sentence was written. The August burst the same pass recorded was the leading indicator, and it was underweighted.
  • Conditions that fired: aria-checked, aria-valuenow and aria-live appear in the listener; the read set includes StateDescription, ToggleableState, ProgressBarRangeInfo and LiveRegion; the draft’s contents landed; CMP-10652 left Open; five of the nine July-2025 tickets are resolved.
  • Conditions that have not fired: a web accessibility docs page; a vendor conformance report; a third-party audit.

What held up: the split between the two architectures, the structural rows (text sizing, contrast, landmarks, heading levels), the warning about automated scanners, and the documentation gap.

What would change this — falsifiable conditions

  • 1.13.0 ships stable with the pre-release accessibility work intact. Until then the improvements are not in a production release.
  • CMP-8621 closes, or a runtime check shows a Compose radio button exposing checked state in the browser’s accessibility tree.
  • aria-level, aria-expanded or aria-invalid appear in the web accessibility sources — a one-minute grep.
  • CMP-10692 moves: any response to browser text size, forced colors or reduced motion.
  • CMP-4714 (Tab and Shift+Tab focus movement) closes.
  • A dedicated web accessibility documentation page ships (currently 404).
  • JetBrains publishes a VPAT / Accessibility Conformance Report or an EN 301 549 statement for Compose Multiplatform on web. None found on 2026-11-10 (one web search, not a read of JetBrains’ own accessibility pages). JetBrains does publish such reports for other products (IntelliJ IDEA, TeamCity).
  • A third-party audit of a shipped Compose-for-Web app reports AA conformance, or documents how the 1.13 mirror behaves under NVDA and VoiceOver. None found.

Open questions

  • Does the 1.13 mirror actually work with screen readers? Every improvement in this pass is “attribute present in source.” No runtime evidence exists in this note.
  • Does a Compose radio button expose its state on web in 1.13? See the role-map reading above.
  • Does the 100 ms / 1 s debounce produce audible staleness with NVDA during typing? Untested.
  • Is PR #3016 closed, and is anything from it still outstanding? Its grid attributes (aria-rowcount and the rest) and aria-invalid are not in source.
  • Is there any production Compose-for-Web app with a published accessibility audit? None found — consistent with kmp-enterprise-adoption-evidence, where web-target production use is already the rare exception.
