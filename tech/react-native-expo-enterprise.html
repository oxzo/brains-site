React Native + Expo in the Enterprise — the JS-Everywhere Lane

As of 2026-08-29. Deep dive on one lane of multiplatform-app-architecture-options: React Native + Expo for iOS/Android, a TypeScript shared core in a monorepo, web either React (separate UI) or React Native Web (shared UI). This is KMP’s strongest rival per the verdict in kotlin-multiplatform-web-enterprise — when mobile is React Native, “the TS monorepo dominates and KMP adds little.” Sibling deep dives: flutter-enterprise, rust-shared-core-enterprise.

The architecture in one line

One language and one runtime across all three clients: React renders to native views on mobile (via React Native) and to the DOM on web, with domain logic, state, and API clients living in shared TypeScript packages that every client imports directly — no FFI, no binding layer, no export annotations.

Current version pins (verified 2026-08-26 in multiplatform-app-architecture-options, reused here): Expo SDK 57 targets React Native 0.86; npm react-native latest is 0.87.0. The New Architecture (JSI + new renderer + new native-module system, bridge removed) has been the default since React Native 0.76 (reactnative.dev, 2024-10-23).

The structural headline: this stack shares more layers with less friction than the compiled-core lanes in this cluster — the entire interop-boundary problem that dominates the KMP evaluation (kmp-js-interop-boundary) simply does not exist. The cost is concentrated elsewhere: runtime guarantees, native fidelity, and vendor coupling.

Decision view for a large enterprise

Pros

  • Hiring and talent portability, the driver that kills shared-core projects, favors this stack most. JS/TS is the dominant frontend skill; Shopify’s stated reasons for adopting RN were “Write it once,” talent portability (enabling developers to work across iOS, Android, and Web), and shipping more value (Shopify Engineering, 2025-01-13). Coinbase reported 113 contributors to its RN repo including “a large number of web engineers, who previously would have been unable to contribute on mobile” (secondary sourcing — the primary post blocked non-browser fetch in this pass).
  • Five-year enterprise retrospective evidence exists — rare in this space. Shopify (Director of Engineering, Mustafa Ali) reports all its apps on RN with “sub-500ms (P75) screen loads” and “>99.9% crash-free sessions” after five years, and states the limitations that historically blocked adoption “simply don’t exist anymore” (Shopify Engineering, 2025-01-13).
  • Fintech-scale precedent. Coinbase completed its transition from native iOS/Android to RN (200+ screens reimplemented, announced May 2021) (secondary sourcing, primary blocked). Note what this is evidence for: a money-moving consumer fintech accepted RN’s runtime and delivery model — the closest thing this lane has to the finserv precedent that kmp-enterprise-adoption-evidence could not find for KMP-web. It is a bounded precedent: a 2021 US crypto exchange does not operate under a chartered bank’s change-management regime, so it answers less of the regulated-OTA question below than it first appears to.
  • The maintainer dogfoods at maximum scale. Meta runs the New Architecture at scale in the Facebook app and in the Facebook/Instagram apps for Quest devices; Expensify, Kraken, and Bluesky are named production adopters (reactnative.dev, 2024-10-23). Microsoft maintains React Native for Windows as open source (microsoft.github.io/react-native-windows), with react-native-macos as a separate Microsoft-maintained project — though that page does not name which Microsoft products use it, and product-level claims (Office, Xbox UI) were not verifiable from primary sources in this pass; treat them as (unverified).
  • OTA updates are a delivery lever no compiled stack has. EAS Update pushes JS bundles without store review — Expo’s customer page quotes MTA: “identify, patch, and deploy an OTA fix in under 90 seconds from the first user report” (expo.dev/customers). The Apple-rules analysis lives in multiplatform-app-architecture-options axis 5.
  • Expo has become the de-facto toolchain, absorbing build/submit/update infrastructure that enterprises would otherwise build (EAS Build/Submit run from CI without local macOS). Named production users include MTA, incident.io, Mollie, Cameo, Phantom, Partiful (expo.dev/customers) — mostly startups/scale-ups; the large-enterprise-shaped evidence is Shopify/Coinbase on RN itself, not on Expo’s cloud. And as with every lane in this cluster, the pros rest on published successes — mid-size RN failures don’t write retrospectives, so the visible record is survivor-weighted.

Cons

  • The upgrade treadmill is real and acknowledged by the friendliest witness. Shopify, in its pro-RN retrospective: “Updating an app to each new version of React Native takes a significant amount of work,” debugging “is flakey” compared to native tooling, and the stack leans more heavily on third-party libraries than native does (Shopify Engineering, 2025-01-13).
  • Native expertise is still required — the pitch says otherwise. Shopify calls 100% React Native “an anti-goal”: hardware-intensive features (scanning, on-device AI), memory-constrained surfaces (widgets, watch apps), and background sync stay native. An org budgeting zero native engineers is planning against the evidence.
  • TypeScript’s guarantees are weaker than a compiled core’s. Types erase at runtime; unsound boundaries (JSON parsing, any leakage) need runtime validators. For the high-assurance domain logic that motivates shared cores in finserv, this is the direct trade against KMP’s Kotlin type system (kotlin-multiplatform-web-enterprise, verdict condition 2).
  • Sharing UI to web is the weak layer. RN Web inherits a mobile component model; React Server Components in Expo remain experimental and not production-recommended (verified 2026-08-26 in multiplatform-app-architecture-options). The honest enterprise default is: share the mobile pair + the TS core, build web UI web-native.
  • Two-vendor concentration. Meta owns the framework’s direction; Expo (the company) owns the build/update cloud that has become the recommended path. Both are healthier bets than a single niche vendor — but an enterprise risk review should note that EAS is a paid SaaS in the critical release path, and self-hosting equivalents is real work.
  • OTA updates cut both ways in a regulated org. The same mechanism that patches in 90 seconds means production code changes without store review or (by default) internal release gates. A compliance regime that requires reviewed, versioned releases must either gate EAS Update behind its own change-management process or forgo the lever entirely. (Inference from the mechanism; no regulator guidance on OTA JS bundles was found either way in this pass.)
  • The canonical walk-away story belongs to this stack. Airbnb sunset React Native in June 2018 after two years, citing “a variety of technical and organizational issues” — hiring polarization, unclear native-vs-RN boundaries per feature, and maintainability at their scale (medium.com/airbnb-engineering; body details via secondary summaries — Medium blocked non-browser fetch; the widely-quoted survey figures 63%-would-choose-again / 74%-would-consider are (unverified)). Udacity is reported to have dropped RN the same year (ADTmag headline, unverified). Both predate the New Architecture by six years; no comparable post-2024 walk-away was found — the same absence-of-evidence caveat as in multiplatform-app-architecture-options applies.

Question marks (genuinely open — and what would resolve each)

  • Does RN Web reach web-parity for a content/SEO-relevant enterprise web surface? Resolves when: Expo ships RSC as production-recommended and a named enterprise reports a public-facing website (not a dashboard) on RNW at scale.
  • Will regulators/auditors accept OTA JS bundles in regulated apps? For an EU finserv org this is specifically a question about DORA-era ICT change-management expectations, not just Apple’s rules. Resolves when: a bank or health-sector engineering/compliance writeup documents an approved EAS-Update-style change-management process. None found — same evidentiary hole as KMP’s condition 5.
  • Is the New Architecture migration complete across the long tail of libraries an enterprise app actually uses? The 2024 launch post claimed 850+ compatible libraries covering all >200K-weekly-download packages; the current figure was not re-verified in this pass. Resolves by: auditing your actual dependency list, not the ecosystem statistic.

Verdict

RN + Expo + TS monorepo is the right call when ALL of these hold:

  1. Web UI is React (or web UI sharing is explicitly not attempted) — the TS core then serves all three channels with zero interop tax.
  2. The org’s engineering base is JS/TS and hiring plans stay that way; the ability to move web engineers onto mobile work is worth more than compile-time domain guarantees.
  3. Mobile UX target is “excellent app” rather than “day-zero platform showcase,” and the org still funds a small native-specialist bench for the layers Shopify keeps native.
  4. OTA delivery either passes the org’s compliance regime (with its own gate) or isn’t load-bearing to the case.
  5. Meta + Expo vendor coupling is acceptable in the risk register.

It is the wrong call when: the mobile apps are hardware/AR/background-heavy native showcases; the org is JVM-based and mobile is already true-native Kotlin/Swift (KMP’s home turf — kotlin-multiplatform-web-enterprise); or regulated change-management rules the OTA lever out and the runtime-typing gap matters, at which point the compiled-core lanes (rust-shared-core-enterprise, KMP) or thin clients win.
