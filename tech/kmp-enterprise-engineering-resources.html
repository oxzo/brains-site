KMP Enterprise Engineering — Resources, Stability and Library Stack

How to build Kotlin Multiplatform (KMP) well for a large app: official guidance, the stability state of each piece, a default library stack, team-scale practice and known failure modes. Part of kotlin-android-kmp-learning-hub.

Already covered elsewhere — not repeated: adoption case studies in kmp-enterprise-adoption-evidence; the Kotlin→JS boundary in kmp-js-interop-boundary and kmp-jsexport-facade-example; Compose web accessibility in kmp-web-accessibility; coroutine bridges to Swift (KMP-NativeCoroutines, SKIE) in the coroutines learning track; the target architecture in 2026-10-10-kmp-shared-viewmodels-navigation.

As of 2026-10-18. The research subagent could not open GitHub pages, so a repo described as “active” means only that its GitHub metadata or Maven Central release is recent, not that its README was read.

Terms: source set = a folder of code compiled for a group of targets (commonMain, iosMain, …); expect/actual = a shared declaration with per-platform implementations; klib = Kotlin’s library format for non-JVM targets.

Read the Kotlin roadmap before committing a 1M-LOC plan. In focus as of Aug 2026: Swift export to Beta, Wasm to Stable, native release-mode compiler caches, native task parallelization without the configuration cache, an Xcode debugger integration, native iOS text input by default, and K2 incremental compilation of common code. The Aug 2025 KMP roadmap aimed for a stable Swift export “in 2026”; a year later it is still Alpha.

Official JetBrains guidance

Project structure — read these first:

  • Choosing a KMP project configuration — the key page for a large codebase. With several shared modules, export one umbrella module and framework to iOS; JetBrains “do[es] not recommend” separate frameworks because Kotlin/Native duplicates shared dependencies (bigger app) and breaks shared state between them. Known limit: iOS can’t consume a subset of feature modules.
  • Project structure basics → Source set hierarchy (the default hierarchy template is “the recommended way”) → Expect/actual → Platform-specific APIs: prefer a common interface plus factory or DI over expecting whole classes; if you already use DI, “continue to use DI” rather than mixing in expect/actual.
  • AGP 9 migration — with AGP 9+, KMP is incompatible with com.android.application/com.android.library. The Android app lives in its own module; shared modules use com.android.kotlin.multiplatform.library (Android docs). Design the module layout for this from day one.

iOS integration:

  • iOS integration methods — direct integration (Kotlin build as an Xcode build phase) is the IDE default; CocoaPods only if the KMP project imports Pods; SwiftPM for XCFramework distribution. How-tos: direct integration (incl. migrating off CocoaPods), SwiftPM export.
  • Swift export — Alpha. Generics type-erased; only final classes inheriting directly from Any exported; direct integration only. Suspend functions become async, Flow becomes AsyncSequence (per What’s new in 2.4).
  • KMP for iOS: myths — hand this to the iOS engineers.
  • Kotlin/Native memory management — one modern shared-heap memory manager (no old-model freezing); concurrent mark-and-sweep GC default.

Build cost:

  • Improving Kotlin/Native compile time — cache ~/.konan in CI; build only needed targets; debug binaries in development (release ≈10× slower); avoid transitiveExport; keep exported modules minimal.

Compose Multiplatform:

  • Versions and compatibility — CMP trails Jetpack Compose by 1–3 months and ships separately from Kotlin; minimum iOS 14.
  • How multiplatform Jetpack libraries are packaged — JetBrains republishes Navigation, Lifecycle and ViewModel for non-Android targets under org.jetbrains.androidx.*.

Tooling and samples:

  • Recommended IDEs — IntelliJ IDEA or Android Studio with the KMP plugin (iOS run/debug, common @Preview, Compose Hot Reload). Note the Kotlin blog’s 2026-10-05 post discontinuing Swift language support in that plugin — iOS engineers will keep using Xcode for Swift.
  • KMP wizard, KMP-App-Template, official samples list, KotlinConf app (shared Compose UI on four platforms). kmp-production-sample still carries KMM-era framing — illustration, not current reference.

Google’s KMP support

  • Kotlin Multiplatform — Android Developers — the Jetpack-on-KMP matrix and support tiers. Latest per the page (2026-10-12): lifecycle/viewmodel 2.11.0, navigation3 1.2.0, room 2.8.5, datastore 1.2.1, paging 3.5.3, sqlite 2.7.1, savedstate 1.5.0. Check per-platform icons on the page itself.

  • Android KMP announcements, I/O + KotlinConf 2025 — Google Workspace KMP “running in production in the Google Docs app on iOS”, performance “on par or better”. Talk: Deploying KMP at Google Workspace (KotlinConf 2025).

Team-scale practice — expert sources

  • KMP for Native Mobile Teams — Kevin Galligan, Touchlab (2024), 7-part series. The scaling is hard part (free signup) argues library-publishing models don’t support feature work, and KMP only pays off where the bulk of feature work happens. The scaling how-to is “currently getting a rewrite”.
  • Share source, not binaries — Galligan, Touchlab (2024). iOS developers can’t browse or debug Kotlin inside a prebuilt XCFramework; Touchlab recommends sharing source (and sells tooling for it — weigh that).
  • Is AndroidX ViewModel the best choice for KMP? — Touchlab (2026-03-02). Directly relevant to the shared-ViewModel proposal: what shared ViewModels do to SwiftUI developer experience.
  • Touchlab iOS dev hub — SKIE, the Xcode Kotlin plugin, and the “Bad Swift Simulation” idea for making Kotlin devs feel iOS pain. Touchlab says its 2019 ebook is outdated.
  • How Bitkey uses cross-platform development — Block Engineering (2025-05-12). The most architecture-relevant first-party write-up found: they started with shared logic emitting UI model data classes consumed natively by Compose and SwiftUI, later moved to Compose Multiplatform UI; KMP is ~95% of the app; one codebase removed “two teams” planning drift.
  • KMP iOS build times: what’s actually driving the cost — John O’Reilly (2026-10-03). Umbrella-framework link time is dominated by generating the Objective-C header for exported API; making generated code internal plus kotlin.incremental.native=true cut a 400-file incremental rebuild from 13.3 s to 3.8 s (Swift ≈3.3 s). Generated code, not a real app — indicative.
  • Moving from SKIE to Swift export — O’Reilly (2026-10-10). Needed a Kotlin 2.5.0-Beta2 dev build and a small umbrella ios-export module.
  • Samples: O’Reilly’s PeopleInSpace and Confetti; Touchlab’s KaMPKit, DroidconKotlin, KMMBridge (XCFramework publishing).
  • Books: Kotlin Multiplatform by Tutorials (Kodeco, May 2025; written for Kotlin 2.1.20 — a starting point, not current). Netflix Studio apps on KMP (2020) — details search-verified only.

Principles

  1. One umbrella framework for iOS — multiple frameworks duplicate dependencies and break shared state (project configuration).
  2. The exported Swift surface is a build-cost lever — export little, keep generated code internal (O’Reilly); avoid transitiveExport (JetBrains). The same “small explicit surface” rule governs the @JsExport facade (kmp-jsexport-facade-example).
  3. Interfaces + DI over expect/actual classes, and don’t mix the two (platform APIs).
  4. Give iOS engineers the Kotlin source, not only binaries (Touchlab — opinionated; JetBrains also documents binary distribution).
  5. KMP pays off only where feature work happens (Touchlab scaling post).
  6. Shared logic with native UIs needs an explicit UI-model boundary (Bitkey); Decompose components offer one with SwiftUI and React stories.
  7. Pin tooling as a matrix — CMP, Kotlin, SKIE, Metro, Mokkery and KSP each carry their own Kotlin compatibility window.
  8. Wrap pre-stable pieces behind your own modules — Swift export, SwiftPM import, Compose web, pre-1.0 kotlinx libraries — so they can be swapped.
  9. Design for AGP 9+ now — separate Android app module, KMP Android library plugin.
  10. Fakes over mocks in commonTest — older mocking libraries don’t cover all targets.
  11. Share logic first; widen UI sharing deliberately — Google’s official support frames Compose Multiplatform as the add-on (Android KMP page).

Known failure modes

  • Swift export is Alpha and its “stable in 2026” target has slipped; real migrations need beta compilers.
  • iOS incremental builds are ~3–4× slower than Swift in O’Reilly’s benchmark; release links ~10× slower than debug. K2 incremental compilation of common code is still roadmap.
  • Compiler-plugin version coupling — SKIE trails Kotlin patch releases; Metro and Mokkery are compiler plugins with their own windows.
  • AGP 9/10 break older KMP module setups.
  • The web path’s maturity is uneven. The planned native-TS web UI rests on Kotlin/JS (Stable), but Jetpack libraries treat JS/Wasm as Tier 3, Room has no web target, and JS export improvements are still on the roadmap.
  • Ecosystem gaps — kotlinx-datetime 0.8, kotlin-inject 0.9, Circuit 0.39, Decompose 3.6 beta; Napier stale; DataStore KMP limited to Preferences.
  • Shared ViewModels can degrade SwiftUI ergonomics unless bridged deliberately (Touchlab).
  • Platform differences resurface as bugs when UI moves to Compose Multiplatform (Bitkey — they also count it as a benefit).
  • Source quality — several tutorials and Medium posts claim Compose web is stable, contradicting JetBrains’ Beta status.
